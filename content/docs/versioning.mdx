description: How Taffy numbers its releases, what counts as a breaking change, where releases and snapshots are published, and which Java and Paper versions it targets.
---

Taffy has one version number for everything it publishes: the Gradle plugins, the `alaz` version catalog and the runtime modules. A plugin picks that version once, in `settings.gradle.kts`, and every Taffy artifact it uses follows.

## One version for plugins, catalog and modules

The version on `so.alaz.taffy.settings` decides the rest:

```kotlin title="settings.gradle.kts"
pluginManagement {
    repositories {
        maven("https://repo.alaz.so/releases")
        gradlePluginPortal()
    }
}

plugins {
    id("so.alaz.taffy.settings") version "0.3.1"
}
```

- `so.alaz.taffy.settings` applies `so.alaz.taffy.repositories` and creates the `alaz` catalog from `so.alaz.taffy:taffy-catalog` at the same version as the plugin itself.
- The convention plugins (`so.alaz.taffy.paper-plugin`, `so.alaz.taffy.paper-api`, `so.alaz.taffy.library`, `so.alaz.taffy.coverage`, `so.alaz.taffy.java`) are applied in `build.gradle.kts` without a version and come from the same `so.alaz.taffy:taffy-gradle` release.
- The catalog holds a `taffy` version and one library per module (`alaz.taffy.platform`, `alaz.taffy.test`, `alaz.taffy.config`, `alaz.taffy.storage`, `alaz.taffy.hooks`, `alaz.taffy.gui`, `alaz.taffy.metrics`, `alaz.taffy.comficonf`), each resolving at that `taffy` version.

```kotlin title="build.gradle.kts"
dependencies {
    implementation(alaz.taffy.config)
    implementation(alaz.taffy.storage)
}
```

Moving to another Taffy release is a change of that one version string. Declaring a module with its own coordinates and a different version mixes Taffy releases in one plugin; use the catalog aliases instead. A build without the Taffy Gradle plugins declares every module at one version from its own catalog, as [Without the Gradle plugins](/docs/consuming-by-coordinates) shows.

`so.alaz.taffy.paper-plugin` relocates `so.alaz.taffy` to `<group>.libs.taffy`, where `<group>` is the plugin project's group, so each plugin carries its own copy of Taffy under its own package.

## Version numbers

Taffy follows [Semantic Versioning](https://semver.org), starting at `0.1.0`.

| Release line | Breaking change | Addition | Fix |
|---|---|---|---|
| Before `1.0.0` | raises the minor version (`0.1.3` to `0.2.0`) | raises the patch version | raises the patch version |
| From `1.0.0` | raises the major version | raises the minor version | raises the patch version |

A breaking change removes or changes, incompatibly, any of:

- a public type or member,
- a Gradle plugin id,
- a catalog alias,
- documented behaviour.

Before `1.0.0`, a patch upgrade (`0.1.0` to `0.1.1`) is safe to take without code changes, and a minor upgrade (`0.1.x` to `0.2.0`) can need them. Read the `Changed` and `Deprecated` groups of the [changelog](#reading-the-changelog) before a minor upgrade. [Upgrading from 0.1](/docs/upgrading-from-0-1) lists each change since `0.1.0` that needs an action from a plugin, with its migration.

### What a patch changes

A patch release leaves a plugin's build as it was, apart from these changes:

- It adds catalog entries and repositories only for a new integration, and each new repository is filtered to that integration's group.
- It changes no existing version except FastStats, bStats and a library whose new version fixes a security issue.
- It changes a convention of the Gradle plugins only to fix a defect in it, such as a jar Paper cannot load or a license that is not the plugin's, and the changelog lists the fix under `Fixed`.
- It never changes the `paper-api` pin. The pin and the oldest supported server change only in a minor release.

Each release names the FastStats and bStats versions it was tested with, and [Without the Gradle plugins](/docs/consuming-by-coordinates#faststats-and-bstats-versions) lists them. A plugin that declares other versions of either SDK runs a pairing that was not tested.

### Backported fixes

Once `0.5.0` exists, security, item-loss, money and data fixes are backported to the last `0.4.x` line while a plugin in production runs it.

### What is and is not a contract

Log lines and exception messages are written for the server owner or for the developer reading the log, and their wording can change in any release. Only text that a Javadoc spells out is part of the API, such as:

- the parser messages of `Durations`, `Colors` and `Expiry` and their public `EXPECTED` texts,
- the `describe()` texts of `HookStatus` and `ComfiConfStatus`,
- the warning and error shapes of `ConfigReader` and its `describe`,
- the `StrictYaml` message shapes, such as `<source> is larger than 16 MiB` and `<source> is not valid YAML: <problem> at line <n>, column <m>`,
- the clause form of the `ConfigLoadException` message (written for the server owner, with no full stop at the end, so it reads after a lead-in),
- the `<red>missing:key` marker that `Messages` renders for a key no language file has.

Plugin code branches on exception types, statuses and return values, never on a message. A test that pins one of Taffy's own log lines (for example through `CapturedLog`) can break on any upgrade.

The conventions the Gradle plugins add are published behaviour: the `tr-TR` test locale and `Pacific/Auckland` test zone, the Mockito agent on test tasks, the javadoc flags `-Xdoclint:all,-missing` and `--no-fonts`, and the root project's `LICENSE` file, when it has one, in `META-INF`. A change to one is listed in the changelog as a change to plugin builds, and a plugin build meets it only when it moves to that Taffy version. A patch release changes one only to fix a defect in it.

## Deprecation and removal

A public element is not removed without warning. Before the release that removes it, an earlier release:

<Steps>
<Step>
Marks the element `@Deprecated(forRemoval = true)`, so the compiler warns at every use.
</Step>
<Step>
Names the replacement in the element's Javadoc.
</Step>
<Step>
Lists it under `### Deprecated` in the changelog.
</Step>
</Steps>

`so.alaz.taffy.java` (applied through `so.alaz.taffy.paper-plugin`) compiles with `-Xlint:all,-processing,-serial`, which includes the deprecation and removal warnings, so a build lists every use of an element a later release removes.

## Releases and snapshots

| Kind | Version | Published to | When |
|---|---|---|---|
| Release | `0.3.1` | `https://repo.alaz.so/releases` | a `v<version>` tag, such as `v0.3.1` |
| Snapshot | `<next>-SNAPSHOT`, the version in Taffy's `gradle.properties` on `main` | `https://repo.alaz.so/snapshots` | every push to `main` that passes CI |

- `main` carries the next version with the `-SNAPSHOT` suffix.
- Each push to `main` builds and tests the repository, then publishes that snapshot. Snapshot artifacts change with every push.
- A release commit drops the suffix and is tagged `v<version>`. The tag publishes the plugins, the catalog and every runtime module to the releases repository. The release build refuses a tag that does not match the version in `gradle.properties`.
- The commit after a release sets the next `-SNAPSHOT` version.

### Building against a snapshot

`so.alaz.taffy.repositories` already declares `https://repo.alaz.so/snapshots` for dependencies, limited to snapshot versions in the `so.alaz` group and its subgroups, so the `alaz` catalog and the modules resolve at a snapshot version. The settings plugin itself resolves through `pluginManagement`, so add the snapshots repository there, and replace `<next>-SNAPSHOT` with the version in Taffy's `gradle.properties` on `main`:

```kotlin title="settings.gradle.kts"
pluginManagement {
    repositories {
        maven("https://repo.alaz.so/releases")
        maven("https://repo.alaz.so/snapshots")
        gradlePluginPortal()
    }
}

plugins {
    id("so.alaz.taffy.settings") version "<next>-SNAPSHOT"
}
```

A snapshot carries changes that the `[Unreleased]` section of the changelog describes, including breaking ones. Release a plugin against a release version, not a snapshot. [Getting started](/docs/getting-started#build-against-a-snapshot-or-a-local-publish) also covers building against a local publish of a Taffy checkout.

## Java and Paper

| Requirement | Value |
|---|---|
| Java | 25. `so.alaz.taffy.java` sets the Java 25 toolchain on each module that applies it, directly or through another Taffy convention plugin. |
| Gradle's own JVM | Java 25, because the Taffy Gradle plugins are Java 25 class files. |
| Server | Paper and Folia, at the builds [Servers](#servers) gives for each release line. `Scheduler` uses only schedulers that both provide. |
| Paper API | `io.papermc.paper:paper-api` `26.3.build.256-stable` from `0.2.0` and `26.1.2.build.66-stable` in `0.1.x`, the `paper` version of the `alaz` catalog (`alaz.paper.api`). |

Gradle picks a Java 25 JVM whatever `JAVA_HOME` is when the plugin project holds this file:

```properties title="gradle/gradle-daemon-jvm.properties"
toolchainVersion=25
```

Taffy's modules compile against the same `paper-api` version the catalog pins, so a plugin compiles against `alaz.paper.api`:

```kotlin title="build.gradle.kts"
dependencies {
    compileOnly(alaz.paper.api)
}
```

The catalog pins the versions of the rest of the stack the same way (HikariCP, the JDBC drivers, bStats, FastStats, the integration APIs, JUnit, AssertJ, Mockito), so a minor upgrade can move any of those versions. A patch moves only FastStats, bStats and a library whose new version fixes a security issue, as [What a patch changes](#what-a-patch-changes) states.

### Servers

| Release line | Compiled against | Servers |
|---|---|---|
| `0.1.x` | `paper-api` `26.1.2.build.66-stable` | Links statically against the `paper-api` of 26.2 and 26.3. Untested on a server, Paper or Folia. |
| `0.2.x` | `paper-api` `26.3.build.256-stable` | Paper 26.2 build 135 (the final 26.2 build) or newer, and Folia 26.3 build 8 (the first stable Folia 26.3 build) or newer, since Folia 26.2 has no stable build. Paper 26.1.2 is not supported. |

The `paper-api` pin and the oldest supported server stay the same for every patch of a release line. From `0.2.0`, `alaz.paper.api` brings Adventure 5.2.0 in place of 4.26.1, so a plugin moving from `0.1.x` recompiles against it. Adventure 5 makes `ClickEvent` generic, so a raw `ClickEvent` compiles with a rawtypes warning until it is written `ClickEvent<?>`.

## Reading the changelog

`CHANGELOG.md` uses the layout of [Keep a Changelog](https://keepachangelog.com):

- `## [Unreleased]` collects what is on `main` and not yet released, which is what a snapshot contains.
- Each release has a section headed `## [<version>]`, and that section is the release's notes.
- Inside a section, entries are grouped under headings such as `### Added`, `### Changed` and `### Deprecated`.

An entry in `### Changed` that starts with `Breaking:` changes a public signature or documented behaviour incompatibly, and names the new signature or behaviour and the one it replaces.

Before an upgrade, read every section between the current version and the target, and search them for `Breaking:` and `### Deprecated`.
