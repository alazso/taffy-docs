---
title: taffy-storage
description: JDBC storage over HikariCP for SQLite, MySQL, MariaDB and PostgreSQL, with transactions on its own threads and migrations from the plugin's scripts.
---

`taffy-storage` gives a plugin one `Storage` object for its database. It connects through HikariCP to SQLite, MySQL, MariaDB or PostgreSQL, brings the schema up to date from SQL scripts the plugin ships, and runs every piece of work in a transaction of its own on database threads that storage owns. The plugin never touches a `Connection`, never passes an executor, and never writes its own migration runner.

| Type | What it is |
|---|---|
| `Storage` | Starts the database, runs migrations, runs work in transactions, copies a SQLite database on demand, closes with a drain. |
| `StorageSettings` | The dialect, the SQLite file or `Server`, the `Pool`, the thread count and the backup count. |
| `Dialect` | `SQLITE`, `MYSQL`, `MARIADB`, `POSTGRES`: driver class names and the SQL that differs between them. |
| `Migration` | One numbered schema step, located by its script name. |
| `Baseline` | The version table of the plugin's previous migration runner, taken over once, with an optional schema check. |
| `Tx`, `TxWork` | The open transaction, and the work run inside it. |
| `Params`, `Row` | Typed placeholder binding and column reading: UUID, text, integer, `int`, boolean, money, decimal, time, JSON, bytes. |
| `MoneyColumn` | Stores an amount as a whole number at 4 decimal places. |
| `StorageException`, `CommitUnknownException`, `MoneyOutOfRangeException` | A failure for the server owner, a commit with an unknown outcome, an amount out of range. |

All types are in the package `so.alaz.taffy.storage`. The module depends on `taffy-platform` (for `ErrorReports`, see [taffy-platform](/docs/modules/platform)).

## Setup

The module is `alaz.taffy.storage` in the catalog. HikariCP and the JDBC drivers are not bundled, and the published metadata of `taffy-storage` names none of them. A plugin lists HikariCP and the driver of every dialect it offers in `paperPlugin.runtimeLibraries`, so that Paper downloads them at server start. A plugin whose own tests start storage also declares HikariCP and the driver of each dialect those tests start as `testRuntimeOnly`.

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.storage)

    testImplementation(alaz.paper.api)
    testImplementation(alaz.taffy.test)
    testImplementation(alaz.junit.jupiter)
    testRuntimeOnly(alaz.junit.platform.launcher)
    testRuntimeOnly(alaz.hikari)
    testRuntimeOnly(alaz.sqlite.jdbc)
}

paperPlugin {
    runtimeLibrary(alaz.hikari)
    runtimeLibrary(alaz.sqlite.jdbc)
    runtimeLibrary(alaz.mysql.connector)
    runtimeLibrary(alaz.mariadb.jdbc)
    runtimeLibrary(alaz.postgresql.jdbc)
}
```

`runtimeLibrary` adds the catalog entry's Maven coordinates to `paperPlugin.runtimeLibraries`, and a non-empty list generates `RuntimeLibraries.COORDINATES` in the plugin's group package for the plugin's `PluginLoader` to read. [Gradle plugins](/docs/gradle-plugins) covers the generated class.

| Library | Catalog alias | Maven coordinates | Driver class |
|---|---|---|---|
| HikariCP | `alaz.hikari` | `com.zaxxer:HikariCP` | |
| SQLite | `alaz.sqlite.jdbc` | `org.xerial:sqlite-jdbc` | `org.sqlite.JDBC` |
| MySQL | `alaz.mysql.connector` | `com.mysql:mysql-connector-j` | `com.mysql.cj.jdbc.Driver` |
| MariaDB | `alaz.mariadb.jdbc` | `org.mariadb.jdbc:mariadb-java-client` | `org.mariadb.jdbc.Driver` |
| PostgreSQL | `alaz.postgresql.jdbc` | `org.postgresql:postgresql` | `org.postgresql.Driver` |

The pool names the driver class explicitly (`Dialect.driverClassName()`), because Paper's library loader puts the drivers on the plugin class loader, where `java.sql.DriverManager` does not find them by URL.

<Callout type="warn" title="Missing libraries fail the start, not the server">
`Storage.start` looks up HikariCP and the driver of the configured dialect before it builds any pool. Without HikariCP its future fails with a `StorageException` whose message is `HikariCP is not available`. Without the driver it fails with `the mysql driver is not available` (with the dialect's id: `sqlite`, `mysql`, `mariadb` or `postgres`). No pool is built and the database threads stop.
</Callout>

## Settings

`StorageSettings` is a final class with no public constructor. The plugin reads its own config, starts from a factory and replaces the values that differ from the defaults; [taffy-config](/docs/modules/config) covers reading the file. Each method that takes a value gives a copy and leaves the original unchanged, and every value is checked by the factory or the method that takes it. The host, the database name, the table prefix and the version table are restricted because they are concatenated into SQL and JDBC URLs.

```java
public static StorageSettings sqlite(String sqliteFile)
public static StorageSettings server(Dialect dialect, Server server)
```

| Value | Read with | Replaced with | Default | Rule |
|---|---|---|---|---|
| The database | `dialect()` | the factory | | `sqlite` gives `SQLITE`; `server` takes `MYSQL`, `MARIADB` or `POSTGRES`. |
| The SQLite file | `sqliteFile()` | `sqlite(String)` | | Relative to the plugin's data folder and not blank. Empty for a server. |
| The server | `server()` | `server(Dialect, Server)` | | `null` for `SQLITE`. |
| The connection pool | `pool()` | `pool(Pool)` | `Pool.of(4)` | |
| The database threads | `asyncThreads()` | `asyncThreads(int)` | 2 | 1 or more, and not above `Pool.maxSize()` when storage starts. |
| The SQLite backups | `backupKeep()` | `backupKeep(int)` | 5 | How many SQLite backups taken before a migration to keep, 0 or more. 0 takes none. |
| The version table | `versionTable()` | `versionTable(String)` | `null`, the default name | 1 to 54 lowercase letters, digits and underscores starting with a letter or underscore. [The version table](#the-version-table) gives the default name. |

`StorageSettings.Pool.of(int maxSize)` gives a pool of up to `maxSize` connections that keeps 1 idle connection open and lets a caller wait 10 seconds for a connection. `maxSize(int)` (1 or more), `minIdle(int)` (0 to `maxSize`) and `connectionTimeout(Duration)` (250 milliseconds or more) each give a copy.

Each database thread uses one connection at a time, so `asyncThreads` must not be above `Pool.maxSize()`, and connections above `asyncThreads` are never used. The two are set by separate methods, so `Storage.start` checks them together and throws `IllegalArgumentException` for more threads than connections. Before `0.4.0` such settings started, and the threads beyond the pool's size failed with a connection timeout under load.

`StorageSettings.Server.of(String host, int port, String database, String user, String password, SslMode sslMode)` gives a server with no table prefix, a socket timeout of 30 seconds and no driver properties. `tablePrefix(String)`, and from `0.4.0` `socketTimeout(Duration)` and `properties(Map<String, String>)`, each give a copy with that value replaced:

| Value | Rule |
|---|---|
| `host` | A host name or IPv4 address of ASCII letters, digits, dots, hyphens and underscores, or an IPv6 address in brackets such as `[::1]`. |
| `port` | 1 to 65535. |
| `database` | 1 to 64 letters, digits, underscores, dollar signs and hyphens. |
| `user`, `password` | The credentials. The password is empty for none. `Server.toString()` shows `(set)` instead of the password. |
| `sslMode` | `DISABLE`, `PREFER`, `TRUST` or `VERIFY_FULL`. [SSL modes](#ssl-modes) describes each. |
| `tablePrefix` | Empty, or up to 32 lowercase letters, digits and underscores starting with a letter or underscore. |
| `socketTimeout` | How long a connection waits for the server to answer during normal work: a whole number of seconds from 1 to 2147483, 30 seconds unless set. [The socket timeout](#the-socket-timeout) describes what it ends. |
| `properties` | Properties handed to the JDBC driver with every connection, empty unless set. [Driver properties](#driver-properties) lists the names storage refuses. |

`StorageSettings.tablePrefix()` returns the server's prefix, or an empty string for SQLite: a SQLite database has no table prefix.

A factory or a method that takes a value throws `NullPointerException` for a `null` argument and `IllegalArgumentException` with a message naming the bad value, so a plugin can show that message to the server owner. `StorageSettings`, `Server` and `Pool` compare by value. Before `0.4.0` the three were records built with `new`; [Upgrading](/docs/upgrading-from-0-1#storage-settings-are-built-through-factories) shows each replacement.

### SSL modes

`SslMode` decides whether the connection to a server is encrypted and what is checked. Each mode becomes the driver's own setting in the JDBC URL:

| `SslMode` | Meaning | MySQL | MariaDB | PostgreSQL |
|---|---|---|---|---|
| `DISABLE` | Not encrypted. | `sslMode=DISABLED` | `sslMode=disable` | `sslmode=disable` |
| `PREFER` (from `0.4.0`) | Encrypted when the server offers TLS, not encrypted when it does not. The server's certificate is not checked. | `sslMode=PREFERRED` | `sslMode=disable`: not encrypted | `sslmode=prefer` |
| `TRUST` | Encrypted, the server's certificate is not checked. | `sslMode=REQUIRED` | `sslMode=trust` | `sslmode=require` |
| `VERIFY_FULL` | Encrypted, the certificate and the host name are checked. | `sslMode=VERIFY_IDENTITY` | `sslMode=verify-full` | `sslmode=verify-full` with `sslfactory=org.postgresql.ssl.DefaultJavaSSLFactory` |

- With `DISABLE` and `PREFER`, MySQL and MariaDB URLs also carry `allowPublicKeyRetrieval=true`, so an unencrypted login with MySQL 8's `caching_sha2_password` can fetch the server key.
- `PREFER` is what the MySQL and PostgreSQL drivers do for a JDBC URL that names no mode, so a plugin that connected with a bare URL before it used Taffy keeps the encryption its owners have. Someone who can change the traffic between the two machines can make such a connection fall back to no encryption, so `PREFER` protects only against someone who reads the traffic. `TRUST` fails on a server without TLS, and `VERIFY_FULL` also checks who the server is.
- The MariaDB driver has no mode that encrypts only when the server offers TLS without checking the certificate, so on MariaDB `PREFER` is `DISABLE`, that driver's own default: the connection is not encrypted, whether or not the server offers TLS. Use `TRUST` or `VERIFY_FULL` to encrypt a MariaDB connection.
- With `VERIFY_FULL`, the certificate is checked against the JVM's default trust store on every server dialect. On PostgreSQL that is what `DefaultJavaSSLFactory` does; the driver's default socket factory would check only a `root.crt` file in the user's home. A server whose certificate comes from a private authority needs that authority in the trust store of the JVM that runs Paper.
- `VERIFY_FULL` checks the host name against the certificate, so `host` must be a name the certificate holds. A certificate for `localhost` is accepted with host `localhost` and refused with host `127.0.0.1`.
- With `TRUST`, PostgreSQL uses `sslmode=require` with the driver's default socket factory.

MySQL and MariaDB URLs also set `useAffectedRows=true`. From `0.4.9`, a MySQL URL also sets `rewriteBatchedStatements=true`, which only [`Tx.batch`](#batches) uses. `SslMode` may gain a constant in a later release, so a `switch` over it needs a `default` branch.

### The socket timeout

Every server URL sets a socket timeout: `socketTimeout` in milliseconds on MySQL and MariaDB and in seconds on PostgreSQL. It is 30 seconds (`socketTimeout=30000`, or `socketTimeout=30` on PostgreSQL) unless the plugin sets another, which it can from `0.4.0` with `Server.socketTimeout(Duration)`. Before `0.4.0` it was always 30 seconds.

A statement that waits longer than the timeout for the server, a wait for a row lock included, fails with an `SQLException` and its connection is closed. Whether the server still ran the statement is then unknown, and `asyncRetrying` does not run the work again. A plugin whose statements or lock waits may pass 30 seconds sets a longer timeout. Migrations run without the timeout.

```java
StorageSettings.Server server = StorageSettings.Server
    .of("db.example.net", 3306, "minecraft", "plugin", "secret", StorageSettings.SslMode.PREFER)
    .socketTimeout(Duration.ofMinutes(2));
```

### Driver properties

From `0.4.0`, `Server.properties(Map<String, String>)` hands properties to the JDBC driver with every connection, under the names and with the values the driver documents. The map replaces the properties the server had and is copied. Storage does not check a name or a value the driver does not know, and `Server.toString()` shows the names and never the values.

```java
StorageSettings.Server server = StorageSettings.Server
    .of("db.example.net", 5432, "minecraft", "plugin", "secret", StorageSettings.SslMode.VERIFY_FULL)
    .properties(Map.of("ApplicationName", "MyPlugin", "connectTimeout", "5"));
```

A name that would replace a value storage sets itself throws `IllegalArgumentException`, in any letter case, because a driver would let the property win:

| Refused | Set instead through |
|---|---|
| `user`, `password` | `Server.of` |
| `sslMode`, `ssl`, `useSSL`, `requireSSL`, `verifyServerCertificate`, `trustServerCertificate`, `disableSslHostnameVerification`, `sslfactory`, `allowPublicKeyRetrieval` | the `SslMode` of `Server.of` |
| `socketTimeout` | `Server.socketTimeout(Duration)` |
| `useAffectedRows` | nothing: storage always sets it on MySQL and MariaDB, and [row counts](#row-counts-differ-per-dialect) depend on it |
| `autoReconnect`, `autoReconnectForPools` | nothing: with either, the MySQL driver replaces a dropped connection without an error, and the new session no longer holds the [migration lock](#per-dialect-behaviour). The pool replaces a dropped connection itself. |

## Starting storage

```java
public static CompletableFuture<Storage> start(Plugin plugin, ErrorReports errors, StorageSettings settings,
                                               List<Migration> migrations, Clock clock)

public static CompletableFuture<Storage> start(Plugin plugin, ErrorReports errors, StorageSettings settings,
                                               List<Migration> migrations, Baseline baseline, Clock clock)
```

`start` reads the plugin's name, version, data path and logger on the calling thread, then does everything else on a new database thread (on SQLite, the writer thread): it checks the libraries, builds the pools, runs the pending migrations and completes the future.

- `Plugin.getName()` names the threads and pools, and on a server the default [version table](#the-version-table), and must not be blank.
- The plugin version is written into the file name of a SQLite backup, with every character other than an ASCII letter, a digit, a dot, an underscore or a hyphen as an underscore.
- `Plugin.getDataPath()` holds the SQLite file and the `backups` folder; missing folders are created.
- `Plugin.getLogger()` receives a line for each applied migration and backup, and the warnings.
- `Plugin.getResource(String)` opens each migration script.
- `errors` receives the failures storage catches and handles itself, under the source `storage`: an `afterCommit` action that throws, and a task on the database threads that throws while storage closes.
- `clock` is the clock of `Tx.now()` and of the times recorded for migrations and backups.

`start` throws `NullPointerException` for a `null` argument and `IllegalArgumentException` when the plugin name is blank or the migration versions are not strictly increasing. Every other failure completes the future exceptionally.

```java title="MyPlugin.java"
public final class MyPlugin extends JavaPlugin {

    private static final List<Migration> MIGRATIONS = List.of(
        new Migration(1, "accounts"),
        new Migration(2, "account_history"));

    private final ErrorReports errors = new ErrorReports();
    private volatile CompletableFuture<Storage> starting;
    private volatile Storage storage;
    private Scheduler scheduler;

    @Override
    public void onEnable() {
        scheduler = new Scheduler(this, errors);
        StorageSettings settings = StorageSettings.sqlite("data.db");
        CompletableFuture<Storage> start = Storage.start(this, errors, settings, MIGRATIONS, Clock.systemUTC());
        starting = start;
        start.whenComplete((started, failure) -> {
            if (failure == null) {
                storage = started;
                return;
            }
            if (failure instanceof CancellationException) {
                return;
            }
            if (failure instanceof StorageException owner) {
                getLogger().severe("Cannot start the database: " + owner.getMessage());
            } else {
                getLogger().log(Level.SEVERE, "Cannot start the database", failure);
            }
            if (!scheduler.global(() -> getServer().getPluginManager().disablePlugin(this))) {
                getLogger().info("The plugin is already disabling");
            }
        });
    }
}
```

A start cancelled at disable completes with a `CancellationException`, which the handler ignores.

The future fails with:

- a `StorageException` when HikariCP or the driver is missing, a migration script is missing, unreadable, not valid UTF-8, cannot be split into statements or changed after it ran, a SQLite migration leaves a broken foreign key, the database was set up by a newer version of the plugin, the version table exists in another layout that no [`Baseline.takeOverSameName()`](#an-old-table-named-as-the-version-table) covers, the connection names no current database (on PostgreSQL, no current schema), or another start has held the migration lock for a day (MySQL, MariaDB and PostgreSQL);
- an `SQLException` when the database refuses a statement; for a statement of a migration script the message names the migration and the statement;
- whatever HikariCP throws when it cannot connect.

A `StorageException` message is written for the server owner as one sentence without a final full stop, so it reads after a lead-in such as `Cannot start the database: `.

When the start fails, it closes the pools it built and stops its threads. When the future was already completed by the time the start finishes (by `cancel`, `orTimeout` or `completeOnTimeout`), the start closes the storage it built itself, so a plugin that gives up on a start has nothing to close.

The future completes on a database thread. On SQLite it completes on a read thread, never on the writer thread.

## Running work

Each piece of work is a `TxWork<T>`, a function from an open `Tx` to a result that may throw `SQLException`. It runs in one transaction with a connection of its own. The transaction commits when the work returns and rolls back when it throws.

| Method | Use |
|---|---|
| `<T> CompletableFuture<T> async(TxWork<T> work)` | Work that may write. |
| `<T> CompletableFuture<T> read(TxWork<T> work)` | Work that only reads. On SQLite it runs on read-only connections that refuse a write. |
| `<T> CompletableFuture<T> asyncRetrying(TxWork<T> work)` | As `async`, retried when the database rolled the transaction back. |
| `<T> CompletableFuture<T> readRetrying(TxWork<T> work)` | As `read`, retried the same way. |

`Tx` runs statements and carries the transaction's context:

| `Tx` method | What it does |
|---|---|
| `int update(String sql, Tx.Binder binder)` | Runs an `INSERT`, `UPDATE` or `DELETE` and returns the row count. |
| `int[] batch(String sql, List<Tx.Binder> binders)` | From `0.4.9`: runs one `INSERT`, `UPDATE` or `DELETE` once for each binder as a JDBC batch and returns one count for each. [Batches](#batches) gives the rules. |
| `<T> List<T> query(String sql, Tx.Binder binder, Tx.Mapper<T> mapper)` | Maps every row of the result, in order. |
| `<T> Optional<T> queryOne(String sql, Tx.Binder binder, Tx.Mapper<T> mapper)` | At most one row. More than one throws `SQLException`; a mapper returning `null` gives an empty `Optional`. |
| `void execute(String sql)` | A statement without values, such as DDL. |
| `void afterCommit(Runnable action)` | Runs `action` once the transaction has committed, on the database thread, before the work's future completes, in the order the actions were added. Never runs for a transaction that rolled back or whose commit has an unknown outcome. An action that throws is logged and reported to `errors`, and the future still completes with the result. |
| `String table(String name)` | The table prefix followed by `name`. |
| `Instant now()` | The storage clock's instant when the transaction opened, the same for every call in it. |
| `Dialect dialect()` | The database. |

`Tx.Binder.NONE` binds nothing, for a statement without placeholders. `Storage` itself also has `table(String)` and `dialect()`.

```java
public CompletableFuture<Optional<BigDecimal>> balance(UUID player) {
    return storage.read(tx -> tx.queryOne(
        "SELECT balance FROM " + tx.table("accounts") + " WHERE player = ?",
        params -> params.uuid(player),
        row -> row.money("balance")));
}

public CompletableFuture<Boolean> deposit(UUID player, BigDecimal amount) {
    return storage.asyncRetrying(tx -> {
        int changed = tx.update(
            "UPDATE " + tx.table("accounts") + " SET balance = balance + ?, updated_at = ? WHERE player = ?",
            params -> params.money(amount).time(tx.now()).uuid(player));
        if (changed == 1) {
            tx.afterCommit(() -> getLogger().info("Deposited " + amount + " for " + player));
        }
        return changed == 1;
    });
}
```

### Binding and reading values

`Params` binds placeholders in order, the first call binding the first `?`, and every method returns the same `Params` so calls chain. Every method that takes an object binds SQL `NULL` for `null`. `Row` reads the current row by column name, decodes each value the way `Params` binds it, and returns `null` for SQL `NULL`.

| `Params` | `Row` | Stored as |
|---|---|---|
| `uuid(UUID)` | `uuid(String)` | 16 bytes, most significant first, on SQLite, MySQL and MariaDB; a native `uuid` on PostgreSQL. |
| `text(String)` | `text(String)` | A string. |
| `integer(long)`, `integer(Long)` | `integer(String)` returns `Long` | A whole number; a `null` `Long` binds `NULL` typed `BIGINT`. |
| `intValue(int)`, `intValue(Integer)` | `intValue(String)` returns `Integer` | A whole number that fits an `int`, for an `INTEGER` or `INT` column; a `null` `Integer` binds `NULL` typed `INTEGER`. From `0.4.9`. |
| `bool(boolean)`, `bool(Boolean)` | `bool(String)` returns `Boolean` | 1 for `true` and 0 for `false` on SQLite, MySQL and MariaDB; a native `boolean` on PostgreSQL. A `null` `Boolean` binds `NULL` typed `BOOLEAN`. From `0.4.9`. |
| `money(BigDecimal)` | `money(String)` | A `BIGINT` at 4 decimal places, through `MoneyColumn.toStored`. |
| `moneyOrNull(BigDecimal)` | `money(String)` | A signed amount through `MoneyColumn.toStoredOrNull`: an amount above `MoneyColumn.MAX` in magnitude binds `NULL`. |
| `signedMoney(BigDecimal)` | `money(String)` | A signed amount through `MoneyColumn.toStoredSigned`: an amount above `MoneyColumn.MAX` in magnitude throws `MoneyOutOfRangeException`. From `0.3.2`. |
| `decimal(BigDecimal)` | `decimal(String)` | A decimal number of any magnitude, unscaled: a `DECIMAL` on MySQL and MariaDB, a `NUMERIC` on PostgreSQL, text on SQLite. From `0.3.2`. |
| `time(Instant)` | `time(String)` | Milliseconds since the epoch in a `BIGINT`; precision below a millisecond is dropped. The instant is one whose milliseconds fit a `long`: `time` throws `ArithmeticException` for `Instant.MAX` and `Instant.MIN`, so "never" is stored as `null`. |
| `json(String)` | `json(String)` | `Types.OTHER` on PostgreSQL (fits `json` and `jsonb`), a string elsewhere. |
| `bytes(byte[])` | `bytes(String)` | A byte array. |

`Row.json` returns a normalized document for a MySQL `JSON` column and a PostgreSQL `jsonb` column, which may differ from the stored text in whitespace, key order and duplicate keys. MariaDB, SQLite and a PostgreSQL `json` column return the stored text.

`MoneyColumn.SCALE` is 4 and `MoneyColumn.MAX` is `Long.MAX_VALUE` at 4 decimal places. `12.5` is stored as `125000`, so stored values sort numerically on every database. `toStored` rounds half even and throws `MoneyOutOfRangeException` (an `IllegalArgumentException`) for an amount of `-0.0001` or less, or above `MAX`. An amount whose magnitude is below `0.0001` is stored as 0 whatever its sign. `fromStored(long)` decodes.

A balance that may be negative is bound with `signedMoney` or `moneyOrNull`. Both encode like `money` and differ only above `MoneyColumn.MAX` in magnitude: `signedMoney` (from `0.3.2`) throws `MoneyOutOfRangeException`, so the transaction rolls back and the caller sees the failure, and `moneyOrNull` binds `NULL`, so the row is written without the balance.

### Whole numbers and booleans

`Params.integer` takes a `long` and `Row.integer` returns a `Long`, which fits every whole-number column. From `0.4.9`, `intValue` and `bool` cover the two narrower types, so a Kotlin `Int` or `Boolean` needs no conversion:

```java
tx.update("INSERT INTO " + tx.table("kits") + " (id, uses, enabled) VALUES (?, ?, ?)",
    params -> params.text(id).intValue(uses).bool(enabled));

Optional<Kit> kit = tx.queryOne("SELECT uses, enabled FROM " + tx.table("kits") + " WHERE id = ?",
    params -> params.text(id),
    row -> new Kit(id, row.intValue("uses"), row.bool("enabled")));
```

- **`Row.intValue` refuses what does not fit.** It returns `null` for `NULL` and throws `SQLException` for a number below `Integer.MIN_VALUE` or above `Integer.MAX_VALUE`, with the same message on every database: `uses holds 2147483648, which does not fit an int`.
- **A boolean column is declared `BOOLEAN` in every script.** That is `TINYINT(1)` on MySQL and MariaDB, a column that holds the whole number on SQLite, and a native `boolean` on PostgreSQL.
- **On SQLite, MySQL and MariaDB a boolean is the whole number 1 or 0**, so any whole-number column holds one, `WHERE enabled = 1` matches it, and `Row.integer` reads it back as `1` or `0`. `Row.bool` returns `null` for `NULL` and throws `SQLException` for any other number: `enabled holds 2, which is neither 0 nor 1`.
- **PostgreSQL keeps the two types apart.** It refuses a boolean for an `INTEGER` or `SMALLINT` column, so a PostgreSQL column that stores 0 and 1 as numbers is bound with `intValue`. `Row.bool` reads there what the driver reads as a boolean: a `boolean` column, or a whole-number column that holds 0 or 1.
- `Row.intValue` and `Row.bool` return the boxed type, like every `Row` reader, because the column may hold `NULL`.

### Amounts above the money ceiling

`MoneyColumn.MAX` is `922337203685477.5807`, about 9.22e14. A prison, tycoon or skyblock economy passes it, and `money` then throws on every save of that balance. From `0.3.2`, `Params.decimal(BigDecimal)` and `Row.decimal(String)` bind and read a `BigDecimal` without scaling or rounding it, for a column the migration script of each dialect declares:

| Dialect | Column type | Bound as |
|---|---|---|
| MySQL, MariaDB | `DECIMAL(precision, scale)`, up to 65 digits | `setBigDecimal` |
| PostgreSQL | `NUMERIC`, or `NUMERIC(precision, scale)` | `setBigDecimal` |
| SQLite | `TEXT` | The text of `BigDecimal.toString`, which keeps every digit and the scale. |

The limits of a decimal column:

- **SQLite compares the stored values as text.** `ORDER BY`, `<`, `>`, `MIN` and `MAX` over the column are not numeric there: `10` sorts before `9`. Arithmetic in SQL, such as `SUM` or `balance = balance + ?`, converts the text to a floating-point number there and loses digits, so read the value, compute in Java and write it back inside one transaction. A top list over a decimal column is sorted in Java on SQLite, and a column that is sorted or compared in SQL on every database stays a `money` column.
- **A SQLite column declared `NUMERIC` or `DECIMAL` loses digits.** SQLite converts the text to a floating-point number in such a column and keeps about 15 digits. Declare it `TEXT`.
- **The declared precision and scale are the range.** The database rounds a value to the declared scale and decides what happens to one with more digits than the declared precision. Taffy checks neither.
- **`Row.decimal` returns the scale the column holds**, which may differ from the scale that was bound (`DECIMAL(65, 4)` returns `12.5000` for `12.5`), so compare with `compareTo`, not `equals`. On SQLite, text that is not a decimal number throws `SQLException`.

### Batches

From `0.4.9`, `Tx.batch(String sql, List<Tx.Binder> binders)` runs one `INSERT`, `UPDATE` or `DELETE` once for each binder as a JDBC batch, inside the transaction like every other statement. On a server the rows travel in fewer round trips than one `update` for each; on SQLite a batch saves nothing over a loop, and both are correct.

```java
public CompletableFuture<int[]> saveCurrencies(List<Currency> currencies) {
    return storage.async(tx -> {
        String sql = tx.dialect().upsert(tx.table("currencies"),
            List.of("id", "name", "decimals", "enabled", "updated_at"),
            List.of("id"),
            List.of("name", "decimals", "enabled", "updated_at"));
        List<Tx.Binder> rows = new ArrayList<>();
        for (Currency currency : currencies) {
            rows.add(params -> params.text(currency.id()).text(currency.name()).intValue(currency.decimals())
                .bool(currency.enabled()).time(tx.now()));
        }
        return tx.batch(sql, rows);
    });
}
```

- **Each binder binds every placeholder** of the statement, for one run of it. An empty list runs nothing and returns an empty array, and a `null` list or binder throws `NullPointerException`.
- **The result holds one element for each binder, in order**: the count `update` gives for that run (see [row counts](#row-counts-differ-per-dialect)), or `Statement.SUCCESS_NO_INFO` (`-2`) where the driver ran the row and does not know its count.
- **MySQL rewrites a batch.** MySQL connections are opened with `rewriteBatchedStatements=true`, so the driver sends a batch as one multi-row `INSERT` or as several statements in one packet, and reports `SUCCESS_NO_INFO` for the rows of a rewritten batch. Work that needs the count of every row on MySQL runs `update` for each. SQLite, MariaDB and PostgreSQL report the counts. The property changes no other statement.
- **A run that fails throws what the driver threw**, usually a `java.sql.BatchUpdateException`. The runs before it stay part of the open transaction, like every statement before them: work that lets the exception through rolls all of it back, and nothing of the batch is written. On PostgreSQL a failed statement ends the transaction, so the work can only throw. On the other databases, work that catches the exception and returns commits what the earlier runs wrote.
- Generated keys are not returned: a row that needs its key is inserted with a key the plugin makes, such as a UUID.

### Dialect SQL

`Dialect` builds the statements that differ between databases. Table and column names are concatenated as given, so they must come from code, never from a player or a server owner; every value is a `?` placeholder.

| Method | Result |
|---|---|
| `insertOrIgnore(String table, List<String> columns, List<String> key)` | An insert that does nothing on a conflict, counting 0. On MySQL and MariaDB it skips a conflict on any unique key, so `key` must be the table's only unique key. |
| `upsert(String table, List<String> columns, List<String> key, List<String> updated)` | An insert that overwrites `updated` on a conflict. Through `Tx.update` on MySQL or MariaDB it counts 1 for an insert, 2 for a changed row and 0 for an unchanged row; on SQLite and PostgreSQL it counts 1. MySQL and MariaDB ignore `key`. |
| `forUpdate()` | `" FOR UPDATE"`, or an empty string on SQLite. |
| `listTables()` | A query listing the tables of the current database or schema. |
| `id()` | `sqlite`, `mysql`, `mariadb` or `postgres`, also the folder of the migration scripts. |
| `transactionalDdl()` | `true` for SQLite and PostgreSQL, `false` for MySQL and MariaDB. |

```java
storage.async(tx -> tx.update(
    tx.dialect().upsert(tx.table("accounts"),
        List.of("player", "balance", "updated_at"),
        List.of("player"),
        List.of("balance", "updated_at")),
    params -> params.uuid(player).money(balance).time(tx.now())));
```

`forUpdate()` is for work that reads a row and then writes a value computed from what it read. On MySQL, MariaDB and PostgreSQL writes run at the same time (see [Threads](#threads)), so without the clause another transaction can change the row between the two statements and one of the two updates is lost. With it, the row is held until the transaction ends, and another transaction that selects the row the same way, or writes it, waits. On SQLite the clause is empty and writes run one at a time.

```java
public CompletableFuture<Boolean> withdraw(UUID player, BigDecimal amount) {
    return storage.asyncRetrying(tx -> {
        BigDecimal balance = tx.queryOne(
            "SELECT balance FROM " + tx.table("accounts") + " WHERE player = ?" + tx.dialect().forUpdate(),
            params -> params.uuid(player),
            row -> row.money("balance")).orElse(BigDecimal.ZERO);
        if (balance.compareTo(amount) < 0) {
            return false;
        }
        tx.update("UPDATE " + tx.table("accounts") + " SET balance = ?, updated_at = ? WHERE player = ?",
            params -> params.money(balance.subtract(amount)).time(tx.now()).uuid(player));
        return true;
    });
}
```

Where one statement can do the work, it needs no lock: `UPDATE ... SET balance = balance - ? WHERE player = ? AND balance >= ?` is a relative, conditional update, and its row count tells whether it applied. Two transactions that lock the same rows in another order can deadlock; the database then rolls one back, and `asyncRetrying` runs it again.

### Row counts differ per dialect

MySQL and MariaDB connections are opened with `useAffectedRows=true`. An `UPDATE` there counts only the rows whose values it changed, so a matched row written with its current values counts 0. SQLite and PostgreSQL count every matched row. A conditional update that must report success on MySQL and MariaDB changes a column, for example a timestamp.

### Retrying rolled-back transactions

`asyncRetrying` and `readRetrying` run the work again when the database rolled its transaction back to break a deadlock or a serialization conflict, up to 4 attempts in all. A failure counts as rolled back when it is, or has as a cause, an `SQLTransactionRollbackException` or an `SQLException` whose SQLState starts with `40` (`40001` on MySQL and MariaDB, `40P01` on PostgreSQL). It counts whether the work, a statement or the commit threw it.

- Each attempt gets its own connection and `Tx`, so `afterCommit` actions of an attempt that rolled back never run. An effect outside the database belongs in `afterCommit`, and each run of the work must be safe to repeat.
- Before attempt `n + 1` the database thread sleeps a random 5n to 20n milliseconds. The sleep holds that thread; on SQLite it holds every write queued behind it. When the thread is interrupted during the sleep, the future fails with an `SQLException` and the thread's interrupt flag is set again.
- When no attempt commits, the future fails with the failure of the last attempt.
- From `0.4.0`, a commit the database refuses because it rolled the transaction back is run again like any other rolled-back attempt: a PostgreSQL `SERIALIZABLE` transaction learns of a serialization failure (`40001`) only at its commit. Before `0.4.0` that commit failed the future with a `CommitUnknownException`.
- A `CommitUnknownException` is never retried. A commit that fails with SQLState `40003` (statement completion unknown) is one, although its state starts with `40`: it does not say whether the commit was written.
- From `0.4.0`, a SQLite write transaction begins with `BEGIN IMMEDIATE`: while another process holds the file's write lock, the work waits for it up to the busy timeout of 5 seconds and then reads what that process wrote. Before `0.4.0` it began deferred, and work that read and then wrote failed at once with `SQLITE_BUSY`. Work passed to `async` holds the write lock while it runs, so work that only reads belongs in `read`.

### Failures

| Failure | Meaning |
|---|---|
| The exception the work threw | The transaction rolled back; nothing was written. |
| An `SQLTransactionRollbackException`, or an `SQLException` whose SQLState or that of a cause starts with `40`, from the commit | From `0.4.0`: the database rolled the transaction back at its commit; nothing was written. `asyncRetrying` and `readRetrying` run the work again. |
| `CommitUnknownException` | The commit statement itself failed for any other reason, or with SQLState `40003` (statement completion unknown), so whether the transaction was written is unknown. It extends `SQLException` and keeps the SQLState and vendor code. Read the state back to find out. |
| `RejectedExecutionException` | Storage is closed, or closed before this work ran. |
| `IllegalStateException` from `update`, `batch`, `query`, `queryOne`, `execute` or `afterCommit` | The `Tx` was used from another thread or after the work returned. |

## Threads

`Storage` owns its threads. `start` creates `asyncThreads` daemon threads named `<name>-db-1`, `<name>-db-2` and so on, where `<name>` is the plugin name, and `close` stops them.

| Dialect | Writes | Reads | Pools |
|---|---|---|---|
| SQLite | One extra thread `<name>-db-writer`, one write at a time in submission order, through a pool of one connection named `<name>-writer`. | The `<name>-db-N` threads, through read-only connections from the pool `<name>-reader` (`Pool.maxSize` connections). | Two |
| MySQL, MariaDB, PostgreSQL | The `<name>-db-N` threads. | The same threads. | One, named `<name>` |

Every SQLite connection opens with `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=5000` and `foreign_keys=true`, so foreign keys are enforced. Read connections also run `PRAGMA query_only = ON`, and from `0.4.0` the writer connection opens with `transaction_mode=IMMEDIATE`. On a server, every connection has [the socket timeout](#the-socket-timeout) of its `Server` during normal work, 30 seconds unless set: a statement that waits longer for the server, a lock wait included, fails and its connection is closed. Migrations run without that timeout.

<Callout type="warn" title="Writes run at the same time on a server">
On SQLite every write runs one at a time on the writer thread, so work that reads a row and then writes a value computed from it is correct there. On MySQL, MariaDB and PostgreSQL writes run in parallel on up to `asyncThreads` threads, each in a transaction on a connection of its own, in no order relative to each other, and the same work loses an update. Such work writes with a single conditional or relative `UPDATE` (`SET balance = balance + ?`, `WHERE id = ? AND state = ?`), or selects the row with [`Dialect.forUpdate()`](#dialect-sql).

On MySQL and MariaDB a transaction reads from the snapshot its first select took (`REPEATABLE READ`). A select without `forUpdate()` that runs again inside one `TxWork` sees the same rows however often it runs, whatever other transactions committed meanwhile. A loop that reads, computes and writes with a condition until its write counts a row therefore runs one `TxWork` per attempt, or reads with `forUpdate()`, which reads the newest committed row.
</Callout>

### Where stages run

- The future of work completes on a database thread after the transaction has ended and the connection is back in the pool, so a stage chained onto it never holds the connection or sees an open transaction.
- The future of `read` and `readRetrying` completes on the thread that ran the work.
- On SQLite, the futures of `async`, `asyncRetrying` and `start` complete on a read thread, not on the writer thread. With more than one read thread, the futures of two writes may complete in another order than the writes, which still commit in submission order.
- A stage chained without an executor runs on that database thread and holds it. The `Executor` from `executor()` runs tasks that use no connection on the database threads (the read threads on SQLite); it refuses new tasks with `RejectedExecutionException` once `close` has begun.
- A `Tx` is confined to the thread that opened it. Bukkit and Paper API calls do not belong on a database thread: hop to the right thread with the [Scheduler](/docs/modules/platform).

```java
deposit(player.getUniqueId(), amount).whenComplete((done, failure) ->
    scheduler.entity(player, () -> player.sendMessage(Component.text(
        failure == null && done ? "Deposited." : "The deposit failed."))));
```

<Callout type="error" title="Waiting on a database thread">
Work, a task from `executor()`, or a stage on a database thread that blocks on the future of other database work holds its thread while it waits. That wait ends only once another `<name>-db-N` thread is free. With `asyncThreads` at 1, or storage from `Storage.over`, such a wait never ends. On SQLite, work must never wait for another write at all: that write queues behind it on the one writer thread and never runs.
</Callout>

### Script rules

- A script is read as UTF-8; one that is not valid UTF-8 stops the start.
- A statement ends at a semicolon that ends its line, and a line holds at most one statement. A semicolon outside a quoted string that does not end its line stops the start.
- Blank lines, lines holding only a `--` comment, and a `--` comment at the end of a line are dropped. A final statement without a semicolon is kept.
- Only single-quoted strings are recognised, so a semicolon or `--` inside one is kept. A string ends on the line it starts, and a quote inside a string is written as two quotes.
- A block comment (`/* ... */`) outside a quoted string is kept and sent with its statement, over as many lines as it has, a MySQL `/*! ... */` comment included. From `0.4.0` nothing inside it is read: no semicolon, quote, `--` or `$$`. A block comment after the semicolon that ends a statement is a second thing on that line and stops the start.
- From `0.4.0`, a pending script stops the start with a `StorageException` that names the file and the line when it holds what these rules cannot read: a single-quoted string that does not end on its line, a block comment that never closes or holds another block comment (PostgreSQL nests them and the other databases do not), dollar quoting (`$$`) outside a quoted string and outside a block comment, or, on MySQL and MariaDB, a quote directly after a backslash, which those two read as part of the string. On SQLite and PostgreSQL a backslash is a plain character, so `ESCAPE '\'` ends its string there. Before `0.4.0` such a script was split wrongly or ran by accident. A script that already ran is only compared by its checksum.
- A script that already ran on any database is never edited, not even to follow these rules: its checksum would no longer match there, and the start would stop with `changed after it ran on this database`. The corrected statement goes into a new migration.
- Double-quoted or backquoted identifiers that hold a semicolon, a quote or `--`, a PostgreSQL escape string (`E'...'`) that holds `\'`, and a body of statements between `BEGIN` and `END` (a trigger or a procedure), are not supported and not recognised.
- A script may hold nothing but `SELECT 1;`, for a version that changes nothing on one dialect, and the scripts of one migration may differ in shape from dialect to dialect: each is recorded with its own checksum and statement count.
- Every script is read, and every pending one is split, before the SQLite backup and before the first migration runs, so a broken script stops the start before anything changes.

### Checksums

The SHA-256 checksum of each script is taken before `${prefix}` is replaced and stored with its version. A script that differs from the one that ran stops the start.

From `0.4.0`, the checksum ignores line endings and a leading byte order mark: it is taken over the text with every line ending as a line feed and without the mark. A build whose scripts were checked out with CRLF starts on a database that ran the LF scripts, and a script with a byte order mark runs. A row written by `0.1.0` to `0.3.2` holds the checksum of the script's exact bytes and is accepted when the script has the same text, whatever line endings (LF or CRLF) or byte order mark either build shipped it with; for a script that shipped with LF and no mark the two checksums are the same. A build pinned to LF so starts on a database an earlier CRLF build recorded. Only a row recorded from a script with lone carriage returns or mixed line endings is accepted just while the script still has those exact bytes. Before `0.4.0` a script that differed only in its line endings stopped the start with `changed after it ran on this database`. A new row for a script with CRLF or a mark does not hold the SHA-256 of the script's bytes, so a build on `0.3.2` that reads the same version table refuses it. Pinning scripts to LF still keeps a jar the same on every build machine:

```text title=".gitattributes"
*.sql text eol=lf
```

### The version table

Storage records applied migrations in the version table (columns `version`, `name`, `checksum`, `statements_done`, `applied_at`) and creates it itself, so no script creates it. A script that creates it with `CREATE TABLE IF NOT EXISTS` still runs.

| Database | Name of the version table |
|---|---|
| SQLite | `schema_version`. The file holds the tables of one plugin. |
| MySQL, MariaDB, PostgreSQL | From `0.4.0`, `<prefix><plugin>_schema_version`, where `<plugin>` is `Plugin.getName()` in lowercase with every character other than a lowercase letter, a digit or an underscore replaced by an underscore: `myplugin_my_plugin_schema_version` for the plugin `My-Plugin` under the prefix `myplugin_`. A name that would pass 54 characters has the plugin part cut at its end, and one that would start with a digit gets an underscore first. Two plugin names that differ only in replaced characters (`My-Plugin` and `My_Plugin`), or only after the cut, give the same name, so one of the two plugins sets a name. |
| Any, with `StorageSettings.versionTable(String)` | The name given, as it is, with no prefix added. |

Two plugins that share a database and a table prefix so keep a migration history and a [migration lock](#per-dialect-behaviour) each. Before `0.4.0` the table was `<prefix>schema_version` for every plugin, and the second plugin to start under one prefix stopped with `set up by a newer version of the plugin` or `changed after it ran on this database`.

A plugin whose tables have fixed names, with no prefix setting, names the version table itself:

```java
StorageSettings settings = StorageSettings.server(Dialect.MYSQL, server).versionTable("myplugin_migrations");
```

A name set this way does not follow the table prefix. A plugin that lets the owner set a prefix either leaves the default or puts the prefix into the name, since two servers that share a database under different prefixes otherwise share one history.

- **The name stays.** The name of the version table, and the plugin name the default is built from, must not change once a release has started on a database. Storage finds its history only under that name: a start under a new name finds none and runs every migration again. A plugin that is renamed sets the name it had with `versionTable`. When the earlier table of `0.1.0` to `0.3.2` was already copied into a table that has recorded more since, a start under another name, the earlier name included, stops with a `StorageException` that names that table: `the table <table> continues the migrations <earlier> records and holds newer ones, so this database was started with <table> as the version table; set the version table to <table> with StorageSettings.versionTable, or restore the plugin name it was derived from`.
- A table of the version table's name in another layout stops the start before anything changes, unless a baseline [takes it over](#an-old-table-named-as-the-version-table).
- A database whose version table records a version higher than the plugin's highest migration stops the start as set up by a newer version of the plugin.
- **The table of `0.1.0` to `0.3.2`.** When the version table does not exist and `<prefix>schema_version` does, in storage's layout and with at least one migration recorded under the checksum of one of this plugin's scripts, it is this plugin's earlier version table. The start copies its rows into the new table before the first pending migration runs and logs `Copied the migrations <earlier> records into <new>, which records them from now on. <earlier> stays as it was and is no longer read.` The earlier table stays as it was and is not read again, so a server that still runs a build on `0.3.2` against the same database keeps starting. On a server a start that finds no version table holds the migration lock of the earlier table too until it ends. A `<prefix>schema_version` that records this plugin's migrations by version and name, but none under the checksum of the current script, is taken as this plugin's table whose scripts changed: the start stops before anything is copied or run, with `the table <earlier> records migration <id> with another checksum (stored ..., now ...) and no migration with a checksum of this plugin's scripts; if this plugin recorded it, the migration changed after it ran on this database: ...`. Another plugin under the same prefix whose migrations carry the same versions and names gives the same rows, so the message names that case too; such a plugin starts once the plugin that owns the table has started on `0.4.0` and copied it, since a version table under the prefix that holds every row of the earlier table marks it as claimed. A `<prefix>schema_version` that matches neither by checksum nor by version and name is read as another plugin's table and is left alone: the start logs one warning that names it, and every migration of this plugin runs under the new table. An applied script is therefore never edited. A migration applied under `0.4.0` is recorded only in the new table: a build on `0.3.2` that holds the same migration would run it again, so every server that shares the database is updated before the plugin ships a new migration.
- When the database holds neither table but holds a version table with this plugin's checksums under another prefix, storage logs a warning naming that prefix. From `0.4.0` a version table of another plugin raises no such warning.

### Per-dialect behaviour

| Dialect | Transaction | Notes |
|---|---|---|
| SQLite | One transaction per migration. | Runs with foreign keys off, so the table rebuild SQLite documents for changes `ALTER TABLE` cannot make neither cascades nor deletes child rows. A `PRAGMA foreign_keys` line in a script has no effect. `PRAGMA foreign_key_check` runs before the migration and again before the commit, and a row that breaks a foreign key only in the second check rolls the migration back and stops the start. From `0.4.0`, rows that already broke one before the migration no longer stop it: one warning per start names their tables. The check gives the rows of a `WITHOUT ROWID` table no row id, so those are counted per table, parent and foreign key, and a higher count in the second check rolls the migration back. |
| PostgreSQL | One transaction per migration. | |
| MySQL, MariaDB | DDL commits on its own. | Progress is recorded after each statement. From `0.4.0` a statement and its record run in one transaction, so a statement that changes rows of an InnoDB table, such as `UPDATE ${prefix}accounts SET balance = balance * 10000`, commits together with its record and never runs twice. A DDL statement commits before its record, and a start interrupted between the two runs it again, so every DDL statement must succeed a second time (`CREATE TABLE IF NOT EXISTS` and similar), as must a statement that changes rows of a table that is not transactional. Before `0.4.0` every statement could run twice. A resumed migration runs on a new connection, so no statement may depend on session state set earlier, such as a user variable, a prepared statement or `SET FOREIGN_KEY_CHECKS`. A resumed migration whose script changed stops the start. |

MariaDB has `CREATE INDEX IF NOT EXISTS` and `ADD COLUMN IF NOT EXISTS`. MySQL has neither, so on MySQL an index belongs inline in its `CREATE TABLE IF NOT EXISTS`.

On MySQL, MariaDB and PostgreSQL, starts that share a database and a version table migrate one at a time: a start holds a lock keyed by the database (on PostgreSQL the schema) and the version table while it reads the applied migrations and runs the pending ones. Starts on another database of the same server, in another PostgreSQL schema, or of another plugin with a version table of its own do not wait for it. A start that waits a day for the lock fails with a `StorageException` whose message is `another start has held the migration lock of <version table> in database <database> for a day; restart once the other server has started` (on PostgreSQL the schema stands in for the database). From `0.4.0` that limit holds on PostgreSQL too, where a start waited with no limit.

### SQLite backups

When a SQLite database already holds a table and has a pending migration, `start` first copies it with `VACUUM INTO` to `backups/data-<version>-<yyyyMMdd-HHmmss>.db` under the plugin's data path, with the plugin version and the UTC time. From `0.4.0`, every character of the version other than an ASCII letter, a digit, a dot, an underscore or a hyphen is written as an underscore, so `1.4.0+build.7` gives `data-1.4.0_build.7-<time>.db`. It then keeps the newest `backupKeep` files of that pattern by modification time and leaves other files in the folder alone. With `backupKeep` at 0 no copy is taken.

#### Backups on demand

```java
public CompletableFuture<Path> backup(String label, int keep)
```

From `0.4.9`, `Storage.backup` copies the SQLite database while the plugin runs, for a backup command or before an import. It returns at once, and its future completes with the file of the copy, `backups/manual-<label>-<yyyyMMdd-HHmmss>.db` under the plugin's data path, with the UTC time of the storage clock.

```java
storage.backup("before-import", 5).whenComplete((copy, failure) -> scheduler.global(() -> {
    if (failure == null) {
        sender.sendMessage(Component.text("Saved " + copy.getFileName()));
    } else if (failure instanceof StorageException owner) {
        sender.sendMessage(Component.text("No backup: " + owner.getMessage()));
    } else {
        getLogger().log(Level.SEVERE, "The backup failed", failure);
    }
}));
```

- **The copy is consistent while writers run.** It is taken with `VACUUM INTO` on the writer thread, behind the writes submitted before it, so it holds each of those in full and nothing of a write submitted after it. Reads keep running while it is taken; writes queue behind it.
- **A file named `manual-...db` is always a complete database.** The copy is written as `<name>.tmp` and moved into place in one step. A `.tmp` file an interrupted copy left is removed by the next backup. A copy taken in the same second under the same label replaces the earlier one.
- **`label`** is 1 to 64 ASCII letters, digits, dots, underscores and hyphens, and **`keep`** is 1 or more. Anything else throws `IllegalArgumentException` on the calling thread, and a `null` label throws `NullPointerException`.
- **Retention is its own.** After the copy, the newest `keep` files named `manual-<label>-<time>.db` are kept by modification time, whatever their label, the new copy among them. The `data-<version>-<time>.db` copies a start takes, files of any other name, and `backupKeep` are untouched. Since the count runs over every label, a plugin passes the same `keep` wherever it calls `backup`.
- **Other databases are refused.** On MySQL, MariaDB and PostgreSQL the future fails with a `StorageException` whose message is `a backup copies a SQLite database file, and this storage runs on mysql; back the database up with the tools of the database server` (with the dialect's id), and storage from `Storage.over` fails with one too, since it owns no database file. Once `close` has begun the future fails with `RejectedExecutionException`.
- The future completes on a read thread, like the future of a write, and work on the writer thread must not wait for it.

<Callout type="warn" title="Copying the file of a running database loses commits">
Storage opens SQLite in WAL mode, so the newest commits of a running database are in `data.db-wal`, not in `data.db`. A file copy of `data.db` taken while the server runs misses them, and the copy can be older than it looks. A backup of a running server therefore uses `Storage.backup`, or the owner stops the server first. This holds for a plugin that moves to Taffy from its own SQLite connection with SQLite's default rollback journal, where copying the file of a quiet server used to give every commit.
</Callout>

#### Restoring a backup

A copy is one complete database file: `VACUUM INTO` writes no `-wal` or `-shm` file beside it. A `data-` copy holds the database as it was when that start began, before any of its pending migrations ran, and the version in its name is the plugin version that took the copy, not the one that last wrote the data in it. A `manual-` copy holds the database as it was when `Storage.backup` reached the front of the write queue. Whatever was written after the copy is not in it. Storage has no restore call, because the database file cannot be replaced while a pool holds it open: the owner restores with the server stopped.

<Steps>
<Step>
Stop the server. Storage holds the database file open while the plugin runs.
</Step>
<Step>
In the plugin's data folder, move the database file out of the way, together with the two files SQLite keeps beside it in WAL mode when they exist. The file has the name the plugin passed to `StorageSettings.sqlite`, so for `data.db` these are `data.db`, `data.db-wal` and `data.db-shm`. A `-wal` file left beside a restored database belongs to the database it replaced.
</Step>
<Step>
Copy the chosen `backups/data-<version>-<yyyyMMdd-HHmmss>.db` or `backups/manual-<label>-<yyyyMMdd-HHmmss>.db` to the name of the database file. The time in the name is UTC. Copy it instead of moving it, so the backup stays in the folder.
</Step>
<Step>
Install the plugin version to run on it. A version that has migrations the copy does not record, such as the version in the file name, takes a new copy and runs those migrations at the start. A version whose newest migration is the newest the copy records, usually the one that ran before the version in the file name, starts on the copy as it is. A version whose newest migration is older than that stops the start with `the database is at schema version <n>, set up by a newer version of the plugin`.
</Step>
<Step>
Start the server.
</Step>
</Steps>

A plugin that offers a restore command follows the same sequence in code, from `0.4.9` as the package documentation of `so.alaz.taffy.storage` states it: close storage with `Storage.close` and wait for it to return, replace the database file and delete its `-wal` and `-shm` files, then call `Storage.start` again. Nothing may use the old `Storage` object afterwards, and the steps run off the server thread and off the database threads, since `close` waits for the queued work.

## Taking over another runner's version table

A plugin that kept its schema with its own migration runner passes a `Baseline` naming that runner's version table to the second `start` overload. On a database that has no [version table](#the-version-table) yet, and none `0.1.0` to `0.3.2` wrote for this plugin, storage takes the database over before any migration runs; once its version table exists, the baseline is ignored, so it can stay in the plugin's start for good.

```java
Storage.start(this, errors, settings, MIGRATIONS, Baseline.versionTable("db_version"), Clock.systemUTC());
```

`Baseline.versionTable(String table)` takes the full name of the old table with no prefix added: 1 to 32 lowercase letters, digits and underscores, starting with a letter or underscore. It is written into SQL unquoted, so it must not be a reserved word such as `order` or `user`.

The old table has a column named `version`, with one row or one row per applied step, each a whole number from 0 to 2147483647 or `NULL` (skipped). Its other columns are not read. Its highest version N is the version the database is at, and a table with no version is at 0.

<Steps>
<Step>
Storage reads N from the old table. When the old table does not exist the database is new and every migration runs. On SQLite the old table is found whatever the case of its declared name; on MySQL, MariaDB and PostgreSQL its stored name must be the lowercase name given.
</Step>
<Step>
It stops the start when N is higher than the highest migration version, or N is 1 or more and no migration has version N. It reads and checks every migration script before it changes anything.
</Step>
<Step>
On SQLite it copies the database file into the backups folder.
</Step>
<Step>
It creates its version table and records every migration up to N as applied, with the checksum of its current script, without running it.
</Step>
<Step>
It renames the old table to `<table>_baseline`, or, when that name is taken, to the first free name of `<table>_baseline2`, `<table>_baseline3` and so on. The old table is never dropped.
</Step>
<Step>
It runs the migrations above N.
</Step>
</Steps>

Creating the version table, recording the versions and renaming the old table take effect together: in one transaction on SQLite and PostgreSQL, and on MySQL and MariaDB through `<version table>_takeover` and one statement that renames it and the old table. An interrupted takeover leaves either no version table of storage's, and the next start takes over again, or a complete one. On the server dialects the takeover runs under the migration lock.

The future of this `start` also fails with a `StorageException` when the old table records a version higher than the highest migration, has no `version` column, holds a version that is not a whole number of 0 or more, or records a version of 1 or more that no migration has, and from `0.4.9` when a baseline that [checks the schema](#checking-the-schema-before-a-takeover) finds a table or a column missing.

<Callout type="warn" title="Recorded on the plugin's word">
Unless the baseline [checks the schema](#checking-the-schema-before-a-takeover), storage does not check that the database matches the scripts up to N. A plugin's scripts up to N describe the layout the old runner produced. An old table under a name other than storage's version table is not noticed without a `Baseline`, so a plugin whose database may hold one passes it.
</Callout>

### An old table named as the version table

An old table that has the name of storage's own version table is not a baseline by default: storage refuses a version table in another layout and stops the start with `the database holds a table named <table> that storage did not create`. That is the case for a hand-rolled `schema_version` on SQLite, where the version table has that name unless the plugin sets another, and on a server for a runner that wrote the name storage uses there.

One way out gives storage another name with `StorageSettings.versionTable` and passes the old table as the baseline. From `0.4.9`, the other keeps the name: `takeOverSameName()` returns a baseline that takes such a table over.

```java
Baseline baseline = Baseline.versionTable("provouchers_schema_version").takeOverSameName();
Storage.start(this, errors, settings, MIGRATIONS, baseline, Clock.systemUTC());
```

- It applies when a table of the version table's name exists in another layout than storage's and the baseline names exactly that table. The start reads N from it and takes over as the steps above describe, in another order: it renames the old table to `<table>_baseline` first and then creates its version table under the freed name.
- On SQLite and PostgreSQL the rename, the new table and the recorded versions are one transaction. On MySQL and MariaDB the versions go into `<version table>_takeover`, and one `RENAME TABLE` then moves the old table away and the filled table into place.
- The old table is renamed, never dropped or rewritten, and its rows stay in `<table>_baseline`. A takeover that fails or is interrupted leaves the old table under its name with its rows, so the next start takes over again.
- On SQLite the old table is found whatever the case of its declared name, so `Schema_Version` is taken over too.
- A table of that name in storage's layout is storage's own version table, and the baseline is ignored. `Baseline.versionTable` without `takeOverSameName()` stops the start as before, so a plugin on `0.4.8` sees no change.
- When a version table `0.1.0` to `0.3.2` wrote for this plugin exists as well, the start stops as it does without the call.

The names meet on a server more often than they look. The default version table is `<prefix><plugin>_schema_version`, so for the plugin `Slate` with an empty table prefix it is `slate_schema_version`, the very table Slate's own runner wrote, and the same holds for `provouchers_schema_version` of ProVouchers. With `Baseline.versionTable("slate_schema_version").takeOverSameName()` that start takes the table over. Under the prefix `slate_` the default is `slate_slate_schema_version`, the names differ, and the plain baseline is enough.

### Checking the schema before a takeover

A takeover trusts the number in the old table. A database that was restored halfway, edited by hand, or left behind by a failed upgrade of the old runner can record version 5 and lack a table version 4 created, and the plugin then fails later on a missing column. From `0.4.9`, `checkSchema()` returns a baseline that compares the database with the scripts before it changes anything:

```java
Baseline baseline = Baseline.versionTable("db_version").checkSchema();
```

`checkSchema()` and `takeOverSameName()` each return a new `Baseline`, so the two combine in either order.

The expected tables and columns are read from the statements of the scripts up to N, in order, after `${prefix}` is replaced:

| Statement | Read as |
|---|---|
| `CREATE TABLE name (...)` | A table with the columns of its list. Constraints and index definitions in the list are skipped. With `IF NOT EXISTS`, a table an earlier statement created keeps its columns. |
| `CREATE TABLE name AS SELECT ...`, or any `CREATE TABLE` without a column list | A table that must exist, with any columns. |
| `ALTER TABLE name ADD`, `DROP`, `RENAME COLUMN`, and `CHANGE` on MySQL and MariaDB | A column added, removed or renamed. A table the scripts alter without creating is expected to exist with the columns they add. |
| `ALTER TABLE name RENAME TO`, `RENAME TABLE` | The table under its new name. |
| `DROP TABLE` | The table is no longer expected, so SQLite's rebuild of a table (create, copy, drop, rename) ends with the new layout. |
| `CREATE TEMPORARY TABLE`, and every other statement (`CREATE INDEX`, `INSERT`, `UPDATE`, `CREATE VIEW`) | Not read. |

- Names are compared without regard to case and without their quotes.
- Column types, constraints, indexes and rows are not compared, and the database may hold tables and columns the scripts do not create, such as the tables of another plugin or a column an owner added.
- With N at 0 no script is recorded as applied, and nothing is compared.
- A mismatch fails the future of `start` with a `StorageException` that lists what is missing, a table as its name and a column as `table.column`: `the table db_version records schema version 5, but the database lacks provouchers_stash.arg, provouchers_use_totals, which the migrations up to that version create; restore a backup of the database, or install the plugin version that set it up and let it finish its own upgrade`. Nothing has changed at that point: no SQLite backup is taken and the old table keeps its name.
- The check reads the scripts as text, so a script that builds its tables in a way the table above does not list, such as a stored procedure, is covered only as far as its statements are read. A plugin turns the check on once its own tests take over a database of every old version with it.

## Shutdown

```java
public boolean close(Duration drain)
```

`close` refuses new work from the moment it begins, waits on the calling thread up to `drain` for the queued work, then closes the pools. It returns `true` when every queued piece of work finished within the drain. A negative drain waits no time; a drain of `Long.MAX_VALUE` nanoseconds or more, such as `ChronoUnit.FOREVER.getDuration()`, waits with no limit.

- Work submitted from a database thread during the drain, such as from a stage chained onto a future, still runs within the drain on the submitting thread, after the work that submitted it. On SQLite such a write can commit before writes submitted earlier, and fails with an `SQLException` when its wait for the writer connection passes `Pool.connectionTimeout`.
- During the drain, the futures of SQLite writes complete on the thread that ran them, and a stage chained onto one without an executor runs there.
- When the drain runs out, the database threads are interrupted. Queued work and work still waiting for a connection fail with `RejectedExecutionException`, and other queued tasks (from `executor()`, write completions) run on the closing thread. A warning names how many queued pieces of work did not run, and `close` returns `false`: some writes may then be missing.
- Work still running sees the interrupt. On SQLite it keeps its connection until it ends. On MySQL, MariaDB and PostgreSQL the pool aborts the connections in use, so that work fails with an `SQLException`, or a `CommitUnknownException` when the abort meets its commit. `close` does not wait for it: it ends afterwards on its daemon thread, where its future completes.
- `close` must not be called from a database thread: the drain would wait on its own thread and run out every time.

In the plugin's disable, storage closes after `PendingSettlements.settleAll` and before `DiscordWebhook.close`, in the order [taffy-platform](/docs/modules/platform) gives. A settlement that writes only queues its write, so the drain must cover that write too. A start still pending at disable is cancelled; the storage that start then builds closes itself.

```java
@Override
public void onDisable() {
    // ... the earlier steps of the platform order, ending with Scheduler.close and TaskGate.close
    Shutdown.closeQuietly("settle pending work",
        () -> settlements.settleAll(failure -> errors.report("settlement", failure)), getLogger(), errors);
    CompletableFuture<Storage> start = starting;
    if (start != null && !start.cancel(false) && !start.isCompletedExceptionally()) {
        Storage started = start.join();
        Shutdown.closeQuietly("close storage", () -> started.close(Duration.ofSeconds(10)), getLogger(), errors);
    }
    // ... later steps: DiscordWebhook.close, Metrics.shutdown
}
```

`cancel(false)` returns `false` when the start already completed; `isCompletedExceptionally()` is then `false` only for a start that succeeded, whose storage `join()` returns at once.

## Testing

A plugin's tests that start storage need HikariCP and the driver of each dialect they start on the test runtime classpath (`testRuntimeOnly(alaz.hikari)`, `testRuntimeOnly(alaz.sqlite.jdbc)`), because `taffy-storage` publishes no dependency on them.

`Storage.over(Plugin plugin, ErrorReports errors, Dialect dialect, DataSource source, String prefix, Clock clock)` builds storage over a data source the test owns. Work runs one transaction at a time on a single thread `<name>-db-1`, every connection comes from `source`, no migration runs and no pool is built. On SQLite a read is not made read-only. `close` stops the thread and leaves `source` open.

It pairs with `FaultyDataSource` from [taffy-test](/docs/modules/test), which makes statements and commits fail on demand: the test brings the schema up to date with `start`, closes that storage, and opens storage with `over` on a `FaultyDataSource` for the same database. The connections carry only the properties the test passes, so a SQLite test that should behave as `start` does passes `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=5000`, `foreign_keys=true` and, from `0.4.0`, `transaction_mode=IMMEDIATE`.

## Thread safety

Every `Storage` method may be called from any thread, `backup` included, except `close`, which must not be called from a database thread. `Params` and `Row` belong to one statement or result and are not thread-safe. A `Tx` is usable only on its own thread while its work runs.
