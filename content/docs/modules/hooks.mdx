---
title: taffy-hooks
description: Custom items, a Vault economy, PlayerPoints, LuckPerms, WorldGuard, Bedrock players, placeholders and holograms behind Taffy interfaces, detected safely at enable.
---

`taffy-hooks` connects a plugin to other Paper plugins without making any of them a hard dependency:

- `CustomItems` builds and reads items of ItemsAdder, Nexo, Oraxen and HeadDatabase, and from `0.4.12` of CraftEngine and MMOItems.
- `EconomyProvider.vault` gives a Vault economy in `BigDecimal` and `UUID`.
- `EconomyProvider.playerPoints` gives PlayerPoints points behind the same interface (from `0.4.7`).
- `PermissionProvider.luckPerms` gives LuckPerms groups and permission writes.
- `RegionProvider.worldGuard` gives the WorldGuard region ids at a location and, from `0.4.12`, whether WorldGuard lets a player build there.
- `BedrockProvider.detect` tells which players joined from Bedrock Edition, through Floodgate or Geyser (from `0.4.3`).
- `PlaceholderExpansionBuilder` registers one set of placeholders with PlaceholderAPI and MiniPlaceholders.
- `PlaceholderCache` gives a placeholder its last known value at once and refreshes it off the asking thread (from `0.4.7`).
- `HologramProvider.detect` places temporary text holograms through DecentHolograms, FancyHolograms, Holograms or HologramLib.
- `HologramProvider.displays` places them as display entities, with no hologram plugin (from `0.4.11`).
- `HookState`, `HookStatus` and `Detected` say what detection found, worded for the server owner.

No public signature names an integration type. Each integration sits behind an interface of `so.alaz.taffy.hooks`, and the class that calls it loads only after its API classes are found visible to the plugin (and, for every integration but Vault, after its plugin is found installed and enabled). A server without an integration never loads a class that names it.

## Setup

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.hooks)
}
```

The module is published as `so.alaz.taffy:taffy-hooks` and is `alaz.taffy.hooks` in the catalog. It brings `taffy-platform` with it as an `api` dependency, so `Scheduler`, `ErrorReports` and `ThreadTag` are on the plugin's compile classpath. `so.alaz.taffy.paper-plugin` shades both and relocates `so.alaz.taffy` to `<group>.libs.taffy`.

### What is not bundled

Taffy compiles against each integration's API with `compileOnly` and ships none of them. They appear in no published dependency of `taffy-hooks`, so the plugin's jar carries none of them, and the plugin needs none of them on its own classpath to call Taffy's types. The server provides each API through the integration plugin itself.

The hologram rows, DecentHolograms, FancyHolograms, Holograms and HologramLib, with their aliases, are available from `0.1.2`.

`0.4.12` is built against CraftEngine `26.10` and against MMOItems-API `6.10.1-SNAPSHOT` with MythicLib `1.7.1-SNAPSHOT`. MMOItems and MythicLib publish only snapshots of their API, so those two catalog versions are snapshot versions. MythicLib is in the catalog because the MMOItems classes extend types of it: a plugin that calls MMOItems itself adds both aliases with `compileOnly`.

`0.4.12` is built against WorldGuard `7.0.20` and WorldEdit `7.4.4`, the WorldEdit version that WorldGuard release is built against. From `0.4.12` Taffy also compiles against `worldguard-bukkit`, which holds `WorldGuardPlugin.wrapPlayer` for the [build check](#whether-a-player-may-build).

A plugin adds one of these aliases with `compileOnly` only when its own code calls that API directly. It never adds one with `implementation`. The `so.alaz.taffy.repositories` settings plugin, applied by `so.alaz.taffy.settings`, already holds the repositories these resolve from.

Floodgate and Geyser are not in the table. From `0.4.3`, Taffy reads the two through method handles and compiles against neither API, so the catalog holds no alias for them and a plugin that uses [`BedrockProvider`](#bedrock-players) declares no dependency and no repository for it. It lists only `floodgate` and `Geyser-Spigot` in `paper-plugin.yml`, as the next section shows.

<Callout type="warn" title="An installed integration that is not listed stays off">
An integration that is installed but missing from `dependencies.server` is `HookState.NOT_VISIBLE`. Detection logs one warning naming the missing entry, and the status's reason tells the server owner the same.
</Callout>

## Wiring it up at enable

Every entry point takes the same arguments in the same order: the owner `Plugin` (whose plugin manager is searched and whose logger receives every warning), the plugin's `ErrorReports`, the owner's switch, then that integration's own options. The switch is a `boolean`, or a `Set<CustomItemPlugin>` for custom items. An integration that is switched off is `HookState.SWITCHED_OFF` and looks at nothing.

```java title="ShopPlugin.java"
import org.bukkit.command.CommandSender;
import org.bukkit.entity.Player;
import org.bukkit.event.EventHandler;
import org.bukkit.event.Listener;
import org.bukkit.event.player.PlayerQuitEvent;
import org.bukkit.plugin.java.JavaPlugin;
import org.jetbrains.annotations.Nullable;
import so.alaz.taffy.hooks.CustomItemPlugin;
import so.alaz.taffy.hooks.CustomItems;
import so.alaz.taffy.hooks.Detected;
import so.alaz.taffy.hooks.EconomyProvider;
import so.alaz.taffy.hooks.EconomyWatcher;
import so.alaz.taffy.hooks.HookStatus;
import so.alaz.taffy.hooks.PermissionProvider;
import so.alaz.taffy.hooks.PlaceholderCache;
import so.alaz.taffy.hooks.PlaceholderExpansionBuilder;
import so.alaz.taffy.hooks.PlaceholderRegistration;
import so.alaz.taffy.hooks.RegionProvider;
import so.alaz.taffy.platform.ErrorReports;
import so.alaz.taffy.platform.Scheduler;

import java.time.Duration;
import java.util.ArrayList;
import java.util.EnumSet;
import java.util.List;
import java.util.UUID;

public final class ShopPlugin extends JavaPlugin implements Listener {

    private final ErrorReports errors = new ErrorReports();
    private Scheduler scheduler;
    private CustomItems items;
    private Detected<PermissionProvider> permissions;
    private Detected<RegionProvider> regions;
    private volatile Detected<EconomyProvider> economy;
    private PlaceholderRegistration placeholders;
    private PlaceholderCache<UUID> balances;

    @Override
    public void onEnable() {
        scheduler = new Scheduler(this, errors);
        balances = new PlaceholderCache<>(Duration.ofSeconds(5), 1000, getLogger());
        getServer().getPluginManager().registerEvents(this, this);
        items = CustomItems.detect(this, errors, EnumSet.allOf(CustomItemPlugin.class));
        permissions = PermissionProvider.luckPerms(this, errors, true);
        regions = RegionProvider.worldGuard(this, errors, true);

        economy = lookUpEconomy();
        getServer().getPluginManager().registerEvents(
            new EconomyWatcher(() -> economy = lookUpEconomy(), getServer()::isStopping), this);
        if (!scheduler.global(() -> economy = lookUpEconomy())) {
            getLogger().warning("The economy is not looked up again on the first tick");
        }

        placeholders = new PlaceholderExpansionBuilder()
            .identifier("shop")
            .player("balance", this::balanceText)
            .register(this, errors, true);
    }

    private Detected<EconomyProvider> lookUpEconomy() {
        return EconomyProvider.vault(this, errors, true, scheduler.mode() == Scheduler.Mode.FOLIA, null);
    }

    private @Nullable String balanceText(Player player) {
        EconomyProvider money = economy.provider();
        if (money == null) {
            return null;
        }
        UUID id = player.getUniqueId();
        return balances.get(id,
            () -> scheduler.dispatch(money.thread(id), () -> money.balance(id).toPlainString()));
    }

    @EventHandler
    public void onQuit(PlayerQuitEvent event) {
        balances.forget(event.getPlayer().getUniqueId());
    }

    void showHooks(CommandSender sender) {
        List<HookStatus> all = new ArrayList<>(items.statuses());
        all.add(economy.status());
        all.add(permissions.status());
        all.add(regions.status());
        all.addAll(placeholders.statuses());
        for (HookStatus status : all) {
            sender.sendPlainMessage(status.line());
        }
    }

    @Override
    public void onDisable() {
        if (placeholders != null) {
            placeholders.unregister();
        }
        if (balances != null) {
            balances.clear();
        }
        if (scheduler != null) {
            scheduler.close();
        }
    }
}
```

PlaceholderAPI may call `balanceText` from any thread, so it reads the last known balance from a [`PlaceholderCache`](#placeholdercache), which asks for a fresh one on the thread `thread(UUID)` names through `Scheduler.dispatch` once the value is five seconds old, with at most one refresh per player in flight. The first request for a player gives no value. Before `0.4.7` the example kept the balances in a map of its own, which never dropped a player.

In a real plugin each `true` comes from the plugin's own config, so the owner can switch an integration off. Register the `EconomyWatcher` and the first-tick lookup only while the economy is switched on. Detection runs once, on the server thread, in `onEnable`. An integration plugin that is not enabled by then stays off until the plugin detects again. There is no listener for an integration enabled later, except the Vault economy through `EconomyWatcher`. [Detecting again](#detecting-again) shows a second detection of the custom item plugins.

At disable, call `PlaceholderRegistration.unregister()` before `Scheduler.close()`, so no placeholder request reaches the plugin while it shuts down. It is the first step of `onDisable`, or the second, after `ComfiConfConnection.close`, when the plugin also uses [taffy-comficonf](/docs/modules/comficonf). The full order is in [taffy-platform](/docs/modules/platform).

## Detection and status

### HookState

Detection stops at the first check that fails and gives its state. The checks run in the order of the constants, except for the Vault economy, which never checks that Vault is enabled: it checks the switch, that the economy API is visible, then that an economy is registered, and gives `NOT_INSTALLED` at either of the last two when no Vault plugin is installed.

| State | `describe()` text | Meaning |
|---|---|---|
| `SWITCHED_OFF` | `<plugin> switched off` | The owner switched the integration off, so its plugin was not looked at. |
| `NOT_INSTALLED` | `<plugin> not installed` | The integration plugin is not installed, or was no longer installed by the time the integration was built. |
| `NOT_ENABLED` | `<plugin> installed but not enabled` | Installed but not enabled at detection, or disabled since. Also read while the plugin runs as another instance than the one detected, with a reason from `0.3.1`. |
| `NOT_VISIBLE` | `<plugin> <version> not visible to this plugin` | Installed with the API, but missing from `dependencies.server`. From `0.3.1`, also WorldGuard while `WorldEdit` is missing from it. |
| `API_MISSING` | `<plugin> <version> lacks the API that is read` | The installed version does not hold the API class that is read. |
| `NOT_REGISTERED` | `<plugin> <version> has nothing registered with it` | Vault is there, but no economy has registered with it. A later registration can turn it on. |
| `FAILED` | `<plugin> <version> could not be hooked` | The API is present, but building or registering the integration threw or a method it calls is missing. |
| `ON` | `<plugin> on` | The integration is on. |
| `LOADING` | `<plugin> on, waiting for its items to load` | On, and the plugin is still loading its items. |

A version that was not read shows as `unknown`.

### HookStatus

`HookStatus` is a record: `HookStatus(String plugin, HookState state, @Nullable String version, @Nullable String reason)`.

- `plugin()` is the integration plugin's name, such as `Vault`.
- `version()` is `null` for `SWITCHED_OFF`, `NOT_INSTALLED` and `NOT_ENABLED`, and set (possibly to `unknown`) for every other state.
- `reason()` is one or more full sentences for the owner on what is missing and what to do, or `null` when `describe()` says enough. It is set for every `NOT_VISIBLE` status, for the Vault economy's `NOT_INSTALLED`, `NOT_REGISTERED`, `API_MISSING` and `FAILED`, for a placeholder backend's `FAILED`, and from `0.3.1` for a `NOT_ENABLED` read while the plugin runs as another instance than the one detected.
- `describe()` never includes the reason. `describe()` plus `reason()` is the owner's line.
- From `0.4.10`, `line()` returns that line: `describe()` alone when there is no reason, and otherwise `describe()`, a full stop, one space and `reason()`. Before `0.4.10` a plugin joins the two itself, as `status.reason() == null ? status.describe() : status.describe() + ". " + status.reason()`. A [`DiagnosticReport`](/docs/modules/platform#diagnostics) takes it as a line without a label, `DiagnosticReport.Line.redacted("", status.line())`: the reason of a `FAILED` status quotes the class and message of an exception another plugin threw, and `Line.redacted` passes the line through [`Redaction.hide`](/docs/modules/platform#redaction).

The constructor throws `NullPointerException` for a `null` plugin or state, and `IllegalArgumentException` for a blank reason.

### Detected

`Detected<T>` holds one integration's result: `status()` and `provider()`. `provider()` is non-null exactly when detection turned the integration on (`ON` or `LOADING`).

Every status is read when asked. An integration bound to its plugin reads `NOT_ENABLED` (no version) while that plugin is disabled, and the status found at detection again once it is enabled. `provider()` stays set after the plugin disables; its calls then give their empty answers. The Vault economy is the exception: its status is fixed and changes only through a new lookup.

An integration stays bound to the plugin instance found at detection. When a plugin manager unloads an integration plugin and loads it again, the server holds a new instance under the same name, and the integration keeps the old, disabled one: it stays off and its status stays `NOT_ENABLED` until the plugin detects again. From `0.3.1`, that `NOT_ENABLED` status carries a reason, which `describe()` plus `reason()` (from `0.4.10`, `line()`) shows to the owner:

```text
ItemsAdder installed but not enabled. ItemsAdder was loaded again as a new plugin instance after this plugin detected it, and this plugin still holds the old one. Restart the server to use ItemsAdder again, or run this plugin's reload command if it detects ItemsAdder again.
```

`CustomItems.statuses()` gives the same reason. Before `0.3.1` the status has no reason in this case. A `NOT_ENABLED` whose plugin is simply disabled has no reason in any version.

`Detected` is immutable and safe to read from any thread. Its public constructor `Detected(HookStatus status, @Nullable T provider)` gives a fixed status, which suits tests:

```java
EconomyProvider testEconomy = Mockito.mock(EconomyProvider.class);
Detected<EconomyProvider> fake = new Detected<>(
    new HookStatus("Vault", HookState.ON, "1.7.3", null), testEconomy);
```

The constructor throws `IllegalArgumentException` when the state is `ON` or `LOADING` and the provider is `null`, or any other state is given a provider.

## Custom items

`CustomItems.detect(Plugin owner, ErrorReports errors, Set<CustomItemPlugin> switchedOn)` detects every custom item plugin once and logs one line naming the state of each. Plugins not in `switchedOn` are `SWITCHED_OFF`. From `0.4.7`, a second `detect` also takes a [callback](#when-an-item-plugin-loads-or-reloads-its-items) that runs when an item plugin has loaded or reloaded its items.

### CustomItemPlugin

The constants run in resolution order:

| Constant | `plugin()` | `key()` | Alias |
|---|---|---|---|
| `ITEMSADDER` | `ItemsAdder` | `itemsadder` | `ia` |
| `NEXO` | `Nexo` | `nexo` | |
| `ORAXEN` | `Oraxen` | `oraxen` | |
| `HEADDATABASE` | `HeadDatabase` | `headdatabase` | `hdb` |
| `CRAFTENGINE` (from `0.4.12`) | `CraftEngine` | `craftengine` | |
| `MMOITEMS` (from `0.4.12`) | `MMOItems` | `mmoitems` | |

From `0.4.0`, the enum may gain a constant in any release, so a `switch` over `CustomItemPlugin` needs a `default` branch. `0.4.12` adds `CRAFTENGINE` and `MMOITEMS` at the end of the order. A plugin that passes `EnumSet.allOf(CustomItemPlugin.class)` to `CustomItems.detect` detects an added plugin from the release that adds it. [Upgrading](/docs/upgrading-from-0-1#customitemplugin-may-gain-a-constant) shows the change to a `switch`.

`CustomItemPlugin.byKey(String hint)` finds a plugin by key or alias, ignoring case and surrounding white space, and returns `null` for `null`, blank or unknown text.

### Ids and references

An id is the plugin's key, a colon and the plugin's own id: `nexo:ruby`, `itemsadder:gems:ruby`, and from `0.4.12` `craftengine:default:topaz` and `mmoitems:SWORD:CUTLASS`. A reference given to `create` may use an alias for the key (`ia:gems:ruby`, `hdb:1234`) or no key at all (`ruby`, and from `0.3.1` also `gems:ruby`).

From `0.4.12`, a reference that starts with `craftengine:` or `mmoitems:` names that plugin and goes only to it, and `hasKnownProvider()` is `true` for it. Before `0.4.12` neither key names a plugin, so such a reference is offered whole to each plugin, as the next paragraphs describe.

`CustomItemRef.parse(String reference)` splits on the first colon into `providerHint()` and `id()`; the id may contain further colons, and a blank hint becomes `null`. It throws `IllegalArgumentException` for `null` or a blank id. The record's public constructor `CustomItemRef(@Nullable String providerHint, String id)` throws `IllegalArgumentException` for a blank hint, or a `null` or blank id. `hasKnownProvider()` is `true` when the hint is `null` or names a `CustomItemPlugin`, and `provider()` returns that plugin or `null`. Use them to check references when loading config. The second message holds from `0.3.1`; before it, `create` returns `null` for such a reference without asking any plugin:

```java
CustomItemRef ref;
try {
    ref = CustomItemRef.parse(text);
} catch (IllegalArgumentException invalid) {
    getLogger().warning("reward " + text + " names no item");
    return;
}
if (!ref.hasKnownProvider()) {
    getLogger().info("reward " + text + " names no item plugin, so every item plugin is asked for it");
}
```

`CustomItemRef.parse` always reads the text before the first colon as a hint, so the ItemsAdder id `gems:ruby` parses to the hint `gems`, which names no plugin, and `hasKnownProvider()` is `false` for it.

From `0.3.1`, `create` treats a reference whose hint names no plugin as unqualified: it offers the whole reference, hint and colon included, to each plugin in order, so `create("gems:ruby")` builds the ItemsAdder item `gems:ruby`. A reference that starts with a plugin's key or alias still goes only to that plugin, and a reference without a colon is offered as before.

<Callout type="warn" title="Before 0.3.1, ItemsAdder ids need their key">
Before `0.3.1`, `create("gems:ruby")` returns `null` without asking any plugin. Write `itemsadder:gems:ruby` or `ia:gems:ruby`, which every version builds and which asks ItemsAdder only.
</Callout>

### Building and reading items

```java
ItemStack reward = items.create("ia:gems:ruby");
if (reward == null) {
    // the hint names no plugin that is on, or no plugin knows the id
}

CustomItems.Resolution found = items.resolve(player.getInventory().getItemInMainHand());
if (found.id() != null) {
    // found.id() is such as "nexo:ruby"
} else if (found.failed()) {
    // a plugin could not answer, so the item may be a custom item whose id was not read
}
```

| Method | Behaviour |
|---|---|
| `create(String reference)` | With a hint that names a plugin, asks only that plugin, with the id without the hint. Without a hint, asks each plugin in order and returns the first item built. From `0.3.1`, a reference whose hint names no plugin is offered whole to each plugin in order. Returns `null` when nothing is built. Throws `IllegalArgumentException` for `null` or a blank id. |
| `build(String reference)` | From `0.3.1`. Builds as `create` does and returns a `CustomItems.Built`: the item, or the reason there is none. Throws as `create` does. |
| `resolve(@Nullable ItemStack item)` | Asks each plugin that reads ids in order and returns the first id as `Resolution(id, failed)`. A `null` or empty item gives no id and no failure. |
| `idOrNull(@Nullable ItemStack item)` | `resolve(item).id()`. |
| `ready()` | `true` when no enabled plugin is still loading its items. |
| `available(String hint)` | `true` when the plugin a key or alias names is on and still enabled. |
| `active()` | The plugins whose integration is on, in `CustomItemPlugin` order, whether or not each is still enabled. |
| `statuses()` | One `HookStatus` per `CustomItemPlugin`, read now: `LOADING`, `ON` or `NOT_ENABLED` for a plugin that is on, the detected state for every other. |
| `close()` | From `0.3.1`. Unregisters every listener `detect` registered for the owner. A second call does nothing. |

A plugin that is on but no longer enabled is skipped by `create` and `resolve`, and counts as a failure in `resolve`. A plugin that is still loading its items is skipped by `create`. In `resolve`, ItemsAdder is skipped while it loads and counts as a failure, because it reads ids from the items it has loaded; from `0.3.1`, Nexo and Oraxen can also be loading, and `resolve` still asks them, because they read the id from the item's own data, as CraftEngine does from `0.4.12`. A plugin that throws is skipped with a warning (at most once a minute, with its stack the first time). In `create` the failure is also reported to `ErrorReports` under `hook.<key>`, such as `hook.nexo`; in `resolve` it is not reported.

### Why no item was built

`create` returns `null` for every cause. From `0.3.1`, `build(String reference)` returns a `CustomItems.Built(@Nullable ItemStack item, @Nullable Built.Reason reason)` with exactly one of the two set, and `create(reference)` is `build(reference).item()`.

| `Built.Reason` | Meaning |
|---|---|
| `UNKNOWN_PLUGIN` | The text before the first colon names no `CustomItemPlugin`, and no plugin knows the whole reference as its own id. |
| `PLUGIN_OFF` | The plugin the reference names has no integration on, or is no longer enabled. For a reference without a hint, no plugin is on and enabled. |
| `NOT_READY` | The plugin the reference names is still loading its items. The same call can build the item once `ready()` is `true`. |
| `UNKNOWN_ID` | Every plugin that was asked answered that it does not know the id. |
| `FAILED` | A plugin threw. The failure is logged and reported under `hook.<key>`. |

A reference that names no plugin is offered to several plugins. When none builds it, the reason is the first of these that holds: `NOT_READY` when a plugin is still loading its items, `FAILED` when a plugin threw, `UNKNOWN_PLUGIN` when the reference has a hint, `UNKNOWN_ID` when a plugin was asked, and `PLUGIN_OFF`.

```java
CustomItems.Built built = items.build(text);
if (built.item() != null) {
    give(player, built.item());
    return;
}
switch (built.reason()) {
    case NOT_READY -> retryLater(text);
    case UNKNOWN_PLUGIN, UNKNOWN_ID -> getLogger().warning("reward " + text + " names no item");
    case PLUGIN_OFF -> getLogger().warning("reward " + text + " needs an item plugin that is off");
    default -> getLogger().warning("reward " + text + " could not be built");
}
```

A later version may add reasons, so a `switch` over `Built.Reason` keeps a `default` branch. The record's constructor throws `IllegalArgumentException` when the item and the reason are both `null` or both set.

### Per plugin

- **ItemsAdder** is `LOADING` until ItemsAdder fires `ItemsAdderLoadDataEvent`, or `ON` at once when it had loaded its items before detection. Its integration registers a listener for the owner, so `detect` runs while the owner is enabled, normally in `onEnable`. The listener stays until the owner disables, or until `close()` is called on the `CustomItems`.
- **Nexo** and **Oraxen** read an item's id from the item's own data, so ids are read before the plugin has loaded its items. From `0.3.1`, Nexo is `LOADING` until it fires `NexoItemsLoadedEvent` and Oraxen until it fires `OraxenItemsLoadedEvent`, or `ON` at once when the plugin already knows an item name at detection, which is the usual case for Oraxen, since it loads its items while it enables. While one of them is `LOADING`, `create` skips it, `build` gives `NOT_READY` and `ready()` is `false`, and `resolve` and `idOrNull` still read its ids. Each integration registers a listener for the owner, as the ItemsAdder one does. A `detect` that follows an items-loaded event an earlier `detect` of the same plugin heard in this server run reads `ON` at once. With no such event heard, a Nexo or Oraxen that loaded with no item at all knows no item name, so after a `detect` that follows its load it reads `LOADING` until its next items-loaded event.
- **HeadDatabase** only builds heads: `hdb:1234` builds head `1234`. It is never asked for an id and never counts as a failure in `resolve`. It knows no id until it has loaded its database shortly after startup, so `create` returns `null` until then. From `0.3.1`, it is `LOADING` until it fires `DatabaseLoadEvent` when it gives no random head at detection: `create` skips it, `build` gives `NOT_READY` and `ready()` is `false` until then, where before `0.3.1` it read `ON` and `ready()` read `true` during the load. Its integration registers a listener for the owner, as the ItemsAdder one does. A `detect` that follows a `DatabaseLoadEvent` an earlier `detect` of the same plugin heard in this server run reads `ON` at once. HeadDatabase has no query for whether its database is loaded, so any other `detect` asks it for a random head and reads `ON` at once when it gives one. A database that holds no head gives none, so it then reads `LOADING` until its next `DatabaseLoadEvent`.

- **CraftEngine** (from `0.4.12`, built against CraftEngine `26.10`) has ids of the form `<namespace>:<id>`: `craftengine:default:topaz` builds the item `default:topaz` through `CraftEngineItems.byId`, and `resolve` reads the id back through `CraftEngineItems.getCustomItemId`, which reads it from the item's own data. An id without a colon, or with nothing before or after its first colon, names no item, like an id CraftEngine does not know: `create` returns `null` and `build` gives `UNKNOWN_ID`. CraftEngine finishes its first load after the server has started, so at a plugin's `onEnable` it is `LOADING`: `create` skips it, `build` gives `NOT_READY` and `ready()` is `false`, while `resolve` and `idOrNull` still read its ids. It is `ON` from its `CraftEngineReloadEvent`, which it fires at the end of its first load and of every reload. A `detect` that runs later reads `ON` at once when CraftEngine says it is fully loaded (`CraftEngine.isFullyLoaded()`), or when an earlier `detect` in this server run heard that event. A CraftEngine without that flag, such as `26.6`, logs one warning at detection and is `LOADING` until the event. Its integration registers a listener for the owner, as the ItemsAdder one does. Call `create` and `resolve` on the thread that owns the item.
- **MMOItems** (from `0.4.12`, built against MMOItems-API `6.10.1-SNAPSHOT`) has ids of the form `<type>:<id>`: `mmoitems:SWORD:CUTLASS` builds the item `CUTLASS` of the type `SWORD` through `MMOItems.getItem(String, String)`, with no player, level or tier. The type and the id are matched exactly as MMOItems holds them. It holds its types, and the ids it reads from its files, in upper case, so `mmoitems:sword:cutlass` names no item. A type that does not exist, an id the type does not hold, and an id without a colon or with nothing before or after its first colon all name no item: `create` returns `null` and `build` gives `UNKNOWN_ID`. `resolve` reads the type and the id from the item's own NBT through `MMOItems.getTypeName` and `MMOItems.getID` and gives `mmoitems:<type>:<id>`, and an item that lacks either is not an MMOItems item. MMOItems reads its types and items while it loads and enables, so it is never `LOADING`: it is `ON` from detection. MMOItems does not run on Folia, and its items are built and read on the server thread. Its integration registers a listener for the owner, for the [callback](#when-an-item-plugin-loads-or-reloads-its-items).

`CustomItems` is immutable and thread-safe. Each call runs the integration plugins on the calling thread, so call it on the thread that owns the item. It stays immutable when an item plugin reloads its items: `ready()` keeps reading `true` during the reload, and from `0.4.7` a [callback](#when-an-item-plugin-loads-or-reloads-its-items) tells the plugin when the reload is over.

### Detecting again

Detection runs once, so a plugin that should pick up an item plugin enabled later, or reloaded, detects again from its own reload command. From `0.3.1`, `CustomItems.close()` unregisters every listener the earlier `detect` registered, so close the `CustomItems` that is held, then detect:

```java
void reloadItems() {
    items.close();
    items = CustomItems.detect(this, errors, EnumSet.allOf(CustomItemPlugin.class));
}
```

Before `0.3.1` there is no `close()`, and each further `detect` leaves one more ItemsAdder listener registered until the plugin disables. From `0.3.1`, `close()` also unregisters the Nexo, Oraxen and HeadDatabase listeners, and from `0.4.12` the CraftEngine and MMOItems ones, and a `detect` without it leaves one more listener for each plugin whose integration is on. A closed `CustomItems` keeps answering, but a plugin that was still loading its items stays `LOADING` in it, because the event that ends its load is no longer heard. The server unregisters the listeners itself when the plugin disables, so `onDisable` needs no `close()`.

### When an item plugin loads or reloads its items

From `0.4.7`, `CustomItems.detect(Plugin owner, ErrorReports errors, Set<CustomItemPlugin> switchedOn, Consumer<CustomItemPlugin> onItemsLoaded)` detects as the three-argument `detect` does and runs `onItemsLoaded` each time a plugin whose integration is on finishes loading its items, with that plugin as the argument. Before `0.4.7` a plugin can only poll `ready()`, which says nothing about a reload. An item built before a reload keeps the look it was built with, so a plugin that shows custom items, as in a menu or a display, checks its ids and builds them again from the callback:

```java
items = CustomItems.detect(this, errors, EnumSet.allOf(CustomItemPlugin.class),
    loaded -> scheduler.global(this::rebuildItems));
if (items.ready()) {
    rebuildItems();
}
```

The callback runs inside the event the item plugin fires, in the integration's `MONITOR` listener, on the thread the item plugin fires it on. Each is a synchronous event, which Paper has a plugin fire on the server thread and Folia on a ticking thread, without saying which one. So the callback only hands the work on, as `Scheduler.global` does above, and builds nothing itself. By the time it runs, the plugin it names counts as loaded: `build` asks it and its status is `ON`. `ready()` can still be `false` then, when another plugin is still loading.

| Plugin | Event | Fires |
|---|---|---|
| ItemsAdder | `ItemsAdderLoadDataEvent` | When ItemsAdder finishes loading its data, at startup and on each reload of it. |
| Nexo | `NexoItemsLoadedEvent` | At the end of every load of its items: the first one, and each time Nexo's reload command reloads them. |
| Oraxen | `OraxenItemsLoadedEvent` | Once after Oraxen has enabled, and each time Oraxen's reload command reloads its items. |
| HeadDatabase | `DatabaseLoadEvent` | When HeadDatabase has loaded its database, shortly after startup. HeadDatabase does not say whether a later refresh of the database fires it again. |
| CraftEngine (from `0.4.12`) | `CraftEngineReloadEvent` | At the end of its first load, after the server has started, and at the end of every reload. |
| MMOItems (from `0.4.12`) | `MMOItemsReloadEvent` | When MMOItems' reload command starts, before it reads its files again. Not at startup. |

Every supported plugin has such an event, so none goes without a notice. The Nexo and Oraxen rows are read from Nexo 1.30.2 and Oraxen 1.220.1, and the CraftEngine and MMOItems rows from CraftEngine 26.10 and MMOItems-API 6.10.1-SNAPSHOT. ItemsAdder and HeadDatabase publish only the signatures of their API, so their rows follow what each documents.

<Callout type="warn" title="MMOItems is announced before its reload, not after">
MMOItems has no event for the end of a load. It fires `MMOItemsReloadEvent` on the server thread first, then reads its files again, and has read them by the time its reload command returns. While the callback runs, MMOItems still builds the items of before the reload. Work the callback hands on to a later tick, as `Scheduler.global` does above, finds the reloaded ones.
</Callout>

- A plugin that had loaded its items before `detect` is not announced until its next reload. `ready()` on the result covers the load that is already over, as the example shows.
- A callback that throws does not stop the event: the failure is logged at most once a minute per item plugin, with its stack the first time, and reported under `hook.<key>`, such as `hook.nexo`.
- `close()` ends the callbacks together with the listeners, and so does the plugin disabling. A `detect` that is not closed keeps running its own callback, so a plugin that detects again without `close()` is called once per result.

## Economy

`EconomyProvider.vault(Plugin owner, ErrorReports errors, boolean switchedOn, boolean folia, @Nullable Integer scale)` looks up the economy registered with Vault. It reads the registration once and calls nothing in the economy.

- `folia` tells whether the server is Folia: `scheduler.mode() == Scheduler.Mode.FOLIA` for a plugin with a Taffy `Scheduler`. It decides what each reason asks the owner to install: on Folia the reasons name VaultUnlocked and an economy plugin that supports Folia. From `0.3.0` the entry point takes this flag, so a plugin with no Taffy `Scheduler` can look the economy up. The overload that takes a `Scheduler.Mode` in its place is deprecated and a later release removes it; it gives the same result.
- `scale` is the number of decimal places to use, from 0 to `EconomyProvider.MAX_SCALE` (4), or `null` to use the economy's own fractional digits, capped at 4, or 2 when it reports none. A scale finer than the economy keeps is warned about on first use. A scale outside 0 to 4 throws `IllegalArgumentException`, also when switched off.

From `0.3.2`, `EconomyProvider.vault(VaultOptions options)` takes the same values as one object, with the options the entry point above has no argument for. `VaultOptions.of(Plugin owner, ErrorReports errors, boolean folia)` gives a lookup that is switched on, uses the economy's own decimal places and calls the economy on the global region thread. `switchedOn(boolean)`, `scale(Integer)`, `threadRule(VaultOptions.ThreadRule)` and `fundsCheck(VaultOptions.FundsCheck)` each give a copy with that value replaced and leave the options unchanged. `vault(owner, errors, switchedOn, folia, scale)` gives the same result as `vault(VaultOptions.of(owner, errors, folia).switchedOn(switchedOn).scale(scale))`.

```java
Detected<EconomyProvider> economy = EconomyProvider.vault(
    VaultOptions.of(this, errors, scheduler.mode() == Scheduler.Mode.FOLIA)
        .threadRule(VaultOptions.ThreadRule.ENTITY));
```

Vault itself need not be enabled: only the API and the registration are read. The status's plugin is always `Vault`, and each state but `SWITCHED_OFF` and `ON` carries a reason:

| State | When |
|---|---|
| `SWITCHED_OFF` | `switchedOn` is `false`; nothing is read. |
| `NOT_INSTALLED` | No Vault plugin is installed. |
| `NOT_VISIBLE` | Vault holds the API, but the plugin does not list `Vault` in `dependencies.server`. Logged as a warning. |
| `API_MISSING` | The installed Vault lacks the economy API. Logged as a warning. |
| `NOT_REGISTERED` | Vault is installed and no economy has registered with it. |
| `FAILED` | The lookup threw. Logged as a warning and reported under `hook.vault`. |
| `ON` | The provider is set. |

### Late economies and EconomyWatcher

An economy plugin that enables after the caller registers with Vault only then, so a `NOT_REGISTERED` found in `onEnable` may not last. While the economy is switched on, the plugin:

1. keeps the latest `Detected<EconomyProvider>` in a `volatile` field;
2. registers `new EconomyWatcher(Runnable resolve, BooleanSupplier stopping)` as a listener, where `resolve` looks the economy up again and stores the result;
3. looks the economy up once more on the first tick, with `scheduler.global(...)`.

`EconomyWatcher` runs `resolve` on `ServiceRegisterEvent` and `ServiceUnregisterEvent` for the Vault `Economy` service, matched by class name so the listener loads no Vault class. An unregistration while `stopping` returns `true` is ignored. `resolve` runs on the thread that fires the event.

Each lookup is a new detection: a Vault that stays `NOT_VISIBLE`, `API_MISSING` or `FAILED` is warned about (and a `FAILED` lookup reported) once per lookup, so at least twice at startup.

From `0.4.7`, `EconomyProvider.vault(VaultOptions options, @Nullable Detected<EconomyProvider> previous)` takes the result of the lookup before it and stays quiet when nothing changed. When the status of the new lookup equals `previous.status()` in plugin, state, version and reason, no warning is logged and nothing is reported. Any other status, and every status when `previous` is `null`, is warned about and reported as before. The reason of a `FAILED` status names what was thrown, so a lookup that fails in another way is warned about and reported again. The result is the same either way, and the entry points without `previous` still warn and report on every lookup.

```java
private Detected<EconomyProvider> lookUpEconomy() {
    return EconomyProvider.vault(
        VaultOptions.of(this, errors, scheduler.mode() == Scheduler.Mode.FOLIA), economy);
}
```

### VaultWatch

From `0.4.7`, `EconomyProvider.watchVault(VaultOptions options, Scheduler scheduler)` does the three steps above and returns a `VaultWatch`:

- it looks the economy up before it returns;
- while the options are switched on, it registers an `EconomyWatcher` for the owner and looks the economy up once more on the first tick through `Scheduler.global`;
- each lookup after the first takes the result before it, so a status is warned about (and a `FAILED` lookup reported) once, and again only after the status changed.

```java
private VaultWatch economy;

@Override
public void onEnable() {
    scheduler = new Scheduler(this, errors);
    economy = EconomyProvider.watchVault(
        VaultOptions.of(this, errors, scheduler.mode() == Scheduler.Mode.FOLIA)
            .switchedOn(getConfig().getBoolean("hooks.vault")),
        scheduler);
}

void pay(UUID player, BigDecimal amount) {
    EconomyProvider money = economy.current().provider();
    if (money != null) {
        scheduler.dispatch(money.thread(player), () -> money.deposit(player, amount));
    }
}
```

`current()` gives the latest `Detected<EconomyProvider>` and is safe to read from any thread. `close()` unregisters the listener and stops every later lookup, the one on the first tick included; `current()` then keeps the last result. Close the watch before starting another, as in a reload command. The server unregisters the listener itself when the plugin disables. Options that are switched off register nothing and schedule nothing, and `current()` reads `SWITCHED_OFF`. Call `watchVault` in `onEnable` or later: the server registers a listener only for a plugin that is enabled, so with options that are switched on, a call before the plugin is enabled or once it is disabled throws `IllegalStateException` before anything is looked up, logged or registered. When the scheduler still refuses the first-tick task, one warning is logged.

### EconomyProvider

| Method | Behaviour |
|---|---|
| `int scale()` | Decimal places, from 0 to 4. |
| `ThreadTag thread(UUID player)` | The thread to call the economy on. The Vault provider gives `ThreadTag.GLOBAL` for every player, unless the lookup opted in to the [entity thread rule](#the-thread-rule). The [PlayerPoints provider](#playerpoints) gives `ThreadTag.ASYNC`. |
| `BigDecimal balance(UUID player)` | The balance rounded half-even to `scale()`, possibly negative. Throws `IllegalStateException` when the economy reports a value that is not finite. |
| `boolean has(UUID player, BigDecimal amount)` | Compares the balance, not rounded to `scale()`, with the amount rounded half-even to `scale()`. Accepts any amount. The Vault provider asks the economy instead when the lookup opted in to the [native funds check](#the-funds-check). |
| `EconomyResult withdraw(UUID player, BigDecimal amount)` | Takes money when `has` holds. Never `NOT_STARTED`. |
| `EconomyResult withdraw(UUID player, BigDecimal amount, BooleanSupplier start)` | As above; `start` runs after the balance check and before money moves, on the same thread, and `false` gives `NOT_STARTED` with no money moved. |
| `EconomyResult deposit(UUID player, BigDecimal amount)` | Gives money. |
| `String probe()` | A self-test that reads what the economy reports about itself and moves no money. Returns one line naming what was reached (for Vault, the economy's name and its decimal places). Throws a `RuntimeException` when nothing was reached. |

Every call is synchronous and runs on the thread `thread(UUID)` names; from `0.3.2` the Vault provider [throws on any other thread](#the-thread-rule). A withdraw or deposit rounds the amount half-even to `scale()` and throws `IllegalArgumentException` for an amount that is negative, rounds to zero, or cannot reach the economy exactly. Vault carries amounts as `double` (the Vault 1.7 API), so an amount that does not survive the conversion to `double` and back is refused. The [PlayerPoints provider](#playerpoints) holds whole points and refuses an amount with a fraction of a point instead of rounding it. A withdraw or deposit that throws has an unknown outcome: money may or may not have moved.

From `0.3.2`, a balance read from Vault is rounded half-even to 8 decimal places, four more than `EconomyProvider.MAX_SCALE`, before it is compared or rounded to `scale()`, and a balance within 16 units in the last place of the `double` of an amount at `scale()` reads as that amount. An economy that keeps balances as `double` holds `0.09999999999999998` after a player with `1.00` pays `0.90`, and that balance now covers `0.10`; one that holds `1000000428.0799999` after a player with `1000000456.18` pays `28.10` covers `1000000428.08`. Before `0.3.2`, `has` answered `false` and `withdraw` gave `INSUFFICIENT` for both. The balance read after a withdraw is measured in units of the balance read before it, so a withdraw of the whole balance gives `OK`, not `OVERDRAWN`. A balance that is short by more than that, such as `0.0999`, is still short. Once the balance covers the amount the provider asks the economy, and an economy that compares its own `double` balance may still refuse, which gives `FAILED` with the economy's message and no money moved. Where one such unit nears the smallest amount at `scale()`, which is from about 1e13 at 2 decimal places and from about 1e11 at 4, a `double` no longer holds the amount and a comparison can be off by one unit of `scale()`.

From `0.3.2`, the Vault provider keeps the plugin that registered the economy, and while that plugin is disabled `withdraw` and `deposit` return `FAILED` with the message `the economy plugin <name> is disabled`. The refusal comes before the amount is checked and calls nothing in the economy, so no money moves. Before `0.3.2` the call reached the disabled plugin's economy, which happens during a server stop or in a plugin that registered no `EconomyWatcher`. `balance` and `has` still read the economy, and the status stays as the lookup found it.

A withdraw reads the balance a second time once the economy confirmed it, to tell `OVERDRAWN`. From `0.3.2`, when that read throws an exception or a `LinkageError`, the result is `OK`, the overdraft check is skipped and a warning is logged. Before `0.3.2` the throwable left `withdraw`.

### The thread rule

`VaultOptions.ThreadRule` names the thread the Vault economy is called on, which is what `thread(UUID)` answers. It exists from `0.3.2`; before it, the Vault provider answered `ThreadTag.GLOBAL` for every player.

| `VaultOptions.ThreadRule` | `thread(player)` answers |
|---|---|
| `GLOBAL` (the default) | `ThreadTag.GLOBAL` for every player: the main thread on Paper, the global region thread on Folia. |
| `ENTITY` | `ThreadTag.entity(player)` for a player who is online, and `ThreadTag.GLOBAL` for a player who is not, since no region owns an offline player. |

`ENTITY` is an opt-in for an economy plugin that is safe to call on region threads. A plugin that is already on a player's region thread, in a click handler or a command, then calls the economy inline and reads the result in the same tick, where `GLOBAL` needs a `Scheduler.dispatch` and a hop back. The answer is read from the server on each call, so ask `thread(player)` right before each dispatch and do not keep it.

Under `ENTITY` the calls for one online player are ordered on that player's thread. On Folia they are not ordered against another plugin that moves the same account on the global region thread, nor against a call made for the player on the global region thread while the player was offline, so a balance check there and a withdraw here can interleave. On Paper every one of these threads is the main thread. Keep `GLOBAL` unless the economy plugin states that it supports Folia's region threads.

From `0.3.2`, `balance`, `has`, `withdraw` and `deposit` of the Vault provider throw `IllegalStateException` when the calling thread is not the one `thread(player)` names. Before `0.3.2` the rule was documentation only: a call from a Folia region thread or an async thread ran, unordered against the other callers of the economy, so the balance check of a withdraw could pass twice. The message names `thread(player)` and `Scheduler.dispatch`, the tag, and the calling thread:

```
an economy call for 069a79f4-44e9-4726-a5be-fca90e38aaf5 runs on the thread thread(player) names, GLOBAL, not on Craft Scheduler Thread - 3; run it through Scheduler.dispatch(economy.thread(player), ...)
```

| `thread(player)` | The call is accepted where |
|---|---|
| `ThreadTag.GLOBAL` | `Server.isGlobalTickThread()` is `true`: the main thread on Paper, the global region thread on Folia. This is where `Scheduler.dispatch(ThreadTag.GLOBAL, ...)` runs its task. |
| `ThreadTag.entity(player)` | `Server.isOwnedByCurrentRegion(player)` is `true`: the main thread on Paper, the region thread that owns the player on Folia. |

Under `ENTITY`, a call for a player who is not online is checked against the global region thread, as `thread(player)` answers `ThreadTag.GLOBAL` for that player. A player who logs in between the `thread(player)` call and a task dispatched to `GLOBAL` makes that task's call throw on Folia, where the global region thread does not own the player; the future of the dispatch carries the exception and no money has moved, so the caller reads `thread(player)` again and dispatches once more.

The check comes after the `null` checks and before the amount is checked, the registering plugin's state is read or anything in the economy is called, so no money moves. `scale()`, `thread(UUID)`, `probe()` and `EconomyProvider.vault` are not checked. A plugin's own `EconomyProvider` may make the same check; the interface allows it.

### The funds check

`VaultOptions.FundsCheck` names who decides whether a balance covers an amount. It exists from `0.3.2`; before it, the Vault provider always decided itself and never called Vault's `Economy.has`.

| `VaultOptions.FundsCheck` | `has` | `withdraw` |
|---|---|---|
| `EMULATED` (the default) | Compares the balance read from the economy with the amount. | Reads the balance, gives `INSUFFICIENT` when it is short without asking the economy, withdraws, and reads the balance again to tell `OVERDRAWN`. |
| `NATIVE` | Answers what `Economy.has` answers for the amount rounded half-even to `scale()` and sent as a `double`. | Reads no balance, before or after: `start` runs first, and `withdrawPlayer` decides. |

`NATIVE` is an opt-in for an economy that allows an overdraft or a loan, or that keeps rules of its own. Under `EMULATED` a player with `5.00` and a credit line of `50.00` is refused a price of `20.00` before the economy is asked; under `NATIVE` the economy takes it and the result is `OK`.

```java
Detected<EconomyProvider> economy = EconomyProvider.vault(
    VaultOptions.of(this, errors, scheduler.mode() == Scheduler.Mode.FOLIA)
        .fundsCheck(VaultOptions.FundsCheck.NATIVE));
```

Under `NATIVE` a withdraw the economy refuses gives `FAILED` with the economy's message, or `the economy refused it` when it gives none, for a short balance too: a Vault response has no type for insufficient funds. A withdraw never gives `INSUFFICIENT` or `OVERDRAWN`, and one that leaves the balance below zero gives `OK`. A plugin that tells the player "not enough money" on `INSUFFICIENT` asks `has` first under `NATIVE`, or shows the message of the `FAILED` result. The amount, the calling thread and the disabled economy plugin are checked as under `EMULATED`, and `NOT_IMPLEMENTED` still gives `UNSUPPORTED`.

### PlayerPoints

From `0.4.7`, `EconomyProvider.playerPoints(Plugin owner, ErrorReports errors, boolean switchedOn)` detects PlayerPoints and gives an `EconomyProvider` on its points. Taffy compiles against PlayerPoints `3.3.5`. The plugin lists `PlayerPoints` under `dependencies.server` with `load: BEFORE` and `required: false`.

```java
Detected<EconomyProvider> points = EconomyProvider.playerPoints(this, errors, true);
```

Detection follows the [states](#detection-and-status) of every other integration but Vault: PlayerPoints is read only when it is switched on, installed, enabled and its API is visible, and it is `FAILED` (logged and reported under `hook.playerpoints`) when a method the provider calls is missing. Detection reads and moves no points. Unlike the Vault economy, the result is bound to the PlayerPoints plugin, so its status reads `NOT_ENABLED` while PlayerPoints is disabled, and no watcher is needed.

| Call | The PlayerPoints provider |
|---|---|
| `scale()` | Always 0. Points are whole, and PlayerPoints holds them as `int`. |
| `thread(player)` | `ThreadTag.ASYNC` for every player. |
| `balance(player)` | The points, with no decimal places. |
| `has(player, amount)` | Compares the points with the amount rounded half-even to whole points. Accepts any amount. |
| `withdraw` | Reads the points, gives `INSUFFICIENT` when they are short, runs `start`, then takes the points. |
| `deposit` | Gives the points. |
| `probe()` | `PlayerPoints <version>, whole points`. Throws `IllegalStateException` while PlayerPoints is disabled. |

**Whole points only.** A withdraw or deposit is never rounded, since rounding would take or give a different number of points than the caller asked for. An amount with a fraction of a point, such as `2.5`, throws `IllegalArgumentException`, as does one above `Integer.MAX_VALUE`, a negative one and zero, before anything in PlayerPoints is called. An amount written with decimal zeros, such as `2.00`, is whole. A plugin that prices in fractions rounds the price to `scale()` itself, with a rounding mode it chose, before it calls the provider.

**Async only.** PlayerPoints loads a balance that is not in its cache from its database on the calling thread, so every call belongs off the server threads. `balance`, `has`, `withdraw` and `deposit` throw `IllegalStateException` on a thread `Server.isPrimaryThread()` is `true` on: the main thread on Paper, and every region thread and the global region thread on Folia. The message names `thread(player)` and `Scheduler.dispatch`, as the [Vault provider's](#the-thread-rule) does, and no points move. `scale()`, `thread(UUID)`, `probe()` and detection are not checked. PlayerPoints declares Folia support, and its calls are safe on an async thread on both Paper and Folia: its `PlayerPointsChangeEvent` is fired as an asynchronous event there.

```java
EconomyProvider money = points.provider();
if (money != null) {
    scheduler.dispatch(money.thread(player), () -> money.withdraw(player, price))
        .thenAccept(result -> { /* hop back to the player's thread before touching the world */ });
}
```

**One withdraw at a time per player.** PlayerPoints checks a balance and queues the change in two steps, so the provider runs its withdraws for one player one after the other, from the balance read through `start` to the take. Two purchases at once cannot both pass the balance check. `start` runs while the other withdraws for that player wait, so it must not wait for a withdraw of another player. A change another plugin makes to the same account is not held back.

**Refusals.** PlayerPoints moves the whole amount or nothing. A take or a give it refuses gives `FAILED` with the message `PlayerPoints refused it` and moves no points: a listener cancelled its `PlayerPointsChangeEvent`, the balance no longer covers the amount, or a deposit would pass `Integer.MAX_VALUE`. A balance that cannot be read at the start of a withdraw gives `FAILED` too. While PlayerPoints is disabled, `withdraw` and `deposit` give `FAILED` with `the economy plugin PlayerPoints is disabled`, before the amount is checked. A withdraw never gives `OVERDRAWN` or `UNSUPPORTED`.

Two things are outside the provider's sight. A listener that changes the amount of a `PlayerPointsChangeEvent` changes how many points move, and the result is still `OK`. PlayerPoints answers a balance it could not load from its database as 0, so such a player reads as having no points.

### EconomyResult

`EconomyResult(Status status, @Nullable String message)`, with `EconomyResult.ok()`, `EconomyResult.of(Status)` and `EconomyResult.failed(String message)`. A `FAILED` result needs a non-blank message; `of(Status.FAILED)` throws `IllegalArgumentException`. From `0.3.2`, `moved()` tells whether the money moved: `true` for `OK` and `OVERDRAWN`, `false` for every other status.

| `EconomyResult.Status` | Meaning |
|---|---|
| `OK` | The money moved. |
| `INSUFFICIENT` | The balance did not cover the amount; no money moved. |
| `UNSUPPORTED` | The economy does not support the call; no money moved. |
| `OVERDRAWN` | The money moved and left the balance below zero. |
| `FAILED` | The economy refused the call, or from `0.3.2` the plugin that registered it is disabled; `message()` holds the reason; no money moved. Under the [native funds check](#the-funds-check) this is also the result of a withdraw the economy refused for a short balance. |
| `NOT_STARTED` | `start` returned `false` before any money moved. Under the native funds check no balance is checked first. |

`OVERDRAWN` is a completed payment: the caller delivers the goods and may log it. A caller that does not want to accept an overdraft reverses it itself with `deposit`.

### Charging a player on Paper and Folia

Run each call on the thread `thread(UUID)` names, through `Scheduler.dispatch`. From `0.3.2` a call made on another thread throws `IllegalStateException`, which on Paper is an async thread and on Folia, under the default rule, every region thread:

```java
void charge(Player player, BigDecimal price) {
    EconomyProvider money = economy.provider();
    if (money == null) {
        player.sendPlainMessage("The shop is closed.");
        return;
    }
    UUID id = player.getUniqueId();
    scheduler.dispatch(money.thread(id), () -> money.withdraw(id, price))
        .whenComplete((result, failure) -> scheduler.entity(player, () -> {
            if (failure != null) {
                player.sendPlainMessage("The payment could not be confirmed.");
            } else if (result.moved()) {
                if (result.status() == EconomyResult.Status.OVERDRAWN) {
                    getLogger().warning(player.getName() + " paid " + price.toPlainString()
                        + " and is overdrawn.");
                }
                player.sendPlainMessage("Paid " + price.toPlainString() + ".");
            } else {
                player.sendPlainMessage("The payment did not go through.");
            }
        }));
}
```

The future also fails when the plugin is disabling (`RejectedExecutionException` for `ThreadTag.GLOBAL`, before anything runs) or when the amount is refused with `IllegalArgumentException` before it reaches the economy. A withdraw that throws inside the economy has an unknown outcome, so the plugin does not refund or retry blindly. The example branches on `moved()`, so an `OVERDRAWN` withdraw, whose money has left the account, counts as paid; a branch on `status() == Status.OK` would keep that money and deliver nothing.

## Permissions

`PermissionProvider.luckPerms(Plugin owner, ErrorReports errors, boolean switchedOn)` detects LuckPerms. It reads LuckPerms only when switched on, installed, enabled and its API classes are visible, and gives `FAILED` when a method the provider calls is missing. A detection failure is reported under `hook.luckperms`.

Plain permission checks go through Bukkit's `Player.hasPermission` and are not part of this interface.

| Method | Behaviour |
|---|---|
| `boolean available()` | LuckPerms is enabled and has finished loading. |
| `@Nullable String primaryGroup(UUID player)` | The primary group, or `null` when the player's data is not loaded or cannot be read. |
| `List<String> groups(UUID player)` | Every group the player inherits, directly or through other groups, without context; empty when the data is not loaded or cannot be read. |
| `boolean addGroup(UUID player, String group)` | Adds a permanent membership; `true` when the player was not already in the group and the change was saved. |
| `boolean addTempGroup(UUID player, String group, Duration duration)` | Adds a membership until a time from now, in whole seconds rounded down. An earlier expiry is moved to the new time; a later one is kept; a permanent membership is left and the temporary one added beside it. Throws `IllegalArgumentException` for under one second or an end after `Instant.MAX`. |
| `boolean removeGroup(UUID player, String group)` | Removes every membership of the group set directly on the player, permanent or temporary, in every context, in saved data only; `true` when the player held at least one and the change was saved. |
| `boolean setPermission(UUID player, String node, boolean value)` | Grants (`true`) or denies (`false`) a node, without context and without an expiry, replacing a node of that name already set without context; `false` when the player already holds it at that value. |
| `boolean unsetPermission(UUID player, String node)` | Clears a node set directly on the player, whatever its value or context, in saved data only. |

Reads come from LuckPerms' cache, so a player whose data is not loaded (usually one who is offline) gives `null` or an empty list. Writes load the player's data when it is not cached, then block until the change is saved, so run them off the server thread; from `0.3.2` a write called on a server thread throws `IllegalStateException`:

```java
PermissionProvider perms = permissions.provider();
UUID buyer = player.getUniqueId();
if (perms != null) {
    if (!scheduler.async(() -> perms.addTempGroup(buyer, "vip", Duration.ofDays(30)))) {
        getLogger().warning("The vip group was not added: the plugin is disabling");
    }
}
```

From `0.3.2`, `addGroup`, `addTempGroup`, `removeGroup`, `setPermission` and `unsetPermission` throw `IllegalStateException` when called on a server thread, with a message that names the calling thread and `Scheduler.async`. Before `0.3.2` the rule was documentation only, and a write from an event handler held the tick for a storage round trip. A server thread is one `Server.isPrimaryThread()` is `true` on: the main thread on Paper, and every region thread and the global region thread on Folia. The check comes after the arguments are checked and before LuckPerms is asked, so nothing is loaded or changed, and it is made whether or not LuckPerms is available. `available`, `primaryGroup` and `groups` are not checked. A write made in `onDisable` throws as well: it runs on a server thread, `Scheduler.async` returns `false` once the plugin is disabling and never runs the task, and `Scheduler.asyncOrRun` runs it on the calling server thread, where the write throws. Make that write before the plugin disables.

A write returns `true` only when the data changed and was saved, and `false` when nothing changed, LuckPerms is not available, or the write failed. A failure inside LuckPerms is logged as a warning (at most once a minute per kind of call, with its stack the first time) and reported under `hook.luckperms`, not thrown.

From `0.3.2`, a saved write is pushed to the other servers of a network: after a successful save the provider calls `pushUserUpdate` on LuckPerms' `MessagingService` when one is set up, so a server that has the player's data loaded applies the change without waiting for its next sync. With no messaging service nothing is pushed. A push that throws is logged as a warning and reported under `hook.luckperms`, and the write still returns `true`, since the change is saved. Before `0.3.2` the provider saved the change and pushed nothing.

From `0.3.2`, `removeGroup` removes a membership that `addTempGroup` added, and one held in a context. Before `0.3.2` it removed only a permanent membership without context, so a rank granted for 30 days and revoked early stayed, and the call returned `false`. The group name is matched without regard to case. A membership held for the session only, or inherited through another group, is left in place.

From `0.3.2`, `setPermission` changes a node the player already holds: every node of that name set directly on the player without context is replaced, so a granted node becomes denied, a denied one granted, and a temporary one permanent, with one save. Before `0.3.2`, `setPermission(player, "fly.use", false)` on a player who held `fly.use` granted returned `false`, saved nothing and left the permission granted. It returns `false` with nothing saved only when the player already holds the node without context and without an expiry at that value. A node of the same name set in a context is left as it is, and only saved data is changed. Only a plain permission node is counted as held and replaced: a node LuckPerms keeps as another kind under that name, such as the group membership `group.vip`, is left as it is. When LuckPerms refuses the new node once the held ones are cleared, that is logged as a warning and reported under `hook.luckperms`, and the call still saves and returns `true`, since the held nodes are gone.

## Regions

`RegionProvider.worldGuard(Plugin owner, ErrorReports errors, boolean switchedOn)` detects WorldGuard the same way, reporting a detection failure under `hook.worldguard`.

The plugin lists both `WorldGuard` and `WorldEdit` under `dependencies.server`. From `0.3.1`, detection also checks that WorldEdit's `BukkitAdapter` is visible. When WorldGuard is visible and that class is not, the status is `NOT_VISIBLE` with one warning and this reason, and nothing is reported:

```text
WorldGuard is installed, but this plugin cannot see WorldEdit, which WorldGuard is read through, because its paper-plugin.yml does not list WorldEdit under dependencies.server.
```

Before `0.3.1` the same setup is `FAILED`, with a report under `hook.worldguard` and no reason.

| Method | Behaviour |
|---|---|
| `boolean available()` | WorldGuard is enabled. |
| `List<String> regionsAt(Location location)` | The ids of every region covering the block, in an unmodifiable list. |
| `boolean canBuild(Player player, Location location)` | From `0.4.12`. Whether WorldGuard lets the player build at the location. |

`regionsAt` returns an empty list when WorldGuard is not available, the location has no world or its world has unloaded, WorldGuard keeps no regions for that world, or the lookup fails. Only a failed lookup is logged (at most once a minute) and reported under `hook.worldguard`. A lookup may run on any thread, since WorldGuard's region index supports concurrent reads.

WorldGuard lowers region ids in the server's default locale, which on a Turkish server turns `I` into a dotless i. Compare ids with `String.equalsIgnoreCase`, not after lowering them in a fixed locale:

```java
RegionProvider wg = regions.provider();
boolean inMarket = wg != null
    && wg.regionsAt(player.getLocation()).stream().anyMatch(id -> id.equalsIgnoreCase("market"));
```

### Whether a player may build

From `0.4.12`, `canBuild(Player player, Location location)` answers whether WorldGuard lets a player build at a location, for a plugin that places or breaks a block for a player. It is built against WorldGuard `7.0.20` and WorldEdit `7.4.4`.

```java
RegionProvider wg = regions.provider();
if (wg != null && !wg.canBuild(player, block.getLocation())) {
    return; // WorldGuard protects the block from this player
}
```

The answer comes in two steps, as in WorldGuard's own listeners:

1. A player WorldGuard lets through answers `true` (`SessionManager.hasBypass`). That is a player with the permission `worldguard.region.bypass.<world>` for the world of the location, unless the player turned the bypass off with WorldGuard's `/rg bypass`. It is also a player another plugin marked as an NPC, while WorldGuard's `regions.fake-player-build-override` setting is on for that world.
2. Every other player gets what WorldGuard's region query gives for the `build` flag at the location (`RegionQuery.testBuild`): the regions covering the block, their members and owners, their priorities and the global region.

| Case | Answer |
|---|---|
| WorldGuard is not installed, switched off or not `ON` at detection | There is no provider: `regions.provider()` is `null`, and the plugin lets the player build, as in the example. |
| WorldGuard was detected and is disabled now (`available()` is `false`) | `true`, and WorldGuard is not asked. |
| The location has no world, or its world has unloaded | `true`, and WorldGuard is not asked. |
| WorldGuard's regions are turned off in that world | `true`. |
| WorldGuard could not load the region data of that world | `false`, as WorldGuard denies building there, unless the player has the bypass. |
| WorldGuard throws, or lacks a method the check calls | `true`, logged as a warning (at most once a minute) and reported under `hook.worldguard`. |
| The player has left the server | Asked in the same way. A player who is not online has no bypass, so the answer is the one of the `build` flag. |
| `player` or `location` is `null` | `NullPointerException`. |

- **Only the `build` flag is read.** WorldGuard's listeners also read flags such as `block-break`, `block-place`, `use` and `chest-access` for the action at hand, and its `build-permission-nodes` setting. `canBuild` reads none of them, so a region that sets `build` to deny and `block-break` to allow answers `false`.
- **Thread.** Call it on the thread that owns the player: the main thread on Paper. The provider asks WorldGuard on the calling thread and schedules nothing. WorldGuard does not run on Folia, so `RegionProvider.worldGuard` gives no provider there and nothing is asked.
- **Detection is unchanged.** `RegionProvider.worldGuard` does not look for the methods the build check calls, so it gives the same status as before `0.4.12`.
- **Other providers.** `canBuild` is a default method of `RegionProvider` that answers `true`. A `RegionProvider` a plugin or a test implements itself keeps compiling and lets every player build until it overrides the method.

## Bedrock players

<Callout type="info" title="From 0.4.3">
`BedrockProvider` is available from Taffy `0.4.3`. Earlier versions have no Bedrock hook.
</Callout>

`BedrockProvider.detect(Plugin owner, ErrorReports errors, boolean switchedOn)` detects Floodgate, then Geyser, and gives a provider that tells which players joined from Minecraft Bedrock Edition. The plugin needs no dependency in its build for it, only the two soft dependencies in `paper-plugin.yml`: it lists `floodgate` and `Geyser-Spigot` under `dependencies.server` with `load: BEFORE` and `required: false`. Taffy calls `FloodgateApi.getInstance().isFloodgatePlayer(UUID)` and `GeyserApi.api().isBedrockPlayer(UUID)` through method handles. Each of the two is read only when it is installed, enabled and its API classes are visible, and is `FAILED` when a method the provider calls is missing. One that is not visible or lacks the API is warned about, and one that could not be hooked is warned about and reported under `hook.floodgate` or `hook.geyser-spigot`.

| The server has | The result |
|---|---|
| A Floodgate that can be read | A provider on Floodgate, with the status `floodgate on`. Geyser is not looked at. |
| A Geyser that can be read, and no Floodgate that can be | A provider on Geyser, with the status `Geyser-Spigot on`. |
| Neither | No provider. The status is Floodgate's, or Geyser's when Floodgate is not installed and Geyser is. With neither installed it reads `floodgate not installed`. |
| Either, with `switchedOn` `false` | No provider and `floodgate switched off`. Nothing is looked at. |

The provider reads the Floodgate or Geyser that runs on the same server as the plugin, and stays bound to the one detection chose until the plugin detects again.

| Method | Behaviour |
|---|---|
| `boolean bedrock(UUID player)` | `true` for a player who joined from Bedrock Edition. |

`bedrock` returns `false` for any other player, for a player who is not online, while the Bedrock plugin is disabled, and when the check fails. Only a failed check is logged (at most once a minute, with its stack the first time) and reported under `hook.floodgate` or `hook.geyser-spigot`. The provider asks the Bedrock plugin on the calling thread and keeps nothing about a player.

`taffy-hooks` does not depend on [taffy-gui](/docs/modules/gui), so a `BedrockProvider` is not a `BedrockPlayers`. A plugin that uses both passes `provider::bedrock` to `Prompts`, whose Bedrock players then always answer in chat:

```java
Detected<BedrockProvider> detected = BedrockProvider.detect(this, errors, true);
BedrockProvider provider = detected.provider();
BedrockPlayers bedrock = provider == null ? BedrockPlayers.NONE : provider::bedrock;
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, bedrock, scheduler::delayedAsync);
```

## Holograms

<Callout type="info" title="From 0.1.2">
`HologramProvider`, `HologramPlugin` and the hologram catalog aliases are available from Taffy `0.1.2`. Earlier versions have no hologram hooks.
</Callout>

`HologramProvider.detect(Plugin owner, ErrorReports errors, boolean switchedOn, HologramPlugin plugin)` detects one hologram plugin the same way, reporting a detection failure under `hook.<plugin key>`. Call it on the server thread while the plugin is enabled, normally in `onEnable`. The provider registers a listener for the plugin that removes a hologram when its world unloads, and removes every hologram the provider placed when the plugin's `PluginDisableEvent` fires, before its `onDisable`. To detect again, such as when the plugin reloads its settings, close the held provider, then detect again. `HologramPlugin.byKey` reads the plugin from a config value such as `fancyholograms`. A later version may add `HologramPlugin` constants, so a `switch` over `HologramPlugin` keeps a `default` branch.

| `HologramPlugin` | Installed as | What to know |
|---|---|---|
| `DECENTHOLOGRAMS` | `DecentHolograms` | 2.10 or newer; Folia from 2.10.2. Lines are converted to `&` colour codes with `&#RRGGBB` hex, so MiniMessage that colour codes cannot hold, such as hover and click, is dropped. A `&` or `#` in a line's text shows as written, so a code such as `&6` or `#ff8800` typed there gives no colour. A gradient or rainbow becomes one colour per character, so a placeholder inside one shows as written. |
| `FANCYHOLOGRAMS` | `FancyHolograms` | FancyHolograms 2. FancyHolograms 3 has another API and reads as `API_MISSING`. A `&` in a line shows as written, so a code such as `&6` or `&#ff8800` typed there gives no colour. A hologram with a placeholder in a line is drawn again every second. Each removal rewrites `plugins/FancyHolograms/holograms.yml`, except while the server stops, and drops any saved hologram of the same name from it. |
| `HOLOGRAMS` | `Holograms` | Holograms by TheNextLvl. A move runs on the location's region thread a little later. |
| `HOLOGRAMLIB` | `HologramLib` | Needs PacketEvents installed. Draws the lines as one text. Fills PlaceholderAPI placeholders for each viewer when a player starts seeing the hologram and when its lines are replaced, not on a timer, and only when PlaceholderAPI enabled before HologramLib. HologramLib parses the filled text as MiniMessage, so a placeholder whose value holds `§` colour codes leaves that viewer's text unfilled and PacketEvents logs the failure. A hologram spawns on the next tick, so a move or removal in the tick it was placed is done again two ticks later. Its Modrinth page lists no Minecraft 26 version yet. |

| Method | Behaviour |
|---|---|
| `boolean create(String id, Location location, List<String> lines)` | Places a hologram with the bottom centre of its text at the location. `false` when any hologram holds the prefixed name, the location has no world or its world unloaded, or the call failed. |
| `boolean update(String id, List<String> lines)` | Replaces every line. `false` when no hologram this provider placed with this id stands, such as after its world unloaded or the hologram plugin dropped it: place it again with `create`. |
| `boolean move(String id, Location location)` | Moves the hologram, the bottom centre of its text to the location. |
| `boolean remove(String id)` | Removes the hologram. `false` when it was refused, and it stays in `ids()`. |
| `boolean exists(String id)` | A hologram with this id stands. |
| `Set<String> ids()` | The ids this provider placed that still stand, for an orphan check. |
| `int removeAll()` | Removes every hologram this provider placed that still stands, and returns how many. |
| `void close()` | Removes every hologram this provider placed and stops the provider: its listener is unregistered, `available()` then answers `false`, and every other call but `plugin()` answers `false`, `0` or an empty set. A second call does nothing. |
| `static String literal(String text)` | Writes text a player supplied so a line shows it as written. |
| `@Nullable HologramPlugin plugin()` | The hologram plugin the provider places holograms through, or `null` for a provider bound to no hologram plugin. |
| `boolean available()` | The provider is not closed and its hologram plugin is enabled. |

Every call answers `false`, `0` or an empty set while the provider is not available or when the call fails; a failure is logged at most once a minute and reported under `hook.<plugin key>`. A `true` from `create`, `update`, `move` or `remove` means the change was made, or was accepted to be made on the region thread of the location a little later. Code that takes any `HologramProvider` checks `plugin()` for `null` before it reads `placeholdersPerViewer()`.

Behaviour to know:

- An id is 1 to 48 of `a-z`, `0-9`, `_` and `-`; any other id throws `IllegalArgumentException`. The hologram plugin stores it after the owner's name in lower case, with every character outside `a-z`, `0-9` and `-` written as `-`, and a `_`, as in `slate_crate-1`. Two plugins share a prefix only when their names differ in nothing but characters written as `-`.
- Every call but `create` reaches only a hologram this provider placed, and `create` refuses a name another hologram holds, such as one a server owner made with the hologram plugin's commands or another plugin placed under the same prefix.
- On every hologram plugin, the location given to `create` and `move` is the bottom centre of the hologram's text, and the lines stack upward from it, the last line lowest.
- Holograms are temporary: the hologram plugin never saves them, so place them again after a restart. A hologram is also removed when its world unloads, and the hologram plugin drops it on its own reload (DecentHolograms on `/dh reload`) or when it disables. Nothing tells the plugin: `update`, `move` and `exists` answer `false` and `ids()` no longer lists it. To keep one standing, keep its id, location and lines, call `create` when `update` answers `false`, and place a world's holograms again from a `WorldLoadEvent` listener with a location built on `event.getWorld()`. A `Location` kept from before the world unloaded can still point at the old world.
- Lines are MiniMessage. A PlaceholderAPI placeholder such as `%player_name%` is filled in for each viewer when PlaceholderAPI is installed and `plugin.placeholdersPerViewer()` is `true`, which is every supported plugin. A line MiniMessage refuses, such as one holding a `§` colour code, makes `create` and `update` fail on DecentHolograms, FancyHolograms and HologramLib.
- Text a player or another untrusted source supplied, such as a display name or an item name, goes into a line only through `HologramProvider.literal(text)`, as in `"<gold>Opened by " + HologramProvider.literal(name)`: it then shows as written, with no tag, colour code or placeholder in it taking effect. Without it, a player can show any placeholder's value, such as `%server_online%`, to every viewer. The result is for the text of a line, not for an argument inside a tag.
- Call every method on the server's global thread: the main thread on Paper, the global region thread on Folia. The exception is `close()` at disable, which runs on the thread that disables the plugin, as `onDisable` does. The provider calls the hologram plugin on the calling thread, so the hologram plugin is called from the global thread except while the plugin disables. The provider's own records are concurrent, so the provider itself is thread-safe.

```java
private Detected<HologramProvider> holograms;

public void onEnable() {
    holograms = detectHolograms();
}

private @Nullable Detected<HologramProvider> detectHolograms() {
    HologramPlugin chosen = HologramPlugin.byKey(settings.get().hologramPlugin());
    return chosen == null ? null : HologramProvider.detect(this, errors, true, chosen);
}

void reloadHolograms() {
    if (!settings.reload()) {
        return;
    }
    HologramProvider held = holograms == null ? null : holograms.provider();
    if (held != null) {
        held.close();
    }
    holograms = detectHolograms();
}

boolean showDailyCrate(Location block) {
    HologramProvider provider = holograms == null ? null : holograms.provider();
    return provider != null && provider.create("daily-crate", block.clone().add(0.5, 1.6, 0.5),
        List.of("<gold>Daily crate", "<gray>%slate_keys_daily% keys"));
}

void refreshDailyCrate(Location block, List<String> lines) {
    HologramProvider provider = holograms == null ? null : holograms.provider();
    if (provider != null && !provider.update("daily-crate", lines)) {
        provider.create("daily-crate", block.clone().add(0.5, 1.6, 0.5), lines);
    }
}

@EventHandler
public void onWorldLoad(WorldLoadEvent event) {
    World world = event.getWorld();
    if (world.getName().equals(crateWorld)) {
        showDailyCrate(new Location(world, crateX, crateY, crateZ));
    }
}

public void onDisable() {
    HologramProvider provider = holograms == null ? null : holograms.provider();
    if (provider != null) {
        Shutdown.closeQuietly("remove holograms", () -> provider.close(), getLogger(), errors);
    }
}
```

`settings` is the plugin's `ConfigHolder` of [taffy-config](/docs/modules/config), and `hologramPlugin()` is the component of its record read from `holograms.plugin`. A reload that fails keeps the settings in effect, and `reloadHolograms` then keeps the provider it holds. After a reload that succeeds, `reloadHolograms` closes the held provider before it detects again. `close()` removes the holograms that provider placed and unregisters its listener, so the plugin places its holograms again through the new provider.

When the plugin disables, the provider removes its holograms by itself. Paper fires the plugin's `PluginDisableEvent` before `onDisable`, and the provider's listener removes every hologram it placed at that point. `close()` in `onDisable` then removes any hologram placed since, such as by a menu closed in `Menus.shutdown`, and stops the provider. It comes after `PlaceholderRegistration.unregister` and `Menus.shutdown` and before `Scheduler.close()`, in the order [taffy-platform](/docs/modules/platform#disable-order) gives.

Both removals run on the thread that disables the plugin. On Paper that is the main thread. On Folia it is the thread that called `disablePlugin`, and while the server stops it is Folia's shutdown thread, not the global region thread. If a hologram plugin refuses a call from that thread, the removal fails like any other call: one warning and a report under `hook.<plugin key>`. The hologram then stays until the hologram plugin drops it, at the latest when the server stops, since it never saves it. A plugin that disables itself on Folia does so through `scheduler.global(() -> getServer().getPluginManager().disablePlugin(this))`, as [storage](/docs/modules/storage#starting-storage) does, so the removal runs on the global region thread.

### Display holograms

<Callout type="info" title="From 0.4.11">
`HologramProvider.displays` and `DisplayHolograms` are available from Taffy `0.4.11`.
</Callout>

`HologramProvider.displays(Plugin owner, Scheduler scheduler, ErrorReports errors)` returns a `DisplayHolograms`: a `HologramProvider` that needs no hologram plugin. A hologram is one `TextDisplay` for each line and an optional `ItemDisplay` above them. Its `plugin()` is `null`, and `HologramPlugin` still names only hologram plugins that are detected. Call it on the server thread while the plugin is enabled, normally in `onEnable`, with the plugin's own `Scheduler`. A plugin holds one display provider at a time: close the held one before building another.

Choose between the two by what the server owner gets:

| | A hologram plugin, `detect` | Display entities, `displays` |
|---|---|---|
| Needs | The hologram plugin installed, and its entry in `paper-plugin.yml`. | Nothing. |
| Lines | MiniMessage. | Adventure components, or MiniMessage through the `HologramProvider` methods. |
| PlaceholderAPI in a line | Filled in for each viewer. | Shown as written. |
| Item above the text | No. | Yes, one `ItemStack`. |
| Calls | On the server's global thread. | From any thread. |

A plugin that wants holograms on every server prefers the hologram plugin the owner chose and falls back to display entities when detection gives no provider:

```java
private final ErrorReports errors = new ErrorReports();
private Scheduler scheduler;
private HologramProvider holograms;

@Override
public void onEnable() {
    scheduler = new Scheduler(this, errors);
    holograms = chooseHolograms();
}

private HologramProvider chooseHolograms() {
    HologramPlugin chosen = HologramPlugin.byKey(settings.get().hologramPlugin());
    if (chosen != null) {
        HologramProvider detected = HologramProvider.detect(this, errors, true, chosen).provider();
        if (detected != null) {
            return detected;
        }
    }
    return HologramProvider.displays(this, scheduler, errors);
}

boolean showDailyCrate(Location block, String opener) {
    Location base = block.clone().add(0.5, 1.6, 0.5);
    if (holograms instanceof DisplayHolograms displays) {
        return displays.create("daily-crate", base, crateLines(opener), ItemStack.of(Material.CHEST));
    }
    return holograms.create("daily-crate", base,
        List.of("<gold>Daily crate", "<gray>Opened by " + HologramProvider.literal(opener)));
}

void showOpener(String opener) {
    if (holograms instanceof DisplayHolograms displays) {
        displays.update("daily-crate", crateLines(opener), ItemStack.of(Material.ENDER_CHEST));
    } else {
        holograms.update("daily-crate",
            List.of("<gold>Daily crate", "<gray>Opened by " + HologramProvider.literal(opener)));
    }
}

private static List<Component> crateLines(String opener) {
    return List.of(
        Component.text("Daily crate", NamedTextColor.GOLD),
        Component.text("Opened by ", NamedTextColor.GRAY).append(Component.text(opener)));
}

@Override
public void onDisable() {
    Shutdown.closeQuietly("remove holograms", () -> holograms.close(), getLogger(), errors);
    scheduler.close();
}
```

`opener` is a player's name. It goes into a component as `Component.text(opener)`, which shows it as written, and never through MiniMessage. On the hologram plugin branch it goes through `HologramProvider.literal`.

| Method | What it does on display entities |
|---|---|
| `boolean create(String id, Location location, List<Component> lines, @Nullable ItemStack item)` | Places a hologram of component lines and an optional item. `false` when the id is in use, the location has no world or its world unloaded, or the provider is not available. |
| `boolean update(String id, List<Component> lines, @Nullable ItemStack item)` | Replaces every line and the item. `false` when the id is not in use. |
| `boolean create(String id, Location location, List<String> lines)` | The same placement with MiniMessage lines and no item. Also `false` when MiniMessage refuses a line, which is logged and reported under `hook.displays` unless the call answers `false` for another reason. |
| `boolean update(String id, List<String> lines)` | Replaces every line and keeps the item. Also `false` when MiniMessage refuses a line, reported the same way. |
| `boolean move(String id, Location location)` | Removes the entities and spawns them again at the new location. `false` when the id is not in use, or the location has no world or its world unloaded. |
| `boolean remove(String id)` | Removes the hologram. `false` when the id is not in use. |
| `boolean exists(String id)`, `Set<String> ids()` | Answer from the provider's records, also before the entities stand and while the hologram's chunk is not loaded. |
| `int removeAll()`, `void close()` | As for every `HologramProvider`. |
| `boolean available()` | The provider is not closed and the plugin is enabled. While it is `false`, every other call answers `false`, `0` or an empty set. |

What to know:

- **Layout.** The location is the bottom centre of the text. The lines stack upward from it, the last line lowest, `DisplayHolograms.LINE_SPACING` (0.28) blocks apart. The item is centred `DisplayHolograms.ITEM_RISE` (0.45) blocks above the bottom of the top line, or above the location when there are no lines, at `DisplayHolograms.ITEM_SCALE` (0.75) of its size with the `FIXED` item transform. Every entity faces the viewer (`Billboard.CENTER`). A line is centred, shadowed, not see-through, on the default background, and never wraps.
- **Who sees it.** Every player in range. The view range is Paper's default of `1.0`, about 64 blocks. There is no per-player visibility and no per-viewer text.
- **Ids.** An id is 1 to 48 of `a-z`, `0-9`, `_` and `-`, and is not prefixed. `create` with an id in use answers `false` and leaves that hologram as it is.
- **Threads.** Every method may be called from any thread, on Paper and on Folia. A call changes the provider's records and answers at once. Each spawn, text change, move and removal of an entity then runs on the region thread of the hologram's location through the plugin's `Scheduler`: the main thread on Paper, a tick later at the earliest. A removal made on the thread that owns the location is done before the call returns. A `true` means the change was accepted. Several changes to one hologram made before its region thread runs are shown as one.
- **Updates.** Text is changed in place when the number of lines stays the same and an item neither appears nor goes. Otherwise the entities are removed and spawned again.
- **Chunks.** The entities stand only while the chunk of the location is loaded. A hologram created in a chunk that is not loaded is kept and spawned when the chunk loads, and its entities are removed when the chunk unloads. `exists` stays `true` throughout, and the plugin does nothing.
- **Worlds.** A location with no world, or whose world has unloaded, makes `create` and `move` answer `false`. When a world unloads, the provider removes its holograms from the world and from its records, as every `HologramProvider` does. Place them again from a `WorldLoadEvent` listener with a location built on `event.getWorld()`.
- **Nothing is saved.** Every entity is non-persistent (`setPersistent(false)`), so the server never writes it to a world file, and none survives a restart or a crash. Place the holograms again in `onEnable`.
- **Leftovers.** Every entity carries the plugin's persistent data key `<plugin namespace>:taffy_hologram` with the hologram's id. An entity with that key that the provider does not hold is removed when the provider is built, in every loaded chunk, and whenever the entities of a chunk load. An entity something else removed, such as with `/kill`, is spawned again at the next `update` of its hologram or the next load of its chunk.
- **A failed spawn or text change.** The hologram's entities are removed, the hologram is forgotten so `exists` answers `false`, one warning is logged at most once a minute, and the failure is reported under `hook.displays`. An entity that refuses its removal is logged and reported the same way, and the other entities are still removed.
- **A refused change.** A change the plugin's `Scheduler` refuses, which it does once the plugin is disabling, answers `false`. A refused `create` or `move` forgets the hologram, and a refused `update` keeps it.
- **Disable.** The provider removes every hologram when the plugin's `PluginDisableEvent` fires, before `onDisable`, and `close()` does the same. On Paper both run on the main thread and the entities are gone before the call returns, those of a move or removal that still waits for its region thread included. On Folia a disabling plugin can schedule nothing, so only the entities whose location the disabling thread owns are removed. The others stay in the world until their chunk unloads or the server stops, are never saved, and are removed by the next display provider the plugin builds. Call `close()` before `Scheduler.close()`, in the order [taffy-platform](/docs/modules/platform#disable-order) gives.

## Placeholders

`PlaceholderExpansionBuilder` collects the plugin's placeholders and registers them with PlaceholderAPI and MiniPlaceholders, each when it is installed, enabled and its API classes are visible. With the identifier `shop`, the name `balance` is `%shop_balance%` in PlaceholderAPI and `<shop_balance>` in MiniPlaceholders.

```java
placeholders = new PlaceholderExpansionBuilder()
    .identifier("shop")
    .player("balance", this::balanceText)
    .offline("veteran", offlinePlayer -> offlinePlayer.hasPlayedBefore() ? "yes" : "no")
    .global("online", () -> String.valueOf(getServer().getOnlinePlayers().size()))
    .register(this, errors, true);
```

| Method | Behaviour |
|---|---|
| `identifier(String identifier)` | Sets the prefix, kept in lower case. Letters `a` to `z` in either case, digits and `-` only; `_` is refused because PlaceholderAPI reads it as the end of the identifier. |
| `player(String name, Function<Player, @Nullable String> handler)` | Resolved for an online player. In PlaceholderAPI it gives no value for an offline player. |
| `offline(String name, Function<OfflinePlayer, @Nullable String> handler)` | Resolved for a player who may be offline. PlaceholderAPI only. |
| `global(String name, Supplier<@Nullable String> handler)` | No player. |
| `playerPrefix(String prefix, BiFunction<Player, String, @Nullable String> handler)` | From `0.4.7`. A [prefix placeholder](#prefix-placeholders) for an online player. |
| `offlinePrefix(String prefix, BiFunction<OfflinePlayer, String, @Nullable String> handler)` | From `0.4.7`. A prefix placeholder for a player who may be offline. PlaceholderAPI only. |
| `globalPrefix(String prefix, Function<String, @Nullable String> handler)` | From `0.4.7`. A prefix placeholder with no player. |
| `register(Plugin owner, ErrorReports errors, boolean switchedOn)` | Registers what was added so far, PlaceholderAPI first, and returns the `PlaceholderRegistration`. |

Without `identifier`, the identifier is the owner's name in lower case with only the letters `a` to `z` and digits kept. When that leaves nothing, `register` throws `IllegalStateException`, also when switched off. A name holds only lower case `a` to `z`, digits, `_` and `-`; any other name throws `IllegalArgumentException`. A later placeholder of the same kind and name replaces the earlier one.

Behaviour to know:

- A handler that returns `null` gives no value. One that throws a `RuntimeException` gives no value, and the failure is logged at most once a minute per placeholder and not reported.
- PlaceholderAPI may call a handler from any thread, so handlers must be thread-safe. The builder itself is not thread-safe.
- In PlaceholderAPI a global placeholder wins over an offline or player one of the same name, and an offline one over a player one. In MiniPlaceholders a player and a global placeholder of the same name collide, and which answers is unspecified.
- MiniPlaceholders inserts a value as plain text, so markup in it is shown as written.
- Registering replaces any PlaceholderAPI expansion that already uses the identifier. MiniPlaceholders refuses an identifier another expansion uses, which makes it `FAILED`. The PlaceholderAPI expansion stays registered across `/papi reload`.
- A backend that refuses or throws is `FAILED`: logged, reported under `hook.placeholderapi` or `hook.miniplaceholders`, with the warning's text as its reason. The other backend is still registered. A backend that is installed but not enabled, not visible, or lacks the API is skipped with a warning; one that is not installed is skipped silently.
- Call `register` on the server thread in `onEnable`: PlaceholderAPI fires a synchronous event when it registers. The owner's authors and version describe the expansion.

### Prefix placeholders

From `0.4.7`, a prefix placeholder answers every name that starts with its prefix and a `_`, and its handler takes the rest of the name. With the identifier `shop` and the prefix `keys`, `%shop_keys_vote%` gives the handler `vote`:

```java
placeholders = new PlaceholderExpansionBuilder()
    .identifier("shop")
    .playerPrefix("keys", (player, crate) -> keyCount(player, crate))
    .offlinePrefix("spent", (offlinePlayer, currency) -> spentText(offlinePlayer.getUniqueId(), currency))
    .globalPrefix("stock", item -> stockText(item))
    .register(this, errors, true);
```

- A prefix holds the same characters as a name, and is written without the `_` that ends it: a prefix that ends with `_`, such as `keys_`, throws `IllegalArgumentException`. A later prefix placeholder of the same kind and prefix replaces the earlier one.
- In PlaceholderAPI a placeholder registered by its whole name answers first, so `player("keys_vote", ...)` wins over the prefix `keys` for `%shop_keys_vote%`. After the whole names, the longest prefix that fits answers: with the prefixes `keys` and `keys_virtual`, `%shop_keys_virtual_vote%` gives `vote` to `keys_virtual`. No shorter prefix is asked when that handler gives no value.
- A global prefix wins over an offline or player one of the same prefix, and an offline one over a player one, as with whole names.
- The rest is passed as written, in the case it was typed in, and is empty for `%shop_keys_%`. `%shop_keys%` alone is not answered by the prefix.
- In MiniPlaceholders the prefix is the tag and the rest is its argument: `<shop_keys:vote>`. Several arguments are joined with `:`, so `<shop_keys:a:b>` gives `a:b`. The tag without an argument, `<shop_keys>`, goes to the placeholder registered under that whole name, when there is one, and otherwise gives no value. An offline prefix is not registered with MiniPlaceholders.
- The rest is text whoever wrote the placeholder chose, which can be a player. Check it against what the plugin knows, such as its crate ids, before using it, and return `null` for anything else.
- A handler that throws gives no value, and the failure is logged as `The prefix placeholder shop_keys_ failed`, at most once a minute per prefix and apart from a placeholder registered under the whole name `keys`.

### PlaceholderCache

PlaceholderAPI asks for a value on whatever thread the requester runs on, often the server thread or a Folia region thread, so a handler must never wait for a database or another thread. From `0.4.7`, `PlaceholderCache<K>` holds the last known value of each key and refreshes it behind the handler:

```java
PlaceholderCache<UUID> sales = new PlaceholderCache<>(Duration.ofSeconds(30), 1000, getLogger());

private @Nullable String salesText(OfflinePlayer player) {
    UUID id = player.getUniqueId();
    String known = sales.get(id, () -> store.countSales(id).thenApply(String::valueOf));
    return known == null ? "..." : known;
}
```

| Method | Behaviour |
|---|---|
| `new PlaceholderCache<>(Duration timeToLive, int maximumEntries, Logger logger)` | An empty cache. A `timeToLive` of zero or less, or a `maximumEntries` below one, throws `IllegalArgumentException`. |
| `get(K key, Supplier<CompletableFuture<@Nullable String>> refresh)` | The last known value, without waiting. Starts a refresh when the key has no value yet or its value is at least `timeToLive` old, unless one is already running for that key. |
| `forget(K key)` | Drops one key, as for a player who quits. |
| `clear()` | Drops every key, as in `onDisable`. The cache can be used again afterwards. |

- Before the first refresh of a key completes, `get` returns `null`. A handler passes that on as no value, or returns a text of its own as above. A refresh that gives `null` leaves the key with no value until the next one.
- The cache owns no thread. `refresh` is called on the thread that called `get`, so it only starts the work and returns its future: a `Scheduler.dispatch`, or a storage call that already returns a `CompletableFuture`. The value is stored on the thread that completes the future.
- A stale value is still returned while its refresh runs, so a reader sees the old value until the new one arrives.
- A refresh fails when `refresh` throws or returns `null`, or when its future completes with a failure, such as a `Scheduler.dispatch` to a player who has just quit. The last known value is kept, the next refresh of that key starts no sooner than one `timeToLive` later, and the failure is logged at most once a minute for the whole cache, with its stack the first time. It is not reported to `ErrorReports`.
- A future that never completes stops further refreshes of its key, and keeps the key in the cache, until `forget` or `clear`.
- An `Error` other than a `LinkageError` that `refresh` throws leaves `get` and is not logged by the cache. The key is otherwise treated as after a failed refresh.
- The cache keeps at most `maximumEntries` keys, counting a key whose first refresh still runs. A new key beyond that drops the key asked for longest ago among the keys with no refresh running, so a refresh that runs is never started a second time for its key.
- While every kept key has a refresh running, a new key is not kept: `get` returns `null` for it and starts no refresh, and a later `get` tries again. Set `maximumEntries` above the number of keys asked for at once, such as the most players a scoreboard or leaderboard shows.
- A refresh that completes after `forget` or `clear` dropped its key stores nothing.
- Every method may be called from any thread. Call `forget` from a `PlayerQuitEvent` listener for a cache keyed by player, and `clear` in `onDisable` after `PlaceholderRegistration.unregister`.

### PlaceholderRegistration

- `statuses()` gives PlaceholderAPI's status, then MiniPlaceholders'. It may be called from any thread and is not changed by `unregister()`.
- `unregister()` removes the placeholders from both backends, leaving an expansion that has since replaced them under the same identifier. A failure is logged as a warning, and a second call does nothing. Call it at the start of `onDisable`, on the server thread, after `ComfiConfConnection.close` when the plugin also uses taffy-comficonf: PlaceholderAPI keeps an expansion registered after the plugin that registered it disables.

## Failures and threads

Detection follows one rule for every integration:

- Not visible, or lacking the API: one warning, not reported.
- Could not be hooked (threw, or a method it calls is missing): `FAILED`, one warning, and a report to `ErrorReports` under `hook.<name>`, the integration plugin's name in lower case.
- An `Error` other than a `LinkageError` propagates.

Beyond these, `CustomItems.detect` logs one line naming every custom item plugin's state, and `register` warns about a placeholder backend that is installed but not enabled. No other state is logged.

A failure inside a later call is logged at most once a minute per kind of call, with its stack the first time. These sources reach `ErrorReports`:

| Source | Reported for |
|---|---|
| `hook.itemsadder`, `hook.nexo`, `hook.oraxen`, `hook.headdatabase`, and from `0.4.12` `hook.craftengine` and `hook.mmoitems` | A failed detection, an item that could not be built, and from `0.4.7` an items-loaded callback that threw. |
| `hook.vault` | A lookup that failed, once per lookup. From `0.4.7`, once per change of status when the lookup is given the previous result or runs in a `VaultWatch`. |
| `hook.playerpoints` | From `0.4.7`. A failed detection. |
| `hook.luckperms` | A failed detection, every failed call, and from `0.3.2` a push of a saved write that threw. |
| `hook.worldguard` | A failed detection, and every failed lookup. From `0.4.12`, also every failed build check. |
| `hook.floodgate`, `hook.geyser-spigot` | From `0.4.3`, a failed detection, and every failed check of a player. |
| `hook.decentholograms`, `hook.fancyholograms`, `hook.holograms`, `hook.hologramlib` | A failed detection, and every failed hologram call. |
| `hook.displays` | From `0.4.11`, a failed spawn, text change or removal of a display hologram, and a line MiniMessage refuses. |
| `hook.placeholderapi`, `hook.miniplaceholders` | A backend that refused the placeholders or threw while registering them. |

Reading an item's id, resolving a placeholder and, from `0.4.7`, a refresh of a `PlaceholderCache` log a failure and do not report it. Install a target on `ErrorReports` to send these reports somewhere; see [taffy-platform](/docs/modules/platform) and [taffy-metrics](/docs/modules/metrics).

A `null` argument throws `NullPointerException`, except where a parameter is marked `@Nullable`, and except a reference given to `CustomItemRef.parse`, `CustomItems.create` or `CustomItems.build`, which throws `IllegalArgumentException`.

| Type | Thread |
|---|---|
| `CustomItems.detect`, `PermissionProvider.luckPerms`, `RegionProvider.worldGuard`, `PlaceholderExpansionBuilder.register` | The server thread, in `onEnable`. |
| `BedrockProvider.detect` | The server thread, in `onEnable`. |
| `HologramProvider.detect` | The server thread while the plugin is enabled, normally in `onEnable`, and again after the held provider is closed. |
| `HologramProvider.displays` | From `0.4.11`. The server thread while the plugin is enabled, normally in `onEnable`, and again after the held provider is closed. |
| `EconomyProvider.vault` | In `onEnable`, on the first tick, and from `EconomyWatcher` on the thread that fires the service event. |
| `PlaceholderRegistration.unregister` | The server thread, at the start of `onDisable`, after `ComfiConfConnection.close` when the plugin uses taffy-comficonf. |
| `CustomItems` calls | The thread that owns the item. |
| `CustomItems.close` | The server thread, before the plugin detects again. |
| The items-loaded callback of `CustomItems.detect` | From `0.4.7`. Called by Taffy on the thread the item plugin fires its event on: the server thread on Paper, a ticking thread on Folia. |
| `EconomyProvider` calls | The thread `thread(UUID)` names. From `0.3.2` `balance`, `has`, `withdraw` and `deposit` of the Vault provider throw `IllegalStateException` on any other thread. From `0.4.7` the PlayerPoints provider names `ThreadTag.ASYNC` for every player and throws `IllegalStateException` on the main thread on Paper and on every region thread and the global region thread on Folia. |
| `PermissionProvider` writes | Off the server thread; they block until saved. From `0.3.2` a write on a server thread throws `IllegalStateException`, in `onDisable` too. |

| `RegionProvider.canBuild` | From `0.4.12`. The thread that owns the player: the main thread on Paper. |
| `BedrockProvider.bedrock` | The thread that asks. `Prompts` asks on the player's entity thread. |
| `HologramProvider` calls | The server's global thread: the main thread on Paper, the global region thread on Folia. |
| `DisplayHolograms` calls | From `0.4.11`. Any thread. The entities change on the region thread of the hologram's location. |
| `HologramProvider.close` | The thread that disables the plugin, in `onDisable`, after `PlaceholderRegistration.unregister` and `Menus.shutdown` and before `Scheduler.close()`. On Folia that is the global region thread only when the plugin disables itself from there. Before detecting again, the server's global thread. |
| `Detected`, `HookStatus`, `PlaceholderRegistration.statuses()` | Any thread. |
| Placeholder handlers | Called from any thread by PlaceholderAPI. |
| `PlaceholderCache` | Any thread. `refresh` runs on the thread that called `get`. |
