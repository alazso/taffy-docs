title: taffy-platform
description: The base module every other Taffy module builds on, with Folia-safe scheduling, shutdown helpers, MiniMessage text and language files, item builders, durations, rate-limited logging and a Discord webhook.
---

`taffy-platform` holds the classes a Paper plugin needs before it needs anything else. Every other Taffy
runtime module (all but `taffy-test`) depends on it through `api`, so a plugin that uses `taffy-config`,
`taffy-storage` or any other runtime module already has it on its classpath.

All classes live in one package, `so.alaz.taffy.platform`.

| Area | Classes |
|---|---|
| Scheduling | `Scheduler`, `Dispatcher`, `ThreadTag`, `EntityThread`, `EntityUnavailableException` |
| Shutdown | `TaskGate`, `PendingSettlements`, `Shutdown`, `ErrorReports` |
| Text | `Text`, `Messages`, `LegacyText` |
| Items | `ItemBuilder`, `SkullBuilder`, `Items`, `InventoryFit`, `PdcKey`, `Colors`, `Sounds` |
| Time | `Durations`, `Expiry`, `CooldownManager` |
| Amounts | `AmountFormat`, `Amounts`, from `0.4.6` |
| Players | `PlayerCache`, from `0.4.5` |
| Logging | `ThrowLog`, `Classes` |
| Diagnostics | `DiagnosticReport`, `Redaction`, from `0.4.10` |
| Commands | `CommandHelpers`, from `0.4.10` |
| Importers | `Importer`, `ImportReport`, `Importers`, from `0.4.15` |
| Update check | `UpdateCheck`, `UpdateSource`, from `0.4.10` |
| Discord | `DiscordWebhook`, `WebhookPayload` |

The module holds no static plugin, logger, executor or thread and ships no resource files. Each class takes the
narrowest thing it uses (a `Plugin`, a `Logger`, a `Path`, an `Executor`) through its constructor or method
arguments. `DiscordWebhook` is the one class here that owns threads: those of its HTTP client. `UpdateCheck` sends
its request on an executor the plugin passes and owns none.

## Setup

Add the module through its catalog alias, `alaz.taffy.platform`. `so.alaz.taffy.paper-plugin` shades it into the
plugin jar and relocates `so.alaz.taffy` to `<group>.libs.taffy`.

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.platform)
}
```

The published coordinates are `so.alaz.taffy:taffy-platform:0.4.14`.

`Text` uses PlaceholderAPI and MiniPlaceholders when they are installed. Neither is bundled, and the plugin needs
no compile dependency on them. A plugin described by `paper-plugin.yml` sees another plugin's classes only when it
lists that plugin under `dependencies.server`, so a plugin that wants those placeholders in its text lists both:

```yaml title="paper-plugin.yml"
dependencies:
  server:
    PlaceholderAPI:
      load: BEFORE
      required: false
    MiniPlaceholders:
      load: BEFORE
      required: false
```

A typical plugin creates these objects once, in its main class:

```java title="ShopPlugin.java"
import so.alaz.taffy.platform.DiscordWebhook;
import so.alaz.taffy.platform.ErrorReports;
import so.alaz.taffy.platform.Messages;
import so.alaz.taffy.platform.PendingSettlements;
import so.alaz.taffy.platform.Scheduler;
import so.alaz.taffy.platform.TaskGate;
import so.alaz.taffy.platform.Text;
import org.bukkit.plugin.java.JavaPlugin;

public final class ShopPlugin extends JavaPlugin {

    private final ErrorReports errors = new ErrorReports();
    private final TaskGate gate = new TaskGate();
    private final PendingSettlements settlements = new PendingSettlements();
    private Scheduler scheduler;
    private Text text;
    private Messages messages;
    private DiscordWebhook webhook;

    @Override
    public void onEnable() {
        scheduler = new Scheduler(this, errors);
        text = new Text(getLogger());
        messages = Messages.load(getDataFolder().toPath(), () -> getResource("lang/en.yml"), getLogger());
        webhook = new DiscordWebhook();
    }
}
```

The disable side of the same class is under [Shutdown](#shutdown).

From `0.4.1`, `new ErrorReports()`, `new Text(Logger)`, `Messages.load` and `Messages.loadLenient` call
`Relocation.check()`, which throws `IllegalStateException` when the plugin's jar holds Taffy in its original package
`so.alaz.taffy`. A jar that `so.alaz.taffy.paper-plugin` builds passes, and so does a unit test, where no plugin
class loader loaded Taffy. [Relocation](/docs/consuming-by-coordinates#relocation) has the message and the rule.

## Scheduler

`Scheduler` runs tasks on Paper's region-threaded schedulers. It behaves the same on Paper and on Folia and never
calls `Bukkit.getScheduler()`, which Folia does not support. Every task is owned by the plugin, so Paper cancels
it when the plugin disables. Every method may be called from any thread.

```java
Scheduler scheduler = new Scheduler(plugin, errors);
```

The constructor takes the owning `Plugin` and the plugin's `ErrorReports`, and throws `NullPointerException` when
either is `null`. `mode()` returns `Scheduler.Mode.FOLIA` when Folia's server class was loadable at construction,
otherwise `Scheduler.Mode.PAPER`. A lookup that failed reads as Paper, with a warning in the plugin's log.

### Running work

| Method | Runs the task | Returns |
|---|---|---|
| `global(Runnable)` | on the global region thread, as soon as possible | `false` when the plugin is disabling |
| `async(Runnable)` | on an async thread, as soon as possible | `false` when the plugin is disabling |
| `asyncOrRun(Runnable)` | on an async thread, or on the calling thread (which it may then block) when the plugin is disabling | nothing |
| `asyncExecutor()` | an `Executor` over `async` whose `execute` throws `RejectedExecutionException` while the plugin is disabling | the executor |
| `delayedAsync(Runnable, Duration)` | once on an async thread after the delay | `false` when the plugin is disabling |
| `repeatingAsync(Runnable, Duration, Duration)` | on an async thread after the initial delay, then every period, until `close()` | `false` when the plugin is disabling |
| `entity(Entity, Runnable)` | on the region thread that owns the entity | nothing |
| `entity(Entity, Runnable, Runnable)` | the task on the entity's region thread, or the `retired` callback | nothing |

```java
boolean loading = scheduler.async(() -> {
    List<Offer> offers = loadOffers();
    if (!scheduler.global(() -> broadcastOffers(offers))) {
        getLogger().info("The offers were loaded while the plugin was disabling and are not broadcast");
    }
});
if (!loading) {
    getLogger().info("The offers are not loaded: the plugin is disabling");
}

if (!scheduler.repeatingAsync(this::saveDirtyAccounts, Duration.ofMinutes(1), Duration.ofMinutes(5))) {
    getLogger().warning("The account autosave was not started");
}
```

From `0.4.4`, `global`, `async`, `delayedAsync` and `repeatingAsync` carry
`org.jetbrains.annotations.CheckReturnValue`, so IntelliJ IDEA flags a call that drops the `boolean`. Their
signatures and behaviour are unchanged. A plugin that replaces a scheduler of its own, one that let Paper throw
`IllegalPluginAccessException` at disable, checks the `boolean` at every place it caught that exception: the
Taffy methods never throw it, so a `catch` that released a ticket or logged a warning no longer runs, and the
`false` branch does that work instead.

From `0.4.4`, these methods return Paper's own `ScheduledTask`, the handle of the one task they started, or
`null` when the task was refused:

| Method | Runs the task |
|---|---|
| `repeatingAsyncTask(Runnable, Duration, Duration)` | as `repeatingAsync` does, until the handle is cancelled or `close()` |
| `delayedGlobal(Runnable, Duration)` | once on the global region thread after the delay |
| `repeatingGlobal(Runnable, Duration, Duration)` | on the global region thread after the initial delay, then every period |
| `region(Location, Runnable)` | on the region thread that owns the block of the location, as soon as possible |
| `delayedRegion(Location, Runnable, Duration)` | once on that region thread after the delay |
| `repeatingRegion(Location, Runnable, Duration, Duration)` | on that region thread after the initial delay, then every period |
| `delayedEntity(Entity, Runnable, Runnable, Duration)` | once on the entity's region thread after the delay, or the `retired` callback |
| `repeatingEntity(Entity, Runnable, Runnable, Duration, Duration)` | on the entity's region thread after the initial delay, then every period, with the `retired` callback when the entity retires |

`null` always means a refusal: the plugin is not enabled, or, for the two entity methods, the entity is already
removed. Nothing else gives `null`. `ScheduledTask.cancel()` stops that one task and leaves every other task of
the plugin running, so a task whose period comes from the config is replaced on a reload without `close()`:

```java
private @Nullable ScheduledTask autosave;

void startAutosave(Duration period) {
    if (autosave != null) {
        autosave.cancel();
    }
    autosave = scheduler.repeatingAsyncTask(this::saveDirtyAccounts, period, period);
}
```

`repeatingAsync` keeps its `boolean` and gives no handle. The tasks of all five repeating methods are tracked for
`close()`, and each new repeating task drops the cancelled ones from that list, so a plugin that cancels and
restarts a task on every reload holds no more than its live tasks.

A task is not passed its own handle. A task that stops itself cancels the returned handle, which the plugin keeps
where the task's thread reads it, in a `volatile` field or an `AtomicReference`:

```java
private final AtomicReference<ScheduledTask> countdown = new AtomicReference<>();

void startCountdown() {
    countdown.set(scheduler.repeatingGlobal(this::tick, Duration.ofSeconds(1), Duration.ofSeconds(1)));
}

private void tick() {
    ScheduledTask self = countdown.get();
    if (secondsLeft.decrementAndGet() <= 0 && self != null) {
        self.cancel();
    }
}
```

When the scheduling call is made on another thread than the one that runs the task, a first run can start before
the handle is stored, and at once for `repeatingAsyncTask` with a zero initial delay. That run finds no handle
(`null` above) and a later run cancels.

#### Ticks

Paper's global, entity and region schedulers count in server ticks of 50 ms. A `Duration` given to
`delayedGlobal`, `repeatingGlobal`, `delayedRegion`, `repeatingRegion`, `delayedEntity` or `repeatingEntity` is
rounded up to whole ticks, and anything shorter than one tick, zero and negative values included, is one tick,
since Paper accepts no shorter delay or period. `Duration.ofMillis(120)` is 3 ticks. The async methods count no
ticks, as below.

#### Region work

`region`, `delayedRegion` and `repeatingRegion` run the task on the thread that owns the block of a `Location`,
which is where a plugin changes a block, spawns an entity or drops an item at a place. On Paper that is the main
thread. On Folia it is the thread of the region that holds the chunk.

```java
Location anchor = crate.location();
ScheduledTask opening = scheduler.delayedRegion(anchor,
    () -> anchor.getBlock().setType(Material.AIR), Duration.ofSeconds(3));
if (opening == null) {
    getLogger().info("The crate stays: the plugin is disabling");
}
```

The region is taken from the world and the block coordinates the `Location` has when the call is made, so a later
change to that `Location` does not move the task. A `null` task and a `Location` with no world throw
`NullPointerException` before anything is scheduled, and a `Location` kept after its world was unloaded throws the
`IllegalArgumentException` of Bukkit's `Location.getWorld()`. There is no `ThreadTag` for a region: `dispatch`
takes the global, async and entity tags only.

<Callout type="warn" title="The global region thread on Folia">
  On Paper the global region thread is the main thread, which owns every chunk and entity, so a `global` task may
  touch any world or entity. On Folia the global region thread owns no chunk and no entity: world and entity work
  in a `global` task, or in a task dispatched with `ThreadTag.GLOBAL`, must hop to the thread that owns its target,
  Paper's region scheduler for a location (from `0.4.4`, `region`) or `entity` for an entity. Use the global region
  thread for work bound to no place, such as the console, world time and weather. The same holds for
  `delayedGlobal` and `repeatingGlobal`.
</Callout>

`delayedAsync`, `repeatingAsync` and `repeatingAsyncTask` pass their delays and periods to Paper in whole
milliseconds. Paper throws `IllegalArgumentException` for a negative delay or a period below one millisecond.

`close()` cancels every task `repeatingAsync` and, from `0.4.4`, `repeatingAsyncTask`, `repeatingGlobal`,
`repeatingRegion` and `repeatingEntity` started through this instance. A run already in progress finishes,
and other one-shot tasks are left to Paper. From `0.2.0`, it also completes every future `dispatch` returned whose
task has not started, as described under [Dispatcher, ThreadTag and EntityThread](#dispatcher-threadtag-and-entitythread).
The instance stays usable after the call: a repeating task started later, or a dispatch made later, is handled by
the next `close()`.

### Entity work

`entity(Entity, Runnable, Runnable)` runs the task on the region thread that owns the entity, or the `retired`
callback when the task cannot run. At most one of the two runs.

- Paper runs `retired` when the entity retires (a player logs out, for example) before the task runs.
- When the entity is already removed, or the plugin is disabling, `retired` runs on the calling thread, so it must
  not assume a region thread.
- A task still scheduled when the plugin disables runs neither.
- `task` and `retired` are checked for `null` before anything is scheduled.

The two-argument `entity(Entity, Runnable)` drops the task when the entity is gone or the plugin is disabling.

```java
scheduler.entity(player,
    () -> Items.giveOrDrop(player, reward),
    () -> getLogger().info(player.getName() + " left before the reward was given"));
```

From `0.4.4`, `delayedEntity(Entity, Runnable, Runnable, Duration)` and
`repeatingEntity(Entity, Runnable, Runnable, Duration, Duration)` run the task on the same thread after a delay, or
after an initial delay and then every period, both counted in [ticks](#ticks). Each returns Paper's `ScheduledTask`.

- Paper runs `retired` when the entity retires before a delayed task runs, or while a repeating task repeats. The
  repeating task then stops.
- When the entity is already removed, or the plugin is disabling, the method returns `null` and `retired` has run
  on the calling thread.
- `retired` runs at most once. A task that is cancelled (through its handle, by `close()` for a repeating task, or
  by Paper when the plugin disables) stops without it.
- A repeating task whose own run removes the entity (it calls `Entity.remove()` or kicks the player, for example)
  also stops without `retired`: Paper stops the task after that run and runs no callback, so such a task does
  itself what `retired` would do.
- `task` and `retired` are checked for `null` before anything is scheduled.

```java
ScheduledTask countdown = scheduler.repeatingEntity(player,
    () -> showSecondsLeft(player),
    () -> abortTrade(player.getUniqueId()),
    Duration.ofSeconds(1), Duration.ofSeconds(1));
```

`countdown.cancel()` ends the countdown when either side changes the trade, and `countdown` is `null` when the
player is already gone, in which case `abortTrade` has run before the call returned.

### Dispatcher, ThreadTag and EntityThread

`Scheduler` implements `Dispatcher`, whose one method runs a `Supplier<T>` on a named thread and returns a
`CompletableFuture<T>`:

```java
<T> CompletableFuture<T> dispatch(ThreadTag tag, Supplier<T> task);
```

`ThreadTag` is a sealed interface with three kinds: `ThreadTag.GLOBAL`, `ThreadTag.ASYNC` and
`ThreadTag.entity(UUID)`, which names the region thread of the online player with that id. Their record types are
`ThreadTag.Global`, `ThreadTag.Async` and `ThreadTag.Entity`; two entity tags are equal when their ids are. On
Folia the thread `ThreadTag.GLOBAL` names owns no chunk and no entity, as under [Running work](#running-work).

The future completes with the task's result, or with what it threw, on the thread the tag names. When that thread
does not take the task, the task never runs and the future completes with:

- `RejectedExecutionException` for `GLOBAL` and `ASYNC` while the plugin is disabling,
- `EntityUnavailableException` for an entity tag when the player is offline, the task was retired, or the plugin is
  disabling. `EntityUnavailableException` is a `RuntimeException` whose `id()` returns the entity's `UUID`.

`EntityThread` wraps a `Dispatcher` for player work. `EntityThread.on(Dispatcher, Server)` dispatches each call with
`ThreadTag.entity` and looks the player up once the task runs:

```java
EntityThread players = EntityThread.on(scheduler, getServer());

players.call(playerId, Player::getLevel)
    .thenAccept(level -> getLogger().info("Level " + level));
```

<Callout type="warn" title="Do not wait on a server thread">
  Every tag queues the task, also when the caller is already on that thread. Calling `join()` or `get()` on the
  future from a server thread can block that thread for good. A `Dispatcher` other than `Scheduler` may also leave
  a future incomplete when the plugin disables before the task runs: bound it with `CompletableFuture.orTimeout`.
  When an `orTimeout` timeout fires, the future and every dependent stage added to it without an executor complete
  on the JDK's timeout thread.
</Callout>

From `0.2.0`, `Scheduler.close()` completes every future `dispatch` returned whose task has not started, as a
refused call does: with `RejectedExecutionException` for `GLOBAL` and `ASYNC`, and with
`EntityUnavailableException` for an entity tag, so an `EntityThread.call` over a `Scheduler` completes too. Such a
task never runs, also when Paper still runs what it accepted, and a task that has started completes its future
with its own result. A dispatch Paper accepts as the plugin stops being enabled is refused the same way. In `0.1`
the future of a task Paper accepted and dropped at disable stayed incomplete for good. Work that must settle is
still tracked in `PendingSettlements`.

`dispatch` with an entity tag looks the player up on the server from the calling thread. A refusal for an entity
tag is always an `EntityUnavailableException`, also when the cause is the plugin disabling.

From `0.4.5`, the test fixtures of `taffy-platform` hold [`FakeDispatcher`](/docs/modules/test#fakedispatcher), a
`Dispatcher` for tests that records each tag and holds, refuses or drops tasks:
`testImplementation(testFixtures(alaz.taffy.platform))`.

### Task failures

Paper's region, async and entity schedulers log a task that throws but fire no `ServerExceptionEvent`, so nothing
that watches the plugin's errors sees it. `Scheduler` therefore catches anything a task Paper runs throws (a
checked exception thrown without being declared included), reports it to its `ErrorReports`, then rethrows it
unchanged so Paper logs and handles it as usual. From `0.2.1`, the report is made through
`ErrorReports.reportUnhandled`, since nothing handles the error, and [taffy-metrics](/docs/modules/metrics) sends it
to FastStats with `handled` set to `false`. Before, it was made through `report` and sent as a handled error.

| Source | Tasks |
|---|---|
| `scheduler.global` | `global`, and from `0.4.4` `delayedGlobal` and `repeatingGlobal` |
| `scheduler.async` | `async`, `asyncExecutor`, `asyncOrRun`, `delayedAsync`, `repeatingAsync`, and from `0.4.4` `repeatingAsyncTask` |
| `scheduler.entity` | `entity` tasks and, from `0.4.4`, `delayedEntity` and `repeatingEntity` tasks, and `retired` callbacks Paper runs |
| `scheduler.region` | From `0.4.4`: `region`, `delayedRegion` and `repeatingRegion` |

Each throw is reported once, so a repeating task that throws on several runs is reported for each run. A task or
`retired` callback run on the calling thread is not reported, and what it throws reaches the caller. `dispatch`
reports nothing: its future carries what the task threw.

### While the plugin disables

The scheduler never waits for work and never runs leftover work on its own. Once the plugin is disabling:

- `global`, `async`, `delayedAsync` and `repeatingAsync` return `false` and run nothing,
- the methods that return a `ScheduledTask` return `null` and run nothing, and `delayedEntity` and `repeatingEntity`
  first run `retired` on the calling thread,
- `entity(Entity, Runnable, Runnable)` runs `retired` on the calling thread,
- `dispatch` completes exceptionally,
- `asyncExecutor()` rejects,
- `asyncOrRun` runs the task on the calling thread.

The same holds before the plugin is enabled, in its constructor or `onLoad`: every method above refuses whenever
`Plugin.isEnabled()` is `false`, so an `asyncOrRun` call made before `onEnable` runs the task on the calling
thread.

A task Paper accepted but has not run when the plugin disables may never run: an entity task then runs neither its
task nor its `retired` callback, and a delayed task is cancelled. From `0.2.0`, `close()` completes the future of
a `dispatch` whose task has not started. Work that must settle is tracked in `PendingSettlements` before it is
scheduled.

## ErrorReports

`ErrorReports` is where a plugin reports an error that nothing watching the plugin's errors would otherwise see:
an error handled inside the plugin, or a scheduler task that threw. The plugin creates one instance and passes it to
the classes that report (`Scheduler`, `Shutdown`, and the hooks, storage, gui, metrics and comficonf modules).

| Method | Behaviour |
|---|---|
| `report(String source, Throwable error)` | Reports a handled error under a short stable source key such as `shutdown`. Never throws: anything the target throws, an `Error` included, is discarded. |
| `reportUnhandled(String source, Throwable error)` | From `0.2.1`. Reports an error the caller does not deal with and rethrows or lets escape, as `Scheduler` does for a task that throws. Held, dropped and delivered as `report` does it. Never throws. |
| `install(BiConsumer<String, Throwable> handle)` | Routes later reports, handled and unhandled alike, to `handle`, on the thread that reported each one, or nowhere when `handle` is `null`. |
| `install(BiConsumer<String, Throwable> handle, BiConsumer<String, Throwable> unhandled)` | From `0.2.1`. Routes later reports made through `report` to `handle` and those made through `reportUnhandled` to `unhandled`. Throws `NullPointerException` when either is `null`. |
| `clear()` | Drops every later report until the next `install`. |

```java
errors.install((source, error) -> getLogger().log(Level.WARNING, "Handled error in " + source, error));
errors.report("import", exception);
```

The sink has one target. Each `install` replaces the one before it; to send each report to two places, install one
target that passes it to both.

Until `install` or `clear` first runs, reports are held: the first one of each source, at most 16 in all. The first
`install` of a non-null target delivers them, in order, on the installing thread, each to the handler that takes
it. A first `clear()` or
`install(null)` discards them, and a plugin that calls neither keeps them for its lifetime. After the first
`install` or `clear`, a report made while no target is installed is dropped.

<Callout type="info" title="With taffy-metrics">
  `MetricsBuilder.start()` of `taffy-metrics` installs its FastStats error tracking target when FastStats error
  tracking is available, and clears the sink otherwise. Either way it replaces a target the plugin installed
  earlier, and the held reports reach FastStats only when nothing was installed or cleared before the call. A
  plugin using it installs no target of its own. See [taffy-metrics](/docs/modules/metrics).
</Callout>

All methods are thread-safe.

## Shutdown

Three classes cover the disable side. Each one solves a different problem: a step that throws, async tasks still
running, and work no callback will ever finish.

### Shutdown.closeQuietly

```java
public static void closeQuietly(String what, Shutdown.ShutdownStep step, Logger logger, ErrorReports errors)
```

Runs one step and catches anything it throws, an `Error` included, so the steps after it still run. The failure is
logged as one warning that reads "Failed to `what` during shutdown" and reported to `errors` under the source
`shutdown`. From `0.2.0`, the warning carries the failure as its thrown, so the log shows the stack trace; in `0.1`
the failure's `toString()` followed the message and no trace was logged. An `InterruptedException` sets the
thread's interrupt flag again.
`ShutdownStep` is a functional interface whose `run()` may throw `Exception`. `what` completes the phrase
"Failed to", for example `close storage`.

### TaskGate

`TaskGate` admits async tasks until the plugin disables. A task calls `enter()` before it does any work and returns
at once when it gets `false`; an admitted task calls `exit()` in a `finally`.

```java
boolean accepted = scheduler.async(() -> {
    if (!gate.enter()) {
        return;
    }
    try {
        processOrders();
    } finally {
        gate.exit();
    }
});
if (!accepted) {
    getLogger().info("The orders are not processed: the plugin is disabling");
}
```

Call `exit()` exactly once for each `enter()` that returned `true`. A call with no task admitted does nothing, and
an unmatched call while tasks run releases one of them, so `close` can return before that task has exited.

`close(Duration wait)` refuses every later entry, then waits up to `wait` for admitted tasks to exit. It returns how
many are still running, `0` once all have exited. An interrupt ends the wait early and stays set. A result above
`0` means a task may still track work after the call.

### PendingSettlements

A task still scheduled on an entity when the plugin disables runs neither its task nor its `retired` callback, and
a delayed task is cancelled. `PendingSettlements` tracks such work so it still settles.

`track(Runnable settlement)` returns a `PendingSettlements.Entry`. Each entry is started exactly once:
`Entry.start()` returns `true` for one caller only, which then does its side of the work. Track before scheduling,
so the work is pending before any callback can start it.

```java
PendingSettlements.Entry entry = settlements.track(() -> refund(buyerId, price));
scheduler.entity(buyer,
    () -> {
        if (entry.start()) {
            Items.giveOrDrop(buyer, purchase);
        }
    },
    () -> {
        if (entry.start()) {
            refund(buyerId, price);
        }
    });
```

`settleAll(Consumer<Throwable> onFailure)` starts every pending entry, runs its settlement on the calling thread and
returns how many ran. A settlement that throws is passed to `onFailure`, and what `onFailure` throws is discarded,
so the rest still run. An entry tracked after `settleAll` began may be left pending, so a caller whose scheduling
call is refused starts the entry itself.

### Disable order

The shutdown classes assume this order, with each step run through `Shutdown.closeQuietly`:

<Steps>
  <Step>`ComfiConfConnection.close` of [taffy-comficonf](/docs/modules/comficonf), which unregisters the plugin's settings from the bridge.</Step>
  <Step>`PlaceholderRegistration.unregister` of [taffy-hooks](/docs/modules/hooks), which unregisters the plugin's placeholders.</Step>
  <Step>`Menus.shutdown` of [taffy-gui](/docs/modules/gui), which ends every prompt and then closes the open menus of the players the disabling thread owns.</Step>
  <Step>`HologramProvider.close` of [taffy-hooks](/docs/modules/hooks#holograms), which removes the holograms the plugin placed and stops the provider. It runs on the thread that disables the plugin; on Folia, while the server stops, that is Folia's shutdown thread and not the global region thread.</Step>
  <Step>`Scheduler.close()`, which stops the repeating tasks and, from `0.2.0`, completes the futures of the dispatches that have not started.</Step>
  <Step>`TaskGate.close`, which refuses new async tasks and waits for the admitted ones.</Step>
  <Step>`PendingSettlements.settleAll`, which settles the work no callback started.</Step>
  <Step>The close of whatever the settlements write to, such as [storage](/docs/modules/storage).</Step>
  <Step>`DiscordWebhook.close()`, which waits for the posts still in flight, from `0.2.0` for at most 5 seconds.</Step>
  <Step>`Metrics.shutdown` of [taffy-metrics](/docs/modules/metrics), which stops reporting and makes the final send, so the reports the steps before it raised are sent.</Step>
</Steps>

For a plugin that uses only this module:

```java title="ShopPlugin.java"
@Override
public void onDisable() {
    Logger log = getLogger();
    Shutdown.closeQuietly("stop repeating tasks", () -> scheduler.close(), log, errors);
    Shutdown.closeQuietly("wait for async tasks", () -> gate.close(Duration.ofSeconds(5)), log, errors);
    Shutdown.closeQuietly("settle pending work",
        () -> settlements.settleAll(failure -> errors.report("settlement", failure)), log, errors);
    Shutdown.closeQuietly("close the webhook client", () -> webhook.close(), log, errors);
}
```

## Text

`Text` renders MiniMessage strings (RGB, gradients, PlaceholderAPI and MiniPlaceholders) into Adventure
`Component`s. `new Text(Logger)` detects PlaceholderAPI and MiniPlaceholders once, by class presence; when a plugin
is absent, its pass is skipped.

| Method | Returns |
|---|---|
| `render(String input)` | MiniMessage with MiniPlaceholders' global tags, no PlaceholderAPI |
| `render(String input, Player viewer)` | MiniMessage with MiniPlaceholders' global and audience tags, and PlaceholderAPI placeholders filled in against the viewer (when non-null and present) |
| `render(String template, Player viewer, TagResolver... values)` | the same, with values filled in |
| `render(List<String> lines, Player viewer)` | each line as `render(String, Player)` |
| `send(Player player, String miniMessage)` | renders with the player as viewer and sends it |
| `resolve(String input, Player viewer)` | PlaceholderAPI only, no MiniMessage |
| `plain(String input, Player viewer)` | the rendered text flattened to plain text |
| `render(String input, OfflinePlayer player)` | from `0.4.7`, as `render(String, Player)`, with PlaceholderAPI asked for a player who may be offline |
| `render(String template, OfflinePlayer player, TagResolver... values)` | from `0.4.7`, the same, with values filled in |
| `resolve(String input, OfflinePlayer player)` | from `0.4.7`, PlaceholderAPI only, for a player who may be offline |
| `plain(String input, OfflinePlayer player)` | from `0.4.7`, the offline render flattened to plain text |
| `renderGlobal(String input)` | from `0.4.7`, as `render(String, Player)`, with PlaceholderAPI asked for no player |
| `renderGlobal(String template, TagResolver... values)` | from `0.4.7`, the same, with values filled in |
| `resolveGlobal(String input)` | from `0.4.7`, PlaceholderAPI only, for no player |
| `plainGlobal(String input)` | from `0.4.7`, the global render flattened to plain text |
| `withPlaceholderFormatting()` | from `0.2.0`, a `Text` that also parses formatting tags in placeholder output |

The viewer and player parameters accept `null`, which skips PlaceholderAPI.

From `0.4.7`, `Text` also asks PlaceholderAPI for an `OfflinePlayer` and for no player:

- The `OfflinePlayer` methods are for text about a player who may be offline, such as a line in a leaderboard or a
  mail. Which placeholders give a value is up to each expansion: one that needs an online player returns nothing,
  and its placeholder stays as written.
- The `Global` methods are for text without a player, such as a console line or a broadcast template. Each
  expansion is asked with a `null` player, so `%server_online%` is filled in and `%player_name%` stays as written.
  `render(String input)` is unchanged and asks PlaceholderAPI for nothing.
- Both insert what a placeholder returns as text, as [placeholder output](#placeholder-output) describes.
- MiniPlaceholders' audience tags are filled in only for a `Player`, so an `OfflinePlayer` who is not one and no
  player get its global tags alone. An `OfflinePlayer` that is a `Player` renders as `render(String, Player)` does.
- A call that passes a literal `null` as the second argument, as `text.render(input, null)` does, still picks the
  `Player` method.

```java
Text text = new Text(getLogger());

player.sendMessage(text.render("<gradient:gold:yellow>Welcome, %player_name%!", player));

player.sendMessage(text.render(
    "<green>{buyer}</green> bought <item> for <price>",
    player,
    Placeholder.unparsed("buyer", buyer.getName()),
    Placeholder.component("item", purchase.displayName()),
    Placeholder.unparsed("price", "250")));
```

### Placeholder output

From `0.2.0`, what a PlaceholderAPI placeholder returns is inserted as text and is never parsed as MiniMessage. A
nickname, clan tag or item name a player set to `<click:run_command:'/pay Mallory 100000'>Click me`, or to the
`<name>` of a supplied value, is shown exactly as written. In `0.1` that output was parsed with the template, so
such a value could add a click or hover event to a message.

- Each run of text between two `%` signs is given to PlaceholderAPI on its own. A run PlaceholderAPI returns
  unchanged, such as the middle of `50% off, 20% more`, stays as written.
- Section-sign colour and format codes in the output still apply, to that output only. A placeholder that returns
  `§c` and nothing else no longer colours the template after it: write the colour in the template.
- A placeholder inside a tag argument MiniMessage does not parse, such as the value of
  `<click:run_command:'/msg %player_name%'>` or an insertion, is not filled in and stays as written, `%` signs
  included: that click runs `/msg %player_name%`. So does one after an escaping backslash. One inside hover text is
  filled in.
- A placeholder written as an unquoted tag argument, as in `<color:%team_color%>` or `<gradient:%a%:%b%>`, or
  inside the URL of `<click:open_url:...>`, leaves a tag MiniMessage cannot read, which is then shown as text.
- For a click or a colour that needs a placeholder's value, build that part in code and supply it as a value, as in
  `text.render("<msg>Reply</msg>", player, Placeholder.styling("msg", ClickEvent.runCommand("/msg " + name)))`.
  `resolve` gives the value where it comes from PlaceholderAPI.
- Tag names that start with `taffy_papi_` are reserved for the render.
- `resolve` is unchanged: it returns what PlaceholderAPI gave, tags included. Supply its result as
  `Placeholder.unparsed` unless every tag in it is meant to be parsed.

`withPlaceholderFormatting()` returns a `Text` that parses a restricted set of tags in placeholder output: the
colour tags (`<red>`, `<#ff8800>`, `<color:...>`), the decoration tags (`<bold>`, `<!italic>` and the like),
`<gradient>`, `<rainbow>` and `<reset>`. Every other tag, `<click>`, `<hover>` and `<name>` included, is still
shown as written, and the formatting applies to that output only. Nothing turns the full `0.1` parse back on. The
instance it is called on is not changed, and the two share their integrations and log, so one plugin keeps both:

```java
Text text = new Text(getLogger());
Text ownerText = text.withPlaceholderFormatting();

// %luckperms_prefix% returns "<gradient:gold:yellow>Admin</gradient>": shown as written here,
player.sendMessage(text.render("%luckperms_prefix% %player_name% joined", player));
// and as a gradient here.
meta.displayName(ownerText.render("%luckperms_prefix% <white>voucher", player));
```

### Values in a template

- A value is written as `<name>`, or as `{name}`, which reads as `<name>` for every name the call supplies. A
  `{name}` nothing supplies stays as written. Only names of lower-case letters, digits, `_` and `-` are rewritten.
- From `0.4.8`, `text.withBracedNamesIgnoringCase()` returns a `Text` that also reads a `{name}` written with
  upper-case letters. The name is matched against the supplied values in lower case, so `{crateName}` reads as
  `<cratename>` when a value named `cratename` is supplied; a value's own name is always lower case, as a
  MiniMessage tag name is. A `{name}` nothing supplies still stays as written. The instance it is called on is
  not changed and renders as before. A supplied value is inserted as it is with either instance: a `{name}` or a
  tag inside `Placeholder.unparsed` text is not read again.
- The order is: `{name}` rewrite, PlaceholderAPI on the template, then MiniMessage with the values. PlaceholderAPI
  never sees a supplied value; a value with placeholders of its own goes through `resolve` first, and is then
  supplied as `Placeholder.unparsed` unless the tags its placeholders return are meant to be parsed. A supplied
  `{name}` inside a `%...%` placeholder is rewritten to `<name>` as well, so that placeholder does not receive the
  value.
- `Placeholder.unparsed` and `Placeholder.component` insert player-typed text as it is. `Placeholder.parsed` is for a
  value that carries MiniMessage on purpose.
- A supplied value wins over a MiniPlaceholders tag of the same name.
- A supplied `{name}` inside a tag argument MiniMessage does not parse, such as a click value, becomes the literal
  text `<name>`. Written as an unquoted tag argument, as in `<hover:show_text:{name}>`, it leaves a tag MiniMessage
  cannot read.

### Legacy codes

MiniMessage refuses a section sign followed by a legacy code character. Every render converts such codes to tags,
as `LegacyText.sectionToMiniMessage` does: in the input and in each `Placeholder.parsed` value. A converted code
such as `<red>` in a parsed value is an open tag, so it colours the rest of the template after the value, as the
legacy code would. From `0.2.0`, the codes in what PlaceholderAPI returned apply to that output only, as
[Placeholder output](#placeholder-output) describes; in `0.1` they were converted with the input and coloured the
rest of the template too. Values supplied
as `Placeholder.unparsed` or `Placeholder.component` are inserted unchanged, section sign included. `render(String, Player, TagResolver...)` throws MiniMessage's
`ParsingException` when the text still holds a section sign followed by a code character once the values are in.

### Threads and failures

An instance is thread-safe and may be shared. PlaceholderAPI expansions and MiniPlaceholders audience tags run on
the calling thread and read the viewer, so a call that passes a viewer belongs on the thread that owns that player.
From `0.4.7`, a call with an `OfflinePlayer` or a `Global` call runs the PlaceholderAPI expansions on the calling
thread as well, with no player to own it: whether an expansion may be asked off the server thread is up to that
expansion.

A PlaceholderAPI pass that throws, or a MiniPlaceholders resolver that cannot be built or throws during parsing, is
skipped and logged through `ThrowLog` under the sources `placeholderapi` and `miniplaceholders`. Nothing is
reported to `ErrorReports`. A single MiniPlaceholders tag that throws an exception is left as written and is not
logged. From `0.1.1`, a tag that throws a `LinkageError` such as `NoSuchMethodError`, as an expansion built against
another API does, skips the whole MiniPlaceholders pass and is logged; in `0.1.0` the error reaches the caller.

## Messages

`Messages` serves player messages from `lang/<locale>.yml` files in the plugin's data folder. The plugin bundles
its English file; Taffy ships none.

```yaml title="src/main/resources/lang/en.yml"
prefix: "<gray>[<gold>Shop</gold>]</gray> "
shop:
  bought: "{prefix}<green>You bought <item> for {price}."
  help:
    - "<gold>/shop buy [item]"
    - "<gold>/shop sell [item]"
```

```java
Messages messages = Messages.load(getDataFolder().toPath(), () -> getResource("lang/en.yml"), getLogger());

player.sendMessage(messages.render(text, player, "shop.bought",
    Placeholder.component("item", purchase.displayName()),
    Placeholder.unparsed("price", "250")));
```

`load(Path dataFolder, Supplier<InputStream> bundled, Logger logger)` uses English as the default locale with
per-player languages on. `load(Path, Supplier<InputStream>, Logger, String defaultLocale, boolean perPlayer)` sets
both. Loading:

1. writes the bundled file to `lang/en.yml` when that file is absent,
2. reads every `.yml` file in `lang`, skipping an unreadable file with a warning and listing the keys each file
   lacks in one warning per file. From `0.4.14`, the warning leaves out two shapes of a
   [delivery section](#delivery-in-the-lang-file): a message the bundled file has as a value and the file has as a
   delivery section, and the entries of a bundled delivery section whose message the file has as a value. Every
   other entry of a bundled delivery section is a key like any other and is listed when the file lacks it. From `0.2.0`, two files whose names read as one locale, such as `pt-BR.yml` and
   `pt_br.yml`, give a warning that names both and the one used (the one the folder listing gives last); in `0.1`
   one replaced the other without a warning. A file with bytes that are not UTF-8 is skipped as a whole; from
   `0.4.0` its warning names the line, `lang/<name> is not saved as UTF-8 (the first byte that is not UTF-8 is on
   line <n>), so its messages are not used.`,
3. falls back to the bundled English text when the folder cannot be written or listed, with a warning,
4. warns when a default locale other than `en` has no file, and uses the bundled English text in its place.

`bundled` opens a new stream on each call. `load` throws `IllegalStateException` when the bundled file is missing,
is not valid UTF-8 or is not valid YAML.

From `0.4.0`, `Messages.loadLenient(Path, Supplier<InputStream>, Logger, String defaultLocale, boolean perPlayer)`
loads the same way, except that a language file an owner saved in a legacy code page such as Windows-1252 is not
skipped. Each byte sequence that is not UTF-8 is read as the replacement character U+FFFD, so the keys of the file
stay in use and only the characters saved in another encoding are lost, as with Bukkit's
`YamlConfiguration.loadConfiguration`. One warning per file, on the load and on each `reload()`, names the file and
the first line with a replaced character:

```text
lang/de.yml is not saved as UTF-8, so each byte that is not UTF-8 is read as the replacement character U+FFFD; the first is on line 3. Save the file as UTF-8.
```

A file that is not valid YAML once it is read that way is still skipped, and the bundled file is still read
strictly. Strict reading stays the default: `load` skips such a file.

### Another folder

From `0.4.8`, `load(Path dataFolder, String folder, Supplier<InputStream> bundled, Logger logger, String
defaultLocale, boolean perPlayer)` reads the files from `dataFolder/<folder>` in place of `dataFolder/lang`, for a
plugin whose owners already keep their files in a folder such as `locales` or `messages`:

```java
Messages messages = Messages.load(
    getDataFolder().toPath(), "locales", () -> getResource("locales/en.yml"), getLogger(), "en", true);
```

The bundled English file is written to `<folder>/en.yml` when that file is absent, and every warning names
`<folder>`. The folder is one path segment: a blank one, `.`, or one that holds `/`, `\`, `:` or `..` throws
`IllegalArgumentException`. The other loads keep `lang`.

### Bundled languages

From `0.4.8`, a plugin that bundles more languages than English names them at the load:

```java
Messages messages = Messages.load(
    getDataFolder().toPath(), "lang", List.of("de", "pt_BR"),
    code -> getResource("lang/" + code + ".yml"), getLogger(), language, true);
```

`bundled` opens the bundled file of a code, a new stream on each call. It is asked for `en` and for each code as
the list writes it; a code that reads as `en` is ignored. This load differs from the others in three ways:

- The load and each `reload()` write every bundled file whose language has no file in the folder, as
  `<folder>/<code>.yml` with the code as the list writes it. A file whose name reads as the same locale counts as
  the file of that language, so an owner's `pt-BR.yml` or `PT_br.yml` keeps the bundled `pt_BR` from being written
  beside it.
- At each step of the [lookup](#lookup), a key the owner's file of that locale lacks is taken from the bundled file
  of the same code, before the next step. For `pt_br` the order is the owner's `pt_br.yml`, the bundled `pt_br`,
  the owner's `pt.yml`, the bundled `pt`, the default locale's file, its bundled file, then the bundled English
  text. So a `de.yml` an owner kept from an older release of the plugin serves a key added since in German. A
  bundled language is served when its file is gone as well, and `loadedLanguages()` lists it.
- The warning about the keys a file lacks lists only the keys that are then shown in another language, and is
  logged once for each file and list of keys while the server runs, not on each reload:

```text
lang/fr.yml lacks shop.sold, shop.help; those messages are shown in another language.
```

A bundled file that is missing, is not valid UTF-8 or is not valid YAML throws `IllegalStateException`. Two codes
that read as one locale, such as `pt_BR` and `pt-br`, and a code that is not one path segment throw
`IllegalArgumentException`.

### New keys in an owner's file

Loading never changes a file an owner has: a key added by a newer release of the plugin is served from the bundled
text. From `0.4.8`, `addMissingKeys()` writes those keys into the owner's `en.yml`, when the plugin calls it:

```java
if (getConfig().getBoolean("add-new-messages", true)) {
    List<String> added = messages.addMissingKeys();
}
```

- Each key of the bundled English file that `en.yml` lacks is appended at the end of the file, with its bundled
  text, in the order of the bundled file. The returned list holds the keys that were added.
- The owner's bytes stay as they are: lines, comments, order, encoding and byte order mark are kept, and the added
  lines end as the file's lines do (`\r\n` in a file that has one). A key is added in its dotted form, such as
  `shop.sold: "..."`, and a list as a YAML list.
- The new content is written to `en.yml.tmp` beside the file and moved over it in one step. The file is then read
  again; no other file is read and no load warning is repeated.
- `addMissingKeys(String locale)` does the same for the file of one language, from that language's own bundled
  file, after a load that names [bundled languages](#bundled-languages). It adds nothing for a language the plugin
  bundles no file of, so a file is never given English text.
- Nothing is written when the file lacks no key, is absent or was removed since it was read. A key the file writes
  with no value, as `key:` or `key: ~`, counts as one the file has and is not added. A file that is not valid YAML
  or is not saved as UTF-8 is left as it is, also after `loadLenient`, with a warning:

```text
lang/en.yml is not valid YAML saved as UTF-8, so no key was added to it.
```

- From `0.4.14`, two shapes add nothing: the entries of a bundled [delivery section](#delivery-in-the-lang-file) whose message the file has as a
  plain value, and a message the bundled file has as a value and the file has as a delivery section. On `0.4.13`
  a file of either shape made `addMissingKeys` change nothing, with the warning below about keys that cannot be
  added at its end.
- From `0.4.14`, each entry of a bundled delivery section is a key like any other:
  the entries the file lacks are added, and each is in the returned list as `pay.sent.delivery.actionbar`. A
  section the file has in part is completed key by key in the dotted form, as on `0.4.13`. A section that has a
  `chat`, `actionbar`, `times` or `sound` entry, in a file that writes no key at or under that `delivery` section,
  is written as one nested section under the dotted key, shown below. An owner who wants an entry gone leaves it
  empty (`sound: ""`) and does not remove the line, which would be added again.

```yaml
pay.sent.delivery:
  actionbar: "<green>Sent <amount> to <target>"
  sound: "entity.experience_orb.pickup 1 1.4"
```

- A file whose end does not take the keys is left as it is with the warning `lang/en.yml was not changed, because
  <keys> cannot be added at its end.`, which lists every key the file lacks and is logged on each call. That is a
  file that holds text under a key the bundled file uses as a section, one that ends inside a block scalar (`|` or
  `>`) with no line break after its last line, one that ends with the document end marker `...`, and one that
  writes its keys as a flow mapping in braces. A file that cannot be written is reported as
  `Could not add keys to lang/en.yml: <reason>.`

### Lookup

A key resolves through, in order: the exact locale's file (`pt_br`), its language's file (`pt`), the default
locale's file, then the bundled English text. The first two apply only when per-player languages are on and a
locale is given. File names and locales are matched in lower case with `-` read as `_`, so `pt-BR` finds
`pt_br.yml`. `Messages.normalizeLocale(String)` gives that form, with `null` or blank read as `en`.

A key no file has renders as the visible marker `<red>missing:key` and never throws.

### Methods

| Method | Behaviour |
|---|---|
| `render(Locale, String key, TagResolver...)` | Renders without PlaceholderAPI or MiniPlaceholders. |
| `render(Text, Player viewer, String key, TagResolver...)` | Renders in the viewer's language through `Text`, so PlaceholderAPI and MiniPlaceholders apply. |
| `renderTemplate(Text, Player viewer, String template, TagResolver...)` | Renders a template that is not a key, with the viewer's prefix. |
| `send(Text, CommandSender, String key, TagResolver...)` | From `0.4.8`. Renders as `render(Text, Player, ...)` does and sends one chat message. From `0.4.14`, a key written as a delivery section is shown as [Delivery in the lang file](#delivery-in-the-lang-file) describes. |
| `sendActionBar(Text, Player, String key, TagResolver...)` | From `0.4.8`. Renders the same way and shows an action bar. |
| `showTitle(Text, Player, String titleKey, String subtitleKey, Title.Times, TagResolver...)` | From `0.4.8`. Shows a title from two keys with the given times. |
| `showTitle(Text, Player, String key, TagResolver...)` | From `0.4.8`. Shows a title written as one lang entry, times included. |
| `withChatPrefix(Supplier<String>)` | From `0.4.8`. A `Messages` over the same files whose `send` puts a prefix from the plugin in front. |
| `withBracedNamesIgnoringCase()` | From `0.4.8`. A `Messages` over the same files that also fills `{crateName}` from a value named `cratename`. |
| `addMissingKeys()`, `addMissingKeys(String locale)` | From `0.4.8`. Appends the bundled keys an owner's file lacks, as [New keys in an owner's file](#new-keys-in-an-owners-file) describes. |
| `lines(Locale, String key, TagResolver...)` | One component per line; a tag opened on one line does not carry into the next. |
| `template(Locale, String key)` | The raw template, lines joined by a newline. |
| `has(Locale, String key)` | Whether the key resolves for that locale. |
| `reload()` | Reads the folder again, with the same warnings as the load, and writes `lang/en.yml` again if it is missing. The one warning that is not repeated is the one a load that names [bundled languages](#bundled-languages) logs once. The bundled text is not read again. |
| `loadedLanguages()` | The loaded locale codes. |
| `defaultLocale()`, `perPlayer()` | The values given at load. |

A `null` locale or viewer is for the console and other output without a viewer. `Messages.FOLDER` is `lang`, the
folder of every load that names no other one, and `Messages.FALLBACK` is `en`.

- A YAML list is kept as its lines; a message of several lines renders joined by a newline, or one component per
  line through `lines`.
- The prefix is the template under the key `prefix`. It is never put in front of a message: it appears only where a
  template writes `<prefix>` or `{prefix}`, and is empty when no file has the key. A value named `prefix` in the
  call replaces it.
- With `render(Text, Player, ...)`, PlaceholderAPI runs on the template and the prefix, never on the values. From
  `0.2.0`, what a placeholder returns is inserted as text in both, as [Placeholder output](#placeholder-output)
  describes; pass `text.withPlaceholderFormatting()` to parse formatting tags in it.

Methods without a viewer may be called from any thread; those with one follow the thread rule of `Text`. A render
during `reload()` sees either all the old files or all the new ones.

### Sending

From `0.4.8`, `Messages` sends a message by its key. Each send renders as `render(Text, Player, String key,
TagResolver...)` does, so PlaceholderAPI and MiniPlaceholders apply for a player, and belongs on the thread that
owns the player.

```java
messages.send(text, sender, "shop.bought", Placeholder.unparsed("price", "250"));
messages.sendActionBar(text, player, "voucher.soulbound");
messages.showTitle(text, player, "crate.won.title", "crate.won.subtitle",
    Title.Times.times(Ticks.duration(10), Ticks.duration(60), Ticks.duration(10)),
    Placeholder.component("prize", prize.displayName()));
```

- `send` takes any `CommandSender`. A player is the viewer; the console and every other sender get the render
  without a viewer. A message of several lines is sent as one chat message, its lines joined by a newline.
- An empty message, one whose lines joined by a newline are an empty text (`""`, a list of no lines `[]` or a
  list of one empty line `[""]`), is not sent, so an owner can switch a message off. An action bar of an empty message is not shown either, and the bar the player
  sees stays. A title is not shown when its title and subtitle are both empty.
- A key no file has sends the `<red>missing:key` marker.
- A `null` `subtitleKey` gives an empty subtitle.

`showTitle(Text, Player, String key, TagResolver...)` shows a title an owner writes as one entry, with its times as
whole numbers of ticks:

```yaml
crate:
  won:
    title: "<gold>You won"
    subtitle: "<gray>{prize}"
    fadeIn: 10
    stay: 60
    fadeOut: 10
```

```java
messages.showTitle(text, player, "crate.won", Placeholder.component("prize", prize.displayName()));
```

A time that no file has, that is not a whole number of at least 0, or that is too long to count in milliseconds,
is the one of Adventure's `Title.DEFAULT_TIMES` (10, 70 and 20 ticks). A `subtitle` no file has gives an empty subtitle, and a `title` no file
has shows the missing-key marker.

### Delivery in the lang file

From `0.4.14`, an owner chooses in the lang file where `send` shows a message. A message is written either as a
value, which is a chat message as before, or as a section named `delivery` under its key:

```yaml title="lang/en.yml"
pay:
  sent:
    delivery:
      actionbar: "<green>Sent <amount> to <target>"
      sound: "entity.experience_orb.pickup 1 1.4"
  received:
    delivery:
      chat: "{prefix}<green>You received <amount>."
      title: "<gold>+<amount>"
      subtitle: "<gray>from <sender>"
      times: "5 40 15"
```

```java
messages.send(text, sender, "pay.sent",
    Placeholder.unparsed("amount", "250"), Placeholder.unparsed("target", target.getName()));
```

The plugin's call is the one it already makes, so moving a message from chat to the action bar needs no code change
and no new release of the plugin.

| Entry | Value | A player gets |
|---|---|---|
| `chat` | A template, or a list of lines | One chat message, with the prefix of [`withChatPrefix`](#a-prefix-from-the-plugin). |
| `actionbar` | A template | An action bar. |
| `title`, `subtitle` | A template each | One title. It is shown when either text is not empty. |
| `times` | Three whole numbers of ticks: fade in, stay and fade out, as `"10 70 20"` or as a list | The times of the title. Absent, they are Adventure's `Title.DEFAULT_TIMES`. |
| `sound` | A sound in the form [`Sounds`](#colors-and-sounds) reads, `key [volume] [pitch]` | The sound, through `Sounds.play`. |

- Each text is rendered as `send` renders a message, with the values of the call, PlaceholderAPI and
  MiniPlaceholders. An entry that is absent or an empty message is left out, so `chat: ""` beside an `actionbar`
  sends no chat message.
- A sender that is not a player, such as the console, gets one chat message and nothing else: the `chat` entry, or
  in a section without one the `actionbar` entry, or without that one the `title` and `subtitle` joined by a
  newline. A section with only a `sound` sends such a sender nothing.
- The [lookup](#lookup) picks the first file that has the message in either form. An owner's `en.yml` with
  `pay.sent` as a delivery section is used before the bundled value, and an owner's value is used before a bundled
  delivery section. After a load that names [bundled languages](#bundled-languages), the owner's form of a message
  replaces the bundled one of that language as a whole: no entry of the bundled section is mixed in.
- `send` belongs on the thread that owns the player, on Folia the thread of the player's region. For a sender that
  is not a player it may be called from any thread.

Only `send` reads a delivery section. For `render`, `lines`, `has`, `template`, `sendActionBar` and `showTitle` the
file is read as on `0.4.13`: the entries are the keys `pay.sent.delivery.actionbar` and so on, and the key
`pay.sent` is one that file does not have, so those methods take it from the next file of the lookup or give the
missing-key marker. A plugin that also renders a key itself keeps that key a value in its bundled file.

What is a delivery section and what is not:

- A section named `delivery` under a key, in which every entry is one of the six names and has a value, is one.
- A `delivery` section with any other entry, with an entry that has no value (`title:`), or with a section inside
  it, is not: a menu item named `delivery`
  with a `name` and a `lore` (`gui.confirm.delivery.name`) stays a plain section, as does a `gui.<id>` section
  with a `title` child, which has no `delivery` section at all.
- A key named `delivery` at the top of a file, with or without children, is not, and neither is a `delivery` key
  that holds a value (`gui.confirm.listing.delivery: "..."`).
- A lang file of `0.4.13` or earlier that holds a `delivery` section made only of those six names, such as a title
  a plugin shows with `showTitle(text, player, "mail.delivery")`, reads as a delivery section of the key above it
  for `send` alone, and `send` of that parent key showed the missing-key marker until now. Every other method
  reads it as before, the load and `reload()` log what they logged on `0.4.13`, with each entry the file lacks in
  the warning about missing keys, and `addMissingKeys` adds each missing entry as its own dotted key.

A bad entry never throws at a send, and the load and `reload()` log nothing about a delivery section. The first
`send` that reads the section after the load or a `reload()` logs a warning that names the file and the key:

```text
lang/en.yml has the times '5 forty 15' at pay.received.delivery.times, which is not three whole numbers of ticks (fade in, stay and fade out, such as 10 70 20), so the title of pay.received has the default times.
lang/en.yml has the sound 'level!up' at pay.sent.delivery.sound, whose key is not a valid sound key, so pay.sent plays no sound.
lang/en.yml has a list of 2 entries at pay.sent.delivery.sound, which takes one sound, so pay.sent plays no sound.
lang/en.yml has pay.sent.delivery.actionbr in the delivery section of pay.sent, which holds only chat, actionbar, title, subtitle, times and sound, so pay.sent is not read from this file.
lang/en.yml has pay.sent.delivery.title (no value) in the delivery section of pay.sent, which holds only chat, actionbar, title, subtitle, times and sound, so pay.sent is not read from this file.
```

The last two are logged by a `send` of the key, once after the load or a `reload()` for each file of the lookup
the send passes, and the message is then taken from the next file of the lookup. A warning about the bundled text
names it as `The bundled en.yml` and is logged once after the load. A lang file whose `delivery` sections no
`send` reads logs none of these. A sound key that parses and names no sound plays nothing and is not reported:
`Sounds.isKnown` needs a running server.

### A prefix from the plugin

The `prefix` key of the lang files appears only where a template writes it. From `0.4.8`,
`withChatPrefix(Supplier<String>)` returns a `Messages` whose `send` also puts a prefix the plugin supplies, such
as a `config.yml` setting, in front of each chat message:

```java
Messages messages = Messages.load(getDataFolder().toPath(), () -> getResource("lang/en.yml"), getLogger())
    .withChatPrefix(() -> getConfig().getString("prefix"));
```

- The prefix is a MiniMessage template, read on each send, so a config reload applies at once. `null` or an empty
  text means no prefix.
- It is written in front of the message's template and rendered with it: its PlaceholderAPI placeholders are filled
  in for a player, and a tag it leaves open, such as `<gray>`, applies to the message.
- Only `send` adds it. `render`, `lines`, `sendActionBar` and `showTitle` do not.
- A message of several lines gets it once, in front of its first line. An empty message, which is not sent, gets
  none.
- A template can still write `<prefix>` for the lang file's prefix; the two are independent.
- The instance it is called on is not changed, and `Messages.load` alone adds no prefix. Both instances share their
  files: `reload()` and `addMissingKeys()` through either apply to both.

### Names with upper-case letters

A `{name}` is rewritten only when its name holds lower-case letters, digits, `_` and `-`, so `{crateName}` stays as
written. From `0.4.8`, `withBracedNamesIgnoringCase()` returns a `Messages` over the same files that matches a
`{name}` against the supplied values in lower case, in a template, in the prefix and in the prefix of
`withChatPrefix`:

```java
Messages messages = Messages.load(getDataFolder().toPath(), () -> getResource("lang/en.yml"), getLogger())
    .withBracedNamesIgnoringCase();

// crate.opened: "{playerName} opened {crateName}"
messages.send(text, player, "crate.opened",
    Placeholder.unparsed("playername", player.getName()), Placeholder.unparsed("cratename", crate.name()));
```

The value's name is written in lower case, as a MiniMessage tag name is. A `{name}` nothing supplies stays as
written, and a supplied value is inserted as it is: a `{name}` or a tag inside `Placeholder.unparsed` text is not
read again. The instance it is called on is not changed, so every render of a plugin that does not call it is the
same as in `0.4.7`. `Text.withBracedNamesIgnoringCase()` is the same setting for templates rendered through `Text`
alone.

## LegacyText

`LegacyText` converts legacy codes to MiniMessage tags.

| Method | Converts |
|---|---|
| `toMiniMessage(String)` | `&` and `§` color and format codes and the `&#RRGGBB` hex form |
| `sectionToMiniMessage(String)` | only codes written with `§`, leaving every `&` as written |

```java
String mini = LegacyText.toMiniMessage("&#ff8800&lADMIN &7Steve");
// "<#ff8800><bold>ADMIN <gray><!bold>Steve"
```

From `0.2.0`, a colour code ends the format codes before it, as it does in legacy text: the colour tag is followed
by the negation of each decoration (`<!bold>`, `<!italic>`, `<!underlined>`, `<!strikethrough>`, `<!obfuscated>`)
that a format code earlier in the same call opened, and `&r` becomes `<reset>`. In `0.1`, `<bold>` stayed open, so
`Steve` above was bold. Only format codes count: a decoration opened by a tag in the input, or by a format code in
a string converted by another call, such as a `Placeholder.parsed` value, stays open after a colour code, unless a
format code earlier in the same call opened the same decoration: the negation tag then ends both.

The input is scanned without regard to MiniMessage tags, so a code inside a tag, such as a query string in a
click URL, is converted too. The paired hex form `§x§R§R§G§G§B§B` is read; the `&x&R&R&G&G&B&B` form is not, and
comes out as a run of color tags.

## Items

### ItemBuilder

A fluent `ItemStack` builder with Adventure names and lore, both with the default italic removed. `build()` needs
a running server, since it edits item meta.

```java
ItemStack voucher = new ItemBuilder(Material.PAPER)
    .amount(1)
    .name(text.render("<gold>Shop voucher"))
    .lore(List.of(text.render("<gray>Right-click to redeem")))
    .glow(true)
    .build();
```

`ItemBuilder.applyGlow(ItemMeta)` gives any item meta the enchantment glint without adding an enchantment.

From `0.4.6`, `new ItemBuilder(ItemStack base)` starts from a stack the plugin did not build, such as a stored
voucher or a listing preview. `build()` copies the stack with `ItemStack.clone()` as it is at that call and never
changes `base`. The copy keeps the amount, name, lore, glint and every other property that no setter was called
for, so a builder that only sets a name replaces only the name:

```java
ItemStack preview = new ItemBuilder(listing.item())
    .name(text.render("<gold>Listing preview"))
    .build();
```

An empty lore and `glow(false)` count as not called: they keep the lore and the glint of the stack.
`new ItemBuilder(Material)` builds what it built before, with an amount of 1 unless `amount` sets it.

From `0.4.6` the builder also has these setters, each applied in `build()`:

| Setter | Paper API it uses | Notes |
|---|---|---|
| `itemModel(NamespacedKey)` | `ItemMeta.setItemModel` | |
| `customModelData(List<Float>, Logger)` | the `CUSTOM_MODEL_DATA` data component, through `ItemStack.setData` | replaces the custom model data of a base stack; an empty list sets nothing |
| `enchant(Enchantment, int level)` | `ItemMeta.addEnchant` | takes a level above the maximum of the enchantment; the server stores a level above 255 as 255 and no enchantment for a level below 1; a second call for the same enchantment replaces its level |
| `unbreakable(boolean)` | `ItemMeta.setUnbreakable` | |
| `damage(int)` | `Damageable.setDamage` | set only on an item whose type has a max durability or that carries a max damage component; any other item ignores it and gets no damage component. For an item that can be damaged, `build()` throws the server's `IllegalArgumentException` for a damage below zero or above the max damage component of the item |
| `trim(ArmorTrim)` | `ArmorMeta.setTrim` | ignored by an item that is not armour |
| `hideTooltip(boolean)` | `ItemMeta.setHideTooltip` | |
| `color(Color)` | `setColor` of `LeatherArmorMeta`, `PotionMeta` or `MapMeta` | ignored by any other item; from Paper 26.3 a map has no colour and `MapMeta.setColor` does nothing |
| `tag(PdcKey<P, C>, C)` | the persistent data container of the item meta | written in call order, so a later call for the same key wins |
| `glowStyle(GlowStyle)` | see below | |

```java
ItemStack voucher = new ItemBuilder(Material.PAPER)
    .name(text.render("<gold>Shop voucher"))
    .itemModel(new NamespacedKey("shop", "voucher"))
    .customModelData(List.of(3f), getLogger())
    .enchant(Enchantment.UNBREAKING, 1)
    .tag(ownerKey, player.getUniqueId().toString())
    .build();
```

`customModelData` takes the plugin's logger for one case: when the data component API of the server cannot be
linked, as after Paper changed it, a list of one whole number is set through `ItemMeta.setCustomModelData` and any
other list is left out. The logger gets one warning for the first such build and none for a later one.

`glowStyle` chooses how `glow(true)` makes the item glint:

| `ItemBuilder.GlowStyle` | What `glow(true)` sets |
|---|---|
| `GLINT_OVERRIDE` (the default) | the enchantment glint override, with no enchantment and no item flag |
| `HIDDEN_ENCHANTMENT` | `UNBREAKING` 1 with `ItemFlag.HIDE_ENCHANTS`; an item that already has an enchantment glints through it and is left as it is |

An item built in one style does not stack with the same item built in the other. A plugin whose glowing items in
players' hands carry the hidden enchantment keeps them stacking with new ones by choosing `HIDDEN_ENCHANTMENT`.
`ItemBuilder.applyGlow(ItemMeta, GlowStyle)` does the same for any item meta, and throws `NullPointerException`
for a `null` style.

The static methods handle a full-fidelity item reference, `serialized:<base64>`, which carries the entire item and
round-trips exactly:

| Member | Behaviour |
|---|---|
| `SERIALIZED_PREFIX` | `serialized:` |
| `isSerialized(String)` | whether the reference starts with the prefix |
| `serialize(ItemStack)` | the item as a `serialized:<base64>` reference |
| `deserialize(String)` | the exact item, or `null` when the reference is malformed or from an incompatible server version |
| `deserializeOrThrow(String)` | the exact item, or an `IllegalArgumentException` that says why there is none (from `0.3.1`) |
| `deserializeAnyOrThrow(String)` | the exact item of a `serialized:<base64>` reference or of bare base64 with no prefix, or an `IllegalArgumentException` that says why there is none (from `0.4.6`) |

`deserialize` skips the prefix by length without checking it, so check the reference with `isSerialized` first.
It returns `null` for every failure, a `null` reference included, and logs nothing.

From `0.3.1`, `deserializeOrThrow` reads the same reference and throws `IllegalArgumentException` where
`deserialize` returns `null`. Its message tells three failures apart, and the original exception is the cause:

| Failure | Message starts with | Cause |
|---|---|---|
| the reference does not start with `serialized:` | `Item reference does not start with 'serialized:'` | none |
| the text after the prefix is not base64 | `Item reference holds invalid base64 after 'serialized:'` | the decoder's `IllegalArgumentException` |
| the server refused the bytes, which are corrupt or were written by a newer data version | `The server refused the bytes of the item reference` | the exception the server threw |

Unlike `deserialize`, it checks the prefix, and a `null` reference throws `NullPointerException`. A plugin that
stores items uses it to log why a stored item is gone, such as after a server downgrade:

```java
try {
    ItemStack item = ItemBuilder.deserializeOrThrow(stored);
    give(player, item);
} catch (IllegalArgumentException ex) {
    getLogger().log(Level.WARNING, "Listing " + id + " holds an item that cannot be read", ex);
}
```

From `0.4.6`, `deserializeAnyOrThrow` also reads an item stored as the bare base64 of
`ItemStack.serializeAsBytes()`, with no prefix. A reference that starts with `serialized:` is read as
`deserializeOrThrow` reads it and fails with the same messages and causes. A reference without the prefix fails in
one of three ways:

| Failure | Message starts with | Cause |
|---|---|---|
| `Material.matchMaterial` finds the reference, so it is a material name | `Item reference does not start with 'serialized:' and is the material name` | none |
| the reference is not base64 | `Item reference does not start with 'serialized:' and is not base64` | the decoder's `IllegalArgumentException` |
| the server refused the bytes, which are corrupt or were written by a newer data version | `The server refused the bytes of the item reference` | the exception the server threw |

A material name is never decoded, so a name that is also valid base64, such as `DIRT` or `DIAMOND`, gives no item
and a plugin whose setting holds either a stored item or a material still reads it as a material. A `null`
reference throws `NullPointerException`. `deserialize` and `deserializeOrThrow` read only the prefixed form, as
before.

`serialize` hands the item to `ItemStack.serializeAsBytes()` as it is and catches nothing that call throws. An
empty stack (air, or an amount of 0) has no reference: the server throws for it, and a `null` item throws
`NullPointerException`. Check `item.isEmpty()` first and store the absence of an item your own way, such as a
`NULL` column.

### SkullBuilder

Builds `PLAYER_HEAD` items.

- `SkullBuilder.fromTexture(String base64)` and `SkullBuilder.fromUrl(String url)` are static, synchronous and need
  no network. `fromUrl` throws `IllegalArgumentException` for a URL holding a double quote or a backslash.
- `fromName(String)` and `fromUuid(UUID)` resolve the player's current skin from Mojang on the executor given to
  the constructor and return a `CompletableFuture<ItemStack>`. They complete with a blank head when the lookup fails
  or the executor rejects it.

```java
SkullBuilder skulls = new SkullBuilder(scheduler.asyncExecutor());

skulls.fromName("Notch").thenAccept(head ->
    scheduler.entity(player, () -> Items.giveOrDrop(player, head)));
```

The executor must run tasks off the calling thread, since a lookup blocks on the network, and must throw
`RejectedExecutionException` when it cannot take a task, as `Scheduler.asyncExecutor()` does. The future completes
on the executor's thread, or on the calling thread for a cached texture, so inventory or entity work is scheduled
back onto the owning thread. A lookup the executor accepted but never runs, as can happen to a task scheduled just
before the plugin disables, leaves its future, and every later future for the same name or uuid from that
instance, incomplete. A lookup that throws an `Error` completes its future exceptionally.

Lookups are cached per instance. From `0.2.0`, the cache expires and has a size bound:

| Lookup | Kept for | Calls in that time |
| --- | --- | --- |
| Resolved a texture | 60 minutes from the moment it completed | get a head with that texture, with no lookup |
| Found no texture, or threw | 2 minutes from the moment it completed | get a blank head, with no lookup |
| Threw an `Error` | 2 minutes from the moment it completed | complete exceptionally, with no lookup |
| Rejected by the executor | not kept | start a new lookup |

After that time the next call looks the name or uuid up again, so a skin change shows within 60 minutes. One
`SkullBuilder` caches at most 1000 names and uuids: a new one past that drops the one whose lookup started longest
ago. In `0.1` a resolved texture stayed for the life of the instance and a failed lookup was not cached, so a call
right after a blank head looked the name up again. From `0.2.0` that call gets the same blank head for 2 minutes.

### Items, InventoryFit and PdcKey

`Items.giveOrDrop(Player, ItemStack)` adds the item to the player's inventory and drops whatever does not fit at the
player's feet. It must be called on the thread that owns the player. From `0.1.1`, the stack passed in is left
unchanged and the player gets a copy of it; `0.1.0` reduces the stack to what did not fit.

`InventoryFit.fits(ItemStack[] storage, int inventoryMax, List<ItemStack> stacks)` tells whether the stacks fit when
added in order, following `Inventory.addItem`, without changing anything. A `null` or empty slot is free.

```java
PlayerInventory inventory = player.getInventory();
boolean room = InventoryFit.fits(inventory.getStorageContents(), inventory.getMaxStackSize(), List.of(voucher));
```

`PdcKey<P, C>` is typed access to one persistent-data key, with `get` (or `null` when absent), `has` and `set`. A
write to an `ItemMeta` reaches its item only once the meta is set back, which `ItemStack.editMeta` does.

```java
PdcKey<String, String> voucherId = new PdcKey<>(new NamespacedKey(this, "voucher_id"), PersistentDataType.STRING);

voucher.editMeta(meta -> voucherId.set(meta, "spring-sale"));
```

`get` throws `IllegalArgumentException` when the key holds a value of another type.

From `0.4.4`, `remove(holder)` removes the key from the holder's container, whatever the type of its value, and
leaves a holder without the key unchanged. Like a write, a removal from an `ItemMeta` reaches its item only once
the meta is set back. `getOrDefault(holder, fallback)` returns the stored value, or `fallback` when the key is
absent, and throws as `get` does. `key()` returns the `NamespacedKey`.

```java
voucher.editMeta(meta -> voucherId.remove(meta));
```

`get`, `getOrDefault`, `has`, `set` and `remove` take a `PersistentDataHolder`, such as an `ItemMeta`, an entity
or a chunk. An `ItemStack` is not one, so read and write an item through its meta.

### Colors and Sounds

`Colors.parse(String)` reads a `org.bukkit.Color` from config: one of the 17 named colors in any case, `#RRGGBB`, or
an `r,g,b` triple of whole numbers from 0 to 255. It throws `IllegalArgumentException` with the message
`invalid color '<raw>': expected ` followed by `Colors.EXPECTED`.

`Sounds.play(Player, String spec)` plays a sound written as `"key [volume] [pitch]"` on the calling thread. The key
is read in lower case; a missing or non-numeric volume or pitch is `1`; a `null` or blank spec does nothing. A key
that does not parse throws Adventure's `InvalidKeyException`, and `Sounds.isValid(String)` checks for that
beforehand, for example while loading config.

A key that parses may still name no sound: the Bukkit enum form `ENTITY_PLAYER_LEVELUP` is valid and plays
nothing. From `0.2.0`, `Sounds.isKnown(String)` tells, so config loading can warn. It looks a `minecraft` key up in
the server's sound registry, and returns `true` for a `null` or blank spec and for a key of another namespace,
which only a resource pack defines. A sound a resource pack adds under the `minecraft` namespace reads as unknown,
so treat `false` as a reason to warn, not to refuse. It reads the registry of the running server.

```java
Sounds.play(player, "minecraft:entity.player.levelup 0.8 1.2");
```

## Time

### Durations

`Durations` parses and formats short durations: 1 to 18 digits followed by `ms`, `s`, `m`, `h` or `d` in any case,
such as `250ms`, `30s` or `7d`. Surrounding whitespace is ignored; a sign, a decimal point or a space before the unit
is not accepted. The longest accepted duration is `Long.MAX_VALUE / 2` milliseconds.

| Method | Behaviour |
|---|---|
| `parseOrNull(Object)` | the duration of the value's `toString()`, or `null` |
| `parse(Object)` | the same, or `IllegalArgumentException` with `invalid duration '<value>': expected ` followed by `Durations.EXPECTED` |
| `format(Duration)` | the largest unit that divides exactly: `1d`, `90s`, `1500ms`; zero is `0s` |
| `format(List<Duration>)` | `[30s, 1d]` |

### Expiry

`Expiry` reads an optional expiry or start setting.

| Method | Behaviour |
|---|---|
| `resolve(String raw, Instant now)` | blank or `null` is never (returns `null`); a duration counts from `now`; a date ends at the end of that day in the system zone; a local date-time is read in the system zone; an ISO-8601 instant is used as written |
| `resolveStart(String raw)` | the same absolute forms, with a plain date at the start of the day; durations are refused |
| `isExpired(Instant expiry, Instant now)` | `true` when `expiry` is non-null and not after `now` |
| `isRelative(String raw)` | whether the value is a duration |

Bad values throw `IllegalArgumentException` with `invalid expiry '<raw>': expected ` plus `Expiry.EXPECTED`, or
`invalid start '<raw>': expected ` plus `Expiry.EXPECTED_START`.

### CooldownManager

Keyed cooldowns against the system clock. A key is any object compared by `equals` and `hashCode`, typically a
record of a player id and what is on cooldown.

```java
record Cooldown(UUID player, String action) {}

CooldownManager cooldowns = new CooldownManager();
Cooldown key = new Cooldown(player.getUniqueId(), "daily");

if (cooldowns.isOnCooldown(key)) {
    player.sendMessage(text.render("<red>Wait " + Durations.format(cooldowns.remaining(key))));
} else {
    cooldowns.set(key, Duration.ofHours(24));
}
```

`set` starts or restarts a cooldown, and a length of zero or less clears it. `extend` keeps the later of the current
expiry and the new one, and a length of zero or less changes nothing. `remaining` is `Duration.ZERO` when the key is not on cooldown. Lengths are read in whole
milliseconds. Each call on a key is atomic, but a check followed by a `set` is two calls, so two threads can both
pass the check for one key.

From `0.4.4`, `tryStart(key, length)` checks and starts in one atomic step. It starts the cooldown and returns
`true` only when the key has none running, so of the threads that call it for one free key at once, exactly one
gets `true`. A running cooldown is left as it is. A length of zero or less starts nothing and returns whether the
key was free.

```java
if (!cooldowns.tryStart(key, Duration.ofSeconds(30))) {
    player.sendMessage(text.render("<red>Wait " + Durations.format(cooldowns.remaining(key))));
    return;
}
broadcastListing(player);
```

Keep `isOnCooldown` and `set` when the cooldown starts only after the action succeeded, and serialise the two calls
yourself.

An expired cooldown stays in memory until its key is read, started again or extended. From `0.4.4`,
`purgeExpired()` removes every expired cooldown and returns how many it removed, for keys that are not read again,
such as those of players who left. It removes them key by key, so a cooldown started while it runs is kept. Call it
from a repeating task, on any thread.

## Amounts

From `0.4.6`, `AmountFormat` writes an amount of money for a player and `Amounts` reads one a player typed. Both
work on `BigDecimal` and never on a `double`.

### AmountFormat

`AmountFormat` is a record of a symbol, an optional number pattern and a scale: the decimal places of the currency,
from 0 to `AmountFormat.MAX_SCALE` (18). The constructor throws `NullPointerException` for a `null` symbol and
`IllegalArgumentException` for a scale outside that range or a pattern `checkPattern` refuses.

```java
AmountFormat coins = new AmountFormat("$", null, economy.scale());

coins.format(new BigDecimal("1250.5"), player.locale());   // $1,250.50, or $1.250,50 for a German client
coins.number(new BigDecimal("1250.5"), player.locale());   // 1,250.50
```

| Method | Behaviour |
|---|---|
| `number(BigDecimal, Locale)` | the number alone, with the digits, the separators and the minus sign of the locale |
| `format(BigDecimal, Locale)` | the symbol directly before that number; with an empty symbol, the number alone |
| `checkPattern(String)` | the pattern, or `IllegalArgumentException` with `invalid number pattern '<value>': expected ` followed by `AmountFormat.EXPECTED` |

Use `number` when a language line places the symbol or the currency name itself.

The pattern is a `java.text.DecimalFormat` pattern such as `#,##0.00`, in which `,` and `.` stand for the grouping
and decimal separators of the player's locale. With `null` for the pattern the number has grouped whole digits and
exactly `scale` decimal places. With a pattern it has the decimal places the pattern allows, or `scale` when that is
more, so an amount is never shown with fewer decimal places than it holds up to the scale:

| Pattern | Scale | `1500` | `1500.25` | `1500.255` |
|---|---|---|---|---|
| `null` | 2 | `1,500.00` | `1,500.25` | `1,500.26` |
| `#,##0` | 2 | `1,500` | `1,500.25` | `1,500.26` |
| `#,##0.##` | 4 | `1,500` | `1,500.25` | `1,500.255` |
| `0.000` | 2 | `1500.000` | `1500.250` | `1500.255` |

An amount with more decimal places than that is rounded with `RoundingMode.HALF_EVEN`, so `0.125` is `0.12` and
`0.135` is `0.14` at two places. An amount that rounds to zero is written without a minus sign: `-0.004` is `0.00`.

The text is for display. A rounded number differs from the amount by up to half a unit of its last decimal place,
so the amount to charge is the `BigDecimal`, rounded by the plugin, and never a reading of the shown text.
`Amounts.parse` is not the inverse of `number`: it refuses the grouping separators written here, and
the digits and the minus sign of a locale that has its own. `250.5` is written `٢٥٠٫٥٠` for `ar-SA`, and a
negative amount starts with U+2212 for `sv-SE`, and `Amounts.parse` gives `NOT_A_NUMBER` for both.

`checkPattern` is for a pattern an owner writes in config. It refuses a `null` or blank pattern, one `DecimalFormat`
refuses, and one that holds `%`, the per mille sign, the currency sign `¤` or `E`, quoted or not: those make
`DecimalFormat` multiply the amount, add the currency symbol of the locale or write an exponent. It does not trim
the pattern.

```java
String pattern = reader.parsed("currency.format", "#,##0.00", AmountFormat.EXPECTED, AmountFormat::checkPattern);
AmountFormat coins = new AmountFormat(reader.text("currency.symbol", "$"), pattern, economy.scale());
```

An `AmountFormat` holds no `DecimalFormat`, which is not thread-safe: each call builds its own, so one
`AmountFormat` can be used from any thread.

### Amounts

`Amounts.parse(String input, Locale locale, BigDecimal maximum)` reads an amount a player typed in chat, an anvil
or a command, from zero to `maximum`.

```java
Locale locale = player.locale();
switch (Amounts.parse(typed, locale, new BigDecimal("1000000000"))) {
    case Amounts.Amount amount ->
        list(player, amount.value().setScale(economy.scale(), RoundingMode.HALF_EVEN));
    case Amounts.Refused refused -> {
        String key = "price.refused." + refused.reason().name().toLowerCase(Locale.ROOT);
        player.sendMessage(messages.render(locale, key));
    }
}
```

The accepted form is the digits `0` to `9` with at most one decimal separator and a digit on at least one side of
it, then nothing or one of `k` (a thousand), `m` (a million) and `b` (a thousand million) in either letter case.
Whitespace around the input is ignored. The decimal separator is that of the locale, and a full stop is read as
one too unless the locale groups with it.

| Input | `en-US` | `de-DE` |
|---|---|---|
| `1500` | `1500` | `1500` |
| `2.5` | `2.5` | `GROUPING_SEPARATOR` |
| `2,5` | `GROUPING_SEPARATOR` | `2.5` |
| `1k`, `1K`, ` 1k ` | `1000` | `1000` |
| `2.5m` | `2500000` | `GROUPING_SEPARATOR` |
| `1b` | `1000000000` | `1000000000` |
| `1,000` | `GROUPING_SEPARATOR` | `1` |
| `-5`, `-0` | `NEGATIVE` | `NEGATIVE` |
| `1.5.5k` | `NOT_A_NUMBER` | `GROUPING_SEPARATOR` |
| `+5`, `1e9`, `1kk`, `1 k`, `0x10`, `k`, `NaN` | `NOT_A_NUMBER` | `NOT_A_NUMBER` |

The result is an `Amounts.Amount` or an `Amounts.Refused`. `Amount.value()` is exact: the digits are multiplied by
the suffix with no rounding, so `0.0001k` is `0.1`, and the value keeps every decimal place the player typed, with
no trailing zero. Round it to the scale of the currency before it is used. An input equal to `maximum` is accepted,
and a `maximum` below zero throws `IllegalArgumentException`.

Zero is accepted, and an amount above zero can round to zero at the scale of the currency: `0.004` is `0.00` at two
places. [`EconomyProvider.withdraw` and `deposit`](/docs/modules/hooks#economyprovider) throw `IllegalArgumentException` for an
amount that rounds to zero, so a command that moves money checks `signum()` after it rounds:

```java
BigDecimal rounded = amount.value().setScale(economy.scale(), RoundingMode.HALF_EVEN);
if (rounded.signum() == 0) {
    player.sendMessage(messages.render(locale, "pay.too-small"));
    return;
}
```

`new Amounts.Amount(BigDecimal)` throws `IllegalArgumentException` for a value below zero.

`Refused.reason()` tells the plugin which of its own messages to show. The reasons are checked in this order:

| `Amounts.Reason` | The input |
|---|---|
| `EMPTY` | is empty or only whitespace |
| `TOO_LONG` | is longer than `Amounts.MAX_LENGTH` (64) characters, whatever it holds |
| `NOT_A_NUMBER` | is not in the accepted form: a plus sign, an exponent, a second suffix, a space before the suffix, letters, or digits other than `0` to `9` |
| `GROUPING_SEPARATOR` | would be in the accepted form without its grouping separators: that of the locale, a comma that is not its decimal separator, or a full stop where the locale groups with one. Where the locale groups with a space, a no-break space or a narrow no-break space, such as `fr-FR` and `sv-SE`, each of the three between two digits counts, so `1 000` typed with an ordinary space is refused with this reason |
| `NEGATIVE` | is in the accepted form after a minus sign, `-0` included |
| `OVER_MAXIMUM` | is an amount above `maximum` |

A grouping separator is refused and never guessed, since `1,000` is a thousand in one locale and one in another. A
later release may add a reason, so give a `switch` over the reasons a `default` branch.

## PlayerCache

From `0.4.5`, `PlayerCache<T>` keeps one value per online player, such as the rows a plugin stores for them. It
loads the value when the player joins and forgets it when the player quits, so a read never waits for the
database.

```java title="ShopPlugin.java"
private PlayerCache<Balance> balances;

@Override
public void onEnable() {
    // errors, scheduler and storage are built first
    balances = new PlayerCache<>(this, errors, scheduler, scheduler::delayedAsync,
        player -> storage.read(tx -> Balances.of(tx, player)));
}

@Override
public void onDisable() {
    Shutdown.closeQuietly("close the balance cache", () -> balances.close(), getLogger(), errors);
    // the rest of the disable order
}
```

| Argument | What it is |
|---|---|
| `Plugin owner` | The plugin the listener belongs to. Its logger takes the warning of a failed load. |
| `ErrorReports errors` | Where a failed load is reported, as `PlayerCache.SOURCE` (`player-cache.load`). |
| `Dispatcher dispatcher` | Runs each call of the loader with `ThreadTag.ASYNC`. A `Scheduler` is one. |
| `BiConsumer<Runnable, Duration> timer` | Runs a retry after a delay, such as `scheduler::delayedAsync`. |
| `Function<UUID, CompletableFuture<T>> loader` | Gives the value of a player, such as a `Storage.read`. |

The constructor registers the cache's own join and quit listener on the owner, so there is no `registerEvents`
call to write and no `listener()` method. It also starts a load for every player already online, through the same
path as a join, so a plugin enabled while players are online has their values too. Build it while the plugin is
enabled, such as in `onEnable`, on the thread that enables the plugin.

On Folia a quit is handled on a region thread while the constructor runs on another. A player who was online and
whose quit is handled before the constructor reaches them keeps an entry, with its value or the retries of its
failed load, until that player joins or quits again or the cache is closed. It takes a plugin enabled while
players are online, and cannot happen on Paper, where the quit and the constructor share the main thread.

| Method | What it does |
|---|---|
| `get(UUID player)` | An `Optional` of the value of the player's last load that succeeded since they joined. |
| `ready(UUID player)` | Whether `get` holds a value for the player. |
| `refresh(UUID player)` | Loads an online player's value again. |
| `close()` | Unregisters the listener and forgets every player. |

### While the value is not loaded

`get` is empty and `ready` is `false` before the first load ends, while it keeps failing, for a player who is not
online and after `close()`. The cache never hands out a value from a failed load and never denies a login, so the
plugin decides what a player without a value may do:

```java
Optional<Balance> balance = balances.get(player.getUniqueId());
if (balance.isEmpty()) {
    player.sendMessage(text.render("<red>Your balance is still loading."));
    return;
}
```

The join starts the load at `EventPriority.LOWEST` and the loader runs on an async thread, so the value is not
there yet in the plugin's own `PlayerJoinEvent` handler. The quit forgets the player at `EventPriority.MONITOR`,
so a quit handler of the plugin at any lower priority still reads the value. A quit handler at `MONITOR` reads it
only when its listener was registered before the cache was built, because the server calls the handlers of one
priority in the order they were registered.

The values are read from any thread while a load may replace them, so `T` is immutable or thread-safe: a record
of immutable fields, or a `Map.copyOf`.

### A failed load

A load fails when the loader throws, returns `null`, or its future completes with `null` or with an exception.
The cache then:

- reports the error to the `ErrorReports` as `PlayerCache.SOURCE`;
- logs a warning through a [`ThrowLog`](#logging) of the owner's logger, so a database that stays down does not
  fill the console;
- runs the load again through the timer after `PlayerCache.FIRST_RETRY_DELAY` (2 seconds), then after twice the
  delay before it each time (4, 8, 16 seconds and so on), up to `PlayerCache.LONGEST_RETRY_DELAY` (5 minutes).

It retries for as long as the player stays online. `ready` stays `false` until a retry succeeds.

### Loads that are dropped

Each player has one current load: the latest one started by a join or by `refresh`. The result, the failure and
the retries of any other load are dropped:

| What happened | What the cache does |
|---|---|
| The player quit before the load ended | The result is dropped, and a failure is neither reported nor retried. |
| The player quit and joined again during a retry | The join starts a new load. The old retry does nothing. |
| `refresh` ran while a load was running | The new load replaces it. |
| The dispatcher refused the load, as a `Scheduler` does once the plugin is disabling | The load ends with no report and no retry. |
| The timer never ran the retry, as `delayedAsync` does once the plugin is disabling | The load ends. A later `refresh` starts a new one. |

`refresh(UUID player)` keeps the value held now readable until the new load succeeds, also while that load fails
and is retried. It does nothing for a player who is not online.

### What it does not do

The cache does not load at `AsyncPlayerPreLoginEvent`, does not save a value at a quit and does not flush at
`close()`. A plugin that writes a player's value keeps writing it to its storage itself, then calls `refresh` or
lets the next join read it. `close()` may run at any point of the [disable order](#disable-order): it waits for
nothing.

### Testing a plugin that uses it

In a plugin test, pass a [`FakeDispatcher`](/docs/modules/test#fakedispatcher) and a timer that collects its
tasks, so the test decides when a load and a retry run. The constructor still needs a `Plugin` whose server has
a plugin manager, which the test mocks. A player the mocked server lists in `getOnlinePlayers()` is loaded when
the cache is built.

A join or a quit reaches the cache only through the listener it registers, and the class of that listener is
not public, so a test cannot call its handlers directly. Capture the listener from the mocked plugin manager and
run a handler through Paper's `EventExecutor`, as the server does. The handlers are named `onJoin` and `onQuit`:

```java title="BalanceCacheTest.java"
Plugin plugin = mock(Plugin.class);
Server server = mock(Server.class);
PluginManager manager = mock(PluginManager.class);
when(plugin.getServer()).thenReturn(server);
when(plugin.getLogger()).thenReturn(Logger.getLogger("test"));
when(server.getPluginManager()).thenReturn(manager);

FakeDispatcher dispatcher = new FakeDispatcher();
List<Runnable> retries = new ArrayList<>();
PlayerCache<Balance> balances = new PlayerCache<>(plugin, new ErrorReports(), dispatcher,
    (task, delay) -> retries.add(task), uuid -> CompletableFuture.completedFuture(new Balance(5)));

ArgumentCaptor<Listener> registered = ArgumentCaptor.forClass(Listener.class);
verify(manager).registerEvents(registered.capture(), same(plugin));
Listener listener = registered.getValue();

Player player = mock(Player.class);
UUID uuid = UUID.randomUUID();
when(player.getUniqueId()).thenReturn(uuid);

EventExecutor.create(listener.getClass().getDeclaredMethod("onJoin", PlayerJoinEvent.class), PlayerJoinEvent.class)
    .execute(listener, new PlayerJoinEvent(player, Component.empty()));
assertThat(balances.get(uuid)).contains(new Balance(5));

EventExecutor.create(listener.getClass().getDeclaredMethod("onQuit", PlayerQuitEvent.class), PlayerQuitEvent.class)
    .execute(listener, new PlayerQuitEvent(player, Component.empty(), PlayerQuitEvent.QuitReason.DISCONNECTED));
assertThat(balances.ready(uuid)).isFalse();
```

`EventExecutor` is `org.bukkit.plugin.EventExecutor` of paper-api. A plain `Method.invoke` on the handler fails
with an `IllegalAccessException`, because the listener class is not public.

## Logging

`ThrowLog` rate-limits warnings about a third party that keeps failing, keyed by source. The first failure of a
source is logged with its stack trace. After that, at most one line per source per `ThrowLog.WINDOW` (one minute) is
logged, without the stack trace and with the number of failures left out since the last one.

```java
ThrowLog failures = new ThrowLog(getLogger());

try {
    refreshPrices();
} catch (RuntimeException ex) {
    failures.warn("prices", "Could not refresh the prices, so the old ones stay.", ex);
}
```

Every distinct source is kept for the life of the instance. `warn` may be called from any thread.

`Classes.present(String className, Class<?> caller, Logger logger)` tells whether a class is loadable from the
caller's class loader, without initializing it. A lookup that throws for another reason, such as another plugin's
closed jar, counts as absent and is logged as a warning; an absent class is not logged.

## Diagnostics

From `0.4.10`, `DiagnosticReport` builds the report a plugin's diagnostics command shows to the server owner: titled
sections of lines, rendered as Adventure components for a command sender or as plain text for the console.

```java
import so.alaz.taffy.platform.DiagnosticReport;
import so.alaz.taffy.platform.DiagnosticReport.Line;

void doctor(CommandSender sender) {
    DiagnosticReport report = DiagnosticReport.builder(this, scheduler.mode())
        .section("Storage", () -> Storage.diagnostics(starting))
        .section("Integrations", () -> hookStatuses().stream()
            .map(status -> Line.redacted("", status.line())).toList())
        .section("Metrics", () -> metrics.diagnostics())
        .section("Config", () -> List.of(
            Line.of(comfiConf.status().line()),
            Line.pendingRestart(RestartKeys.changed(startup, current, RESTART_ONLY::contains))))
        .build();
    report.components().forEach(sender::sendMessage);
}
```

```text
Server
  Plugin: Shop 1.4.0
  Server: Paper 26.3
  Java: 25.0.1
  Scheduler: Paper
Storage
  Database: SQLite
  State: open
  Write pool: 0 active, 1 idle, 0 waiting, 1 max
  Read pool: 0 active, 2 idle, 0 waiting, 4 max
Integrations
  Vault 1.7.3 has nothing registered with it. Install an economy plugin.
Metrics
  bStats: on
  FastStats: bukkit 0.33.0, submitting metrics and the plugin's charts
  FastStats error tracking: on
Config
  ComfiConf on
  Waiting for a restart: storage.type
```

`DiagnosticReport.builder(Plugin plugin, Scheduler.Mode mode)` reads nothing until `build()`. Every report starts
with the section `Server`:

| Line | Value |
|---|---|
| `Plugin` | `Plugin.getName()` and the version of `Plugin.getPluginMeta()` |
| `Server` | `Server.getName()` and `Server.getMinecraftVersion()` |
| `Java` | `Runtime.version()` |
| `Scheduler` | `Paper` or `Folia`, from the `Scheduler.Mode` passed |

`taffy-platform` names no other module, so each module gives the lines of its own section:

| Lines | From |
|---|---|
| `Storage.diagnostics()` and `Storage.diagnostics(CompletableFuture<Storage>)` | [taffy-storage](/docs/modules/storage#diagnostics) |
| `Metrics.diagnostics()` | [taffy-metrics](/docs/modules/metrics#diagnostics) |
| `HookStatus.line()` | [taffy-hooks](/docs/modules/hooks#hookstatus) |
| `ComfiConfStatus.line()` | [taffy-comficonf](/docs/modules/comficonf#status-for-the-server-owner) |

| Member | Behaviour |
|---|---|
| `Builder.section(String title, Supplier<? extends Collection<Line>> lines)` | Adds a section whose lines are read at `build()`. A blank title throws `IllegalArgumentException`. |
| `Builder.section(String title, Collection<Line> lines)` | Adds a section of lines the plugin already holds. |
| `Builder.build()` | Runs every supplier once, in the order added, on the calling thread. A builder can build again, which reads every section again. |
| `sections()` | The sections, the standard one first, as `Section(String title, List<Line> lines)`. |
| `plainText()` | A `List<String>`: each title on a line of its own, then each line of the section behind two spaces. |
| `components()` | One `Component` for each line of `plainText()`, with the same text: titles in gold, labels in gray, values in white. A value is plain text and is never read as MiniMessage or as legacy colour codes. |
| `new Line(String label, String value)` | Shown as `<label>: <value>`, or as the value alone when the label is empty. |
| `Line.of(String value)` | A line without a label, for a value that names its subject, such as `ComfiConfStatus.line()`. |
| `Line.redacted(String label, String text)` | A line whose value is `Redaction.hide(text)`, for text the plugin did not write. A `HookStatus.line()` goes through it with an empty label. |
| `Line.pendingRestart(Collection<String> paths)` | The line `Waiting for a restart`. |
| `Line.plain()` | The line as plain text. |

`Line.pendingRestart` takes the paths [`RestartKeys.changed`](/docs/modules/config#restartkeys) returns between the
configuration loaded at startup and the current one. It names the paths and never a value, so a changed
`storage.password` shows as `storage.password`. It reads `none` for no path, names at most 32 paths and counts the
rest, as in `storage.type, locale.default and 3 more`.

### A section that fails

A supplier that throws a `RuntimeException` or a `LinkageError`, returns `null` or returns a `null` line does not
lose the report. Its section holds one line, and the other sections are kept:

```text
Storage
  could not be read: java.lang.IllegalStateException
```

The failure is logged as a warning on the plugin's logger with its stack trace. Its message is not part of the
report.

### What a report may hold

Server owners paste a report into public support channels. The `Server` section, the lines of `Storage.diagnostics`
and `Metrics.diagnostics` and a `ComfiConfStatus.line()` hold no password, token, connection URL, host, address,
file path, player name or player UUID. The message of a failed storage start is text Taffy did not write, and it is
shown as `Redaction.hide` leaves it. The reason of a `HookStatus` in the state `FAILED` quotes the class and message
of an exception another plugin threw, as in `The economy could not be read (<exception>).`, so a `HookStatus.line()`
goes into a report as `Line.redacted("", status.line())`. `Redaction.hide` leaves the rest of the line as written,
except that a plugin version of four numbers, such as `5.4.0.1`, reads as an address. Keep such values out of the lines the plugin writes itself: show a count of players or rows, not their names, and a setting's path, not its
value. Text the plugin did not write, such as the message of an exception, goes through `Line.redacted`.

A label and a value never hold a line break or a legacy colour code: each control character, line separator and
section sign (`U+00A7`) becomes a space. A report is
bounded, and what is left out is counted in a line of its own:

| Limit | Value |
|---|---|
| Sections after `Server` (`MAX_SECTIONS`) | 32; a further section is counted in a last section `Not shown` and its supplier never runs |
| Lines in a section (`MAX_LINES`) | 64, then the line `<n> more lines not shown`, or `1 more line not shown` |
| Characters in a title or a label (`MAX_LABEL`) | 64, cut with `...` |
| Characters in a value (`MAX_VALUE`) | 512, cut with `...` |
| Paths in `Line.pendingRestart` (`MAX_PATHS`) | 32, each up to 128 characters |

### Threads

`build()` runs on the thread that calls it and so does every supplier. A supplier must not block or wait for a
future, and reads only what that thread may read. On Folia a command runs on the region thread of its sender, or
on the global region thread for the console, and neither owns another region's worlds or entities. The `Server`
section, `Storage.diagnostics`, `Metrics.diagnostics` and a status `line()` read cached state without blocking, so
a report of those builds on any thread. A built report is immutable. Send `components()` on the thread that owns
the sender.

The texts of a report are written for the server owner and can change in any release.

### Redaction

From `0.4.10`, `Redaction.hide(String text)` hides secrets and personal data in free text before it is shown where
others can read it. It applies the 19 rules listed under
[Anonymizing](/docs/modules/metrics#anonymizing), in their order, then hides what is left of a path behind
`[path hidden]`, and replaces each IPv4 and IPv6 address with `[address hidden]`.

```java
Redaction.hide("Access denied for user 'mc_prod'@'10.0.0.5' (using password: YES)");
// Access denied for user [user hidden]@[host hidden] (using password: YES)

Redaction.hide("Could not connect to jdbc:mysql://db.example.net:3306/shop");
// Could not connect to jdbc:[redacted]
```

The Unix path rule reads only letters, digits, `_`, `.` and `-` in a folder name, so it ends at the `+` of
`/home/john+smith/server/data.db`. `hide` hides the text behind `[path hidden]` up to the next whitespace or quote
when it holds a `/` or a backslash; what follows a space in such a folder name stays. Four numbers of up to three
digits with dots between them read as an IPv4 address, also before the full stop of a sentence and as the version
`5.4.0.1`, and not with a fifth number, as in `1.2.3.4.5`. A run of two or more groups of up to four hex digits that
each end in a colon reads as an IPv6 address when it holds a hex digit, so a time of day such as `12:34:56` and a
short word such as `a::b` are hidden too, and a `::` alone stays. The rules read what a JDBC driver, a connection pool or an HTTP client writes.
They do not find a name in a sentence of its own, such as a player name, so `hide` is no reason to put one in a
report. `Redaction.rules()` returns the 19 rules as `Redaction.Rule(String pattern, String replacement)`, without
the address rule, for code that hands them to something that applies regular expressions itself. `hide` throws
`NullPointerException` for a `null` text, runs in time linear in the length of the text and may be called from any
thread.

## Commands

From `0.4.10`, `CommandHelpers` holds three pieces a plugin's commands repeat: the permission check of a Brigadier
node, the candidates that start with what was typed, and the player a typed name or UUID stands for. It registers
no command and sends no message, and it never reads typed text as MiniMessage or as a legacy colour code.

| Member | Behaviour |
|---|---|
| `permission(String node)` | The `Predicate<CommandSourceStack>` for `requires`: whether the sender of the source holds the node. |
| `matching(String typed, Collection<String> candidates)` | The candidates that start with the typed text, in the collection's order, as an unmodifiable `List<String>`. |
| `suggest(SuggestionsBuilder builder, Collection<String> candidates)` | Suggests `matching(builder.getRemaining(), candidates)` and returns `builder.buildFuture()`. |
| `target(Server server, String input)` | The `OfflinePlayer` the text stands for, or `null`. |

```java
import so.alaz.taffy.platform.CommandHelpers;

LiteralArgumentBuilder<CommandSourceStack> give = Commands.literal("give")
    .requires(CommandHelpers.permission("shop.give"))
    .then(Commands.argument("target", StringArgumentType.word())
        .then(Commands.argument("id", StringArgumentType.word())
            .suggests((context, builder) -> CommandHelpers.suggest(builder, registry.ids()))
            .executes(context -> {
                CommandSender sender = context.getSource().getSender();
                String name = StringArgumentType.getString(context, "target");
                OfflinePlayer target = CommandHelpers.target(sender.getServer(), name);
                if (target == null) {
                    sender.sendMessage(Component.text("No player is known as " + name));
                    return 0;
                }
                stash.add(target.getUniqueId(), StringArgumentType.getString(context, "id"));
                return Command.SINGLE_SUCCESS;
            })));
```

The typed name goes into the answer through `Component.text`, as plain text.

- `permission` asks `CommandSourceStack.getSender()`, so for a command run through `/execute as` it asks the one
  who ran the command, not the entity it runs as.
- `matching` ignores letter case, with both sides lower-cased under `Locale.ROOT`, so the server's default locale
  does not change the answer. An empty typed text matches every candidate, a candidate is returned as it was given,
  and one given twice is returned twice. It takes and returns plain text, so it also fills the list a Bukkit
  `TabCompleter` or `BasicCommand.suggest` returns.
- `matching` and `suggest` show the candidates to whoever asked. Pass only names that sender may see: for player
  names, the online players the sender `canSee`, not every online player. `CommandHelpers` has no method that
  lists players.
- `target` takes the first of these that applies: a UUID in its 36 character form with dashes, in either letter
  case, through `Server.getOfflinePlayer(UUID)`; the exact name of an online player, ignoring letter case, through
  `Server.getPlayerExact`; a name in the server's profile cache, through `Server.getOfflinePlayerIfCached`. A blank
  text and a name that is neither online nor cached give `null`, so a mistyped name stands for no player.
- `target` never asks Mojang for a name, so it does not wait on the network, unlike
  `Server.getOfflinePlayer(String)`. The server returns a player for every UUID, also one that has never joined,
  whose `getName()` is `null`.
- `target` finds an online player whether or not the sender can see them. A command that must not reveal a hidden
  player checks `Player.canSee` on the result and answers as for an unknown name.

Each method throws `NullPointerException` for a `null` argument or candidate.

## Importers

From `0.4.15`, three types give the import command of a plugin its shape: `Importer`, which a plugin implements
once for each plugin it can import from, `ImportReport`, which says what a run did, and `Importers`, which finds an
importer by the id an owner typed. Taffy reads no other plugin's data: how the source is read, where the result is
written and the backup before a real run stay in the plugin.

| Type | What it is |
|---|---|
| `Importer` | An interface with `id()`, `displayName()`, `present()` and `run(boolean dryRun)`. |
| `ImportReport` | A final class built with `ImportReport.builder()`: the count of entries read, the counts and lines of the imported and the skipped entries, and the warnings. |
| `Importers` | The registry: `create(Logger, ErrorReports)`, `register(Importer)`, `byId(String)`, `presentIds()` and `allIds()`. |

### Writing an importer

```java
import so.alaz.taffy.platform.ImportReport;
import so.alaz.taffy.platform.Importer;
import so.alaz.taffy.platform.Scheduler;

public final class CrazyVouchersImporter implements Importer {

    private final Path source;
    private final Scheduler scheduler;
    private final Vouchers vouchers;

    @Override
    public String id() {
        return "crazyvouchers";
    }

    @Override
    public String displayName() {
        return "CrazyVouchers";
    }

    @Override
    public boolean present() {
        return Files.isDirectory(source);
    }

    @Override
    public CompletableFuture<ImportReport> run(boolean dryRun) {
        try {
            return CompletableFuture.supplyAsync(() -> read(dryRun), scheduler.asyncExecutor());
        } catch (RejectedExecutionException disabling) {
            return CompletableFuture.failedFuture(disabling);
        }
    }

    private ImportReport read(boolean dryRun) {
        ImportReport.Builder report = ImportReport.builder();
        for (SourceVoucher voucher : SourceVoucher.readAll(source, report)) {
            report.read(1);
            if (vouchers.exists(voucher.id())) {
                report.skipped(voucher.id() + ": a voucher of this id exists");
                continue;
            }
            if (!dryRun) {
                vouchers.write(voucher);
            }
            report.imported(voucher.id());
        }
        return report.build();
    }
}
```

`SourceVoucher` and `Vouchers` stand for the plugin's own reading and writing code. The four methods are the
whole contract, and a plugin's importers keep working as later releases add to the other two types.

| Method | Contract |
|---|---|
| `id()` | The id an owner types: 1 to 64 ASCII letters, digits, dots, underscores and hyphens, written in lower case, and the same text on every call. Ids are matched without regard to case. |
| `displayName()` | The name of the source as its author writes it, as plain text, for the plugin's messages. |
| `present()` | Whether the source has data on this server. It is asked each time and never cached, so it is cheap and does not block: it opens no database and parses no file. It can be called from any thread, on Folia too, so it reads only what any thread may read (whether a folder exists, whether a plugin is enabled) and no world, chunk or entity. It does not throw. |
| `run(boolean dryRun)` | Starts the run and returns without blocking, from any thread. It never throws: a run that could not finish completes the future exceptionally, and a run that finished completes it with a report, never with `null`. |

- **A dry run writes nothing.** With `dryRun` true the importer reads and checks the source as a real run does,
  and no file, row or state of the plugin changes. Its report says what a real run would do with the data as it is
  now. Neither kind of run changes the source's own files or tables.
- **One entry that fails does not fail the run.** It becomes a skipped line or a warning, and the future still
  completes with a report. The future fails only when the run as a whole could not finish.
- **The importer chooses its thread.** `run` moves the work to the thread it needs, an async thread for files and
  a database, and the future completes on a thread the importer chooses, usually that one. The example catches the
  `RejectedExecutionException` that `Scheduler.asyncExecutor()` throws while the plugin is not enabled, so `run`
  keeps its promise not to throw.

### The report

```java
ImportReport report = ImportReport.builder()
    .read(3)
    .imported("gold")
    .imported("silver")
    .skipped("vip: a voucher of this id exists")
    .warning("gold: options.glow has no equivalent")
    .build();

report.read();           // 3
report.importedCount();  // 2
report.imported();       // [gold, silver]
report.skippedCount();   // 1
report.skipped();        // [vip: a voucher of this id exists]
report.warnings();       // [gold: options.glow has no equivalent]
```

| Builder method | Effect |
|---|---|
| `read(int count)` | Counts that many more entries of the source as read. |
| `imported(String line)` | Counts one imported entry and names it. |
| `imported(int count)` | Counts that many more imported entries without a line. |
| `skipped(String line)` | Counts one skipped entry and names it with the reason. |
| `skipped(int count)` | Counts that many more skipped entries without a line. |
| `warning(String line)` | Adds a warning, which counts nothing. |
| `build()` | The report of what was added so far. The builder can be added to and built again. |

- **Counts and lines are separate.** An importer of a few files names each entry, and its counts are then the
  numbers of its lines. An importer of many rows, such as one balance for each player, counts them with
  `imported(1)` and `skipped(1)` and writes a line only for what the owner has to look at. `importedCount()` and
  `skippedCount()` hold both kinds, so they are never below the sizes of `imported()` and `skipped()`.
- **In a dry run, imported means would be imported.** The report of a dry run has the same parts, and the plugin
  that called `run(true)` words its message accordingly.
- **Every line is plain text.** No MiniMessage tag or colour code in a line is meant as one, since a line holds
  text read from another plugin's files. Show it with `Component.text(line)` or as the value of
  `Placeholder.unparsed`, never through `Text.render` as part of a template. A plugin that writes lines to a
  public place passes them through `Redaction.hide` first.
- **Nothing is cut or dropped.** The lines keep their order, and the report holds every line it was given.
- **A report is immutable** and is read from any thread; its lists cannot be changed. Two reports are equal when
  their counts and lines are. The builder is not thread-safe: the thread that runs the import builds the report.
- `read`, `imported(int)` and `skipped(int)` throw `IllegalArgumentException` for a negative count and
  `ArithmeticException` when a count would pass `Integer.MAX_VALUE`. A `null` line throws `NullPointerException`.

`ImportReport` is a class with a builder, not a record, so a later release can add a count without changing how
a plugin builds or reads one.

### The registry and the command

```java
import so.alaz.taffy.platform.CommandHelpers;
import so.alaz.taffy.platform.Importer;
import so.alaz.taffy.platform.Importers;

importers = Importers.create(getLogger(), errors)
    .register(new CrazyVouchersImporter(getDataPath().resolveSibling("CrazyVouchers"), scheduler, vouchers));

LiteralArgumentBuilder<CommandSourceStack> command = Commands.literal("import")
    .requires(CommandHelpers.permission("shop.import"))
    .then(Commands.argument("source", StringArgumentType.word())
        .suggests((context, builder) -> CommandHelpers.suggest(builder, importers.presentIds()))
        .executes(context -> runImport(context.getSource().getSender(),
            StringArgumentType.getString(context, "source"), true))
        .then(Commands.literal("confirm")
            .executes(context -> runImport(context.getSource().getSender(),
                StringArgumentType.getString(context, "source"), false))));
```

| Member | Behaviour |
|---|---|
| `Importers.create(Logger logger, ErrorReports errors)` | A registry without importers. The logger and the `ErrorReports` receive what a `present()` threw. |
| `register(Importer importer)` | Adds the importer under its `id()`, which is read once, here, and returns the registry. |
| `byId(String id)` | The `Optional<Importer>` registered under the id, without regard to case, whether or not its source is present. It is the object that was registered. |
| `presentIds()` | The ids of the importers whose `present()` is true, in registration order, as an unmodifiable `List<String>`. |
| `allIds()` | The ids of every importer, in registration order, as an unmodifiable `List<String>`. It calls no importer. |

- **An id names one source.** `register` throws `IllegalArgumentException` for an id that is already registered,
  in any letter case, and the registry keeps the importer it has. It throws the same for an id that is not 1 to 64
  ASCII letters, digits, dots, underscores and hyphens, which is what `StringArgumentType.word()` reads.
- **Ids keep the spelling of the importer.** `presentIds()` and `allIds()` return each id as `id()` gave it when
  the importer was registered, and `byId` finds `CrazyVouchers`, `crazyvouchers` and `CRAZYVOUCHERS` alike.
- **`presentIds()` asks every time.** It calls `present()` of every importer in each call, on the calling
  thread, and caches nothing, so a source installed since the last call is seen.
- **A `present()` that throws counts as absent.** What it threw is logged as a warning, at most once a minute for
  each importer with the stack trace the first time, and reported to the `ErrorReports` under `importer.<id>` with
  the id in lower case. An `Error` other than a `LinkageError` propagates. `byId(id).get().present()` is the
  importer's own method and is not guarded, which is why the command below asks `presentIds()`.
- **The registry runs nothing.** It never calls `run` and takes no backup.
- **Thread-safe.** Every method can be called from any thread, on Folia too, and importers can be registered
  while another thread reads.

### Backup, then the real run

The plugin takes the backup it wants before a real run and calls `run(false)` once that backup has completed. With
`taffy-storage` that is [`Storage.backup`](/docs/modules/storage#sqlite-backups):

```java
private int runImport(CommandSender sender, String id, boolean dryRun) {
    Importer importer = importers.byId(id).orElse(null);
    if (importer == null || !importers.presentIds().contains(importer.id())) {
        sender.sendMessage(Component.text("There is nothing to import from " + id));
        return 0;
    }
    CompletableFuture<?> backup = dryRun
        ? CompletableFuture.completedFuture(null)
        : storage.backup("before-import", 5);
    backup.thenCompose(copy -> importer.run(dryRun)).whenComplete((report, failure) -> {
        if (!scheduler.global(() -> show(sender, importer, dryRun, report, failure))) {
            getLogger().info("The import from " + importer.displayName() + " ended while the plugin disabled");
        }
    });
    return Command.SINGLE_SUCCESS;
}

private void show(CommandSender sender, Importer importer, boolean dryRun, ImportReport report,
                  Throwable failure) {
    if (failure != null) {
        getLogger().log(Level.SEVERE, "The import from " + importer.displayName() + " failed", failure);
        sender.sendMessage(Component.text("The import failed, and the console has the reason"));
        return;
    }
    sender.sendMessage(Component.text(importer.displayName() + (dryRun ? " (dry run)" : "") + ": read "
        + report.read() + ", imported " + report.importedCount() + ", skipped " + report.skippedCount()));
    report.skipped().forEach(line -> sender.sendMessage(Component.text("Skipped: " + line)));
    report.warnings().forEach(line -> sender.sendMessage(Component.text("Warning: " + line)));
}
```

- **A failed backup stops the import.** `thenCompose` does not call `run` when the backup future failed, so
  `failure` is then the backup's. `Storage.backup` fails on MySQL, MariaDB and PostgreSQL, which have no database
  file to copy, so a plugin that supports those asks for the backup only on SQLite.
- **The future completes on the importer's thread.** `whenComplete` therefore hops before it touches the server:
  `scheduler.global` for the console, as above, or `scheduler.entity(player, task, retired)` to answer a player on
  the thread that owns them on Folia. `global` returns `false` once the plugin is disabling.
- **A dry run takes no backup,** since it writes nothing.
- **The module does not depend on `taffy-storage`.** A plugin with another kind of storage takes its backup its
  own way, in the same order.

`LegacyText` converts the colour codes of imported text and leaves tokens such as `{player}` as they are. An
importer that maps another plugin's tokens to its own does that itself.

## Update check

From `0.4.10`, `UpdateCheck` asks once, at enable, whether a newer release of the plugin is published, and tells the
server owner in the log. It downloads nothing, sends no message to a player and owns no thread.

```java
import so.alaz.taffy.platform.UpdateCheck;
import so.alaz.taffy.platform.UpdateSource;

updates = UpdateCheck.start(this, errors, getConfig().getBoolean("update-check.enabled", true),
    UpdateSource.github("alaz", "shop"), scheduler::async);
```

```text
[Shop] A newer release is available: 1.5.0 (running 1.4.0). https://github.com/alaz/shop/releases
```

| Member | Behaviour |
|---|---|
| `UpdateCheck.start(Plugin, ErrorReports, boolean enabled, UpdateSource, Executor)` | Submits the one request to the executor and returns at once. With `enabled` false it sends and logs nothing. |
| `latest()` | The newest published version when it is above the running one, such as `1.5.0` or `1.5.0-rc.1`; otherwise `null`. |
| `UpdateSource.github(String owner, String repository)` | The 30 newest releases of a GitHub repository. |
| `UpdateSource.modrinth(String project)` | The versions of a Modrinth project, by id or slug. |

The `enabled` argument is the plugin's own config switch, so a server owner can turn the check off. Taffy reads no
config key itself.

### What is compared

The running version is `getPluginMeta().getVersion()`. Versions are read as [Semantic Versioning](https://semver.org)
2.0.0, with a leading `v` and a missing patch number allowed and build metadata dropped.

| Running version | Compared with |
|---|---|
| `1.4.0`, no pre-release part | the published releases only |
| `1.5.0-rc.1` or `1.5.0-SNAPSHOT`, with a pre-release part | the published releases and pre-releases |
| `build-17`, not a semantic version | nothing: one warning is logged and no request is sent |

- A pre-release is below its own release and above the release before it: `1.5.0-SNAPSHOT` is below `1.5.0` and
  above `1.4.9`. Pre-release identifiers compare as the specification orders them, so `1.5.0-rc.2` is above
  `1.5.0-rc.1` and `1.5.0-rc.1` is above `1.5.0-beta.3`.
- Whether a published version is a pre-release is what the source says about it, not the form of its text. On
  GitHub it is a release with `prerelease` set, and a draft is left out. On Modrinth it is a version whose
  `version_type` is not `release`, and a version whose `status` is not `listed` is left out.
- The version of a GitHub release is its `tag_name`, and of a Modrinth version its `version_number`. A published
  version that is not a semantic version is skipped.
- The newest version that is left is compared. When it is not above the running version, nothing is logged and
  `latest()` stays `null`.

`latest()` holds only ASCII letters, digits, `.` and `-`, at most 66 characters. A plugin that tells its staff on
join reads it there and chooses who sees it:

```java
@EventHandler
void onJoin(PlayerJoinEvent event) {
    String latest = updates.latest();
    if (latest != null && event.getPlayer().hasPermission("shop.admin")) {
        event.getPlayer().sendMessage(Component.text("Shop " + latest + " is available"));
    }
}
```

### The request

- One `GET` over HTTPS, to `https://api.github.com/repos/<owner>/<repository>/releases?per_page=30` or
  `https://api.modrinth.com/v2/project/<project>/version?include_changelog=false`, without an account or token. It
  follows no redirect.
- Its headers are `Host`, `Connection`, `Cache-Control: no-cache`, `Pragma: no-cache`, `Accept`, for GitHub
  `X-GitHub-Api-Version`, and a `User-Agent` of the plugin's name and version, such as `Shop/1.4.0`. It holds no
  player data and nothing about the server.
- Connecting and each read wait at most 10 seconds. The read of the status line and headers is ended 30 seconds
  after the request began, and no read of the body starts after that, so a request whose connection is made in time
  ends within 40 seconds. How long the host name takes to resolve is the system's, and the TLS handshake is bound
  by the 10 seconds of each read alone.
- At most 262144 bytes of the answer are read, and of them the first 100 entries. What is complete within that is
  compared, since both sources answer newest first.
- The request runs on the executor passed to `start` and blocks it until the answer is read. Pass an executor that
  runs off the server threads, such as `scheduler::async`. A task that finds itself on a server thread logs a
  warning and sends nothing.
- `UpdateSource.github` and `UpdateSource.modrinth` throw `IllegalArgumentException` for a name that is not a
  GitHub owner, a repository name or a Modrinth id or slug, so a name cannot change the address.

### A failed check

Nothing is thrown into enable for a failed check. Each of these logs one warning on the plugin's logger and leaves
`latest()` at `null`:

| Case | Line |
|---|---|
| An answer other than status 200, a redirect included | `Update check failed: api.github.com answered with status 404` |
| A failed or timed out connection | `Update check failed: could not read from api.github.com (java.net.SocketTimeoutException)` |
| An answer that is not a list of releases | `Update check failed: the answer of api.github.com is not a list of releases` |
| A running version that is not a semantic version | `Update check skipped: the plugin's version build-17 is not a semantic version such as 1.4.0` |
| An executor that refuses the task | `Update check skipped: the executor refused it (java.util.concurrent.RejectedExecutionException)` |
| An executor that runs the task on a server thread | `Update check skipped: the executor ran it on a server thread, and the request waits on the network` |

An exception of another kind is logged as `Update check failed: <exception class>` and reported to the
`ErrorReports` under `update-check`. A network failure is not reported there. An executor that drops the task
without throwing, as `scheduler::async` does once the plugin disables, logs nothing. The wording of these lines can
change in any release.

A request that is still waiting when the plugin disables ends by its timeouts. After it was sent it touches only
the plugin's logger and the `UpdateCheck`. `start` throws `NullPointerException` for a `null` argument.

## Discord

`DiscordWebhook` posts to Discord webhooks asynchronously through one HTTP client.

| Member | Behaviour |
|---|---|
| `post(String url, String content, Consumer<String> onError)` | Posts `content` as the message text, cut to 2000 characters. From `0.2.0`, no mention in it pings. |
| `post(String url, String content, PostOptions options, Consumer<String> onError)` | From `0.2.0`. The same, with the mention types of `options` allowed to ping. |
| `postBody(String url, String body, Consumer<String> onError)` | Posts a ready JSON body as given, with nothing added. |
| `isWebhookUrl(String)` | Static. Whether the URL is an `https` Discord webhook URL on `discord.com` or `discordapp.com`, with optional `canary.` or `ptb.` and API version. |
| `close()` | Closes the client and waits for the in-flight requests. From `0.2.0`, for at most 5 seconds. |
| `close(Duration wait)` | From `0.2.0`. The same, waiting at most `wait`. |

```java
String url = settings.get().webhookUrl();
if (DiscordWebhook.isWebhookUrl(url)) {
    webhook.post(url, buyer.getName() + " bought a voucher",
        reason -> getLogger().warning("Discord webhook failed: " + reason));
}
```

`settings` is the plugin's `ConfigHolder` of [taffy-config](/docs/modules/config), so the post uses the URL of the last
reload that succeeded.

Failures are never thrown. Each one reaches `onError` as a one-line reason for the server owner's log, such as
`invalid webhook URL` or `Discord returned HTTP 404`, and nothing is reported to `ErrorReports`. The callback runs at
most once per post, either on the calling thread (a URL that does not parse, or a post after `close()`) or later on
a thread the caller does not choose. A callback for a request that has already finished can still run after
`close()` has returned. It must not throw: what it throws for a request that was sent is discarded, and for a URL
that does not parse it reaches the caller of the post method. Neither post method checks that the URL points at
Discord:
apply `isWebhookUrl` when reading the URL from config.

### Mentions

From `0.2.0`, `post` sends `"allowed_mentions": {"parse": []}` with the content, so `@everyone`, `@here`, a role
mention such as `<@&roleId>` and a user mention such as `<@userId>` are shown as text and ping no one. In `0.1` the
key was not sent, Discord's default applied, and player text in a post (an item renamed to `@everyone free nitro`,
a reason, a chat line) could ping the whole guild.

A post that is meant to ping names the mention types to allow in a `DiscordWebhook.PostOptions`:

| `DiscordWebhook.Mention` | Allows | Name in `allowed_mentions.parse` |
|---|---|---|
| `EVERYONE` | `@everyone` and `@here` | `everyone` |
| `ROLES` | role mentions | `roles` |
| `USERS` | user mentions | `users` |

```java
import so.alaz.taffy.platform.DiscordWebhook.Mention;
import so.alaz.taffy.platform.DiscordWebhook.PostOptions;

webhook.post(url, "<@&" + restockRoleId + "> the shop restocked",
    PostOptions.allowing(Mention.ROLES),
    reason -> getLogger().warning("Discord webhook failed: " + reason));
```

`PostOptions` is a record of a `Set<Mention>`; `PostOptions.allowing(Mention...)` and `PostOptions.noMentions()`
build one. An allowed type covers every mention of that type in the content, the ones in player text too, so allow
a type only for content the plugin or the server owner wrote.

`postBody` passes its body through raw: it is sent as given, with nothing added, removed or checked. A body without
an `allowed_mentions` key leaves Discord's default in force, under which every mention in it pings.

From `0.2.0`, `close()` blocks the calling thread until every in-flight request has finished or 5 seconds have
passed, whichever comes first, and `close(Duration wait)` does the same with the given wait. The requests still in
flight when the wait ends are aborted and fail through their callbacks; a zero or negative wait aborts them at
once. In `0.1`, `close()` had no upper bound: each request fails when no response headers arrive within 15 seconds,
but a server that sent headers and then stalled kept the disabling thread blocked longer. An interrupt ends the
wait, aborts the in-flight requests through their callbacks and stays set. Closing the webhook is meant to be the
last step of a shutdown before metrics.

`WebhookPayload.render(Map<String, Object> template, UnaryOperator<String> resolve)` turns a payload template (nested
maps, lists, strings, numbers and booleans) into the JSON body `postBody` sends. Every string goes through
`resolve` first, and the structure is then serialized, so a resolved value cannot change the JSON structure.

From `0.2.0`, a value in the template is one of these types, at any depth:

| Value | Rendered as |
|---|---|
| `String` | the result of `resolve` |
| `Number`, `Boolean` | itself |
| `null` | `null` in a list; a key whose value is `null` is left out of its object |
| `Map` | an object, with each key as `String.valueOf` gives it |
| `List` | an array |
| Bukkit `ConfigurationSection` | an object of the section's own keys |

Any other type makes `render` throw `IllegalArgumentException`, and the message names the value by its key path,
such as `embeds[0].timestamp`. A `Double` or `Float` that is `NaN` or infinite is refused the same way. A payload read from config holds a `ConfigurationSection` for each nested object, so
it can go to `render` as read:

```java
Map<String, Object> template = settings.get().source().getConfigurationSection("payload").getValues(false);
```

`source()` is the section the settings record was read from, kept as a component as in
[taffy-config](/docs/modules/config#the-settings-model).

In `0.1` a section and every other type went to the JSON serializer as they were, which did not write a section as
the object the config held.

From `0.2.0`, `render` adds `"allowed_mentions": {"parse": []}` to the top level of a template that has no
`allowed_mentions` key of its own, or sets the key to `null`, so a mention in a resolved value pings no one. A
template that gives the key any other value keeps that value unchanged. That is how a server owner allows mentions from config:

```yaml title="config.yml"
payload:
  content: '<@&123456789012345678> {buyer} bought {item}'
  allowed_mentions:
    parse: [roles]
```

```java
Map<String, Object> template = Map.of(
    "username", "Shop",
    "embeds", List.of(Map.of("title", "{buyer} bought {item}", "color", 5814783)));

String body = WebhookPayload.render(template,
    value -> value.replace("{buyer}", buyer.getName()).replace("{item}", "a voucher"));
webhook.postBody(url, body, reason -> getLogger().warning("Discord webhook failed: " + reason));
```

## Threads at a glance

| Class | Thread rule |
|---|---|
| `Scheduler`, `ErrorReports`, `TaskGate`, `PendingSettlements`, `CooldownManager`, `ThrowLog`, `Redaction` | any thread |
| `CommandHelpers` | `permission`, `matching` and `suggest` on any thread; `target` on a thread that may read the server's player list |
| `Importers`, `ImportReport` | any thread; `presentIds()` calls each `Importer.present()` on the calling thread; an `ImportReport.Builder` is used by one thread |
| `Importer` | `present()` and `run` are called from any thread; the future of `run` completes on a thread the importer chooses |
| `UpdateCheck` | `start` and `latest` on any thread; the request runs on the executor passed to `start`, never on a server thread |
| `DiagnosticReport` | `build()` runs every section's supplier on the calling thread; a built report is read from any thread |
| `PlayerCache` | any thread for `get`, `ready`, `refresh` and `close`; the loader runs on an async thread |
| `Text`, `Messages` | any thread without a viewer; the player's thread with one; for the `OfflinePlayer` and `Global` methods of `Text`, a thread the asked PlaceholderAPI expansions accept |
| `Items.giveOrDrop`, `Sounds.play` | the thread that owns the player |
| `InventoryFit.fits` | the thread that owns the inventory, for live slots |
| `SkullBuilder.fromName`, `fromUuid` | any thread; the future completes on the lookup executor, or on the calling thread for a cached texture |
| `DiscordWebhook` callbacks | the calling thread for a URL that does not parse or a post after `close()`, otherwise a thread the caller does not choose |
