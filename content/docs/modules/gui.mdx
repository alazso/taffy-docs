---
title: taffy-gui
description: Chest menus with layouts from code or the plugin's own files, pagination, a footer, click safety and text prompts in chat, an anvil or a Paper dialog.
---

`taffy-gui` gives a plugin chest menus. A menu's look (its rows, filler, list slots and items) is a layout the plugin builds in code or reads from its own files, and the menu's code only says what each action does and what the list holds. The module opens every menu on the viewer's entity thread, pages lists, draws a footer with back, page arrows, refresh and close, loads slow data in the background, and keeps the items a menu shows from leaving it. `Prompts` asks a player for one line of text in chat or in an anvil and returns to the menu with the answer. From `0.4.3` it also asks in a Paper dialog (experimental) and, with a `TextRequest`, from a command or a plugin's own screen with no menu to return to. Names and lore come from the plugin's lang files through `Messages` from [taffy-platform](/docs/modules/platform), where a YAML list is one lore line per entry. From `0.3.0`, a plugin that keeps its text elsewhere passes its own [`TextSource`](#text-source) in their place.

Every type is in `so.alaz.taffy.gui`.

| Area | Types |
|---|---|
| Layouts | `MenuLayout`, `ItemLayout`, `PagerLayout`, `MenuKind` |
| Drawing | `Icon` (`Icon.Button`, `Icon.Filler`, `Icon.Real`, `Icon.Saved`), `MenuText`, `TextSource`, `Frame` (`Frame.Spec`, `Frame.Entry`), `Pager` (`Pager.Page`) |
| Runtime | `Menus` (`Menus.Parts`), `Menu`, `MenuSession`, `MenuSettings`, `Route`, `Click`, `ClickHandler`, `ClickGuard`, `Cue`, `ViewMemory` |
| Text prompts | `Prompts`, `PromptRequest`, `TextRequest`, `Answer` (`Answer.Accept`, `Answer.Retry`, `Answer.Later`), `PromptEnd`, `PromptMode`, `BedrockPlayers` |
| Tests | `MenuTesting`, from `0.4.5` |

## Setup

The module is `so.alaz.taffy:taffy-gui`, `alaz.taffy.gui` in the catalog. It depends on `taffy-platform` as an API dependency, so `Messages`, `Scheduler`, `EntityThread` and `ErrorReports` come with it.

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.gui)
}
```

`so.alaz.taffy.paper-plugin` shades the module and relocates `so.alaz.taffy` to `<group>.libs.taffy`, so two plugins that both carry it never share a copy. Adventure and MiniMessage come from Paper and are not bundled. The library reads no file and ships no lang file: the plugin reads its layouts, settings and lang files and passes the values in.

## Enable and disable

The plugin builds one `Menus` at enable from a `Menus.Parts`, builds its `Prompts` over it when it asks for text, and registers each `Menu`. From `0.3.0`, `new Menus(parts)` registers the menu listener and `new Prompts(menus, ...)` the prompt listener, each as a listener of the plugin in `Menus.Parts`, so a menu cannot open with nothing to cancel its clicks and the plugin registers no listener itself. Before `0.3.0` the plugin passed `menus.listener()` and `prompts.listener()` to `registerEvents`, and a plugin that forgot the call opened menus whose icons players could take.

Build the menus while the plugin is enabled, such as in `onEnable`. The server refuses a listener of a plugin that is not enabled with an `IllegalPluginAccessException`, which leaves `new Menus(parts)`, so no menus exist then.

From `0.3.0`, `Menus.Parts` is built through `Menus.Parts.of(plugin, text, tasks, entity, errors)`, which takes what has no default, and a method per other value, each of which gives a copy with that value replaced. Before `0.3.0` it was a record built with `new Menus.Parts(...)` and all twelve values by position. The methods that read a value (`layouts()`, `settings()` and the rest) keep their names.

| Argument of `Menus.Parts.of` | Type | What to pass |
|---|---|---|
| `plugin` | `Plugin` | The plugin that owns the menus, `this` in `onEnable`. The menus and their prompts register their listeners as its listeners. |
| `text` | `TextSource`, or `Messages` | The text of each lang key: the plugin's `Messages`, or its own [`TextSource`](#text-source). |
| `tasks` | `BiConsumer<Player, Runnable>` | Runs work on a player's entity thread on the next tick: `scheduler::entity`. |
| `entity` | `EntityThread` | Runs load results and prompt answers on the player's entity thread: `EntityThread.on(scheduler, getServer())`. |
| `errors` | `ErrorReports` | The plugin's error sink. |

| Method of `Menus.Parts` | Type | What to pass | Default |
|---|---|---|---|
| `layouts` | `Map<String, MenuLayout>` | The layout of each menu, keyed by menu id. Each key equals its layout's `menu()`, or the method throws `IllegalArgumentException`. | no layouts |
| `settings` | `MenuSettings` | The page size, filler, click debounce and loading item, from the plugin's config. | `MenuSettings.DEFAULTS` |
| `locales` | `Function<Player, Locale>` | The locale menu and prompt text renders in. | `Player::locale` |
| `sounds` | `Supplier<Map<Cue, Sound>>` | The Adventure `Sound` of each `Cue`, read every time one plays. | no sounds |
| `home` | `String`, nullable | The id of the menu the back button opens when a menu has no back route, or `null`. | `null` |
| `server` | `Server` | The server, which creates each menu inventory, tells whether the calling thread owns a player and registers the listeners. | `plugin.getServer()` |
| `preview` | `NamespacedKey` | The key every shown stack carries. | `new NamespacedKey(plugin, "preview")` |
| `logger` | `Logger` | The logger handled failures are logged through. | `plugin.getLogger()` |

```java title="WarpsPlugin.java"
import net.kyori.adventure.key.Key;
import net.kyori.adventure.sound.Sound;
import org.bukkit.plugin.java.JavaPlugin;
import so.alaz.taffy.gui.BedrockPlayers;
import so.alaz.taffy.gui.Cue;
import so.alaz.taffy.gui.Menus;
import so.alaz.taffy.gui.PromptMode;
import so.alaz.taffy.gui.Prompts;
import so.alaz.taffy.platform.EntityThread;
import so.alaz.taffy.platform.ErrorReports;
import so.alaz.taffy.platform.Messages;
import so.alaz.taffy.platform.Scheduler;
import so.alaz.taffy.platform.Shutdown;

import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CopyOnWriteArrayList;

public final class WarpsPlugin extends JavaPlugin {

    private final ErrorReports errors = new ErrorReports();
    private volatile Map<Cue, Sound> sounds = Map.of(
        Cue.CLICK, Sound.sound(Key.key("ui.button.click"), Sound.Source.MASTER, 0.5f, 1f),
        Cue.SUCCESS, Sound.sound(Key.key("entity.experience_orb.pickup"), Sound.Source.MASTER, 0.5f, 1f),
        Cue.FAIL, Sound.sound(Key.key("block.note_block.bass"), Sound.Source.MASTER, 0.5f, 1f));
    private Scheduler scheduler;
    private Messages messages;
    private Menus menus;
    private final CopyOnWriteArrayList<String> warpNames = new CopyOnWriteArrayList<>();
    private final WarpsMenu.Warps warps = new WarpsMenu.Warps() {
        @Override
        public CompletableFuture<List<String>> names() {
            return CompletableFuture.completedFuture(List.copyOf(warpNames));
        }

        @Override
        public void create(String name) {
            warpNames.addIfAbsent(name);
        }
    };

    @Override
    public void onEnable() {
        scheduler = new Scheduler(this, errors);
        messages = Messages.load(getDataFolder().toPath(), () -> getResource("lang/en.yml"), getLogger());
        menus = new Menus(Menus.Parts.of(this, messages, scheduler::entity,
                EntityThread.on(scheduler, getServer()), errors)
            .layouts(Map.of(WarpsMenu.KIND.id(), MenuLayouts.warps()))
            .sounds(() -> sounds));
        Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
        menus.register(new WarpsMenu(menus, prompts, warps));
    }

    @Override
    public void onDisable() {
        Shutdown.closeQuietly("close the menus", () -> menus.shutdown(), getLogger(), errors);
        Shutdown.closeQuietly("close the scheduler", () -> scheduler.close(), getLogger(), errors);
    }
}
```

`register` throws `IllegalArgumentException` when no layout was given for the menu's id, when a menu is already registered under it, or when the layout does not fit the kind: a kind that shows a list with a layout that has none, or an item whose action is neither one of the kind's actions nor a footer action. `registered(id)` tells whether a menu is registered.

`Menus.shutdown()` runs before `Scheduler.close()`, in the disable order the [taffy-platform](/docs/modules/platform) package states. See [Shutdown](#shutdown) for what it does.

## Layouts

### MenuKind

A `MenuKind` is a menu's id, whether it shows a list, and its actions, each with the lang key base its text reads. An action reads its name from `<base>.name` and its lore from `<base>.lore`.

```java
public static final MenuKind KIND = MenuKind.of("warps", true, "create",
    MenuKind.BACK, MenuKind.PREVIOUS_PAGE, MenuKind.NEXT_PAGE, MenuKind.REFRESH, MenuKind.CLOSE);
```

`MenuKind.of(id, paged, actions...)` gives every action the base `gui.<id>.<action>`. `text(action, base)` returns a copy with one action reading another base, and a `null` base means the menu supplies the whole icon through `Frame.Spec.icon`. It throws `IllegalArgumentException` for an action the kind does not have. `actions()`, `has(action)` and `textBases(action)` read the kind back.

The footer actions are the constants `BACK` (`back`), `PREVIOUS_PAGE` (`previous-page`), `NEXT_PAGE` (`next-page`), `REFRESH` (`refresh`) and `CLOSE` (`close`). When their own base has no text they fall back to `gui.footer.<action>` (`MenuKind.FOOTER_TEXT` is the prefix `gui.footer.`), so one set of footer text serves every menu.

### Building a layout in code

From `0.3.0`, `MenuLayout`, `ItemLayout`, `PagerLayout`, `MenuSettings` and `Menus.Parts` are final classes with no public constructor. Each is built through a static factory that takes what has no default, and a method named after each other value gives a copy with that value replaced, so a value a later release adds breaks no plugin. Before `0.3.0` they were records built with `new` and every value by position. Each still checks what it is given, and the three layout types and `MenuSettings` still compare by value.

```java title="MenuLayouts.java"
import org.bukkit.Material;
import so.alaz.taffy.gui.ItemLayout;
import so.alaz.taffy.gui.MenuKind;
import so.alaz.taffy.gui.MenuLayout;
import so.alaz.taffy.gui.PagerLayout;

import java.util.List;

final class MenuLayouts {

    static MenuLayout warps() {
        PagerLayout list = PagerLayout.of(
                List.of(10, 11, 12, 13, 14, 15, 16, 19, 20, 21, 22, 23, 24, 25, 28, 29, 30, 31, 32, 33, 34))
            .emptySlot(22)
            .emptyMaterial(Material.PAPER);
        return MenuLayout.of("warps", 6)
            .filler(Material.BLACK_STAINED_GLASS_PANE)
            .pager(list)
            .items(List.of(
                ItemLayout.of("header", List.of(4), Material.COMPASS).name("<aqua>Warps"),
                ItemLayout.of("back", List.of(45), Material.ARROW).action(MenuKind.BACK),
                ItemLayout.of("previous", List.of(48), Material.ARROW).action(MenuKind.PREVIOUS_PAGE),
                ItemLayout.of("create", List.of(49), Material.EMERALD).action("create").permission("warps.create"),
                ItemLayout.of("next", List.of(50), Material.ARROW).action(MenuKind.NEXT_PAGE),
                ItemLayout.of("refresh", List.of(52), Material.SUNFLOWER).action(MenuKind.REFRESH),
                ItemLayout.of("close", List.of(53), Material.BARRIER).action(MenuKind.CLOSE)));
    }
}
```

| Type | Factory | Methods that replace a value | Checks |
|---|---|---|---|
| `MenuLayout` | `MenuLayout.of(menu, rows)`, with `rows` from 1 to 6: no items, no list, the settings' filler and the lang title | `filler` (nullable: the settings' filler), `pager` (nullable: no list), `items` (a collection, in the order `items()` keeps), `item` (adds one item, or replaces the item of the same id in its place), `title` (nullable: the lang title) | Rows in range, no item id twice, every item slot and list slot inside `rows * 9`. `items()` gives the items keyed by item id, `size()` gives `rows * 9`, `items(action)` the items of one action. |
| `ItemLayout` | `ItemLayout.of(id, slots, material)`, with `slots` not empty: a shown item with no action, permission, name or lore | `action` (nullable: decoration), `permission` (nullable), `enabled`, `name` (nullable), `lore` (nullable) | At least one slot. |
| `PagerLayout` | `PagerLayout.of(slots)`, the slots in fill order: no empty state | `emptySlot` (nullable), `emptyMaterial` (nullable: `PAPER`) | Slots not empty, each from 0 to 53, none twice, and `emptySlot` one of them. |
| `MenuSettings` | `MenuSettings.DEFAULTS` | `pageSize`, `filler`, `clickDebounce`, `loadingItem` | See [Click safety](#click-safety). |

Each method returns a new value and leaves the one it was called on unchanged, so a layout or `MenuSettings.DEFAULTS` is safe to share.

A bad value throws `IllegalArgumentException` (or `NullPointerException` for a missing required part) with a message that names the value it refuses: the menu and item for a `MenuLayout`, the item for an `ItemLayout`, the slot for a `PagerLayout`. A plugin that reads layouts from files catches it and shows the message to the owner.

The layouts do not check that a material is an item, since that needs a running server. From `0.3.0`, `Menus.register` and `Menus.reload` do: they throw `IllegalArgumentException` for a material that is not an item a slot can show, air included, whether it is the material of an `ItemLayout` (shown or not), the `filler` of a `MenuLayout`, the `emptyMaterial` of a `PagerLayout` or, in `register`, the `filler` or `loadingItem` of the `MenuSettings`. The message names the menu and the item, such as `item buy of the shop menu has the material WALL_TORCH, which is not an item`. Before `0.3.0` such a layout registered and every open of the menu failed with a stack trace.

Behaviour of a layout:

- An item with an action is a button the menu draws for that action. An item without one is decoration, drawn as written, with its tooltip hidden when it has no name.
- An item with a `permission` shows only to viewers who have it, and one with `enabled` false never shows. The permission decides only whether the item is drawn, each time the menu draws. A click is not checked against it, so a viewer who lost the permission since the last draw can still click the button: a handler whose action needs a permission checks it itself.
- A `name`, `lore` or `title` written in the layout is trusted MiniMessage from the owner and replaces the lang text in every language.
- `items` keeps its order. Decoration is placed first, then each action when the menu draws it. Where two items share a slot, the one placed later wins.
- Every slot nothing fills shows the filler.

```java title="LayoutFiles.java"
import org.bukkit.Material;
import org.bukkit.configuration.ConfigurationSection;
import org.bukkit.configuration.InvalidConfigurationException;
import org.bukkit.configuration.file.YamlConfiguration;
import so.alaz.taffy.gui.ItemLayout;
import so.alaz.taffy.gui.MenuLayout;
import so.alaz.taffy.gui.PagerLayout;

import java.io.IOException;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

final class LayoutFiles {

    static MenuLayout read(String menu, Path file) throws IOException, InvalidConfigurationException {
        YamlConfiguration yaml = new YamlConfiguration();
        yaml.load(file.toFile());
        return layout(menu, yaml);
    }

    static MenuLayout layout(String menu, ConfigurationSection file) {
        List<ItemLayout> items = new ArrayList<>();
        ConfigurationSection section = file.getConfigurationSection("items");
        if (section != null) {
            for (String id : section.getKeys(false)) {
                ConfigurationSection item = section.getConfigurationSection(id);
                if (item == null) {
                    throw new IllegalArgumentException("items." + id + " of the " + menu + " menu is not a section");
                }
                items.add(ItemLayout.of(id, item.getIntegerList("slots"), material(item.getString("material")))
                    .action(item.getString("action"))
                    .permission(item.getString("permission"))
                    .enabled(item.getBoolean("enabled", true))
                    .name(item.getString("name"))
                    .lore(item.isList("lore") ? item.getStringList("lore") : null));
            }
        }
        ConfigurationSection list = file.getConfigurationSection("list");
        PagerLayout pager = list == null ? null : PagerLayout.of(list.getIntegerList("slots"))
            .emptySlot(list.isInt("empty-slot") ? list.getInt("empty-slot") : null)
            .emptyMaterial(list.isString("empty-item") ? material(list.getString("empty-item")) : null);
        return MenuLayout.of(menu, file.getInt("rows", 6))
            .filler(file.isString("filler") ? material(file.getString("filler")) : null)
            .pager(pager)
            .items(items)
            .title(file.getString("title"));
    }

    private static Material material(String name) {
        Material material = name == null ? null : Material.matchMaterial(name);
        if (material == null) {
            throw new IllegalArgumentException("unknown material " + name);
        }
        return material;
    }
}
```

The YAML keys of `items` become the item ids, and a YAML section holds no key twice, so no item id is given twice. A missing `slots` list reaches `ItemLayout` as an empty list and is refused with "item `<id>` fills no slot". The plugin writes its default file with `saveResource("menus/warps.yml", false)` and reads it at enable and on reload. [taffy-config](/docs/modules/config) has `YamlFolder` for a plugin that keeps one file per menu in a folder.

## Writing a menu

A `Menu<S>` is the code side of one menu, where `S` is the state it shows (a page number, a tab, a selected entry). Every method runs on the viewer's entity thread.

| Method | When it runs |
|---|---|
| `MenuKind kind()` | The kind whose id names the menu and its layout. |
| `S initial(Player viewer)` | The state the menu opens with when no route names one. Never `null`. |
| `Class<? super S> stateType()` | From `0.3.0`: a type every state of the menu is an instance of, such as `Integer.class` for a `Menu<Integer>`. `Menus.open(viewer, route)` and `openLater(viewer, route)` refuse a route whose state is no instance of it. By default `Object.class`, which accepts every state. |
| `Component title(Frame<S> frame)` | Once, when the menu opens. By default the layout's title, or the lang key `gui.<id>.title`. A redraw keeps the title, so a new title takes a new open. |
| `void render(Frame<S> frame)` | On every draw. Places the actions, list rows and states. |
| `void opened(MenuSession<S> session, Player viewer)` | After the inventory opened. The place to start loads. Does nothing by default. |
| `void closed(MenuSession<S> session, boolean left)` | Once the session ended. `left` is `true` when the viewer closed it, quit, died, or another plugin's inventory replaced it, and `false` when these menus opened another menu in its place, a prompt took over through `Prompts.ask`, or the menus are stopping. The session never opens again after this call, whatever `left` is. Does nothing by default. |

```java title="WarpsMenu.java"
import net.kyori.adventure.text.Component;
import net.kyori.adventure.text.minimessage.tag.resolver.Placeholder;
import org.bukkit.Material;
import org.bukkit.entity.Player;
import so.alaz.taffy.gui.Answer;
import so.alaz.taffy.gui.Frame;
import so.alaz.taffy.gui.Icon;
import so.alaz.taffy.gui.Menu;
import so.alaz.taffy.gui.MenuKind;
import so.alaz.taffy.gui.MenuSession;
import so.alaz.taffy.gui.Menus;
import so.alaz.taffy.gui.Pager;
import so.alaz.taffy.gui.PromptRequest;
import so.alaz.taffy.gui.Prompts;

import java.util.List;
import java.util.concurrent.CompletableFuture;

public final class WarpsMenu implements Menu<WarpsMenu.State> {

    public static final MenuKind KIND = MenuKind.of("warps", true, "create",
        MenuKind.BACK, MenuKind.PREVIOUS_PAGE, MenuKind.NEXT_PAGE, MenuKind.REFRESH, MenuKind.CLOSE);

    public record State(int page) {
    }

    public interface Warps {
        CompletableFuture<List<String>> names();

        void create(String name);
    }

    private record Loaded(List<String> names) {
    }

    private final Menus menus;
    private final Prompts prompts;
    private final Warps warps;

    public WarpsMenu(Menus menus, Prompts prompts, Warps warps) {
        this.menus = menus;
        this.prompts = prompts;
        this.warps = warps;
    }

    @Override
    public MenuKind kind() {
        return KIND;
    }

    @Override
    public State initial(Player viewer) {
        return new State(0);
    }

    @Override
    public void opened(MenuSession<State> session, Player viewer) {
        menus.load(session, warps.names(), (s, names) -> s.data(new Loaded(names)));
    }

    @Override
    public void render(Frame<State> frame) {
        MenuSession<State> session = frame.session();
        frame.action("create", Frame.Spec.click(click -> prompts.askLater(click.player(), nameRequest(session))));
        Pager.Page page = null;
        if (session.data() instanceof Loaded loaded) {
            List<Frame.Entry> rows = loaded.names().stream()
                .map(name -> Frame.Entry.display(icon(frame, name)))
                .toList();
            page = frame.list(rows, frame.state().page());
            if (rows.isEmpty()) {
                frame.empty();
            }
        } else {
            frame.loading();
        }
        frame.footer(page, State::new,
            click -> menus.load(session, warps.names(), (s, names) -> s.data(new Loaded(names))));
    }

    private static Icon icon(Frame<State> frame, String name) {
        return new Icon.Button(Material.ENDER_PEARL, 1, Component.text(name),
            frame.text().lines(frame.locale(), "gui.warps.row.lore", Placeholder.unparsed("name", name)), false);
    }

    private PromptRequest nameRequest(MenuSession<State> session) {
        Player viewer = session.viewer();
        return new PromptRequest(
            menus.text().label(viewer.locale(), "gui.warps.create.question"),
            "",
            session.route(),
            text -> {
                if (!text.matches("[a-z0-9_]{1,16}")) {
                    return new Answer.Retry(menus.text().label(viewer.locale(), "gui.warps.create.invalid"));
                }
                warps.create(text);
                return new Answer.Accept(session.route());
            });
    }
}
```

`warps` keeps names in memory; a plugin that keeps warps across restarts implements `WarpsMenu.Warps` over its own storage.

Each row is a display entry with no click. A row that opens another menu uses `Frame.Entry.click(icon, click -> menus.openLater(click.player(), new Route(id, state, session.route())))`, where `id` is a menu the plugin registered with a layout in `Menus.Parts.layouts` and `state` is of the type that menu accepts. Passing `session.route()` as the back route makes that menu's back button return to this page.

### Frame

A `Frame<S>` is one render. It reads `state()`, `viewer()`, `locale()`, `layout()`, `kind()`, `session()`, `text()` and `menus()`, and places content:

| Method | What it places |
|---|---|
| `action(action, spec)` | Every enabled layout item with that action the viewer has the permission for. Throws `IllegalArgumentException` for an action the kind does not have. |
| `list(entries, requestedPage)` | The page of `entries` nearest `requestedPage` in the first `capacity()` list slots. Returns the `Pager.Page` shown. |
| `list(count, requestedPage, entryAt)` | From `0.3.0`: the same page of a list of `count` entries, asking the `IntFunction<Frame.Entry>` only for the entries on that page, each once and in order. Use it for a long list, so a render builds no icon for a row it does not show. Throws `NullPointerException` when `entryAt` gives `null`. |
| `capacity()` | How many rows a page shows: the smaller of the page size and the number of list slots. |
| `loading()` | The settings' loading item, named by `Frame.LOADING` (`gui.common.loading.name`), in the first `capacity()` list slots. Clicks on it do nothing. |
| `empty()` | The empty state in the list's `emptySlot`, named and described by `gui.<id>.empty.name` and `gui.<id>.empty.lore` where the lang files hold them. Nothing when the list has no empty slot. |
| `footer(page, turn, refresh)` | The footer actions. See [Pagination and the footer](#pagination-and-the-footer). |

`list`, `capacity`, `loading` and `empty` throw `IllegalStateException` when the layout has no list. Only the slots a render placed with a handler are buttons: a redraw that leaves a slot out removes its button.

`Frame.Spec` says how an action renders. `Spec.display()` shows it with no click, and `Spec.click(handler)` acts on any plain left or right click, shift included. The withers return copies:

| Wither | Effect |
|---|---|
| `with(TagResolver...)` | Adds placeholders the action's name and lore read. |
| `lore(List<Component>)` | Lines added after the lang lore. |
| `glint(boolean)` | The enchantment glint. |
| `icon(Icon)` | A whole icon that replaces the layout's item and text. |
| `amount(int)` | The stack amount. |
| `clicks(Set<ClickType>)` | The click types the button acts on, such as `ClickGuard.LEFT_ONLY`. |
| `exclusively()` | The button is exclusive: a click on it is dropped while the session is busy. See [Exclusive buttons](#exclusive-buttons). |

```java
frame.action("balance", Frame.Spec.display()
    .with(Placeholder.unparsed("amount", Integer.toString(coins)))
    .glint(coins > 0));
```

`Frame.Entry` is one list row: `Entry.display(icon)`, `Entry.click(icon, handler)` and `exclusively()`, or the constructor `new Frame.Entry(icon, handler, clicks, exclusive)` for other click types.

From `0.3.0`, `key(String)` gives a row a stable key: what names the thing the row acts on among the entries of the menu, the same on every render that shows it, such as the id of a listing. The key tells the menus whether a redraw put another row in a slot, as [Click safety](#click-safety) describes, and the click debounce of a keyed row follows the key when the row moves to another slot. `key()` reads it and is `null` for a row with none, which is what `Entry.click`, `Entry.display` and the four-argument constructor give; the record's fifth component is the key.

```java
frame.list(listings.size(), frame.state(), index -> {
    Listing listing = listings.get(index);
    return Frame.Entry.click(icon(listing), click -> buy(click, listing))
        .exclusively()
        .key(listing.id().toString());
});
```

## Icons

An `Icon` describes what one slot shows. The menus build the stack from it when they draw the slot, and a slot whose icon equals the one it shows is not drawn again.

| Icon | Shows |
|---|---|
| `Icon.Button(material, amount, name, lore, glint)` | A button or display item. A named button hides its item's attribute, enchantment and similar detail lines, so only its own text shows. A `null` name hides the whole tooltip, lore included. |
| `Icon.Filler(material)` | A slot that holds nothing, with its tooltip hidden. |
| `Icon.Real(base, amount, extraLore)` | A copy of a real item that keeps its own name and lore, with `extraLore` under a blank line. |
| `Icon.Saved(material, amount, customName, itemName, lore, extraLore, glint)` | An item drawn from its saved description: `customName` as `ItemMeta.displayName()` holds it, `itemName` as `ItemMeta.itemName()` holds it, the stored lore, then `extraLore` under a blank line. |

```java
Icon forSale = new Icon.Real(stack.clone(), stack.getAmount(),
    List.of(frame.text().line(frame.locale(), "gui.shop.price", Placeholder.unparsed("price", price))));
```

An amount shows from 1 to the smaller of the item's maximum stack size and 99. `Icon.Real` draws on a clone of its base and never changes it, but it holds the base itself and compares by it, so a stack that changes (one in a player's inventory) is passed as a copy. Contents such as a shulker box's items or a bundle's stacks are the caller's to strip before building the icon.

Every stack a menu or prompt anvil shows carries the plugin's preview key (`Menus.Parts.preview()`, from `0.3.0` `new NamespacedKey(plugin, "preview")` unless the plugin sets another) in its persistent data, so a copy that leaves a menu can be told apart from a real item. A plugin that checks items in its own code (a sell command, a trade) keeps the key and refuses stacks that carry it.

## Text

`MenuText` gives a menu's title and each item's name and lore. Text written in the layout wins in every language; otherwise it comes from the first lang key base that holds the key, as the menus' [`TextSource`](#text-source) resolves it for the viewer's locale. `Frame.text()` and `Menus.text()` return it.

| Method | Gives |
|---|---|
| `title(locale, layout, key, placeholders...)` | The layout's title, or the lang key. |
| `name(locale, item, bases, placeholders...)` | The item's own name, or `<base>.name` of the first base that holds it. `null` (a hidden tooltip) when the item has no name and `bases` is empty. |
| `lore(locale, item, bases, placeholders...)` | The item's own lore, or `<base>.lore` of the first base that holds it. Empty when neither has lore. |
| `label(locale, key, placeholders...)` | A lang key as a name. |
| `line(locale, key, placeholders...)` | A lang key as one lore line. |
| `lines(locale, key, placeholders...)` | A lang key as lore, one component per line. |
| `has(locale, key)` | Whether the text source holds the key for the locale. With `Messages` that includes the bundled English text. |
| `source()` | The `TextSource` behind it. From `0.3.0` it replaces `messages()`, which returned the `Messages`. |

Names are not italic. Lore lines are not italic and are gray unless the text sets a colour. With `Messages` as the text source, a lang key that no file holds renders as the marker `<red>missing:key`.

Text written in the layout or the lang files is trusted MiniMessage from the owner. Values go in through placeholders after the template is parsed, so a player-typed value passed as `Placeholder.unparsed` or `Placeholder.component` shows as typed. A lang template may write a value as `{name}` or `<name>` and may write `<prefix>`; text written in the layout reads only `<name>` and does not read `<prefix>`. A section-sign colour code in either is converted to MiniMessage.

### Text source

From `0.3.0`, the menus and prompts read the text of a lang key through a `TextSource`, a function from the viewer's locale, the key and the placeholders to a `Component`. Before `0.3.0` they required Taffy's `Messages`, so a plugin had to move its lang files to Taffy before it could show a menu.

| Way to pass the text | What the menus read |
|---|---|
| `Menus.Parts.of(..., messages, ...)` with the plugin's `Messages` | `Messages.render`, `has` and `lines`, as before `0.3.0`. `TextSource.of(messages)` gives the same source as a value. |
| `Menus.Parts.of(..., text, ...)` with a lambda or the plugin's own `TextSource` | The plugin's function. |

```java
TextSource text = (locale, key, placeholders) -> lang.component(locale, key, placeholders);
```

`TextSource` has two more methods with defaults, which a source of the plugin's own overrides when it can do better:

- `has(locale, key)` tells whether the source holds a key, and defaults to `true`. The menus ask it before they read text that is optional: an item's lore, each lang key base but the last of an item's name, a list's empty state and the word that cancels a prompt. With the default, each of these is rendered whatever the function gives for a key it does not hold, so a source that can tell overrides `has` to leave that text out.
- `lines(locale, key, placeholders...)` gives lore one component per line, and defaults to the one component `render` gives.

The menus and prompts call the source on the viewer's entity thread.

## Pagination and the footer

`Pager.page(count, capacity, requested)` gives the `Pager.Page` closest to the requested index: a list of `count` entries has `ceil(count / capacity)` pages, an empty list has one empty page, and a request below 0 or past the last page gives the first or the last page. It throws `IllegalArgumentException` for a negative `count` or a `capacity` below 1. `Page` holds `index`, `pages`, `from` (inclusive) and `to` (exclusive), and `previous()` and `next()` tell whether a page lies on either side. `Frame.list` uses it with `capacity()`, so a menu rarely calls it directly.

`frame.footer(page, turn, refresh)` draws the footer actions wherever the layout places them:

- **Back** opens the session's back route. Without one it opens the home menu from `Menus.Parts.home()`, unless there is no home, the session is the home menu, or the home menu is not registered.
- **Previous page** and **next page** show only when a page lies that way. A click sets the session's state to `turn.apply(newIndex)` and redraws on the next tick. Their name and lore read `<page>` (counting from 1) and `<pages>`.
- **Refresh** shows only when `refresh` is not `null`, and it is always exclusive.
- **Close** closes the menu on the next tick.

A footer action the kind does not have, or one that does not apply (no previous page, no back route), shows the filler. Pass `null` for `page` and `turn` on a menu without a list, and `null` for `refresh` when the menu has nothing to reload.

## Opening menus and threads

A menu opens, draws and handles clicks on the viewer's entity thread, the region thread that owns the player on Folia and the main thread on Paper.

| Method | Thread |
|---|---|
| `open(viewer, menu, back)` | Opens a menu in its initial state now. Call on the viewer's entity thread, outside an inventory event. |
| `open(viewer, route)` | Opens `route.menu()` in `route.state()` now. Same thread rule. |
| `openLater(viewer, menu, back)`, `openLater(viewer, route)` | Opens on the next tick on the viewer's entity thread. Safe from a click handler or a command. |
| `rerender(session)` | Draws the session again in place, nothing once it closed. Viewer's entity thread. |
| `rerenderLater(session)` | Draws again on the next tick unless the session closed by then. |
| `animate(session, period, step)` | From `0.4.15`, runs `step` and draws again every `period` until the session closes. Viewer's entity thread. See [Animating a menu](#animating-a-menu). |
| `closeLater(viewer)` | Closes the viewer's menu on the next tick when one is open then. |

Each `open` and `openLater` throws `IllegalArgumentException` when no menu is registered under the id. From `0.3.0`, `open(viewer, route)` and `openLater(viewer, route)` also throw it, naming the menu, the expected type and the type given, when `route.state()` is no instance of the menu's `stateType()`, before anything opens or is scheduled. A menu that keeps the default `stateType()` accepts every state, and a state of the wrong type then fails inside `render` with a `ClassCastException`. A `ClickHandler` runs inside the click event, so it opens, closes and redraws only through the `*Later` methods and asks for text through `Prompts.askLater`. A command opens with `menus.openLater(player, WarpsMenu.KIND.id(), null)`.

From `0.3.0`, `open`, `rerender`, `load` and `Prompts.ask` check the calling thread. On a thread that does not own the viewer, such as the thread that completed a storage future, each throws `IllegalStateException` before it changes anything, with a message that names the method and what to call instead, such as "Menus.open must run on the viewer's entity thread; use Menus.openLater". `rerender` still does nothing for a closed session, and `open` and `ask` still do nothing once `shutdown()` ran. `openLater`, `rerenderLater`, `closeLater` and `Prompts.askLater` are called from any thread, so a callback of a future opens or redraws through them:

```java
storage.save(warp).thenRun(() -> menus.rerenderLater(session));
```

A `Route(menu, state, back)` is a menu with the state it shows and the route its back button returns to. The menu registered under `menu` must accept the type of `state`, which a menu that overrides `stateType()` checks when the route opens. `MenuSession.route()` gives the open menu with its current state, for a back route or a prompt to return to.

Opening a menu while the viewer has another open is a hand-off: the previous session's `closed` gets `left = false`. A prompt that takes over through `Prompts.ask` is a hand-off too. Opening a menu also ends a pending prompt for that viewer.

A session never resumes once its `closed` ran. The menu a hand-off opens, and the origin a prompt opens when its ask ends, is a new session built from a `Route`, so `closed` is the last call a session gets. A menu that holds something outside its state, such as escrowed items, releases it in `closed` or moves it out there, whatever `left` is. When a prompt takes over, `left = false` does not promise that the menu comes back: the viewer can quit, die, or have another plugin's inventory open when the ask ends. From `0.3.0`, the [`abandoned` step of the `PromptRequest`](#when-an-ask-opens-no-menu) runs in those cases.

### MenuSession

A `MenuSession<S>` is one open menu for one viewer and is its inventory's `InventoryHolder`. Every field is read and written on the viewer's entity thread.

| Method | Purpose |
|---|---|
| `viewer()`, `menu()`, `id()`, `layout()` | Who sees it, which menu, and the layout it opened with (a reload does not change it). |
| `state()`, `state(S)` | The state; the next render shows a new one. |
| `data()`, `data(Object)` | Data for the renders, such as the value a load brought. |
| `busy()`, `busy(boolean)` | Whether an exclusive action is in flight, and a handler's own hold. See [Exclusive buttons](#exclusive-buttons). |
| `back()`, `route()` | The back route, and this menu as a route. |
| `closed()` | Whether the session ended. |
| `getInventory()` | The inventory. Throws `IllegalStateException` before it was created. |

`Menus.session(uuid)` gives the viewer's open session as an `Optional`.

### Loading data

`menus.load(session, source, apply)` waits for a `CompletableFuture` that completes on any thread, runs `apply` with the value on the viewer's entity thread and draws the session again, unless the session closed or a later load started meanwhile. Call it on the viewer's entity thread, from `opened` or a click handler. From `0.3.0` it throws `IllegalStateException` on a thread that does not own the viewer and starts no load; code on another thread hops to the viewer's thread first, through the `EntityThread` the menus were built with (`entity.call(viewer.getUniqueId(), player -> ...)`).

- From `0.3.0`, a load the handler of an exclusive button starts keeps the session busy with no call in the handler.
- From `0.3.0`, a load clears `busy` only for the hold that belongs to it: the exclusive button whose handler started it, or a `busy(true)` taken in the same handler or `opened` as the `load` call. It clears that hold when it applies, fails or is cancelled, also when a later load started meanwhile. Before `0.3.0` the end of the latest load of a session cleared every hold. See [Exclusive buttons](#exclusive-buttons).
- A failure of `source` or `apply` is logged with its stack and reported under `gui.load`. While the session is open and no later load started, the viewer is told `gui.error` and hears `Cue.FAIL`.
- A cancelled `source` is no failure: nothing is logged, reported or told.
- A viewer who left the server is told nothing; a failure of `source` itself is still logged and reported.
- Once `shutdown()` ran, a load that ends without applying does nothing more.

### Animating a menu

From `0.4.15`, `menus.animate(session, period, step)` redraws an open menu every `period`, for a countdown or an opening animation. Each frame runs `step`, which moves the state through `MenuSession.state`, and then draws the session as `rerender` does. `step` is a `Predicate<MenuSession<S>>` that returns whether another frame follows.

```java title="CountdownMenu.java"
@Override
public void opened(MenuSession<Integer> session, Player viewer) {
    menus.animate(session, Duration.ofSeconds(1), counting -> {
        int left = counting.state() - 1;
        counting.state(left);
        return left > 0;
    });
}
```

- Call it on the viewer's entity thread, such as in `opened` or a click handler. On a thread that does not own the viewer it throws `IllegalStateException` and starts nothing, as `rerender` does; code on another thread hops there first through the `EntityThread` the menus were built with. The step and the draw run on the viewer's entity thread, which on Folia is the region thread that owns the player.
- The period is counted in server ticks of 50 ms, rounded up, and is at least one tick, so `Duration.ZERO`, a negative period and one shorter than a tick all mean every tick. The first frame comes one period after the call, not at the call. A lagging server stretches the period.
- The call returns nothing and there is no handle to cancel. The animation ends when `step` returns `false`, and that last frame is still drawn, so a step that reads a flag of the plugin stops it from outside.
- It also ends, with no further step or draw, when the session closes (the viewer closed the menu or quit, or another menu or a prompt opened in its place), when `shutdown()` ran, and when `animate` is called again for the session. A session has one animation: a later call replaces the running one, also when the step itself makes that call. The menu a hand-off opens is a new session and is not animated until its own `opened` calls `animate`.
- For a session that already closed, and once `shutdown()` ran, the call does nothing. A session another `Menus` opened is refused with `IllegalArgumentException`, and a `null` argument with `NullPointerException`; neither ends a running animation.
- A `step` that throws draws nothing and ends the animation, and so does a draw that throws. Either is logged with its stack and reported under `gui.render`.
- A frame is a step of its own for [exclusive buttons](#exclusive-buttons): a `session.busy(true)` the step takes belongs to a `menus.load` only when the same frame starts that load, and is then released when the load ends. A hold taken in one frame is not released by a load a later frame starts.
- It counts the ticks with one task a tick through the `tasks` of the parts, whatever the period, so `Menus.Parts` has no new value and nothing stays scheduled once the animation ended.

A frame writes only the slots whose icon changed. A stack the plugin wrote into `session.getInventory()` itself, carrying the preview key of the parts, therefore stays in its slot through every frame in which the rendered icon of that slot is the same as before, and is replaced by the frame that renders another icon there.

The [redraw rule of click safety](#click-safety) applies to every frame. A list row that keeps its `Frame.Entry.key` takes clicks on the tick of every frame, whatever its icon shows, and so does a layout action. A row with no key whose icon changes in a frame, and a slot that gets a row with another key, drops clicks for the click debounce window after that frame, so a row that is animated and clickable needs a key.

## Click safety

The menu listener keeps menu views safe. From `0.3.0` the menus register it themselves when they are built, as [Enable and disable](#enable-and-disable) states. `menus.listener()` and `prompts.listener()` are deprecated and a later release removes them: each returns a listener with no event handler, so a `registerEvents` call left in a plugin registers nothing and cannot register the menus or the prompts twice.

- Every click and drag in a menu view is cancelled at `LOWEST`, and again at `HIGHEST` in case another plugin uncancelled it.
- From `0.3.0`, a session belongs to the `Menus` that opened it. A plugin with two `Menus`, such as one for player menus and one for admin menus, has two listeners: each cancels the clicks and drags in a menu of either, and only the listener of the owning `Menus` runs the button's handler, plays `Cue.CLICK` and `Cue.FAIL` and ends the session, so a click runs its handler once and `closed` is called once. Before `0.3.0` both listeners dispatched every click and a handler ran twice. From `0.3.0`, the anvil of a prompt is left alone by the listener of every `Menus`; before `0.3.0` the listener of a second `Menus` with the same preview key deleted the anvil's paper as a leaked menu copy and logged a `preview.leak` warning.
- Only a click of a type in `ClickGuard.ANY_PLAIN` (`LEFT`, `SHIFT_LEFT`, `RIGHT`, `SHIFT_RIGHT`), by the session's own viewer, on a slot of the menu inventory whose button accepts that type, reaches a button. Number keys, drops, double clicks and creative clicks never do. `ClickGuard.LEFT_ONLY` is a plain left click alone.
- A click within the click debounce window after the menu opened is dropped, an exclusive button is dropped while the session is busy (see [Exclusive buttons](#exclusive-buttons)), and a second click on the same button within the debounce window is dropped. Slots of one layout item share one debounce. From `0.3.0`, these windows and the deadline of a prompt are measured with `System.nanoTime()`, so a step of the server's wall clock neither drops clicks nor lets one through early.
- From `0.3.0`, a click on a slot is also dropped for the click debounce window after a redraw (`rerender`, or a load that applied) put another button in that slot. Before `0.3.0` the click ran the handler of whatever the slot showed by then, so when a sold listing shifted the rows up, a viewer aiming at one listing bought the next. Another button is a list row with another `Frame.Entry.key`, for a row with no key a row with another icon, a button of another layout item, or any button in a slot that had none. A layout action that redraws with other text or another icon keeps taking clicks, and so does a keyed row that stays in its slot, whatever its icon shows. A row with no key whose icon changes on every redraw, such as a countdown, drops the clicks of the window after each redraw, so give each clickable row a key. From `0.3.0` the click debounce of a keyed row follows its key, and that of a row with no key its slot.
- An accepted click plays `Cue.CLICK`. A handler that throws a `RuntimeException` leaves the event cancelled, is logged and reported under `gui.click`, clears `busy` and plays `Cue.FAIL`. From `0.3.0` it leaves `busy` as it is when the session was busy before the handler ran, so a failing button that is not exclusive does not release the hold of another button's work.
- In any view that is neither a menu nor a prompt anvil, a stack carrying the preview key on the clicked slot, the cursor, a number key's hotbar slot or the offhand is deleted, the click is cancelled and a `preview.leak` warning naming the player is logged. A drag outside menus with a marked cursor is cancelled and the cursor cleared on the next tick.
- A close ends the session (watched at `MONITOR`), and a quit forgets the player's debounce, view memory, session and pending prompt.
- From `0.3.0`, the listener sends a player's inventory again, through `Player.updateInventory()` on the next tick on the player's entity thread, after it cancelled the player's shift-click in a menu view and after the viewer's menu closed. The client moves a stack on its own screen before the server answers, so it could keep showing a stack the server never moved. A menu that another inventory replaces sends nothing more, since the server sends the new inventory in full.

A `Click` record carries `session()`, `player()`, `type()` (the `ClickType`) and `slot()` (the raw slot), so one handler can act on left and right clicks differently:

```java
// In the render of a Menu<Integer> whose state is the amount
MenuSession<Integer> session = frame.session();
frame.action("amount", Frame.Spec.click(click -> {
    int step = click.type().isShiftClick() ? 10 : 1;
    session.state(session.state() + (click.type().isLeftClick() ? step : -step));
    menus.rerenderLater(session);
}).with(Placeholder.unparsed("amount", Integer.toString(frame.state()))));
```

`Click.session()` is a `MenuSession<?>`, so a handler that sets the state uses the typed session from `frame.session()`.

`MenuSettings` holds the shared limits: `pageSize` from 1 to `MenuSettings.MAX_PAGE_SIZE` (45), `filler`, `clickDebounce` from `MIN_DEBOUNCE` (50 ms) to `MAX_DEBOUNCE` (2 s), and `loadingItem`. `MenuSettings.DEFAULTS` is a page size of 45, `GRAY_STAINED_GLASS_PANE` as filler, a 250 ms debounce and `CLOCK` while loading. From `0.3.0`, a plugin starts from `MenuSettings.DEFAULTS` and replaces what its config sets, such as `MenuSettings.DEFAULTS.pageSize(28).clickDebounce(Duration.ofMillis(400))`; before `0.3.0` it called `new MenuSettings(pageSize, filler, clickDebounce, loadingItem)`. A method throws `IllegalArgumentException` for a value outside its range.

### Exclusive buttons

An exclusive button (`Frame.Spec.exclusively()`, `Frame.Entry.exclusively()` and the footer's refresh) is for an action that must not run twice at once, such as a purchase. A click on any exclusive button of the session is dropped while `session.busy()`; other buttons still act.

From `0.3.0`, a handler that does its work through `menus.load` calls nothing else. When the handler of an exclusive button returns with a load it started still in flight, the session is busy until that load applies, fails or is cancelled. A load another button starts, such as a page turn, does not free a purchase still in flight when it ends, and neither does it stop the purchase's own load from freeing the session:

```java
frame.action("buy", Frame.Spec.click(click ->
    menus.load(session, shop.buy(click.player().getUniqueId(), item), (s, receipt) -> s.data(receipt)))
    .exclusively());
```

Before `0.3.0`, `exclusively()` did nothing unless the handler called `session.busy(true)` itself, so the handler above ran a second purchase once the click debounce passed. A handler that calls `busy(true)` before its load keeps working: a hold taken in the same handler as a `menus.load` call is released when that load ends.

A handler whose work runs outside `menus.load`, such as a service that calls back when it is done, holds the session itself. `session.busy(true)` in the handler lasts past the handler's return, and nothing releases it but `session.busy(false)` or that handler throwing; a load another button starts does not release it. Before `0.3.0` any load of the session that ended, and any handler that threw, released it. Release it on the viewer's entity thread when the work ends, on success and on failure:

```java
frame.action("claim", Frame.Spec.click(click -> {
    session.busy(true);
    stash.claim(click.player(), card, () -> {   // runs on the player's entity thread
        session.busy(false);
        menus.rerenderLater(session);
    });
}).exclusively());
```

A callback that runs on another thread hops to the viewer's thread first, through the `EntityThread` the menus were built with, since a session is read and written on the viewer's entity thread only. `session.busy()` reads `false` inside the handler of the first click, so a handler that starts with `if (session.busy()) return;` keeps working. A hold on a session that closed needs no release: the next open is a new session.

## Text prompts

`Prompts` asks a player for one line of text in place of a menu and opens a menu with the answer.

```java
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
```

| Constructor argument | Meaning |
|---|---|
| `menus` | The plugin's menus. The prompts read their text source, locale function, entity-thread seams, logger and error reports. |
| `mode` | `PromptMode.CHAT` (the next chat line), `PromptMode.ANVIL` (the name field of an anvil the prompts build) or, from `0.4.3`, the experimental `PromptMode.DIALOG` (the text field of a Paper dialog, see [Dialog prompts](#dialog-prompts)). It holds for the life of the prompts. A later release may add a mode, as `0.4.3` did, so a plugin's own `switch` over `PromptMode` keeps a `default` branch. |
| `bedrock` | A `BedrockPlayers` that tells which players joined from Bedrock Edition, or `BedrockPlayers.NONE`. Bedrock players always answer in chat, under `ANVIL` and under `DIALOG` alike, and get no cancel link. |
| `timer` | Runs a task on any thread after a delay: `scheduler::delayedAsync`. |

From `0.4.3`, `BedrockProvider.detect` of [taffy-hooks](/docs/modules/hooks#bedrock-players) finds Floodgate or Geyser. `taffy-hooks` does not depend on `taffy-gui`, so the plugin passes the provider's `bedrock` method as the `BedrockPlayers`:

```java
BedrockProvider provider = BedrockProvider.detect(this, errors, true).provider();
BedrockPlayers bedrock = provider == null ? BedrockPlayers.NONE : provider::bedrock;
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, bedrock, scheduler::delayedAsync);
```

Building the prompts links them to the menus. A second `Prompts` over the same menus, or prompts over menus that were shut down, throws `IllegalStateException`. From `0.3.0`, building the prompts also registers their listener as a listener of the menus' plugin, before the prompts link to the menus; prompts that are refused register nothing.

A `PromptRequest(question, initial, origin, answer)` is one question: the `Component` shown, the text an anvil's name field starts with, the `Route` a cancel or timeout opens again, and a `Function<String, Answer>` that judges the typed text on the player's entity thread. The function returns `new Answer.Accept(route)` to take the answer and open `route`, or `new Answer.Retry(reason)` to tell the player `reason` and keep waiting.

From `0.3.0`, a function whose decision needs storage or an economy returns `new Answer.Later(future)` instead of blocking the player's entity thread. The `CompletableFuture<Answer>` completes on any thread, and its result is applied on the player's entity thread as a result the function returned: an `Accept` opens its menu, a `Retry` tells the player and waits for the next answer, and another `Later` waits again.

```java
new PromptRequest(question, "100", session.route(), text -> {
    long price = Long.parseLong(text);
    return new Answer.Later(economy.balance(player.getUniqueId())      // completes on any thread
        .thenApply(balance -> balance >= price
            ? new Answer.Accept(new Route("shop", price, null))
            : new Answer.Retry(Component.text("You cannot afford that."))));
});
```

- While the future runs the ask takes no chat line and no anvil submit, and an anvil stays open. A chat line typed then is ordinary chat. Under `PromptMode.DIALOG` no dialog shows while the future runs.
- The ask's first deadline, the cancel link, a closed anvil, another menu, a newer ask, a quit and `Menus.shutdown()` still end the ask. The result of a future that completes after that is dropped, and nothing runs for a player who left the server, so the future itself must not take money or items.
- A future that fails or completes with `null` is handled as an answer function that throws. A cancelled future opens `origin` again with no message, and nothing is logged or reported.
- `Answer` is sealed and a later release may add a result, so a plugin's own `switch` over it keeps a `default` branch.

`ask(player, request)` asks now, on the player's entity thread outside an inventory event. It replaces any ask still pending for the player without a message (from `0.4.2`, also an ask of another `Prompts` of the same plugin), and does nothing once `Menus.shutdown()` ran or when the server refused to open the anvil. `askLater(player, request)` asks on the next tick and is what a click handler calls. Both throw `NullPointerException` for a `null` request; from `0.3.0`, `ask` does so before it closes the menu or replaces a pending ask. From `0.4.3` both also take a [`TextRequest`](#text-outside-a-menu), so a call that passes the literal `null` needs a cast to compile. From `0.3.0`, `ask` also throws `IllegalStateException` on a thread that does not own the player, before it closes or replaces anything, with the message "Prompts.ask must run on the player's entity thread; use Prompts.askLater"; `askLater` is called from any thread.

Behaviour of an ask:

- A chat ask closes the menu and sends `gui.prompt.question` and `gui.prompt.hint` in chat. An anvil ask shows the question as the anvil's title and sends no chat message. From `0.4.3`, a dialog ask closes the menu, shows the question as the dialog's title and sends no chat message.
- An ask waits `Prompts.TIMEOUT` (30 seconds) from when it was asked. A refused answer keeps the first deadline.
- An answer is stripped of surrounding whitespace and cut to `Prompts.MAX_LENGTH` (256) characters.
- The cancel word from `gui.prompt.cancel-word` cancels, and so does `Prompts.DEFAULT_CANCEL_WORD` (`cancel`) in every locale. A chat ask also shows a clickable `gui.prompt.cancel-button` link after the hint (not for Bedrock players), which works for one click while the ask waits.
- Submit, cancel and timeout open a menu again unless the player is dead or offline, has another plugin's inventory open, or the plugin is stopping. An ask ended by another menu, another plugin's inventory, a newer ask or a quit opens nothing. From `0.3.0`, an ask that opens no menu runs the request's `abandoned` step, see [When an ask opens no menu](#when-an-ask-opens-no-menu).
- An answer function that throws a `RuntimeException` or returns `null` is logged, reported under `gui.prompt`, and the player is told `gui.error` and returned to `origin`.
- The chat handlers run at `LOWEST` with `ignoreCancelled = false`, so a mute plugin cannot leave a prompt waiting. The answer line is cancelled and never modified. From `0.3.0`, its audience is emptied too (`AsyncChatEvent.viewers()` and `AsyncPlayerChatEvent.getRecipients()`, where the set can be changed), so a chat plugin that delivers cancelled lines has nobody to deliver the answer to. The event still reaches every handler that does not ignore cancelled events, at any priority, and such a handler can read the answer. A line from a player with no chat prompt is left alone.
- Paper posts the legacy `AsyncPlayerChatEvent` and then `AsyncChatEvent` for one chat line. From `0.3.0`, the line is judged once: after a refused answer, or an answer whose function asked again, the second event no longer answers the ask waiting by then with the same text.
- A plugin with two `Menus` can build a `Prompts` over each. From `0.4.2`, the `Prompts` of one plugin (the `Menus.Parts.plugin()` of their menus) share the ask of a player: `ask` and `askLater` also end the ask another `Prompts` of the plugin holds for the player, pending or waiting for its `Answer.Later`, which gets `PromptEnd.REPLACED`, and one chat line answers one ask, judged by the `Prompts` that asked it. Before `0.4.2`, an ask ended only a pending ask of the same `Prompts`, so a player could hold one ask in each and one chat line answered both. Opening a menu still ends only an ask of the `Prompts` built over its `Menus`, and `Menus.shutdown()` ends only the asks of that `Prompts`.
- The anvil is a virtual anvil at a repair cost of 0, holding a marked paper. Every click and drag on it is cancelled, a click on its result slot submits the name field, and closing it cancels the ask. Another inventory opening over it ends the ask with no message.

### When an ask opens no menu

An ask ends in one of two ways. Either the prompts open a menu, the origin after a cancel, a timeout or a failed answer and the route of an `Answer.Accept` after an accepted one, or they open none. Before `0.3.0` nothing told the plugin about the second case, so a menu that had handed its session to an ask, with `closed(session, false)`, never learned that the ask would not open it again.

From `0.3.0`, `PromptRequest.abandoned(Consumer<PromptEnd>)` gives a question a step that runs once when its ask ended and the prompts opened no menu for it, with how it ended:

| `PromptEnd` | The ask ended because |
|---|---|
| `TIMED_OUT` | it reached its deadline and the origin did not open: the player is dead or has another plugin's inventory open, the server refused the origin's inventory (another plugin cancelled the open), or opening the origin failed. |
| `CANCELLED` | the player cancelled it (the cancel word, the cancel link, a closed anvil or, from `0.4.3`, the cancel button or escape key of a dialog) and the origin did not open, for one of the reasons `TIMED_OUT` lists, or `Menus.shutdown()` ended it. |
| `LEFT` | the player quit while it waited, was gone when it was to end, or was dead or offline when an accepted or failed answer was to open its menu. |
| `REPLACED` | something took its place: a menu of these menus opened, a newer ask started, another inventory opened over the prompt's anvil, the player had another inventory open when an accepted, refused or failed answer was to show its menu or its anvil, or the server refused to show the anvil of a refused answer again. It is also how an ask ends when the menu an accepted or failed answer was to open did not open: the server refused its inventory, its route names no registered menu or a state of another type, or the menu failed to draw. |

```java
// In a click handler of a sell menu that holds the item the viewer is pricing
ItemStack held = escrow.take(session);
prompts.askLater(click.player(), new PromptRequest(question, "100", session.route(), text -> price(text, held))
    .abandoned(end -> escrow.giveBack(click.player().getUniqueId(), held)));
```

- The step runs on the player's entity thread, except `LEFT` for a player who is gone, which runs on the thread that found the player gone, where the player must not be used. At `Menus.shutdown()` it runs with `CANCELLED` on the disabling thread, and only for a player that thread owns, as a menu's `closed` does.
- It is not called for an ask that opens a menu, and not for one that never started: an ask after `Menus.shutdown()`, or one whose anvil the server refused to open, which closes the menu with `left = true`.
- A menu that fails to open is still logged and reported under `gui.prompt`, after the step ran. A menu that opened and then threw in its `opened` is open, so the step is not called for it.
- A step that throws a `RuntimeException` is logged and reported under `gui.prompt`.
- `PromptRequest` has `abandoned` as a fifth record component. `new PromptRequest(question, initial, origin, answer)` still compiles and gives a request whose step does nothing.
- A later release may add a `PromptEnd`, so a `switch` over it keeps a `default` branch.

### Dialog prompts

From `0.4.3`, `PromptMode.DIALOG` asks in a Paper dialog: a title, one text field, a submit button and a cancel button.

```java
Prompts prompts = new Prompts(menus, PromptMode.DIALOG, bedrock, scheduler::delayedAsync);
```

<Callout type="warn" title="Experimental">
Paper marks its Dialog API as experimental and may change it, so `PromptMode.DIALOG` carries `@ApiStatus.Experimental` too. It is the only experimental part of the prompts: `TextRequest`, the constructor over `Menus.Parts` and `Prompts.shutdown()` are not. Taffy's tests run the mode against a stand-in for the dialog, so check it on your own server version before you ship it.
</Callout>

- The dialog's title is the request's question, and the field starts with its `initial` text, cut to `Prompts.MAX_LENGTH` (256) characters, which is also the most the field takes.
- The submit button sends the field's text, which is judged as a chat line or an anvil submit is: stripped, cut, checked against the cancel word and given to the answer function on the player's entity thread. `Answer.Accept` opens its route, and an `Answer.Later` is waited for as in the other modes.
- A refused answer shows the dialog again on the next tick, with the `gui.prompt.refused` text above the field and the refused text in it. Nothing is sent to chat. With another inventory open on that tick the ask ends as `PromptEnd.REPLACED`.
- The cancel button cancels the ask, and so does closing the dialog with the escape key, which the client sends as that button: the player is told `gui.prompt.cancelled` and the origin opens again.
- The deadline, a menu of the menus the prompts are built over that opens, a newer ask and `shutdown()` take the dialog away from the player. A chat line typed while a dialog ask waits is ordinary chat.
- Paper has no event for a dialog that the client takes away without a button, as when another plugin opens an inventory or the player dies. Such an ask takes no chat line and ends at its deadline as `PromptEnd.TIMED_OUT`.
- A `RuntimeException` of the server that fails to show the dialog is thrown on. From `ask` no ask is left behind. From the task that shows the dialog again after a refusal, the ask first ends as `PromptEnd.REPLACED`.
- The two buttons carry the client's own text for `gui.done` and `gui.cancel`, in the player's language, so the mode adds no lang key and `Prompts.KEYS` is unchanged. A dialog reads `gui.prompt.refused` and, when the ask ends, `gui.prompt.cancelled`, `gui.prompt.timed-out` and `gui.error`.
- Bedrock players answer in chat, as under `ANVIL`.
- On a server whose Paper has no Dialog API, building the prompts logs one warning and every ask is asked in chat. When the API is there but cannot be linked, as after Paper changed it, the first ask logs one warning, and that ask and every later ask of those prompts are asked in chat.
- No `io.papermc.paper.dialog` type is part of a Taffy signature. Forms with more than one field and confirmations are not part of this mode.

### Text outside a menu

From `0.4.3`, a `TextRequest` asks for text that opens no menu, for a command or a plugin's own screen. `ask(player, request)` and `askLater(player, request)` take it as they take a `PromptRequest`, and the ask uses the same chat, anvil or dialog, cancel word, cancel link, deadline and Bedrock rule.

```java
prompts.ask(player, new TextRequest(
    Component.text("Name of the crate?"), "",
    text -> text.length() < 3 ? Component.text("At least 3 characters.") : null,
    name -> crates.create(player, name),
    end -> { }));
```

| Part of `TextRequest` | Type | Meaning |
|---|---|---|
| `question` | `Component` | The text shown. |
| `initial` | `String` | The text an anvil's name field or a dialog's text field starts with. |
| `refusal` | `Function<String, @Nullable Component>` | Judges the typed text on the player's entity thread: `null` takes the answer, and a text refuses it and is shown to the player as the reason, as an `Answer.Retry` is. |
| `accepted` | `Consumer<String>` | Gets the answer that was taken, once. |
| `ended` | `Consumer<PromptEnd>` | Gets how the ask ended when no answer was taken, once. |

The prompts open nothing after either step. `ended` gets:

| `PromptEnd` | The ask ended because |
|---|---|
| `CANCELLED` | the player cancelled it (the cancel word, the cancel link, a closed anvil, the cancel button or escape key of a dialog), the refusal check failed, its future was cancelled, or `shutdown()` ended it. |
| `TIMED_OUT` | it reached its deadline. |
| `LEFT` | the player quit while it waited or was gone when it was to end. |
| `REPLACED` | a newer ask started, a menu of the menus the prompts are built over opened, another inventory opened over the prompt's anvil, or the anvil or dialog of a refused answer could not be shown again. |

- A check that decides off the player's entity thread uses `TextRequest.later(question, initial, refusal, accepted, ended)`, whose `refusal` is a `Function<String, CompletableFuture<@Nullable Component>>`. The function runs on the player's entity thread, its future completes on any thread with `null` or the reason, and the result is applied on the player's entity thread. While it runs the ask takes no answer, as with an `Answer.Later`, and what ends the ask meanwhile drops the result, so the future itself must not take money or items.
- A check that throws a `RuntimeException`, returns no future, or whose future fails is logged and reported under `gui.prompt`, the player is told `gui.error`, and the ask ends as `CANCELLED`. A cancelled future ends it as `CANCELLED` with no message.
- `accepted` and `ended` run on the player's entity thread, except `LEFT` for a player who is gone, which runs on the thread that found the player gone, and `CANCELLED` at `shutdown()`, which runs on the disabling thread for a player that thread owns. One that throws a `RuntimeException` is logged and reported under `gui.prompt`.
- Neither step runs for an ask that never started: one after `shutdown()`, or one whose anvil the server refused to open.
- The ask closes the inventory the player has open. On prompts built over menus, a Taffy menu closes with `left = true`, since no menu opens again, and a menu of those menus that opens ends the ask as `REPLACED`.

A plugin with no `Menus` builds its prompts over a `Menus.Parts`:

```java
Prompts prompts = new Prompts(
    Menus.Parts.of(this, messages, scheduler::entity, EntityThread.on(scheduler, getServer()), errors),
    PromptMode.CHAT, BedrockPlayers.NONE, scheduler::delayedAsync);

// onDisable, before scheduler.close()
Shutdown.closeQuietly("end the prompts", () -> prompts.shutdown(), getLogger(), errors);
```

- The prompts read the parts' plugin, text source, `locales`, `server`, `preview` (the key the paper of the prompt anvil carries), `tasks`, `entity`, `logger` and `errors`. The layouts, settings, sounds and home menu are not read.
- Building them registers the prompt listener as a listener of the plugin, with no `registerEvents` call: it reads the chat answers, guards the prompt anvil and ends the ask of a player who quits as `LEFT`. The server refuses a listener of a plugin that is not enabled with an `IllegalPluginAccessException`.
- Such prompts ask with a `TextRequest` only. `ask(player, promptRequest)` and `askLater(player, promptRequest)` throw `IllegalStateException` at the call, since they have no menu to open.
- They share a player's ask with the other `Prompts` of the plugin, built over menus or not, as the list above states from `0.4.2`. No menu ends their asks.
- `Prompts.shutdown()` is public from `0.4.3`. The plugin calls it at disable for prompts built this way: it ends every ask as `CANCELLED` for the players the calling thread owns, takes their anvils and dialogs away, and nothing is asked afterwards. `Menus.shutdown()` still calls it for prompts built over menus.

## Sounds and view memory

`menus.play(player, cue)` plays the sound `Menus.Parts.sounds()` maps the `Cue` to, from where the player stands, on the player's entity thread. A cue the map leaves out plays nothing, so an empty map turns sounds off. `Cue.key()` gives `click`, `success` or `fail`, for a plugin that reads its sounds from a file.

`menus.memory()` is the `ViewMemory`: what each viewer last chose in each menu (a tab, a sort), kept until the viewer quits. It is safe from any thread.

```java
menus.memory().put(viewer.getUniqueId(), "warps", Sort.NAME);
Sort sort = menus.memory().get(viewer.getUniqueId(), "warps", Sort.class); // null when nothing was kept
```

## Reload

| What changes | How | Takes effect |
|---|---|---|
| Lang text | `messages.reload()` | Every menu and prompt drawn afterwards. |
| Layouts | `menus.reload(layouts)` | Every menu opened afterwards. Open sessions keep their layout. |
| Sounds | A new map behind the `sounds` supplier | The next cue played. |

`reload` checks the new map as `register` does and throws `IllegalArgumentException` when a key differs from its layout's menu, a registered menu has no layout, a layout does not fit its kind or, from `0.3.0`, a registered menu's layout holds a material that is not an item. A refused map leaves the layouts as they were:

```java
try {
    menus.reload(Map.of(WarpsMenu.KIND.id(),
        LayoutFiles.read("warps", getDataFolder().toPath().resolve("menus/warps.yml"))));
} catch (IOException | InvalidConfigurationException | IllegalArgumentException e) {
    getLogger().warning("menus/warps.yml was not reloaded, the menus keep their layout: " + e.getMessage());
}
```

`MenuSettings`, the home menu, the rest of `Menus.Parts` and the `PromptMode` hold until the plugin builds the menus anew, so they are restart settings.

## Shutdown

`menus.shutdown()` ends every prompt of the `Prompts` built over the menus first, then closes the open menus and anvils of the viewers the calling thread owns and runs each menu's `closed` with `left = false` itself, since no close event arrives while the plugin disables. From `0.3.0` it also sends each viewer whose menu it closed their inventory again, through `Player.updateInventory()`. Nothing opens and nothing is asked afterwards, and a second call does nothing. From `0.4.3`, prompts built over a `Menus.Parts` with no menus are ended by their own `prompts.shutdown()`, see [Text outside a menu](#text-outside-a-menu).

<Callout type="warn" title="Folia">
On Folia the disabling thread does not own every player. The menus and anvils of viewers it does not own are forgotten and stay open with no listener guarding them. From `0.3.0`, `shutdown()` empties the inventory of each such menu and anvil, so its viewer is left with an empty menu and has no copy to take. From `0.3.0`, while the plugin stays enabled after `shutdown()`, as in a reload command, the listener still cancels the clicks in such a menu and runs no handler; before `0.3.0` such a click ran the handler of the button its slot had held. Before `0.3.0` such a menu stayed stocked, and a copy taken from it was deleted only when a click met it outside a menu after a later enable. On Paper the disabling thread owns every player, so this does not happen.
</Callout>

## Failure reporting

Every handled failure is logged with its stack through the plugin's logger and reported to its `ErrorReports` under one source:

| Source | Failure |
|---|---|
| `gui.click` | A button's `ClickHandler` threw. |
| `gui.load` | A load's `source` or `apply` failed. |
| `gui.render` | A menu failed to draw in a task `openLater` or `rerenderLater` scheduled. From `0.4.15`, also a `step` or a draw of `animate` that threw. |
| `gui.close` | A menu's `closed` threw. |
| `gui.prompt` | A prompt's answer function threw or returned `null`, the future of an `Answer.Later` failed or completed with `null`, or prompt work on the player's entity thread failed. From `0.4.3`, also a refusal check of a `TextRequest` that threw or whose future failed, and an `accepted` or `ended` step that threw. |

A menu that throws from `render` or `initial` during a direct `open` or `rerender` passes the exception to the caller.

## Testing menus

From `0.4.5`, `MenuTesting` builds the menus for a plugin's own tests, which run with no server. `new MenuTesting(parts).menus()` gives a `Menus` over the same `Menus.Parts` the plugin builds in `onEnable`, with four differences from `new Menus(parts)`:

- Its menu inventories are fakes that record the `Icon` each slot shows. `icon(inventory, slot)` gives it, `title(inventory)` the title, and `inventories()` every inventory created so far.
- Its time source stands still until `advance(Duration)` moves it, so a test steps over the click debounce window instead of sleeping.
- The calling thread owns every player until `owned(Predicate<Player>)` says otherwise, which is how a test reaches the `IllegalStateException` of `open` on a thread that does not own the viewer.
- Its listener is registered with no plugin manager. `deliver(event)` passes an `InventoryClickEvent`, an `InventoryDragEvent`, an `InventoryCloseEvent` or a `PlayerQuitEvent` to the listeners by priority, as a server does.

`MenuTesting` is in `taffy-gui` itself and uses no Mockito, so it needs no extra dependency. The test supplies the plugin, the players and their views, here as Mockito mocks, and the `tasks` and `entity` of the parts as it would for any other test:

```java title="ShopMenuTest.java"
        when(player.openInventory(any(Inventory.class))).thenAnswer(call -> {
            close(InventoryCloseEvent.Reason.OPEN_NEW);
            InventoryView opened = mock(InventoryView.class);
            when(opened.getTopInventory()).thenReturn(call.getArgument(0));
            when(opened.getPlayer()).thenReturn(player);
            view = opened;
            return opened;
        });
        doAnswer(call -> {
            close(call.getArgument(0));
            return null;
        }).when(player).closeInventory(any(InventoryCloseEvent.Reason.class));
    }

    // A server posts the close event itself, also for the view an open replaces.
    private void close(InventoryCloseEvent.Reason reason) {
        InventoryView closing = view;
        if (closing != null) {
            view = null;
            testing.deliver(new InventoryCloseEvent(closing, reason));
        }
    }

    @Test
    void buyingAddsOneToTheStack() {
        menus.open(player, ShopMenu.KIND.id(), null);
        Inventory top = view.getTopInventory();
        assertEquals(Material.DIAMOND, ((Icon.Button) testing.icon(top, 13)).material());

        testing.advance(MenuSettings.DEFAULTS.clickDebounce().plusMillis(1));
        InventoryClickEvent click = new InventoryClickEvent(view, InventoryType.SlotType.CONTAINER, 13,
            ClickType.LEFT, InventoryAction.PICKUP_ALL);
        testing.deliver(click);
        while (!ticks.isEmpty()) {
            ticks.poll().run();
        }

        assertTrue(click.isCancelled());
        assertEquals(2, ((Icon.Button) testing.icon(top, 13)).amount());
    }
```

`ShopMenu` is the plugin's own menu: here its `buy` action sits in slot 13 and shows the state as the stack amount, and a click adds one and calls `menus.rerenderLater`.

`prompts(timer)` builds chat `Prompts` over the menus on the same time source, and `chat(player, line)` passes a chat line to them and returns whether a prompt took it as its answer:

```java
List<Runnable> timers = new ArrayList<>();
Prompts prompts = testing.prompts((task, delay) -> timers.add(task));

prompts.ask(player, new PromptRequest(Component.text("How many?"), "", origin,
    line -> new Answer.Accept(new Route(ShopMenu.KIND.id(), Integer.parseInt(line), null))));

assertTrue(testing.chat(player, "7"));
```

To let an ask time out, call `testing.advance(Prompts.TIMEOUT)` and run the tasks the timer was given.

From `0.4.15`, a menu that calls `animate` queues one task every tick while it is open, so a test of it does not run the queue until it is empty, as the loop in `buyingAddsOneToTheStack` does. It runs only the tasks that were queued when the tick began, once per tick:

```java
private void tick() {
    for (int due = ticks.size(); due > 0; due--) {
        ticks.remove().run();
    }
}
```

- A fake menu inventory answers `getHolder()`, `getHolder(boolean)`, `getSize()` and `clear()`, which empties its slots, and equals only itself. Every other method throws `UnsupportedOperationException`. `icon` returns `null` for a slot nothing was drawn into since the inventory was created or cleared.
- A menu counts as shown only when the view `player.openInventory(inventory)` returns has that inventory as its `getTopInventory()`.
- Every material but `AIR`, `CAVE_AIR` and `VOID_AIR` passes `Menus.register` as an item, also a block that has no item form, because `Material.isItem()` needs a running server.
- `deliver` calls the handlers by priority and, at one priority, in the order the listeners were registered: the menus' listener first, then the prompts'. What a handler throws is thrown on to the test, and the later handlers do not run.
- `chat` passes the line as an `AsyncPlayerChatEvent`, the event a server posts first, on the calling thread.
- The prompts are always chat prompts with no Bedrock players: the anvil and the dialog need a running server. Their cancel link runs nothing, so a test cancels by typing the cancel word.
- After an answer, a menu opens only when the player is on their own screen: `player.getOpenInventory()` returns `null`, or a view whose top inventory has the player as its `getHolder(false)`.
- `Menus.Parts.server()` is not used, so a mocked `Server` with no stubbing is enough.
- Each `MenuTesting` holds one `Menus` and delivers to its listeners only.
