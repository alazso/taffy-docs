---
title: taffy-config
description: Strict YAML loading, typed reading that reports every problem at once, and a reload that never replaces working settings with broken ones.
---

`taffy-config` turns a plugin's YAML files into an immutable settings object. It gives the plugin:

- `ConfigLoader`, which writes the `config.yml` shipped in the jar on first start and upgrades an older file to the shipped layout, keeping the owner's values and comments.
- `ConfigReader`, which reads typed values and reports every value it cannot use in one pass, with lines written for the server owner.
- `ConfigHolder`, which holds the settings in effect and replaces them on a reload only when the new ones load.
- `RestartKeys`, which names the settings a reload changed that take effect only after a restart.
- `YamlFolder`, which reads a folder in which each `.yml` file is one entry (one kit, one menu) and reports a bad file without stopping the others.
- `ConfigUpgrade`, the steps that rename, move and remove keys when `config.yml` or a file of a folder is brought to a newer layout version (from `0.4.9`).
- `AtomicWriter`, which writes a file the plugin edits so that a crash never leaves half of it, and replaces it only while it still holds what the edit started from (from `0.4.9`).
- `StrictYaml`, the one way a file becomes a `YamlConfiguration`: a file that is missing, not UTF-8 or not valid YAML fails instead of reading as empty.
- `ConfigLoadException`, the one checked exception of the module, whose message is written for the server owner.

All classes are in the package `so.alaz.taffy.config`. No class takes a `Plugin`, keeps a thread or calls `JavaPlugin.getConfig` or `reloadConfig`. A logger is used only where the plugin passes one in. A plugin that reads `getConfig()` today moves every read onto the holder, as [Moving a plugin off getConfig()](#moving-a-plugin-off-getconfig) describes.

## Setup

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.config)
}
```

The module is published as `so.alaz.taffy:taffy-config` and is `alaz.taffy.config` in the catalog. It depends on `taffy-platform` as an `api` dependency, so `Durations`, `Colors` and the other parsers come with it. The Paper API (and the SnakeYAML inside it) is `compileOnly`: the server provides `YamlConfiguration`. `so.alaz.taffy.paper-plugin` shades the module and relocates it under `<group>.libs.taffy.config`. See [Getting started](/docs/getting-started) for the settings plugin and repositories.

## The settings model

The module has no base type for settings. A plugin writes its settings as an immutable record with a static `read` factory that takes a `ConfigReader`:

- Each component is read with one reader call, and its default is a constant of the record passed as the fallback of that call.
- A value that depends on the running server, such as a world name, is checked through a predicate passed to the factory, so the factory runs without a server and can be unit tested.
- After the factory returns, `ConfigReader.errors()` says whether the settings can be used.
- The record is held in a `ConfigHolder`, whose loader loads the file, reads the record and checks the errors. Settings that take effect only after a restart are read from `ConfigHolder.startup()`, and `RestartKeys.changed` names the ones the owner changed. The holder keeps only the record, so a record that needs this keeps the `ConfigurationSection` it was read from as a component, taken from `ConfigReader.root()`.
- A value whose form a parser in `so.alaz.taffy.platform` checks, such as a duration, a colour or an expiry, is read with the `parsed` overload that takes a fallback text, with the parser's `EXPECTED` text as the expected form and the fallback written as the owner would write it. A date with a time has to be written in quotes.

```yaml title="src/main/resources/config.yml"
config-version: 1

storage:
  # The table the homes are kept in.
  table: homes

max-homes: 3
teleport-delay: 3s
particle-color: aqua
mode: normal
worlds:
  - world
```

```java title="Settings.java"
import org.bukkit.Color;
import org.bukkit.configuration.ConfigurationSection;
import so.alaz.taffy.config.ConfigReader;
import so.alaz.taffy.platform.Colors;

import java.time.Duration;
import java.util.List;
import java.util.Objects;
import java.util.function.Predicate;

public record Settings(
    ConfigurationSection source,
    String table,
    int maxHomes,
    Duration teleportDelay,
    Color particleColor,
    Mode mode,
    List<String> worlds) {

    public enum Mode { NORMAL, STRICT }

    static final int MAX_HOMES = 3;
    static final Duration TELEPORT_DELAY = Duration.ofSeconds(3);
    static final Color PARTICLE_COLOR = Color.AQUA;
    static final Mode MODE = Mode.NORMAL;
    static final List<String> WORLDS = List.of("world");

    public static Settings read(ConfigReader reader, Predicate<String> worldExists) {
        List<String> worlds = reader.strings("worlds", WORLDS);
        for (String world : worlds) {
            if (!worldExists.test(world)) {
                reader.error("worlds has " + ConfigReader.describe(world) + ", which is not a loaded world.");
            }
        }
        return new Settings(
            reader.root(),
            Objects.requireNonNullElse(reader.requiredText("storage.table", "set it to the name of the table"), ""),
            reader.integer("max-homes", MAX_HOMES, 0, 100),
            reader.duration("teleport-delay", TELEPORT_DELAY, Duration.ZERO, Duration.ofMinutes(1)),
            reader.parsed("particle-color", PARTICLE_COLOR, "aqua", Colors.EXPECTED, Colors::parse),
            reader.choice("mode", MODE),
            worlds);
    }
}
```

The record keeps the section it was read from (`source`) only because `RestartKeys` needs it; a plugin without restart-only settings leaves it out.

## Loading and reloading

```java title="MyPlugin.java"
import org.bukkit.plugin.java.JavaPlugin;
import so.alaz.taffy.config.ConfigHolder;
import so.alaz.taffy.config.ConfigLoadException;
import so.alaz.taffy.config.ConfigLoader;
import so.alaz.taffy.config.ConfigReader;

import java.util.List;

public final class MyPlugin extends JavaPlugin {

    private ConfigHolder<Settings> settings;

    @Override
    public void onEnable() {
        ConfigLoader files = new ConfigLoader(
            getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger());
        try {
            settings = ConfigHolder.load(() -> loadSettings(files), getLogger()::warning);
        } catch (ConfigLoadException failure) {
            getLogger().severe("The settings could not be loaded: " + failure.getMessage());
            getServer().getPluginManager().disablePlugin(this);
            return;
        }
        // settings.get() is now the record in effect.
    }

    private Settings loadSettings(ConfigLoader files) throws ConfigLoadException {
        ConfigReader reader = new ConfigReader(files.load(), getLogger()::warning);
        Settings loaded = Settings.read(reader, name -> getServer().getWorld(name) != null);
        List<String> errors = reader.errors();
        if (!errors.isEmpty()) {
            errors.forEach(getLogger()::severe);
            throw new ConfigLoadException(ConfigLoader.FILE_NAME + " has " + errors.size() + " errors, listed above");
        }
        return loaded;
    }

    public boolean reloadSettings() {
        return settings.reload();
    }
}
```

When the reader has errors, the loader logs each error line and throws a `ConfigLoadException` with a one-line summary. At startup the exception stops the start. On a reload the holder keeps the settings in effect and passes its failure line to the consumer given to `ConfigHolder.load`. The owner sees every error line, then one line that says what happened. The loader, the reader's warning consumer and the failure consumer are all fixed when the holder is built, so a reload reports to the same place every time and its caller learns only whether it succeeded.

A reload of a data folder without `config.yml` writes the shipped file and succeeds, so the shipped defaults take effect.

### Keeping warnings out of a failed load

The reader passes each warning on as soon as it finds it, so a warning that names a fallback as used can come before the load fails. When it fails, the holder's line says that no value read by that reload is used. A loader that keeps such warnings out of a failed load collects them and logs them only when there are no errors:

```java
private Settings loadSettings(ConfigLoader files) throws ConfigLoadException {
    List<String> warnings = new ArrayList<>();
    ConfigReader reader = new ConfigReader(files.load(), warnings::add);
    Settings loaded = Settings.read(reader, name -> getServer().getWorld(name) != null);
    List<String> errors = reader.errors();
    if (!errors.isEmpty()) {
        errors.forEach(getLogger()::severe);
        throw new ConfigLoadException(ConfigLoader.FILE_NAME + " has " + errors.size() + " errors, listed above");
    }
    warnings.forEach(getLogger()::warning);
    return loaded;
}
```

### Unknown keys

`ConfigReader.unreadKeys()` lists the leaf keys no call read, in file order. A plugin that warns about them leaves out `ConfigLoader.VERSION_KEY`, which the loader keeps in every file:

```java
reader.unreadKeys().stream()
    .filter(path -> !path.equals(ConfigLoader.VERSION_KEY))
    .forEach(path -> getLogger().warning(path + " is not a setting this version reads, so it is ignored."));
```

Only the path a method is called with is recorded. The leaves beneath a group read whole through `value` or `children` are listed as unread, and a plugin that reads a group that way leaves those paths out itself.

## Moving a plugin off getConfig()

A plugin that reads `config.yml` through `JavaPlugin.getConfig()` and then adds a `ConfigHolder` has two copies of its settings: Bukkit's, which `reloadConfig()` replaces, and the holder's, which `ConfigHolder.reload()` replaces. `reload()` replaces only the holder's settings and never Bukkit's copy. A site left on `getConfig()` keeps its old value after every reload of the holder, and a value saved in the ComfiConf editor is answered as applied while that site still acts on the old one ([taffy-comficonf](/docs/modules/comficonf#a-plugin-that-reads-getconfig)). The move therefore covers every site in one change:

- **One reader for every site.** Each value the plugin reads from `config.yml` becomes a component of the settings record, read by one `ConfigReader` call in its factory. No class reads the file another way, the classes for metrics, commands and diagnostics included.
- **Live values from `get()`.** Code that follows a reload calls `settings.get()` each time it needs the value and keeps no copy of it in a field.
- **Enable-time values from `startup()`.** A value the plugin uses once while it enables, such as the storage backend, the metrics switch or the aliases of a command it registers, is read from `settings.startup()`, which holds what the running plugin started with.
- **`getConfig`, `reloadConfig` and `saveConfig` throw.** The plugin overrides the three, so a site that was missed fails the first time it runs, in a test or on a test server, instead of reading a value no reload refreshes:

```java title="MyPlugin.java"
@Override
public FileConfiguration getConfig() {
    throw new UnsupportedOperationException("Read settings.get() or settings.startup() instead of getConfig()");
}

@Override
public void reloadConfig() {
    throw new UnsupportedOperationException("Call settings.reload() instead of reloadConfig()");
}

@Override
public void saveConfig() {
    throw new UnsupportedOperationException("config.yml is written by ConfigLoader, not by saveConfig()");
}
```

A call to `saveDefaultConfig()` is removed as well: `ConfigLoader.load()` writes the shipped file when none is there.

### What the server owner sees

Two things differ from Bukkit's copy, and both belong in the plugin's own changelog:

- **The first load is strict.** With `getConfig()`, a `config.yml` that is not valid YAML is logged and the plugin starts on the values shipped in its jar, and bytes that are not UTF-8 are read as replacement characters. `ConfigHolder.load` passes on the `ConfigLoadException` that `StrictYaml` throws for both, so a plugin that follows the `onEnable` above logs the reason and stays disabled until the owner corrects the file. On a reload, such a file keeps the settings in effect.
- **No value comes from the jar unasked.** `getConfig()` attaches the `config.yml` inside the jar as defaults, so `getConfig().getStringList("aliases")` gives the shipped list when the owner's file has no `aliases` key. The configurations `StrictYaml` and `ConfigLoader` return have no defaults attached, and `ConfigLoader` adds a missing shipped key only when it upgrades a file with an older `config-version`. An absent key gives the fallback of the reader call and nothing else.

A list read is where the second one is easy to miss, because `getStringList` without defaults gives an empty list. The fallback passed to `ConfigReader.strings(path, fallback)` is the shipped list, not `List.of()`, or the entries disappear on every `config.yml` that omits the key:

```java
static final List<String> ALIASES = List.of("home", "h");

List<String> aliases = reader.strings("aliases", ALIASES);
```

A list the owner wrote as empty (`aliases: []`) stays empty: only an absent or blank key gives the fallback.

## ConfigLoader

`new ConfigLoader(Path dataFolder, Supplier<@Nullable InputStream> shipped, Logger logger)` loads `config.yml` (`ConfigLoader.FILE_NAME`) from `dataFolder`. `shipped` opens the `config.yml` inside the jar, or gives `null` when the jar has none; it is asked on every load and the loader closes the stream. The data folder is created when the file is first written.

From `0.4.1`, every `ConfigLoader` and `YamlFolder` constructor calls `Relocation.check()` of `taffy-platform` and throws `IllegalStateException` when the plugin's jar holds Taffy in its original package `so.alaz.taffy`, as [Relocation](/docs/consuming-by-coordinates#relocation) describes.

`load()` returns a new `YamlConfiguration` with the file's comments kept, and blocks the calling thread for the file I/O. The shipped file carries its layout version under `config-version` (`ConfigLoader.VERSION_KEY`) as a whole number from 1 to 2147483647, written without quotes. From `0.4.0`, a shipped file without one makes every `load()` throw `ConfigLoadException`, the first start included, and nothing is written. Before `0.4.0` such a file counted as version 0, so no owner's file was ever upgraded and nothing was logged.

In the owner's file the version may also be written as text, and a number is read as an `int`: a decimal number counts as its whole part, and a number above 2147483647 is not supported. An owner's file with no such key, or with a value that is neither a number nor text holding a whole number of at most nine digits, counts as the baseline version, which is 0 unless the plugin [sets another](#a-file-without-a-version).

| The owner's file | What `load()` does |
|---|---|
| Absent | Writes the shipped text byte for byte, logs that it wrote the default file and loads it. |
| Older version | Runs the [upgrade steps](#renamed-moved-and-removed-keys) the plugin gave, adds every shipped key the file lacks, with its comments, sets the version to the shipped one, writes the previous file to `config.yml.v<N>.bak` (N is the old version; an earlier copy of that name is replaced) and saves the upgraded file. Logs the keys it added. |
| Same version | Reads the file as it is, even when a shipped key is missing. |
| Newer version | Reads the file as it is and logs a warning. Nothing is changed. After [`refuseNewer()`](#a-file-newer-than-the-plugin) the load throws in place of that. |

During an upgrade the owner's keys and values are kept, unknown keys included. A shipped key is not added beneath a path where the owner's file holds a plain value. The `.bak` copy holds the file exactly as it was, byte for byte. YAML drops a key whose value is empty or null while it parses, so such a key counts as missing: it gets the shipped value and comments when the shipped file has the key, and is left out of the saved file otherwise.

### What an upgrade rewrites

The save of an upgrade writes the file anew from the parsed settings. Every value is kept, and the way it is written can change:

| In the owner's file | In the saved file |
|---|---|
| A text without a line break, of any length | On one line. From `0.4.0` a text is never folded; before `0.4.0` a text longer than 80 columns, such as a MiniMessage line, was broken over several indented lines. |
| Quotes | Not kept. A text that needs none is written without them, and one that needs them gets the quotes the writer picks: `"0451"` becomes `'0451'`. |
| A text of several lines | A literal block (the `\|` style), also when it was a folded block (`>`). |
| A number, a date, `true`/`false` | The plain form of the value: `0x10` becomes `16`, `yes` becomes `true` and `2026-12-31` becomes `2026-12-31T00:00:00Z`. |
| A key the upgrade adds | After the keys the owner's file has in that section, not at the place it has in the shipped file. |
| Comments | A comment inside a list is not written back. The indent of a list can change, and a comment or blank line elsewhere can move. The last comment line of a file that holds no key is not written back. |
| Line endings and a byte order mark | Every line ends in a line feed, and a byte order mark is not written back. |

From `0.4.0`, the text of the upgraded file is produced, parsed again and compared with the upgraded settings before anything is written. When the text cannot be produced, or a value would not be read back as it is, nothing is written and no copy is made. A text with half of a surrogate pair (`"a\ud83db"`) is one the writer cannot write, and a text with a control character (`"ding\a"`) is one it turns into `!!binary`, which loads as bytes. Before `0.4.0` the first threw a `RuntimeException` out of `load()` after the copy was written, and the second was saved as `!!binary`.

When the copy or the save of an upgrade fails, or that check refuses the text, a warning is logged, the file stays as the owner left it and the upgraded settings are returned, so the next load tries the upgrade again.

The copy and the save each go through a temporary file in the same folder that is flushed to the device and then replaces the target: `config.yml.tmp` for the save, and the name of the copy followed by `.tmp` for the copy. From `0.4.0` the copy is on the device before the save replaces the file; before `0.4.0` it was copied without a flush. A save follows a symbolic link to the file it names (the temporary file is then the linked file's name followed by `.tmp`) and keeps the file's POSIX permissions where the file system has them, and the copy gets those permissions too. A leftover temporary file from a write that was cut off is removed by the next load or the next write of that name.

### A file without a version

From `0.4.0`, `ConfigLoader.baselineVersion(int version)` gives a copy of the loader that reads an owner's file without a usable `config-version` as `version`. It is for a plugin whose released versions shipped `config.yml` without the key: every file its owners have lacks it, and read as version 0 each of them would be rewritten on the first start under a shipped `config-version: 1`.

```java
ConfigLoader files = new ConfigLoader(getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger())
    .baselineVersion(1);
```

| Shipped `config-version` | An owner's file without the key, baseline 1 |
|---|---|
| `1` | Read as it is. Nothing is written and no copy is made. |
| `2` | Upgraded from version 1: the missing shipped keys and `config-version: 2` are added, and the previous file is kept as `config.yml.v1.bak`. |

The baseline is the version of the layout those releases wrote, and the first shipped file with the key carries the same number. A file that holds a version is not affected. `version` is 0 or more, and a negative one throws `IllegalArgumentException`. A baseline above the shipped `config-version` is a mistake in the plugin: every `load()` throws `ConfigLoadException` with `the baseline version 3 is above the config-version 2 of the config.yml inside the plugin jar` and writes nothing.

### Renamed, moved and removed keys

An upgrade without steps only adds keys. When version 2 of a plugin renames `cooldown` to `cooldown-seconds`, it adds `cooldown-seconds` with the shipped default: the owner's value is no longer read, and the old key stays in the file and shows up in `ConfigReader.unreadKeys()` on every load.

From `0.4.9`, `ConfigUpgrade` holds a step for each version whose layout changed, and `ConfigLoader.upgrades(ConfigUpgrade upgrades)` gives a copy of the loader that runs them:

```java
ConfigUpgrade upgrades = ConfigUpgrade.none()
    .from(1, keys -> keys.move("cooldown", "cooldown-seconds"))
    .from(2, keys -> {
        keys.move("storage.host", "storage.mysql.host");
        keys.remove("legacy-mode");
    });

ConfigLoader files = new ConfigLoader(getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger())
    .upgrades(upgrades);
```

`ConfigUpgrade.none()` has no steps, and `from(int version, Consumer<ConfigUpgrade.Keys> step)` returns a copy with one step added under the version it upgrades from. `version` is 0 or more, and a negative one or a second step for one version throws `IllegalArgumentException`. A `ConfigUpgrade` is immutable.

For an owner's file of version `v` and a shipped version `s`, the steps registered under `v` up to, not including, `s` run in ascending order on the parsed file, before the shipped keys are added. A file of version 1 under a shipped version 3 runs the steps of 1 and 2; a version without a step is skipped. A file without a usable `config-version` counts as the [baseline version](#a-file-without-a-version). A file that already has the shipped version runs no step, so a saved upgrade is not repeated.

Every path a step names is a full dotted path from the top of the file. `ConfigUpgrade.Keys` has:

| Method | What it does |
|---|---|
| `boolean move(String from, String to)` | Moves the value or the section at `from` to `to`, which renames a key when both paths are in one section. The value stays as the owner wrote it, with the comments above and beside it; a section moves with every key beneath it. Returns whether the file held a key at `from` that is no longer there, so `false` when both paths are the same. |
| `boolean remove(String path)` | Removes the key with its comments, and every key beneath it. Returns whether the file held it. |
| `YamlConfiguration yaml()` | The parsed file, for any other change, such as a value rewritten in another unit. |

The rules of `move`:

- What the file already holds at `to` wins. A value there is kept and the moved one is dropped. When both paths hold a section, each key beneath `from` moves unless the section at `to` already has it.
- A moved key is also dropped where the file holds a plain value above its new place, as `storage: local` does for `storage.mysql.host`.
- In each of those cases the key is still removed from `from`.
- When the file has no key at `from`, or both paths are the same, nothing changes. A step that runs twice on one file leaves it as the first run did.
- The moved key is written after the keys its new section already has. No other key changes its place or its comments.
- The section `from` was in stays, also when the move leaves it empty. `remove` leaves an emptied section in place too; a step removes it by its own path.
- A blank path throws `IllegalArgumentException`.

The result goes through the same check, copy and save as any upgrade. `config.yml.v<N>.bak` holds the file as it was before the steps ran. When the save fails, the file stays as the owner left it and the next load runs the steps again on that file. The log line of the upgrade names the shipped keys that were added and not the keys a step moved.

A step that throws a `RuntimeException` stops the load: `load()` throws `ConfigLoadException` with `the step that upgrades config.yml from version 1 failed: <exception class> <message>` and that exception as the cause. Nothing is written and no copy is made.

### A file newer than the plugin

An owner who goes back to an older build of the plugin has a `config.yml` whose `config-version` is above the shipped one. `load()` reads such a file as it is and logs a warning, and the older build may misread keys whose meaning changed.

From `0.4.9`, `ConfigLoader.refuseNewer()` gives a copy of the loader that does not read it: `load()` throws `ConfigLoadException` with `config.yml is version 3, newer than the version 2 this build knows, so it is not read`. With or without it, a newer file is never rewritten or given a lower version. At startup the exception stops the start, and on a reload a [`ConfigHolder`](#configholder) keeps the settings in effect.

```java
ConfigLoader files = new ConfigLoader(getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger())
    .upgrades(upgrades)
    .refuseNewer();
```

### Owner-keyed sections

Some sections hold entries the owner names, such as a list of kits. Without help, an upgrade adds back a shipped entry the owner renamed or removed. The four-argument constructor takes those sections as full dotted paths, each with the keys under it that are not entries:

```yaml title="config.yml (shipped)"
config-version: 2
kits:
  default: starter
  starter:
    cooldown: 1h
    icon: GOLD_INGOT
```

```java
ConfigLoader files = new ConfigLoader(
    getDataPath(),
    () -> getResource(ConfigLoader.FILE_NAME),
    getLogger(),
    Map.of("kits", Set.of("default")));
```

When the owner's file already holds `kits` with at least one key, a shipped entry the owner does not have (`starter`) is not added, while the fixed key `default` still is, and missing keys inside an entry the owner kept are added. An empty section (`kits: {}`) gets the shipped entries, and so does a file without the section. No listed section may lie inside another listed section: from `0.4.0` the constructor throws `IllegalArgumentException` for one that does, such as `kits.special` beside `kits`, and for a blank path. The map and its sets are copied.

### Failures

`load()` throws `ConfigLoadException` when the shipped file is absent, unreadable, not UTF-8 or not valid YAML, when it has no whole number of 1 or more under `config-version` (from `0.4.0`, with the message `the config.yml inside the plugin jar has no whole number of 1 or more under config-version`), when the owner's file cannot be read, is not UTF-8 or is not valid YAML, or when a missing file cannot be written. From `0.4.9` it also throws when an [upgrade step](#renamed-moved-and-removed-keys) throws, and for a [newer file](#a-file-newer-than-the-plugin) after `refuseNewer()`. An existing file is not changed in any of these cases. From `0.4.0`, a message about a file that cannot be read or written names it as `config.yml`, without its path (`cannot write config.yml: AccessDeniedException`), and the I/O failure is the cause. The loader holds no state between loads, and calls to `load()` must not overlap; `ConfigHolder.reload()` never overlaps, so a loader used only through a holder keeps to that.

## ConfigReader

`new ConfigReader(ConfigurationSection root, Consumer<String> warnings)` reads paths relative to `root`. Paths are dotted, such as `storage.table`. One instance serves one load of one configuration and is not thread-safe.

Problems come in two tiers, and no method throws for a value it cannot use:

- A **warning** goes to the consumer at once, on the calling thread. The value is replaced with the fallback of the call and reading goes on.
- An **error** is collected and returned by `errors()`, an unmodifiable copy in the order the errors were added. The caller decides what a configuration with errors means.

A key that is absent gives the fallback with no warning. A single value is a text, a number, `true`/`false` or a date.

From `0.4.8`, `new ConfigReader(ConfigurationSection root, String source, Consumer<String> warnings)` also names the file `root` was read from, such as `config.yml`. The lines are the same with either constructor; `source` is the file of the records [`problems()`](#problems-as-records) returns.

### Typed readers

| Method | Accepts | Otherwise |
|---|---|---|
| `int integer(String path, int fallback)` | A value YAML reads as an `int` | Warning, fallback |
| `int integer(String path, int fallback, int min, int max)` | As above, from `min` to `max` inclusive | Warning, fallback |
| `long whole(String path, long fallback)` | An `int` or a `long` | Warning, fallback |
| `double decimal(String path, double fallback)` | Any finite number, whole numbers included | Warning, fallback (`.inf` and `.nan` included) |
| `boolean bool(String path, boolean fallback)` | A value YAML reads as a boolean | Warning, fallback |
| `<E extends Enum<E>> E choice(String path, E fallback)` | The name of a constant of the fallback's enum, trimmed, in any letter case | Warning, fallback |
| `<E extends Enum<E>> E choiceWithHyphens(String path, E fallback)` (from `0.4.8`) | As `choice`, with a hyphen read as an underscore | Warning, fallback |
| `@Nullable Integer optionalInteger(String path, String fallbackText)` | An `int`; absent gives `null` | Warning naming `fallbackText`, `null` |
| `Duration duration(String path, Duration fallback)` | The form of `Durations.parseOrNull`, such as `30s` | Warning, fallback |
| `Duration duration(String path, Duration fallback, Duration min, Duration max)` | As above, from `min` to `max` inclusive | Warning, fallback |
| `List<Duration> durations(String path, List<Duration> fallback)` | A non-empty list in which every entry is a duration | One warning, the whole fallback |
| `List<String> strings(String path, List<String> fallback)` | A list, empty included; each single value as text | Bad entries skipped with a warning each; not a list gives a warning and the fallback |
| `<T> T parsed(String path, T fallback, String expected, Function<String, T> parser)` | A single value `parser` accepts | Warning, fallback |
| `<T> T parsed(String path, T fallback, String fallbackText, String expected, Function<String, T> parser)` | As above; warnings name `fallbackText` | Warning, fallback |

The range overloads of `integer` and `duration` throw `IllegalArgumentException` when `min` is greater than `max` or the fallback lies outside them. A value outside the range gives the warning `<path> is <value>; expected <min> to <max>, so <fallback> is used.`

`choice` matches with `Locale.ROOT`, so the result does not depend on the server's locale. A hyphen does not stand for an underscore. The constants are listed in lower case and in declaration order in the warning.

From `0.4.8`, `choiceWithHyphens` reads as `choice` does and also reads a hyphen as an underscore, so `complete-on-close` names `COMPLETE_ON_CLOSE` as `complete_on_close` does. Its warning is the one of `choice`, with the constants written with their underscores. `choice` is unchanged.

`durations` and `strings` return an unmodifiable list, or the fallback itself.

`parsed` hands the parser the text form of the value. The parser rejects it by throwing `IllegalArgumentException` or, from `0.4.0`, `DateTimeException`, whose message is not shown. The parsers of `java.time` throw the second: `reader.parsed("reset-at", LocalTime.NOON, "a time such as 18:30", LocalTime::parse)` gives the fallback and a warning for `25:99`, and `ZoneId::of` does for a zone that does not exist. Before `0.4.0` that exception left `parsed` and failed the load. Any other exception of the parser is thrown on to the caller. The parser is not called for a list or a group of keys. The four-argument form writes the fallback with `String.valueOf`, so `T` needs a `toString` an owner can read; for a type such as `org.bukkit.Color`, the five-argument form takes the fallback as the owner would write it. With a parser from `taffy-platform`, pass the parser's `EXPECTED` constant (`Durations.EXPECTED`, `Colors.EXPECTED`, `Expiry.EXPECTED`) as `expected`.

### Text readers

| Method | Absent key | Blank text | A list or a group of keys | Other problems |
|---|---|---|---|---|
| `String text(String path, String fallback)` | `fallback` | Returned as it is | Warning, `fallback` | |
| `String quoted(String path, String fallback)` | `fallback` | Returned as it is | Warning, `fallback` | A number, a date or `true`/`false` adds an error and gives `fallback` |
| `@Nullable String strictText(String path, @Nullable String fallback, String expected)` | `fallback` | Returned as it is | Error, `null` | |
| `@Nullable String requiredText(String path, String fix)` | Error, `null` | Error, `null` | Error, `null` | |

A number and `true`/`false` read as their text form in `text`, `strictText` and `requiredText`. `quoted` is for values that must be written in quotes, such as a code like `0451`, which YAML reads as a number.

`fix` in `requiredText` is what the owner has to do, without a full stop: the error is `<path> is missing; <fix>.` for an absent key and `<path> is <value>; <fix>.` otherwise.

### Blank values

A blank text (empty or only whitespace) reads as an absent key in `integer`, `optionalInteger`, `whole`, `decimal`, `bool`, `duration`, `durations`, `strings`, `parsed` and `choice`, and from `0.4.8` in `sections` and `choiceWithHyphens`: it gives the fallback with no warning. `text`, `quoted` and `strictText` return a blank text as it is, and `requiredText` reports it as an error.

### Dates

YAML reads an unquoted `2026-12-31` as a date at midnight UTC, and an unquoted date with a time as an instant in UTC whether the text names a zone or not. The reader handles both:

- Every reader that gives text reads an unquoted date as text written `yyyy-MM-dd`, and `parsed` hands it to the parser that way.
- An unquoted date with a time makes `text` and `parsed` warn and use the fallback, makes `strings` skip the entry with a warning, and makes `requiredText` and `strictText` add an error. The line asks the owner to write the value in quotes.
- `quoted` adds its error for any unquoted date.
- An unquoted date and time whose offset brings it to midnight UTC, such as `2026-12-31T19:00:00-05:00`, cannot be told apart from a date: `text`, `strings`, `requiredText`, `strictText` and `parsed` read it as the UTC date, `2027-01-01`, with no warning.

A value with a time, such as an expiry read through `Expiry`, has to be written in quotes in the file.

### Structure and bookkeeping

| Method | What it does |
|---|---|
| `Set<String> children(String path)` | The keys directly beneath the group at `path`, in file order. Absent gives an empty set; a plain value gives an empty set and a warning. |
| `List<ConfigReader> sections(String path)` (from `0.4.8`) | One reader for each group of keys in the list at `path`. See [Lists of groups](#lists-of-groups). |
| `boolean absentOrSection(String path)` | Whether `path` is absent or holds a group of keys. |
| `boolean isSection(String path)` | Whether `path` holds a group of keys. |
| `@Nullable Object value(String path)` | The raw value: a `ConfigurationSection`, a `List`, the single value, or `null`. |
| `ConfigurationSection root()` | The section given to the constructor. Nothing is recorded as read. |
| `void warn(String message)` | Passes a line of the plugin's own to the warning consumer. |
| `void error(String message)` | Adds a line of the plugin's own to `errors()`. |
| `void warn(String path, String message, @Nullable String fix)` (from `0.4.8`) | A warning of the plugin's own about one key. See [Problems as records](#problems-as-records). |
| `void error(String path, String message, @Nullable String fix)` (from `0.4.8`) | An error of the plugin's own about one key. |
| `List<String> errors()` | The errors collected so far. |
| `List<ConfigProblem> problems()` (from `0.4.8`) | One record for each warning and each error so far, in order. |
| `Set<String> readPaths()` | Every path a method was called with, each once, in order of first read, whether or not the key exists. An unmodifiable view that follows later reads. |
| `List<String> unreadKeys()` | The leaf keys of the root not in `readPaths()`, in file order. A list is one leaf. |
| `static String describe(@Nullable Object value)` | How warnings and errors write a value. |

`describe` writes a group of keys as `a group of keys`, a text in double quotes, a date in UTC as `2026-12-31` at midnight and as `2026-12-31T23:59:59Z` otherwise, and anything else as `String.valueOf` writes it. A text longer than 100 characters is written as its first 100 characters in double quotes followed by `...`. Any other value whose written form is longer than 100 characters is written as `a list of <n> entries` (or `a list of 1 entry`), `a group of <n> keys` (or `a group of 1 key`) for a map, or its first 100 characters followed by `...`.

<Callout type="warn" title="Refused values reach the log">
A warning names the value it refuses, cut to 100 characters. Part of a mistyped secret, such as a database password written as a list, can therefore reach the log.
</Callout>

### Lists of groups

From `0.4.8`, `sections(String path)` reads a list in which each entry is a group of keys, such as rewards, costs or conditions, and gives one `ConfigReader` per entry in file order:

```yaml
rewards:
  - type: money
    amount: 50
  - type: item
    amount: many
```

```java
for (ConfigReader reward : reader.sections("rewards")) {
    String type = reward.requiredText("type", "write money or item");
    int amount = reward.integer("amount", 1);
}
```

Each reader takes its paths relative to its entry and shares the warning consumer, `errors()`, `problems()` and `readPaths()` of the reader it came from, so the plugin still checks one `errors()` at the end. It writes a key as `<path>[<index>].<key>` in every line and read path, with the index of the entry in the file counted from 0. The second entry above gives:

```text
rewards[1].amount is "many"; expected a whole number, so 1 is used.
```

The reader of an entry gives the readers of a list inside that entry the same way, as in `rewards[1].costs[0].amount`. Its `root()` holds the keys of the entry, and its `unreadKeys()` lists the unread keys of the entry in the same form. A key written `""` inside an entry cannot be read: it is left out of the entry without a warning and is not among its unread keys. The `IllegalArgumentException` of a range overload names the key the same way, as in `the fallback 5 of rewards[0].amount is not within 1 to 2`.

| The value at `path` | Result |
|---|---|
| Absent, a blank text or an empty list | An empty list, no warning |
| A list | One reader per group of keys. Any other entry is skipped with a warning, and the other entries keep their index. |
| Anything else | An empty list and a warning |

`ConfigurationSection.getMapList` drops an entry that is not a group of keys without a word; `sections` warns about each one. The returned list is unmodifiable.

### Problems as records

From `0.4.8`, `problems()` gives every warning and error of the reader as a `ConfigProblem`, for code that lists, counts or sorts them: a validate command, a doctor report, or a reload that tells warnings from errors. No line changes, and the warning consumer and `errors()` receive what they did before.

| Component | Holds |
|---|---|
| `@Nullable String file()` | The `source` given to the constructor, or `null` for a reader built without one |
| `@Nullable String path()` | The key the line names, written as the line writes it, such as `limits.homes` or `rewards[1].type`. `null` for `warn(String)` and `error(String)`. |
| `ConfigProblem.Severity severity()` | `WARNING` for a line of the warning consumer, `ERROR` for a line of `errors()` |
| `String message()` | The full line |
| `@Nullable String fix()` | What the owner has to do, without a full stop. The reader sets it for `requiredText`, from its `fix` argument, and leaves it `null` for its other lines. |

A plugin's own check on one key goes through `warn(String path, String message, @Nullable String fix)` or `error(String path, String message, @Nullable String fix)`. The line is `<path> <message>.`, or `<path> <message>; <fix>.` with a fix, with the path written as the reader writes it, so a check inside an entry of `sections` names `rewards[0].amount` without building that name by hand:

```java
if (amount <= 0) {
    reward.error("amount", "must be above 0", "write a whole number such as 5");
}
```

```text
rewards[0].amount must be above 0; write a whole number such as 5.
```

`message` and `fix` are written without a full stop at the end. Neither call records the path as read.

## The lines an owner sees

Every warning and error line of `ConfigReader` names the path first and is a full sentence without the plugin's name, which the logger adds. The shapes:

| Situation | Line |
|---|---|
| A value is replaced | `<path> is <value>; expected <what>, so <fallback> is used.` |
| A value is outside a range | `<path> is <value>; expected <min> to <max>, so <fallback> is used.` |
| A whole number does not fit an `int` (`integer`, `optionalInteger`; from `0.4.0`) | `<path> is <value>; expected a whole number from -2147483648 to 2147483647, so <fallback> is used.` |
| A list entry is dropped | `<path> has <entry>, which is not a single value, so it is skipped.` |
| An entry of `sections` is not a group of keys (from `0.4.8`) | `<path>[<index>] is <entry>, which is not a group of keys, so it is skipped.` |
| The value of `sections` is not a list (from `0.4.8`) | `<path> is <value>; expected a list of groups of keys, so it is ignored.` |
| A check of the plugin's own on a key (from `0.4.8`) | `<path> <message>.` or `<path> <message>; <fix>.` |
| A value where a group of keys belongs | `<path> should hold keys beneath it, so its value is ignored.` |
| A required text is absent | `<path> is missing; <fix>.` |
| A required text is blank, a list or a group | `<path> is <value>; <fix>.` |
| A strict text is a list or a group | `<path> is <value>; expected <expected>.` |
| A date with a time is unquoted (`requiredText`, `strictText`) | `<path> must be in quotes, because YAML reads a date and time written without them in UTC.` |
| A date with a time is unquoted (`text`, `parsed`) | `<path> must be in quotes, because YAML reads a date and time written without them in UTC, so <fallback> is used.` |
| A list entry is an unquoted date with a time (`strings`) | `<path> has <entry>, which must be in quotes, because YAML reads a date and time written without them in UTC, so it is skipped.` |
| A quoted value is unquoted | `<path> must be in quotes, because YAML changes an unquoted value it reads as a number, a date or true/false.` |

With the settings above, an owner who writes `max-homes: five`, `teleport-delay: soon` and `particle-color: pink` sees:

```text
max-homes is "five"; expected a whole number, so 3 is used.
teleport-delay is "soon"; expected a whole number followed by ms, s, m, h or d (for example 30s), so 3s is used.
particle-color is "pink"; expected a named color, "#RRGGBB" hex in quotes or r,g,b, so aqua is used.
```

`choice` adds a hint when YAML turned the value into `true` or `false` and a constant has a name YAML reads as that value (`yes`, `no`, `on`, `off`, `true` or `false`). For an enum `Switch { ON, OFF, AUTO }` with fallback `AUTO`, an unquoted `toggle: on` gives:

```text
toggle is true; expected on, off or auto, so auto is used. YAML reads an unquoted yes, no, on or off as true or false, so write the value in quotes, for example "on".
```

Before `0.4.0` a whole number outside the `int` range gave `expected a whole number`. `integer(path, fallback, min, max)` names its own range for such a number, and `whole` names the `long` range for a number beyond it.

The message of a `ConfigLoadException` is a clause without a full stop, such as `config.yml is larger than 16 MiB`, written to follow a lead-in. `ConfigHolder.reload()` puts its own lead-in before it; a plugin that logs the failure of the first load gives one too, as `onEnable` above does. Every error line of a `YamlFolder` names its file.

The log lines `ConfigLoader` writes for a default file, an upgrade, a failed save and a newer file are worded for the owner and can change in any release. Code branches on exception types and return values, never on a message.

## ConfigHolder

`ConfigHolder<T>` implements `Supplier<T>`.

| Member | What it does |
|---|---|
| `static <T> ConfigHolder<T> load(ConfigHolder.Loader<T> loader, Consumer<String> failures)` | Runs the first load and returns a holder of its settings. Throws the loader's `ConfigLoadException` as it was thrown, without passing it to `failures`. |
| `T get()` | The settings in effect: those of the first load, or of the last reload that succeeded. |
| `T startup()` | The settings of the first load, which never change. |
| `boolean reload()` | Runs the loader again and returns `true` when the new settings are in effect. |

`ConfigHolder.Loader<T>` is a functional interface with one method, `T load() throws ConfigLoadException`, which must not return `null`.

When the loader throws `ConfigLoadException` during `reload()`, the settings in effect stay, `false` is returned and the failure consumer receives:

```text
The reload failed, so the settings in effect stay active and no value read by this reload is used: <message>
```

A `RuntimeException` from the loader is thrown on to the caller of `reload()` and also keeps the settings in effect. A loader that returns `null` throws `NullPointerException` with the message `the loader returned null`, at the first load and on a reload, and the settings in effect stay. A value the reader replaced with its fallback and a warning does not fail a reload: the new settings hold the fallback.

`holder::reload` serves as a `BooleanSupplier` and as a `Callable<Boolean>`, the form `YamlFileProvider.builder` in [taffy-comficonf](/docs/modules/comficonf) takes for the plugin's reload. The failure consumer receives its line on the thread that called `reload()`.

### Threads

The loader runs on the thread that calls `load` or `reload()` and blocks it while it reads files. Reloads never overlap: a call waits while another one runs. `get()` may be called from any thread. The settings are handed out as they are, so `T` should be immutable, such as a record.

## RestartKeys

Settings that take effect only after a restart, such as the storage backend, are read from `startup()`. After a reload, `RestartKeys.changed(ConfigurationSection before, ConfigurationSection after, Predicate<String> restartOnly)` names the restart-only paths whose value differs, sorted:

```java
public boolean reloadSettings(CommandSender sender) {
    if (!settings.reload()) {
        sender.sendMessage("The reload failed. The console lists why.");
        return false;
    }
    List<String> waiting = RestartKeys.changed(
        settings.startup().source(), settings.get().source(), path -> path.startsWith("storage."));
    if (!waiting.isEmpty()) {
        sender.sendMessage("Takes effect after a restart: " + String.join(", ", waiting));
    }
    return true;
}
```

- `restartOnly` is asked about every path of both configurations that holds a value. A path is dotted and relative to the section passed, such as `storage.type` when the root is passed. It is never asked about a path that holds a section, so a section present in both is not reported: the keys beneath it are.
- A list is one value. Values compare by content: a list entry by entry, and from `0.4.0` a `!!binary` value by its bytes, where before `0.4.0` an unchanged binary value was reported on every reload. Any other value compares with `equals`, so a number written in another form counts as a change: `3306` and `3306.0` differ. A value only one of the two has is reported; an empty section is not.
- `before` is the configuration loaded at startup, not the one from the previous reload. A key set back to its startup value is no longer reported, and a second reload of an unchanged file reports what the first one did.
- Values are read with `ConfigurationSection.get(String)`. The configurations `StrictYaml` and `ConfigLoader` return have no defaults attached, so a removed key is always seen as removed.

## YamlFolder

`new YamlFolder(Path folder)` reads the files directly inside `folder`. A file counts when its name ends in `.yml` in any letter case with at least one character before it and does not start with a dot; its id is the name without those four characters, in the letter case the file has. Subfolders are not read.

From `0.4.0`, a name that starts with a dot is skipped without a line, so a hidden file and the `._<name>.yml` files macOS writes beside a file on a foreign file system are no longer reported as files that are not UTF-8. A regular file whose name ends in `.yaml` is still not read, and from `0.4.0` `load` reports it with a line that tells the owner to rename it, where it was skipped without a word.

```java
record Kit(String id, Duration cooldown, List<String> items) {
}

Map<String, Kit> loadKits() throws ConfigLoadException {
    YamlFolder folder = new YamlFolder(getDataPath().resolve("kits"));
    YamlFolder.Loaded<Kit> loaded = folder.load((id, fileName, yaml) -> {
        ConfigReader reader = new ConfigReader(yaml, line -> getLogger().warning(fileName + ": " + line));
        Kit kit = new Kit(id, reader.duration("cooldown", Duration.ofHours(1)), reader.strings("items", List.of()));
        if (!reader.errors().isEmpty()) {
            throw new ConfigLoadException(String.join(" ", reader.errors()));
        }
        return kit;
    });
    loaded.errors().forEach(getLogger()::warning);
    return loaded.entries();
}
```

`YamlFolder.Parser<T>` is a functional interface: `T parse(String id, String fileName, YamlConfiguration yaml) throws ConfigLoadException`, never returning `null`. A parser that reads through a `ConfigReader` puts the file name and `": "` before each warning, as above, so every warning names its file as the error lines do. When the reader has errors, it throws `ConfigLoadException` with the error lines joined by a space, which becomes the one line of that file.

`YamlFolder.Loaded<T>` is a record of `Map<String, T> entries()` (by id, in file name order) and `List<String> errors()` (one line per failed file, in file name order). Both are unmodifiable copies.

### load and loadOne

`load(Parser<T> parser)` reads every file in the order `String.compareTo` sorts their names. When two names give the same id, as `kit.yml` and `kit.YML` can on a case-sensitive file system, the entry read later replaces the earlier one. A folder that does not exist or is not a directory gives an empty `Loaded`. When the folder cannot be listed, `load` throws `ConfigLoadException` and no file has been read. From `0.4.0` the message is `cannot read the folder <folder name>: <exception class> <reason>`, with the name of the folder and not its path, and the I/O failure as the cause; before `0.4.0` it held the path.

`loadOne(String id, Parser<T> parser)` reads only `<id>.yml`, with the suffix in lower case, and returns a `Loaded` holding the entry or the error line. It returns `null` when `id` is empty or starts with a dot (before `0.4.0` only for `.` and `..`), when it is not a plain file name, or when the folder holds no regular file by that name. The entry is keyed by `id` as given: on a file system that ignores letter case, such as those of Windows and macOS, `id` can match a file whose name has another letter case.

A file that fails adds one line to `errors()` and the other files still load:

| Failure | Line |
|---|---|
| The file cannot be read or parsed | The `StrictYaml.read` message, which names the file |
| The parser throws `ConfigLoadException` | `<file name>: <message>` |
| The read or the parser throws another `RuntimeException` | `<file name>: <exception class> <message>` |
| The parser returns `null` | `<file name>: NullPointerException the parser returned null` |
| A regular file is named `<name>.yaml` (from `0.4.0`) | `<name>.yaml: rename it to <name>.yml to have it read` |

`load` reports a subfolder whose name ends in `.yml` as a file that cannot be read. A folder built with one of the two constructors above is never written to. Nothing is kept between calls, so one instance may be used from any thread. The reads block the calling thread, and the consumers below are called on it.

### Warnings beside a loaded entry

`Loaded.errors()` holds lines, and a file either loads or adds one. From `0.4.8`, `loadReport(ReportingParser<T> parser)` reads the folder as `load` does and also gives the problems of the load as [`ConfigProblem`](#problems-as-records) records, so a file that loads with warnings keeps its entry and its warnings are listed beside it:

```java
YamlFolder.Report<Kit> report = folder.loadReport((id, fileName, yaml) -> {
    ConfigReader reader = new ConfigReader(yaml, fileName, line -> getLogger().warning(fileName + ": " + line));
    Kit kit = new Kit(id, reader.duration("cooldown", Duration.ofHours(1)), reader.strings("items", List.of()));
    if (!reader.errors().isEmpty()) {
        throw ConfigLoadException.withProblems(String.join(" ", reader.errors()), reader.problems());
    }
    return new YamlFolder.Parsed<>(kit, reader.problems());
});
```

`YamlFolder.ReportingParser<T>` is a functional interface: `YamlFolder.Parsed<T> parse(String id, String fileName, YamlConfiguration yaml) throws ConfigLoadException`. `Parsed<T>` is a record of `T entry()`, never `null`, and `List<ConfigProblem> problems()`. The parser builds its reader with `fileName` as the source, so every record names its file.

`YamlFolder.Report<T>` is a record of `entries()` and `errors()`, which hold what `Loaded` holds for the same folder, and `List<ConfigProblem> problems()` in file name order:

| File | Records |
|---|---|
| It loaded | The problems of its `Parsed`, such as the warnings of its reader |
| Its parser threw `ConfigLoadException` | One `ERROR` record with the file name, no path and the line of `errors()` as the message, then the records given to `ConfigLoadException.withProblems(String message, List<ConfigProblem> problems)`. A failure built with a constructor carries none. |
| Any other failure | One `ERROR` record with the file name, no path and the line of `errors()` as the message |

The record of a file named `<name>.yaml` has the fix `rename it to <name>.yml`; the other file records have none. `ConfigLoadException.problems()` returns the records a failure carries, and an empty list for one built without them. `Loaded`, `load` and `loadOne` are unchanged, and no `loadOne` returns a `Report`.

The records of a file that loaded are the ones its parser hands over. The line of [`lenient`](#files-saved-in-a-legacy-code-page) about replaced bytes is not among them: it reaches only the consumer given to `lenient`. When two file names give the same id and the later entry replaces the earlier one, the records of both files are kept, each under the name of its file.

### Parser bugs

The line of a `RuntimeException` holds its class name and message and no stack trace, which is too little to find a bug in the plugin's own parser. From `0.4.0`, `new YamlFolder(Path folder, BiConsumer<String, Throwable> failures)` hands the consumer the file name and the exception whenever the read or the parser throws a `RuntimeException`, a `null` entry included. The file still gets its line and the other files still load. A `ConfigLoadException` is the parser's own verdict and is not passed on.

```java
YamlFolder folder = new YamlFolder(getDataPath().resolve("kits"),
    (fileName, failure) -> getLogger().log(Level.SEVERE, "Could not read kits/" + fileName, failure));
```

### Files saved in a legacy code page

A file an owner saved as Windows-1252 or another legacy code page holds bytes that are not UTF-8, and a strict read reports it as an error, so its entry is gone. Bukkit's `YamlConfiguration.loadConfiguration` reads such bytes as the replacement character U+FFFD and loads the file. From `0.4.0`, `lenient(Consumer<String> warnings)` gives a copy of the folder that reads each file with [`StrictYaml.readLenient`](#strictyaml), for a plugin that moves to `YamlFolder` and has such files on its owners' servers:

```java
YamlFolder folder = new YamlFolder(getDataPath().resolve("vouchers")).lenient(getLogger()::warning);
```

Each byte sequence that is not UTF-8 is read as U+FFFD, the file loads, and `warnings` receives one line per file that names it and the first line with a replaced character. Strict reading stays the default.

### Files with a version

From `0.4.9`, a third constructor reads a layout version from each file, upgrades an older file and does not read a newer one:

```java
ConfigUpgrade upgrades = ConfigUpgrade.none()
    .from(1, keys -> keys.move("prize", "reward"));

YamlFolder crates = new YamlFolder(getDataPath().resolve("crates"), getLogger(), "crate-version", 2, upgrades, false);
```

`new YamlFolder(Path folder, Logger logger, String versionKey, int currentVersion, ConfigUpgrade upgrades, boolean recursive)` takes the key that holds the version as a full dotted path, the version of the layout the plugin reads (1 or more) and the [steps](#renamed-moved-and-removed-keys), each under the version it upgrades from. A blank key or a version below 1 throws `IllegalArgumentException`. The version of a file is read as `ConfigLoader` reads `config-version`: a number, or text holding a whole number of at most nine digits, and 0 for a file without a usable one. So a folder whose files never had the key registers its first step under 0, and every such file is rewritten once, with the key added after the keys it has.

| The file | What a load does |
|---|---|
| Current version | Reads it as it is. It is never written. |
| Older version | Runs the steps registered under its version up to, not including, the current one on the parsed file, sets the version key and hands the result to the parser. Writes the previous file, byte for byte, to `<file name>.v<N>.bak` beside it (N is the old version; an earlier copy of that name is replaced) and saves the upgraded file. Logs `Upgraded <name> from version 1 to 2; the previous file is kept as <file name>.v1.bak.` |
| Newer version | Does not hand it to the parser, upgrade or write it. Adds the line `<name>: <versionKey> is 3, newer than the version 2 this build knows, so the file is not read`, and the other files still load. |

The save rewrites the file [as an upgrade of `config.yml` does](#what-an-upgrade-rewrites), and both the copy and the save go through a temporary file that replaces its target in one step. When the save fails, the file stays as it was, byte for byte, the parser still gets the upgraded file and the next load tries again; the logger receives a warning that starts with `Could not save the upgraded <name>: ` and states the reason. A file is not saved when its text would not be read back as it is, when it changed on the disk since it was read, when it holds bytes that are not UTF-8 and was read through [`lenient`](#files-saved-in-a-legacy-code-page), or when the version key is a dotted path beneath a key of the file that holds a value, which stays as the owner wrote it.

A step that throws leaves its file unchanged, and the parser does not see the file. The file adds the line `<name>: the step that upgrades it from version 1 failed: <exception class> <message>`, and the logger receives a warning with the exception, so its stack trace is in the log.

`loadOne` upgrades its file the same way. Such a folder is written only inside `load`, `loadReport` and `loadOne`, on the calling thread. Two loads of one folder that overlap both load every entry, and the one that comes second to a file logs that it could not save it. The `.bak` copies and the temporary files do not end in `.yml`, so no load reads them.

With `recursive` set, the files in subfolders are read too:

- The name of a file, in the lines and for the parser, is its path from the folder with `/` between the parts, such as `rare/gold.yml`. Its id is that name without the suffix: `rare/gold`.
- The files are read in the order of those names.
- A folder whose name starts with a dot is skipped with everything in it, and a folder reached through a symbolic link is not entered.
- `loadOne("rare/gold", parser)` reads that one file. It returns `null` when a part of the id is empty, starts with a dot or is not a plain name.

With `false`, only the files directly inside the folder are read, as the other constructors read them.

## AtomicWriter

A plugin that edits its own files from a command or a menu saves them with `YamlConfiguration.save(file)` or `Files.writeString`, which truncate the file and then write it: a crash or a full disk in between leaves half a file, and a second writer replaces what the first one wrote. From `0.4.9`, `AtomicWriter` writes a text file, as UTF-8 and exactly as given, through a temporary file named as the target followed by `.tmp`. The temporary file is flushed to the device and then put in place in one step, so a reader sees the previous file or the new one. All four methods are static.

| Method | What it does |
|---|---|
| `void create(Path file, String text)` | Writes a new file. Throws `FileAlreadyExistsException` when `file` exists, a symbolic link included, and leaves that file as it is. A parent of `file` that exists and is not a folder throws it too. |
| `void write(Path file, String text)` | Replaces the file, or writes it when it does not exist. |
| `String revision(byte[] content)` | The SHA-256 of the bytes as 64 lower-case hex digits. |
| `Result replace(Path file, String text, String baseRevision, Path backups, int keep)` | Replaces the file only while it still has `baseRevision`, and keeps a copy of what it replaced. |

`create` gives the flushed temporary file its name with a hard link, which the file system refuses when the name is taken, so of two writers of one new id only one succeeds. On a file system without hard links it moves the file without replacing, which Windows does in one step and other systems do as a check followed by a move.

```java
try {
    AtomicWriter.create(vouchersFolder.resolve(id + ".yml"), yaml.saveToString());
} catch (FileAlreadyExistsException taken) {
    // another voucher has the id
}
```

An edit that starts from what the file held takes the revision of the bytes it read, and `replace` writes only while the file still has it:

```java
byte[] read = Files.readAllBytes(file);
String base = AtomicWriter.revision(read);
YamlConfiguration yaml = StrictYaml.parse(new String(read, StandardCharsets.UTF_8), "gold.yml");
yaml.set("reward", "EMERALD");

switch (AtomicWriter.replace(file, yaml.saveToString(), base, dataFolder.resolve("backups"), 10)) {
    case AtomicWriter.Written written -> base = written.revision();
    case AtomicWriter.Conflict conflict -> tellTheEditorTheFileChanged();
}
```

- `AtomicWriter.Result` is sealed. `Written` is a record of `String revision()`, the revision of the content now in the file, and `Path backup()`, the copy of the content that was replaced, or `null` when the file did not exist. `Conflict` is a record of `String currentRevision()`; nothing was written or copied.
- `AtomicWriter.ABSENT` (`absent`) is the revision of a file that does not exist: as `baseRevision` it writes the file only when there is none, and a `Conflict` carries it when the file is gone.
- The copy is written to `backups`, which is created when missing, as `<file name>.<path id>.<yyyyMMdd-HHmmss-SSS>.bak`. The time is UTC, `-<n>` follows it for a further copy of the same millisecond, and the path id is the first 12 hex digits of the SHA-256 of the file's absolute path without its `.` and `..` parts, so files of one name in different folders can share one folder of copies. The letter case of the path as given is part of the name and of the id, so on a file system that ignores letter case a plugin passes one spelling of a file to keep its copies together. The copy holds the file byte for byte. No copy is taken when the newest copy of that file already holds the same bytes, and a call whose text is what the file already holds is a write like any other and takes its copy.
- The copies are ordered by the time in their names alone. A copy never gets a time before the one of the newest copy of its file: when the clock is behind that copy, the new one gets its time and the next `-<n>`.
- After the write, the copies of that file beyond the newest `keep` are deleted. `keep` is 1 to 1000, and another number throws `IllegalArgumentException`. A delete that fails leaves that copy and does not fail the call.

`write` and `replace` follow a symbolic link to the file it names, so the link stays and the file it leads to is replaced. A link that leads to a file that does not exist is not followed: both throw `NoSuchFileException` and write nothing. The new file gets the POSIX permissions of the file it replaces where the file system has them, and so does the copy. A file written where none existed gets the permissions of any new file. A missing parent folder is created. A hard link of the target is not updated.

Every method throws the `IOException` of the step that failed:

| Failure | What is left |
|---|---|
| The device is full, or the temporary file cannot be written | The file holds what it held before the call. The temporary file and the copy `replace` took in that call are removed. |
| The folder refuses new files | The same, and nothing was written. |
| The file is marked read-only | On a POSIX file system the file is replaced, because the folder allows the rename, and the new file has the same permissions. On Windows the move is refused, and the file and its attribute stay. |
| The temporary file cannot be removed after a failure | It stays until the next write of that name removes it. |

Every call blocks the calling thread for its file I/O and uses no scheduler: call it from an async task, on Paper and on Folia. Calls for one file made through the plugin's copy of the class run one after another. A change by another plugin, another process or the owner's editor is not held off, and only the revision check of `replace` detects it. `ConfigLoader` and a `YamlFolder` with a version write through the same routine.

## StrictYaml

`StrictYaml` never replaces a document it cannot use with an empty configuration. Both methods return a new `YamlConfiguration` with the document's comments kept, which is not thread-safe. From `0.4.0` its line width is `Integer.MAX_VALUE`, so `saveToString()` writes a text without a line break on one line whatever its length; before `0.4.0` it folded a text longer than 80 columns over several indented lines.

- `static YamlConfiguration parse(String text, String source)` parses text. Empty text is an empty configuration.
- `static YamlConfiguration read(Path file, String source)` reads a file as UTF-8 and parses it, blocking the calling thread.
- From `0.4.0`, `static YamlConfiguration readLenient(Path file, String source, Consumer<String> warnings)` reads as `read` does, except that a byte sequence that is not UTF-8 does not fail the read: each one is read as the replacement character U+FFFD. `warnings` receives one line when the file held such bytes, `<source> is not saved as UTF-8, so each byte that is not UTF-8 is read as the replacement character U+FFFD; the first is on line <n>. Save the file as UTF-8.`, and nothing for a file that is UTF-8. The text that results is parsed, so a replaced character ends up in a value, a key or a comment, or makes the YAML invalid.

`source` names the document in the failure message, such as `config.yml` or `messages.yml`:

```java
YamlConfiguration messages = StrictYaml.read(getDataPath().resolve("messages.yml"), "messages.yml");
```

| Failure | `ConfigLoadException` message |
|---|---|
| Text the parser rejects | `<source> is not valid YAML: <problem> at line <n>, column <m>` (line and column from 1, when the parser gives a position) |
| A top level that is not a mapping, or a second document | `<source> is not valid YAML: <reason>` |
| An anchor used inside the value it names | `<source> is not valid YAML: an anchor is used inside the value it names` |
| Aliases that repeat more than 100000 values | `<source> is not valid YAML: its aliases repeat more than 100000 values` |
| Bytes that are not UTF-8 (`read`) | `<source> is not saved as UTF-8: the first byte that is not UTF-8 is on line <n>` (lines from 1; before `0.4.0` the message ended after `UTF-8`) |
| A file larger than 16 MiB (`read`) | `<source> is larger than 16 MiB` |
| Any other read failure, a missing file included (`read`) | `cannot read <source>: <exception class>`, followed by a space and the reason when the I/O failure states one, such as `cannot read config.yml: NoSuchFileException`. The I/O failure is the cause. Before `0.4.0`: `cannot read <path>: <exception class> <message>`, which held the path twice. |

A parse error names a line and column, not the text of the line, though it can name a key or a character. A reason without a position is the parser's own message, which can quote a value. The exception for a parse error carries no cause.

YAML details a plugin's users meet:

- A key written twice in one mapping is not an error: the last one is kept. Where it holds a section, the keys of the earlier section are dropped.
- A key that holds a dot is read as a path, so `"a.b": 1` sets `b` inside a section `a`.
- An unquoted key `yes`, `no`, `on`, `off`, `true` or `false` becomes the key `true` or `false`, and an unquoted number key becomes the text of that number.
- An unquoted `#` starts a comment, so a hex colour such as `"#ff0000"` has to be quoted; unquoted, the key reads as empty and gives the fallback with no warning.
- The 16 MiB cap bounds the file size, not the parse time: one very long line can take SnakeYAML minutes to parse.

## Testing settings

`Settings.read` takes a `ConfigReader` and a predicate, so it runs in a plain JUnit test with the Paper API on the test classpath:

```java
import org.junit.jupiter.api.Test;
import so.alaz.taffy.config.ConfigLoadException;
import so.alaz.taffy.config.ConfigReader;
import so.alaz.taffy.config.StrictYaml;

import java.util.ArrayList;
import java.util.List;

import static org.junit.jupiter.api.Assertions.assertEquals;

final class SettingsTest {

    @Test
    void aWordForTheHomeLimitFallsBackToTheDefault() throws ConfigLoadException {
        List<String> warnings = new ArrayList<>();
        ConfigReader reader = new ConfigReader(
            StrictYaml.parse("storage:\n  table: homes\nmax-homes: five\n", "config.yml"), warnings::add);

        Settings settings = Settings.read(reader, world -> true);

        assertEquals(3, settings.maxHomes());
        assertEquals(List.of("max-homes is \"five\"; expected a whole number, so 3 is used."), warnings);
        assertEquals(List.of(), reader.errors());
    }
}
```

[taffy-test](/docs/modules/test) has `CapturedLog`, whose public `logger` field is a `Logger` to pass to a `ConfigLoader` in a test and whose `records` field keeps what it logged. The wording of those lines is not part of the API.

## Behaviour summary

- **Threads:** no class keeps a thread. File reads and writes block the calling thread. `ConfigHolder.get()`, `YamlFolder`, `ConfigUpgrade` and `AtomicWriter` are safe from any thread; `ConfigReader` and the returned `YamlConfiguration` objects are not thread-safe; calls to one `ConfigLoader.load()` must not overlap.
- **Failure handling:** `ConfigLoadException` is the only checked exception. A bad value is a warning with a fallback or a collected error, never an exception; the plugin's loader turns errors into a `ConfigLoadException`.
- **Reloads:** a failed reload keeps the settings in effect and reports one line; a missing `config.yml` is written again and its defaults take effect.
- **Not bundled:** the Paper API and SnakeYAML come from the server. `taffy-platform` comes with the module.
- **Web editing:** [taffy-comficonf](/docs/modules/comficonf) builds on this module to let owners edit the same file in the ComfiConf editor.
