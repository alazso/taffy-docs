This page lists every change since `0.1.0` that needs an action from a plugin, release by release. Each section
says what changed, who it affects and what to do. No patch of `0.1` (`0.1.1`, `0.1.2`) needs an action. The
[changelog](/docs/versioning#reading-the-changelog) holds every other change, and each later release adds its own
part to this page.

## 0.2.0

Change the version of the settings plugin, and the rest of Taffy follows, as
[One version for plugins, catalog and modules](/docs/versioning#one-version-for-plugins-catalog-and-modules)
describes:

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.0"
}
```

| Change | Affects | Action |
|---|---|---|
| [Paper 26.2 build 135 and paper-api 26.3](#paper-262-build-135-and-paper-api-263) | every plugin | run on a supported server and recompile |
| [Filtered repositories](#filtered-repositories) | a build that took another group from a Taffy repository, or uses `mavenLocal()` for Taffy | declare the repository, or point `alazsoSnapshots` at the local repository |
| [PlaceholderAPI output is inserted as text](#placeholderapi-output-is-inserted-as-text) | a plugin that renders placeholders whose output holds MiniMessage tags, or a template with a placeholder inside a click value or a tag argument | render through `text.withPlaceholderFormatting()`; supply a click or a colour as a `Placeholder.styling` value |
| [A colour code ends the format codes before it](#a-colour-code-ends-the-format-codes-before-it) | a config or language file with a format code written before a colour code | write the colour first |
| [Webhook mentions ping no one](#webhook-mentions-ping-no-one) | a post or payload that is meant to ping | pass `PostOptions`, or give the template `allowed_mentions` |
| [DiscordWebhook.close waits at most 5 seconds](#discordwebhookclose-waits-at-most-5-seconds) | a plugin whose last posts need longer | call `close(Duration)` |
| [WebhookPayload.render refuses unknown value types](#webhookpayloadrender-refuses-unknown-value-types) | a template holding another type of value | convert the value first |
| [SkullBuilder remembers a failed lookup](#skullbuilder-remembers-a-failed-lookup) | a plugin that retries right after a blank head | ask again later |
| [Scheduler.close completes unstarted dispatches](#schedulerclose-completes-unstarted-dispatches) | a plugin that awaits a `dispatch` future | handle the refusal |
| [Shutdown.closeQuietly logs the stack trace](#shutdownclosequietly-logs-the-stack-trace) | a log filter or test that matched the failure text | read the failure from the record's thrown |

### Paper 26.2 build 135 and paper-api 26.3

Taffy compiles against `paper-api` `26.3.build.256-stable` and supports Paper 26.2 build 135 or newer and Folia
26.3 build 8 or newer. Paper 26.1.2 is no longer supported. The `paper` version of the `alaz` catalog moves from
`26.1.2.build.66-stable` to `26.3.build.256-stable`, so a plugin that declares `alaz.paper.api` compiles against
that build, which brings Adventure 5.2.0 in place of 4.26.1. [Servers](/docs/versioning#servers) lists the builds
for each release line.

**Migration:** run the plugin on Paper 26.2 build 135 or newer, or Folia 26.3 build 8 or newer, and recompile it
against `paper-api` 26.3. Adventure 5 makes `ClickEvent` generic, so a raw `ClickEvent` compiles with a rawtypes
warning until it is written `ClickEvent<?>`.

`compileJava` accepts a call that exists in `paper-api` 26.3 and not on Paper 26.2. The new
[`compileAgainstPaperFloor`](/docs/gradle-plugins#compiling-against-the-oldest-supported-paper) task compiles the
plugin against `paper-api` `26.2.build.135-stable` and fails on such a call. No task depends on it, so add it to
`check` to run it with every build:

```kotlin title="build.gradle.kts"
tasks.check {
    dependsOn("compileAgainstPaperFloor")
}
```

### Filtered repositories

`so.alaz.taffy.repositories` asks each repository it declares, Maven Central apart, only for the groups the `alaz`
catalog takes from it, and `jitpack` moves to the end of the list. In `0.1` only the two `repo.alaz.so`
repositories and the three hologram repositories had a filter, so a module an earlier repository lacked was looked
up on every other host. Every entry of the `alaz` catalog resolves to the same modules as before, and
[so.alaz.taffy.repositories](/docs/gradle-plugins#soalaztaffyrepositories) lists the groups of each repository.

**Migration:** a build that took a module of another group from one of these repositories fails with
`Could not find` for that module. Declare the repository in `settings.gradle.kts`:

```kotlin title="settings.gradle.kts"
dependencyResolutionManagement {
    repositories {
        maven("https://repo.example.org/releases") { name = "example" }
    }
}
```

The `so.alaz` group and its subgroups resolve from `alazso` and `alazsoSnapshots` and from no other repository,
Maven Central and a repository the build adds included. A `mavenLocal()` in
`dependencyResolutionManagement.repositories` is therefore no longer asked for a locally published Taffy.

**Migration:** a build that added `mavenLocal()` there to use a locally published Taffy sets the URL of
`alazsoSnapshots` to the local repository instead, as
[Build against a snapshot or a local publish](/docs/getting-started#build-against-a-snapshot-or-a-local-publish)
shows in full:

```kotlin title="settings.gradle.kts"
dependencyResolutionManagement {
    repositories.named<MavenArtifactRepository>("alazsoSnapshots") {
        url = uri(File(System.getProperty("user.home"), ".m2/repository"))
    }
}
```

### PlaceholderAPI output is inserted as text

`Text` and `Messages` insert what a PlaceholderAPI placeholder returns as text and no longer parse it as
MiniMessage. In `0.1` a player-set value such as a nickname could carry
`<click:run_command:'/pay Mallory 100000'>`, or the `<name>` of a supplied value, into a message. Now every tag in
placeholder output is shown as written, on `Text.render`, `Text.send`, `Text.plain` and on the template and the
prefix of `Messages.render(Text, ...)` and `Messages.renderTemplate`.

- Section-sign colour and format codes in the output still apply, to that output only. A colour a placeholder
  returns no longer colours the template after it: write the colour in the template.
- Each run between two `%` signs is given to PlaceholderAPI on its own, so a placeholder inside a tag argument
  that MiniMessage does not parse, such as a click value or an insertion, is no longer filled in and stays as
  written: `<click:run_command:'/msg %player_name%'>` runs `/msg %player_name%`. A placeholder inside hover text
  is still filled in.
- A placeholder written as an unquoted tag argument, such as `<color:%team_color%>`, or inside the URL of
  `<click:open_url:...>`, no longer forms the tag, which is then shown as text.
- `Text.resolve` is unchanged and returns what PlaceholderAPI gave, tags included.

**Opt-in:** where an expansion returns MiniMessage formatting on purpose, such as a rank prefix with a gradient,
render through `text.withPlaceholderFormatting()`. It returns a `Text` that parses colour tags, decoration tags,
`<gradient>`, `<rainbow>` and `<reset>` in placeholder output and shows every other tag as written:

```java
Text text = new Text(getLogger());
Text ownerText = text.withPlaceholderFormatting();
```

No option brings back click, hover or any other tag from placeholder output: write those in the template, around
the placeholder.

**Click values and tag arguments:** a template that put a placeholder inside a click value or a tag argument
builds that part in code and supplies it as a value, with `Text.resolve` where the value comes from PlaceholderAPI:

```java
String name = text.resolve("%player_name%", player);
text.render("<msg>Reply</msg>", player,
    Placeholder.styling("msg", ClickEvent.runCommand("/msg " + name)));
```

[Placeholder output](/docs/modules/platform#placeholder-output) has the details.

### A colour code ends the format codes before it

`LegacyText.toMiniMessage`, `LegacyText.sectionToMiniMessage` and every `Text` and `Messages` render follow a
legacy colour code with the negation of each decoration a format code before it opened, as legacy text does. In
`0.1` the decoration stayed open, so text written format first, such as `&l&6Title` or a prefix of `§l§6`, was
bold. Now the colour code ends the bold.

**Migration:** write the colour first, `&6&lTitle`, where the text is meant to keep its format.
[LegacyText](/docs/modules/platform#legacytext) describes the conversion.

### Webhook mentions ping no one

`DiscordWebhook.post(String, String, Consumer<String>)` sends `"allowed_mentions": {"parse": []}` with the content,
and `WebhookPayload.render` adds the same key to the top level of a template that has no `allowed_mentions` key of
its own or sets it to `null`. In `0.1` neither sent the key, so Discord's default applied and player text in a post, such as an item
renamed to `@everyone free nitro`, pinged the guild. Now `@everyone`, `@here`, role mentions and user mentions in
such a post are shown as text and ping no one. A template with an `allowed_mentions` key keeps its value
unchanged, and `DiscordWebhook.postBody` still sends its body as given and adds nothing.

**Opt-in:** where a post is meant to ping, name the mention types to allow:

```java
webhook.post(url, content, PostOptions.allowing(Mention.ROLES), onError);
```

For a payload template, give it its own `allowed_mentions` object, such as this one in the server owner's config:

```yaml title="config.yml"
payload:
  content: '<@&123456789012345678> {buyer} bought {item}'
  allowed_mentions:
    parse: [roles]
```

[Mentions](/docs/modules/platform#mentions) lists the mention types.

### DiscordWebhook.close waits at most 5 seconds

`DiscordWebhook.close()` waits at most 5 seconds for the posts still in flight and then aborts them, so each fails
through its callback. In `0.1` it had no upper bound, and a Discord that sent its response headers and then stalled
kept the disabling thread blocked.

**Migration:** call `close(Duration)` with a longer wait where a plugin must give its last posts more than 5
seconds:

```java
webhook.close(Duration.ofSeconds(15));
```

### WebhookPayload.render refuses unknown value types

`WebhookPayload.render` throws `IllegalArgumentException` for a template value that is not a `String`, `Number`,
`Boolean`, `null`, `Map`, `List` or Bukkit `ConfigurationSection`. The message names the value by its key path,
such as `embeds[0].timestamp`. In `0.1` such a value was handed to the JSON serializer, which wrote whatever its
reflection found.

**Migration:** turn the value into a `String`, `Number` or `Boolean` before the template is given to `render`.
[Discord](/docs/modules/platform#discord) lists how each type is rendered.

### SkullBuilder remembers a failed lookup

`SkullBuilder.fromName` and `SkullBuilder.fromUuid` remember a failed lookup for 2 minutes and reuse a resolved
texture for 60 minutes, and one `SkullBuilder` caches at most 1000 names and uuids.

- In `0.1` a failed lookup was not cached, so the next call for the same name or uuid looked it up again at once.
  Now a lookup that found no texture or threw is kept for 2 minutes from the moment it completed: calls in that
  time start no lookup and complete with a blank head, or exceptionally when the lookup threw an `Error`. A lookup
  the executor rejected is still not remembered.
- In `0.1` a resolved texture stayed for the life of the instance. Now it is looked up again once 60 minutes have
  passed since its lookup completed, and past 1000 entries the one whose lookup started longest ago is dropped.

**Migration:** a plugin that called `fromName` or `fromUuid` again right after a blank head to retry gets the same
blank head for 2 minutes. Show the blank head and ask again later, or use a new `SkullBuilder`, which starts with
an empty cache. [SkullBuilder](/docs/modules/platform#skullbuilder) has the full table.

### Scheduler.close completes unstarted dispatches

`Scheduler.close()` completes every future `Scheduler.dispatch` returned whose task has not started, as a refused
call does: with `RejectedExecutionException` for `ThreadTag.GLOBAL` and `ThreadTag.ASYNC`, and with
`EntityUnavailableException` for an entity tag, which covers `EntityThread.call` over a `Scheduler`. In `0.1` such
a future stayed incomplete for good when Paper accepted the task and dropped it as the plugin disabled, so a caller
waiting on it never returned. A task refused this way never runs, and a task that has started completes its future
with its own result. A dispatch Paper accepts as the plugin stops being enabled is refused the same way.

**Migration:** call `Scheduler.close()` in `onDisable`, handle the refusal where a dispatched future is awaited,
and drop an `orTimeout` that was there only for this case.
[Dispatcher, ThreadTag and EntityThread](/docs/modules/platform#dispatcher-threadtag-and-entitythread) describes
the refusals.

### Shutdown.closeQuietly logs the stack trace

`Shutdown.closeQuietly` logs a failed step with its stack trace. The warning reads
`Failed to <what> during shutdown` and carries the failure as the record's thrown. In `0.1` the failure's
`toString()` was appended to the message and no trace was logged.

**Migration:** a log filter or test that matched the failure text in the message matches
`Failed to <what> during shutdown` and reads the failure from `LogRecord.getThrown()`.
[Shutdown.closeQuietly](/docs/modules/platform#shutdownclosequietly) describes the step.

## 0.2.1

`0.2.1` needs no action from a plugin: change the version of the settings plugin and rebuild. Every signature of
`0.2.0` is still there and no call needs a change. What changes is what is sent and logged, listed below, and each
addition is unused until a plugin calls it.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.1"
}
```

The release changes what a plugin built with [taffy-metrics](/docs/modules/metrics) sends to FastStats and bStats,
so the plugin's error list and Taffy's usage graph read differently after the upgrade:

| Change | What is sent |
|---|---|
| [More of a message is hidden](/docs/modules/metrics#anonymizing) | The user name and password of a URI of any scheme, a UUID in upper case or without dashes, the quoted user and host of a MySQL or MariaDB account, the quoted name after `user` or `role` in a PostgreSQL message, the value of a key such as `password` or `token`, an absolute Unix path and a host name with a common ending are replaced by a placeholder. A jdbc URL with a user name before an `@` is redacted whole. |
| [The SQL rule needs the start of a statement](/docs/modules/metrics#anonymizing) | A message with the bare word `select`, `insert`, `update` or `delete`, such as `Failed to update balance for shop 12`, is sent as written, where it was cut to `Failed to [sql hidden]`. A statement of another shape, such as `SELECT 1`, is no longer hidden. |
| [Addresses and numbers no longer split a kind](/docs/modules/metrics#what-faststats-receives) | Reports whose messages differ only in an IPv4 address, an IPv6 address, a run of digits or a value the rules hide merge into one error with a count, sent with the message of the first report. Each took one of the 32 kinds of its source before. |
| [A task that throws under Scheduler is unhandled](/docs/modules/metrics#what-faststats-receives) | The error is sent with `handled` set to `false`, where it was sent as a handled error. It is sent once for its kind and source for the life of the handle, where a repeating task that threw on every run was one error with a count. |
| [One plugin per server reports the Taffy usage chart](/docs/modules/metrics#the-taffy-usage-chart) | On a server with several plugins built with Taffy `0.2.1` or newer, one of them starts the second FastStats context and the second bStats instance that report `taffy_version`. A plugin built with an older Taffy still starts its own. |

Two more changes are visible on the server and send nothing new:

- `Metrics.shutdown()` waits at most 5 seconds for the final FastStats send, which runs on a daemon thread named
  `taffy-metrics-final-send`. A chart supplier read during that send runs on that thread. A supplier already may
  run on any thread, as [the supplier contract](/docs/modules/metrics#the-supplier-contract) states.
- The first time a source of error reports holds 32 kinds, one warning that names the source is logged on the
  plugin's logger. Reports of a further kind were dropped with no log line.

Three additions are there for a plugin that wants them:

- `MetricsBuilder.usageChart(false)` leaves the Taffy usage chart off for that plugin alone, such as from a key of
  its own in the plugin's config. [Turning the chart off](/docs/modules/metrics#turning-the-chart-off) shows it.
- `ErrorReports.reportUnhandled` reports an error the plugin rethrows or lets escape, and FastStats receives it
  with `handled` set to `false`.
- `ErrorReports.install(handle, unhandled)` installs one handler for each of the two kinds of report. A plugin that
  installed a target of its own after `start()` with the one-handler `install` and passes every report to
  `Metrics.report` still receives each report, and a `Scheduler` failure it passes on is sent as a handled
  error, as in `0.2.0`. To send it as unhandled, install two handlers and pass the second one's reports to
  `Metrics.reportUnhandled`, as [The error sink has one target](/docs/modules/metrics#the-error-sink-has-one-target)
  shows.

## 0.2.2

`0.2.2` needs no action from a plugin: change the version of the settings plugin and rebuild. Every signature of
`0.2.1` is still there and no call needs a change. Every change is in [taffy-comficonf](/docs/modules/comficonf),
and each addition is unused until a plugin calls it.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.2"
}
```

A server owner who edits a plugin's settings through a `YamlFileProvider` sees one difference in the ComfiConf
editor:

| Change | What the owner sees |
|---|---|
| [Every waiting restart-only field is reported](/docs/modules/comficonf#restart-only-fields) | A save that changes only live fields is answered as saved with a restart required, with the paths that wait, for as long as a field declared `restartRequired()` differs from the value the file held when the provider was built. It was answered as applied, although a restart-only change of an earlier save, or of an edit of the file by hand, still waited. Once the file holds the startup values again, the answer is applied. A change of the save itself inside an object list is still reported as waiting even when its new value equals the startup value, as before. |

A plugin's own test that expects `applied` from a live-only apply after a restart-only change now receives
`savedRestartRequired` with the waiting paths.

Three more changes are visible on the server and none of them needs a change in the plugin:

- `ComfiConfRegistration.register` refuses a bridge whose `ComfiConfApi.apiVersion()` is lower than the
  `ComfiConfApi.API_VERSION` Taffy is compiled against. `ComfiConfConnection.connect` then gives `API_MISSING` and
  logs the one warning that asks the owner to update ComfiConf, with both versions in it. Such a bridge was noticed
  only when a call reached a class or method it lacks. [At enable](/docs/modules/comficonf#at-enable) lists the
  checks.
- `ComfiConfConnection.connect` reads the link's `resourceId()` once, and `ComfiConfConnection.resourceId()` returns
  that id. A `ComfiConfLink` of the plugin's own that throws from `resourceId()` is closed and gives `FAILED` with
  one warning and a report under `hook.comficonf`, where the error left `connect`. The link
  `ComfiConfRegistration.register` returns never throws there.
- `YamlFileProvider.read()`, the first read of `apply` and the read of `build` hold the lock
  `ComfiConfConnection.lockFor(file)` gives while a resource is registered, so none of them sees a file the plugin
  has written in part. A plugin that holds that lock around its own writes, as
  [Reloads and the plugin's own writes](/docs/modules/comficonf#reloads-and-the-plugins-own-writes) shows, changes
  nothing.

Two additions are there for a plugin that wants them:

- `YamlFileProvider.Builder.notLoadedMessage(String)` sets the message the editor shows when the file was saved and
  the plugin could not load it, so it can name the plugin's reload command.
  [The apply result](/docs/modules/comficonf#the-apply-result) shows it.
- `YamlFileProvider.Builder.backups(BackupPolicy)` sets the folder that receives the backups of the file and the
  number kept. Without it the 10 newest stay in the `backups` folder beside the file, as before. Each backup is a
  full copy of the file, secrets included, as [What the bridge calls](/docs/modules/comficonf#what-the-bridge-calls)
  states.

The release also documents a move that needs no new Taffy version: a plugin that still reads
`JavaPlugin.getConfig()` beside a `ConfigHolder` keeps old values after a reload and after a save in the editor.
[Moving a plugin off getConfig()](/docs/modules/config#moving-a-plugin-off-getconfig) describes the move and what
the server owner sees after it.

| [PromptRequest has a fifth component](#promptrequest-has-a-fifth-component) | a plugin with a record pattern over `PromptRequest`; every `new PromptRequest(question, initial, origin, answer)` still compiles | add a fifth component to the pattern |
| [Menus read their text through a TextSource](#menus-read-their-text-through-a-textsource) | a plugin that calls `Menus.Parts.messages()` or `MenuText.messages()` | call `MenuText.source()`, or keep the plugin's own `Messages` |
| [Answer has a third result](#answer-has-a-third-result) | a plugin with a `switch` over `Answer` that has no `default` branch | add a `default` branch, or a case for `Answer.Later` |
| [EconomyProvider.vault takes a folia flag](#economyprovidervault-takes-a-folia-flag) | a plugin that calls `EconomyProvider.vault`; the old call still compiles, with a deprecation warning | pass `scheduler.mode() == Scheduler.Mode.FOLIA` |

### Menus refuse a material that is not an item

`Menus.register` and `Menus.reload` throw `IllegalArgumentException` for a material that is not an item a slot
can show, air included: the material of an `ItemLayout` (shown or not), the `filler` of a `MenuLayout`, the
`emptyMaterial` of a `PagerLayout`, and, in `register`, the `filler` and `loadingItem` of the `MenuSettings`. The
message names the menu and the item. In `0.2` such a layout registered and every open of the menu failed with a
stack trace.

**Migration:** give each of these an item material. A plugin that reads layouts or settings from a file catches
the `IllegalArgumentException` of `register` and `reload` and shows its message to the owner, as
[Reload](/docs/modules/gui#reload) shows; a refused `reload` leaves the layouts as they were.

```java title="0.2"
// MenuLayouts.shop() holds ItemLayout.of("buy", List.of(13), Material.WALL_TORCH).action("buy")
menus.register(new ShopMenu(menus));   // registers, and every open of the shop menu fails
```

```java title="0.3.0"
// MenuLayouts.shop() holds ItemLayout.of("buy", List.of(13), Material.TORCH).action("buy")
try {
    menus.register(new ShopMenu(menus));
} catch (IllegalArgumentException e) {
    // "item buy of the shop menu has the material WALL_TORCH, which is not an item" for the layout of 0.2
    getLogger().warning("The shop menu is not registered: " + e.getMessage());
}
```

### Menu settings, layouts and parts are built through factories

`MenuSettings`, `ItemLayout`, `MenuLayout`, `PagerLayout` and `Menus.Parts` are final classes with no public
constructor and are no longer records, so a value a later release adds to one breaks no plugin. Each is built
through a static factory that takes what has no default, and a method named after each other value gives a copy
with that value replaced. The methods that read a value keep their names, the layouts and `MenuSettings` still
compare by value, and every check a constructor made is made by the factory or the method that takes the value.
`Menus.Parts` compares by identity, and a record pattern over one of the five no longer compiles.

**Migration:** replace each `new` with the factory, and add a method call for each value that differs from the
default.

| `0.2` | `0.3.0` | Defaults left out |
|---|---|---|
| `new MenuSettings(28, filler, debounce, loading)` | `MenuSettings.DEFAULTS.pageSize(28).filler(filler).clickDebounce(debounce).loadingItem(loading)` | the values of `MenuSettings.DEFAULTS` |
| `new ItemLayout(id, slots, material, action, permission, enabled, name, lore)` | `ItemLayout.of(id, slots, material).action(action).permission(permission).enabled(enabled).name(name).lore(lore)` | no action, permission, name or lore, and shown |
| `new PagerLayout(slots, emptySlot, emptyMaterial)` | `PagerLayout.of(slots).emptySlot(emptySlot).emptyMaterial(emptyMaterial)` | no empty state |
| `new MenuLayout(menu, rows, filler, pager, items, title)` | `MenuLayout.of(menu, rows).filler(filler).pager(pager).items(items.values()).title(title)` | no filler, list, items or title |
| `new Menus.Parts(layouts, settings, messages, locales, server, preview, tasks, entity, sounds, home, logger, errors)` | `Menus.Parts.of(plugin, messages, tasks, entity, errors).layouts(layouts).settings(settings).locales(locales).sounds(sounds).home(home)` | no layouts, `MenuSettings.DEFAULTS`, `Player::locale`, no sounds, no home menu, and the plugin's own server, logger and `new NamespacedKey(plugin, "preview")` |

```java title="0.2"
MenuSettings settings = new MenuSettings(28, Material.GRAY_STAINED_GLASS_PANE, Duration.ofMillis(400),
    Material.CLOCK);
PagerLayout list = new PagerLayout(List.of(10, 11, 12, 13, 14, 15, 16), 13, Material.PAPER);
ItemLayout close = new ItemLayout("close", List.of(26), Material.BARRIER, MenuKind.CLOSE, null, true, null, null);
```

```java title="0.3.0"
MenuSettings settings = MenuSettings.DEFAULTS.pageSize(28).clickDebounce(Duration.ofMillis(400));
PagerLayout list = PagerLayout.of(List.of(10, 11, 12, 13, 14, 15, 16)).emptySlot(13).emptyMaterial(Material.PAPER);
ItemLayout close = ItemLayout.of("close", List.of(26), Material.BARRIER).action(MenuKind.CLOSE);
```

`ItemLayout.of(id, slots, material)` and the `ItemLayout` methods that replace a value are there in `0.2` too, so
an item built through them needs no change. [Building a layout in code](/docs/modules/gui#building-a-layout-in-code)
and [Enable and disable](/docs/modules/gui#enable-and-disable) show each type in a plugin.

### MenuLayout takes its items as a collection

`MenuLayout.items(Collection<ItemLayout>)` takes the items themselves, in the order `MenuLayout.items()` keeps,
and keys each by its own id. In `0.2` the constructor took a map and refused a key that differed from its item's
id. Two items with one id are refused with an `IllegalArgumentException` such as "item buy is in the shop menu
twice". `MenuLayout.item(ItemLayout)` adds one item, or replaces the item of the same id in its place.
`MenuLayout.items()` still returns the map.

**Migration:** pass `map.values()` where the plugin built a map, or build a list.

```java title="0.2"
Map<String, ItemLayout> items = new LinkedHashMap<>();
items.put("back", ItemLayout.of("back", List.of(45), Material.ARROW).action(MenuKind.BACK));
items.put("close", ItemLayout.of("close", List.of(53), Material.BARRIER).action(MenuKind.CLOSE));
MenuLayout layout = new MenuLayout("warps", 6, Material.BLACK_STAINED_GLASS_PANE, list, items, null);
```

```java title="0.3.0"
MenuLayout layout = MenuLayout.of("warps", 6)
    .filler(Material.BLACK_STAINED_GLASS_PANE)
    .pager(list)
    .items(List.of(
        ItemLayout.of("back", List.of(45), Material.ARROW).action(MenuKind.BACK),
        ItemLayout.of("close", List.of(53), Material.BARRIER).action(MenuKind.CLOSE)));
```

### Menus and Prompts register their own listeners

`Menus.Parts.of` takes the owning `Plugin` first. `new Menus(parts)` registers the menu listener with the plugin
manager of `Parts.server()` as a listener of that plugin, and `new Prompts(menus, ...)` registers the prompt
listener the same way before it links to the menus. In `0.2` the plugin registered `menus.listener()` and
`prompts.listener()` itself, and a plugin that forgot the call opened menus whose icons players could take.

The server, the logger and the preview key are no longer required: they default to `plugin.getServer()`,
`plugin.getLogger()` and `new NamespacedKey(plugin, "preview")`, and `Parts.server(Server)`,
`Parts.logger(Logger)` and `Parts.preview(NamespacedKey)` replace them. The server refuses a listener of a plugin
that is not enabled with an `IllegalPluginAccessException`, so the menus are built while the plugin is enabled,
such as in `onEnable`.

**Migration:** pass the plugin to `Menus.Parts.of`, add `.preview(key)` when the plugin's preview key is not
`new NamespacedKey(plugin, "preview")`, and delete both `registerEvents` calls.

```java title="0.2"
menus = new Menus(new Menus.Parts(layouts, MenuSettings.DEFAULTS, messages, Player::locale, getServer(),
    new NamespacedKey(this, "preview"), scheduler::entity, EntityThread.on(scheduler, getServer()),
    () -> sounds, null, getLogger(), errors));
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
getServer().getPluginManager().registerEvents(menus.listener(), this);
getServer().getPluginManager().registerEvents(prompts.listener(), this);
```

```java title="0.3.0"
menus = new Menus(Menus.Parts.of(this, messages, scheduler::entity, EntityThread.on(scheduler, getServer()), errors)
    .layouts(layouts)
    .sounds(() -> sounds));
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
```

### Menus.listener() and Prompts.listener() register nothing

`Menus.listener()` and `Prompts.listener()` are deprecated and a later release removes them. Each returns a
listener with no event handler, so a `registerEvents` call left in a plugin registers nothing and cannot register
the menus or the prompts twice. In `0.2` each returned the listener that guards the menus or takes the prompt
answers, for the plugin to register.

**Migration:** delete the calls that pass them to `registerEvents`. `new Menus(parts)` and
`new Prompts(menus, ...)` have registered both listeners by then.

```java title="0.2"
Prompts prompts = new Prompts(menus, PromptMode.CHAT, BedrockPlayers.NONE, scheduler::delayedAsync);
getServer().getPluginManager().registerEvents(menus.listener(), this);
getServer().getPluginManager().registerEvents(prompts.listener(), this);
```

```java title="0.3.0"
Prompts prompts = new Prompts(menus, PromptMode.CHAT, BedrockPlayers.NONE, scheduler::delayedAsync);
```

### Menus and Prompts check the calling thread

`Menus.open`, `Menus.rerender`, `Menus.load` and `Prompts.ask` throw `IllegalStateException` on a thread that
does not own the viewer, before they change anything. The message names the method and what to call instead,
such as "Menus.open must run on the viewer's entity thread; use Menus.openLater". In `0.2` the call went on off
the viewer's thread, where it changed the session and the inventory unguarded on Paper and failed part way inside
the server on Folia. `rerender` still does nothing for a closed session, and `open` and `ask` still do nothing
once `Menus.shutdown` ran.

**Migration:** from a callback on another thread, such as `thenRun` of a storage future, call
`Menus.openLater`, `Menus.rerenderLater` or `Prompts.askLater`, which schedule the work on the viewer's entity
thread. Call `Menus.load` from `Menu.opened` or a click handler, or hop to the viewer's thread first through
`EntityThread.call`.

```java title="0.2"
storage.save(warp).thenRun(() -> menus.rerender(session));
storage.find(name).thenAccept(warp -> menus.open(player, new Route("warp", warp, null)));
storage.count(owner).thenRun(() -> prompts.ask(player, request));
```

```java title="0.3.0"
storage.save(warp).thenRun(() -> menus.rerenderLater(session));
storage.find(name).thenAccept(warp -> menus.openLater(player, new Route("warp", warp, null)));
storage.count(owner).thenRun(() -> prompts.askLater(player, request));
```

### A click just after a redraw is dropped

A click on a menu slot is dropped for the click debounce window (250 ms by default) after a redraw put another
button in that slot, as a click within that window of the menu opening already is. In `0.2` a click that arrived
just after `Menus.rerender` or a load redrew the menu ran the handler of whatever the slot showed by then, so a
viewer aiming at one listing bought the one that had moved into its slot. Another button is a list row with
another `Frame.Entry.key`, for a row with no key a row with another icon, a button of another layout item, or any
button in a slot that had none. A layout action that redraws with other text keeps taking clicks.

`Frame.Entry` has `key` as a fifth record component. `Entry.click`, `Entry.display` and the four-argument
constructor still compile and give a row with no key; a record pattern over `Frame.Entry` needs a fifth
component.

**Migration:** give each clickable row a key that stays the same while the row shows the same thing, as in
`Frame.Entry.click(icon, handler).key(listing.id().toString())`. A row with no key whose icon changes on every
redraw, such as an animated one, otherwise drops the clicks of the window after each redraw.
[Frame](/docs/modules/gui#frame) shows a keyed list.

```java title="0.2"
Frame.Entry row = Frame.Entry.click(icon(listing), click -> buy(click, listing));
if (row instanceof Frame.Entry(var icon, var handler, var clicks, var exclusive)) {
    // ...
}
```

```java title="0.3.0"
Frame.Entry row = Frame.Entry.click(icon(listing), click -> buy(click, listing)).key(listing.id().toString());
if (row instanceof Frame.Entry(var icon, var handler, var clicks, var exclusive, var key)) {
    // ...
}
```

### A load releases only its own hold

A load clears `MenuSession.busy()` only for the hold that belongs to it: the exclusive button whose handler
started the load, or a `busy(true)` taken in the same handler or `Menu.opened` as the `Menus.load` call. It
clears that hold when it applies, fails or is cancelled, also when a later load started meanwhile. In `0.2` the
end of the latest load of a session released every hold, so a refresh or a page turn that ended while a claim
held the session with `busy(true)` let the same claim run a second time. A handler that throws likewise clears
`busy()` only when the session was not busy before it ran. A handler that calls `busy(true)` and then
`Menus.load` needs no change.

**Migration:** a handler that takes `busy(true)` for work outside `Menus.load`, and relied on a later load or a
failing handler to release it, calls `session.busy(false)` on the viewer's entity thread when its work ends, on
success and on failure. [Exclusive buttons](/docs/modules/gui#exclusive-buttons) shows such a handler.

```java title="0.2"
frame.action("claim", Frame.Spec.click(click -> {
    session.busy(true);
    stash.claim(click.player(), card, () -> menus.load(session, stash.cards(owner), (s, cards) -> s.data(cards)));
}).exclusively());
```

```java title="0.3.0"
frame.action("claim", Frame.Spec.click(click -> {
    session.busy(true);
    stash.claim(click.player(), card, () -> {
        session.busy(false);
        menus.load(session, stash.cards(owner), (s, cards) -> s.data(cards));
    });
}).exclusively());
```

### PromptRequest has a fifth component

`PromptRequest` has `abandoned` as a fifth record component: a `Consumer<PromptEnd>` that runs once when an ask
ended and the prompts opened no menu for it, as
[When an ask opens no menu](/docs/modules/gui#when-an-ask-opens-no-menu) describes. Every
`new PromptRequest(question, initial, origin, answer)` compiles and behaves as in `0.2`, with a step that does
nothing, and `request.abandoned(step)` gives a copy with a step. `PromptEnd` and `PromptMode` may gain constants
in a later release.

**Migration:** a record pattern over `PromptRequest` takes a fifth component, as in
`PromptRequest(var question, var initial, var origin, var answer, var abandoned)`, and a `switch` over
`PromptMode` keeps a `default` branch. A menu that hands something to an ask, such as escrowed items, releases it
in the `abandoned` step.

```java title="0.2"
if (request instanceof PromptRequest(var question, var initial, var origin, var answer)) {
    // ...
}
```

```java title="0.3.0"
if (request instanceof PromptRequest(var question, var initial, var origin, var answer, var abandoned)) {
    // ...
}
```

### Menus read their text through a TextSource

The menus and prompts hold a [`TextSource`](/docs/modules/gui#text-source), a function from a locale, a lang key
and its placeholders to a `Component`, and no longer the `Messages`. `Menus.Parts.of` still takes the plugin's
`Messages` and reads them as before, so a plugin that passes them changes nothing there. `Menus.Parts.messages()`
and `MenuText.messages()` are gone; `Menus.Parts.text()` and `MenuText.source()` give the `TextSource`, whose
`render`, `has` and `lines` take the same arguments as those of `Messages`.

**Migration:** call `menus.text().source().render(locale, key)` where a menu called
`menus.text().messages().render(locale, key)`, and keep the plugin's own `Messages` field for anything else it
read from them.

```java title="0.2"
Component note = menus.text().messages().render(locale, "gui.shop.note");
```

```java title="0.3.0"
Component note = menus.text().source().render(locale, "gui.shop.note");
```

### Answer has a third result

`Answer.Later(CompletableFuture<Answer>)` is a third result of a `PromptRequest` answer function, as
[Text prompts](/docs/modules/gui#text-prompts) describes. `Answer` is sealed, so a `switch` over it that names
`Accept` and `Retry` and has no `default` branch no longer compiles. An answer function that returns an `Accept`
or a `Retry` needs no change.

**Migration:** give the `switch` a `default` branch, which also covers a result a later release adds, or a case
for `Answer.Later`.

```java title="0.2"
String outcome = switch (answer) {
    case Answer.Accept accept -> "accepted";
    case Answer.Retry retry -> "refused";
};
```

```java title="0.3.0"
String outcome = switch (answer) {
    case Answer.Accept accept -> "accepted";
    case Answer.Retry retry -> "refused";
    default -> "pending";
};
```

### EconomyProvider.vault takes a folia flag

`EconomyProvider.vault(Plugin, ErrorReports, boolean switchedOn, boolean folia, Integer scale)` takes the server
kind as a flag, `true` on Folia, so a plugin with no Taffy `Scheduler` can look the economy up. The overload that
takes a `Scheduler.Mode` still works, gives the same result and is deprecated; a later release removes it.

**Migration:** pass `scheduler.mode() == Scheduler.Mode.FOLIA` in place of `scheduler.mode()`.

```java title="0.2"
Detected<EconomyProvider> economy = EconomyProvider.vault(this, errors, true, scheduler.mode(), null);
```

```java title="0.3.0"
Detected<EconomyProvider> economy =
    EconomyProvider.vault(this, errors, true, scheduler.mode() == Scheduler.Mode.FOLIA, null);
```

## 0.3.1

`0.3.1` needs no change to a call: change the version of the settings plugin and rebuild. Every signature of
`0.3.0` is still there. Every change but one is in
[taffy-hooks](/docs/modules/hooks), and each addition is unused until a plugin calls it. One case needs a look: a
plugin that waits for `CustomItems.ready()` on a server whose Nexo, Oraxen or HeadDatabase holds nothing, described
under the table.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.3.1"
}
```

A plugin that uses `CustomItems`, `Detected` or `RegionProvider` reads four things differently after the upgrade:

| Change | What the plugin reads |
|---|---|
| [Nexo, Oraxen and HeadDatabase have a loading state](/docs/modules/hooks#per-plugin) | Each of the three is `LOADING` in `statuses()` and makes `ready()` `false` until it has loaded its items, where it read `ON` and `ready()` read `true` during the load. `create` returns `null` for their ids during the load, as before. `resolve` and `idOrNull` read Nexo and Oraxen ids during the load, as before. |
| [A reference whose hint names no plugin is offered to each plugin](/docs/modules/hooks#ids-and-references) | `create("gems:ruby")` builds the ItemsAdder item `gems:ruby`, where it returned `null` without asking any plugin. A reference that starts with a plugin's key or alias goes only to that plugin, as before. |
| [A replaced plugin instance has a reason](/docs/modules/hooks#detected) | The `NOT_ENABLED` status of an integration whose plugin was loaded again as a new instance carries a reason for the owner, where it had none. The state and the provider are unchanged. |
| [WorldGuard without WorldEdit is not visible](/docs/modules/hooks#regions) | `RegionProvider.worldGuard` gives `NOT_VISIBLE` with a reason that names the missing `WorldEdit` entry and reports nothing, where it gave `FAILED` with a report under `hook.worldguard`. The integration was off in both versions, and a plugin that lists `WorldEdit` beside `WorldGuard` under `dependencies.server` reads `ON`. |

The Nexo, Oraxen and HeadDatabase integrations each register a listener for the plugin, as the ItemsAdder one
already did, so `CustomItems.detect` still runs while the plugin is enabled, normally in `onEnable`.

A Nexo or Oraxen that loaded with no item at all, and a HeadDatabase whose database holds no head, give `detect`
nothing to tell a finished load from one still running. When `detect` runs after their load, and no earlier `detect`
of the plugin heard that load end in this server run, the integration reads `LOADING` and `ready()` reads `false`
until their next items-loaded event, where `0.3.0` read `ON` and `true`. A plugin that waits for `ready()` before it
builds bounds the wait, and builds what it can once the wait ends.
[Per plugin](/docs/modules/hooks#per-plugin) describes each of the three.

Three additions let a plugin deliver custom items it could only guess at before:

- **Wait for item plugins to load.** `ready()` is `true` only once ItemsAdder, Nexo, Oraxen and HeadDatabase have
  each loaded their items, so a plugin that builds its menus or rewards once `ready()` is `true` no longer builds
  them while one of the four knows no item. [Per plugin](/docs/modules/hooks#per-plugin) names the event that ends
  each load.
- **Read why an item did not build.** `CustomItems.build(String reference)` returns the item or a `Built.Reason`:
  `UNKNOWN_PLUGIN`, `PLUGIN_OFF`, `NOT_READY`, `UNKNOWN_ID` or `FAILED`. `create` still returns `null` for each of
  them. [Why no item was built](/docs/modules/hooks#why-no-item-was-built) lists the reasons.
- **Close `CustomItems` on reload.** `CustomItems.close()` unregisters every listener `detect` registered, so a
  reload command that detects again calls it first on the `CustomItems` it holds, as
  [Detecting again](/docs/modules/hooks#detecting-again) shows. A plugin that detects once needs no `close()`.

One addition is in [taffy-platform](/docs/modules/platform#itembuilder):
`ItemBuilder.deserializeOrThrow(String reference)` rebuilds the item of a `serialized:<base64>` reference or throws
`IllegalArgumentException` with the cause, so a plugin that stores items can log why a stored item is gone.
`ItemBuilder.deserialize` still returns `null` for every failure.
