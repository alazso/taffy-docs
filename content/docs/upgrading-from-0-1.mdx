This page lists every change since `0.1.0` that needs an action from a plugin, release by release. Each section
says what changed, who it affects and what to do. No patch of `0.1` (`0.1.1`, `0.1.2`) needs an action: the one
entry `0.1.1` lists under Changed is about how Taffy is released, in a build job that holds no credentials. The
[changelog](/docs/versioning#reading-the-changelog) holds every other change, and each later release adds its own
part to this page.

## 0.2.0

Change the version of the settings plugin, and the rest of Taffy follows, as
[One version for plugins, catalog and modules](/docs/versioning#one-version-for-plugins-catalog-and-modules)
describes:

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.0"
}
```

| Change | Affects | Action |
|---|---|---|
| [Paper 26.2 build 135 and paper-api 26.3](#paper-262-build-135-and-paper-api-263) | every plugin | run on a supported server and recompile |
| [Filtered repositories](#filtered-repositories) | a build that took another group from a Taffy repository, or uses `mavenLocal()` for Taffy | declare the repository, or point `alazsoSnapshots` at the local repository |
| [PlaceholderAPI output is inserted as text](#placeholderapi-output-is-inserted-as-text) | a plugin that renders placeholders whose output holds MiniMessage tags, or a template with a placeholder inside a click value or a tag argument | render through `text.withPlaceholderFormatting()`; supply a click or a colour as a `Placeholder.styling` value |
| [A colour code ends the format codes before it](#a-colour-code-ends-the-format-codes-before-it) | a config or language file with a format code written before a colour code | write the colour first |
| [Webhook mentions ping no one](#webhook-mentions-ping-no-one) | a post or payload that is meant to ping | pass `PostOptions`, or give the template `allowed_mentions` |
| [DiscordWebhook.close waits at most 5 seconds](#discordwebhookclose-waits-at-most-5-seconds) | a plugin whose last posts need longer | call `close(Duration)` |
| [WebhookPayload.render refuses unknown value types](#webhookpayloadrender-refuses-unknown-value-types) | a template holding another type of value | convert the value first |
| [SkullBuilder remembers a failed lookup](#skullbuilder-remembers-a-failed-lookup) | a plugin that retries right after a blank head | ask again later |
| [Scheduler.close completes unstarted dispatches](#schedulerclose-completes-unstarted-dispatches) | a plugin that awaits a `dispatch` future | handle the refusal |
| [Shutdown.closeQuietly logs the stack trace](#shutdownclosequietly-logs-the-stack-trace) | a log filter or test that matched the failure text | read the failure from the record's thrown |

### Paper 26.2 build 135 and paper-api 26.3

Taffy compiles against `paper-api` `26.3.build.256-stable` and supports Paper 26.2 build 135 or newer and Folia
26.3 build 8 or newer. Paper 26.1.2 is no longer supported. The `paper` version of the `alaz` catalog moves from
`26.1.2.build.66-stable` to `26.3.build.256-stable`, so a plugin that declares `alaz.paper.api` compiles against
that build, which brings Adventure 5.2.0 in place of 4.26.1. [Servers](/docs/versioning#servers) lists the builds
for each release line.

**Migration:** run the plugin on Paper 26.2 build 135 or newer, or Folia 26.3 build 8 or newer, and recompile it
against `paper-api` 26.3. Adventure 5 makes `ClickEvent` generic, so a raw `ClickEvent` compiles with a rawtypes
warning until it is written `ClickEvent<?>`. Inside `taffy-gui` the package-private `CancelLink.link` returns
`ClickEvent<?>` for the same reason: its erasure is the same and no public signature changes.

`compileJava` accepts a call that exists in `paper-api` 26.3 and not on Paper 26.2. The new
[`compileAgainstPaperFloor`](/docs/gradle-plugins#compiling-against-the-oldest-supported-paper) task compiles the
plugin against `paper-api` `26.2.build.135-stable` and fails on such a call. No task depends on it, so add it to
`check` to run it with every build:

```kotlin title="build.gradle.kts"
tasks.check {
    dependsOn("compileAgainstPaperFloor")
}
```

### Filtered repositories

`so.alaz.taffy.repositories` asks each repository it declares, Maven Central apart, only for the groups the `alaz`
catalog takes from it, and `jitpack` moves to the end of the list. In `0.1` only the two `repo.alaz.so`
repositories and the three hologram repositories had a filter, so a module an earlier repository lacked was looked
up on every other host. Every entry of the `alaz` catalog resolves to the same modules as before, and
[so.alaz.taffy.repositories](/docs/gradle-plugins#soalaztaffyrepositories) lists the groups of each repository.

**Migration:** a build that took a module of another group from one of these repositories fails with
`Could not find` for that module. Declare the repository in `settings.gradle.kts`:

```kotlin title="settings.gradle.kts"
dependencyResolutionManagement {
    repositories {
        maven("https://repo.example.org/releases") { name = "example" }
    }
}
```

The `so.alaz` group and its subgroups resolve from `alazso` and `alazsoSnapshots` and from no other repository,
Maven Central and a repository the build adds included. A `mavenLocal()` in
`dependencyResolutionManagement.repositories` is therefore no longer asked for a locally published Taffy.

**Migration:** a build that added `mavenLocal()` there to use a locally published Taffy sets the URL of
`alazsoSnapshots` to the local repository instead, as
[Build against a snapshot or a local publish](/docs/getting-started#build-against-a-snapshot-or-a-local-publish)
shows in full:

```kotlin title="settings.gradle.kts"
dependencyResolutionManagement {
    repositories.named<MavenArtifactRepository>("alazsoSnapshots") {
        url = uri(File(System.getProperty("user.home"), ".m2/repository"))
    }
}
```

### PlaceholderAPI output is inserted as text

`Text` and `Messages` insert what a PlaceholderAPI placeholder returns as text and no longer parse it as
MiniMessage. In `0.1` a player-set value such as a nickname could carry
`<click:run_command:'/pay Mallory 100000'>`, or the `<name>` of a supplied value, into a message. Now every tag in
placeholder output is shown as written, on `Text.render`, `Text.send`, `Text.plain` and on the template and the
prefix of `Messages.render(Text, ...)` and `Messages.renderTemplate`.

- Section-sign colour and format codes in the output still apply, to that output only. A colour a placeholder
  returns no longer colours the template after it: write the colour in the template.
- Each run between two `%` signs is given to PlaceholderAPI on its own, so a placeholder inside a tag argument
  that MiniMessage does not parse, such as a click value or an insertion, is no longer filled in and stays as
  written: `<click:run_command:'/msg %player_name%'>` runs `/msg %player_name%`. A placeholder inside hover text
  is still filled in.
- A placeholder written as an unquoted tag argument, such as `<color:%team_color%>`, or inside the URL of
  `<click:open_url:...>`, no longer forms the tag, which is then shown as text.
- Tag names that start with `taffy_papi_` are reserved for the render.
- `Text.resolve` is unchanged and returns what PlaceholderAPI gave, tags included.

**Opt-in:** where an expansion returns MiniMessage formatting on purpose, such as a rank prefix with a gradient,
render through `text.withPlaceholderFormatting()`. It returns a `Text` that parses colour tags, decoration tags,
`<gradient>`, `<rainbow>` and `<reset>` in placeholder output and shows every other tag as written:

```java
Text text = new Text(getLogger());
Text ownerText = text.withPlaceholderFormatting();
```

No option brings back click, hover or any other tag from placeholder output: write those in the template, around
the placeholder.

**Click values and tag arguments:** a template that put a placeholder inside a click value or a tag argument
builds that part in code and supplies it as a value, with `Text.resolve` where the value comes from PlaceholderAPI:

```java
String name = text.resolve("%player_name%", player);
text.render("<msg>Reply</msg>", player,
    Placeholder.styling("msg", ClickEvent.runCommand("/msg " + name)));
```

[Placeholder output](/docs/modules/platform#placeholder-output) has the details.

### A colour code ends the format codes before it

`LegacyText.toMiniMessage`, `LegacyText.sectionToMiniMessage` and every `Text` and `Messages` render follow a
legacy colour code with the negation of each decoration a format code before it opened, as legacy text does. In
`0.1` the decoration stayed open, so text written format first, such as `&l&6Title` or a prefix of `§l§6`, was
bold. Now the colour code ends the bold.

**Migration:** write the colour first, `&6&lTitle`, where the text is meant to keep its format.
[LegacyText](/docs/modules/platform#legacytext) describes the conversion.

### Webhook mentions ping no one

`DiscordWebhook.post(String, String, Consumer<String>)` sends `"allowed_mentions": {"parse": []}` with the content,
and `WebhookPayload.render` adds the same key to the top level of a template that has no `allowed_mentions` key of
its own or sets it to `null`. In `0.1` neither sent the key, so Discord's default applied and player text in a post, such as an item
renamed to `@everyone free nitro`, pinged the guild. Now `@everyone`, `@here`, role mentions and user mentions in
such a post are shown as text and ping no one. A template with an `allowed_mentions` key keeps its value
unchanged, and `DiscordWebhook.postBody` still sends its body as given and adds nothing.

**Opt-in:** where a post is meant to ping, name the mention types to allow:

```java
webhook.post(url, content, PostOptions.allowing(Mention.ROLES), onError);
```

For a payload template, give it its own `allowed_mentions` object, such as this one in the server owner's config:

```yaml title="config.yml"
payload:
  content: '<@&123456789012345678> {buyer} bought {item}'
  allowed_mentions:
    parse: [roles]
```

[Mentions](/docs/modules/platform#mentions) lists the mention types.

### DiscordWebhook.close waits at most 5 seconds

`DiscordWebhook.close()` waits at most 5 seconds for the posts still in flight and then aborts them, so each fails
through its callback. In `0.1` it had no upper bound, and a Discord that sent its response headers and then stalled
kept the disabling thread blocked.

**Migration:** call `close(Duration)` with a longer wait where a plugin must give its last posts more than 5
seconds:

```java
webhook.close(Duration.ofSeconds(15));
```

### WebhookPayload.render refuses unknown value types

`WebhookPayload.render` throws `IllegalArgumentException` for a template value that is not a `String`, `Number`,
`Boolean`, `null`, `Map`, `List` or Bukkit `ConfigurationSection`. The message names the value by its key path,
such as `embeds[0].timestamp`. It throws the same way for a `Double` or `Float` that is `NaN` or infinite. In
`0.1` such a value was handed to the JSON serializer, which wrote whatever its reflection found.

**Migration:** turn the value into a `String`, `Number` or `Boolean` before the template is given to `render`,
and a `NaN` or infinite number into a finite one or a `String`.
[Discord](/docs/modules/platform#discord) lists how each type is rendered.

### SkullBuilder remembers a failed lookup

`SkullBuilder.fromName` and `SkullBuilder.fromUuid` remember a failed lookup for 2 minutes and reuse a resolved
texture for 60 minutes, and one `SkullBuilder` caches at most 1000 names and uuids.

- In `0.1` a failed lookup was not cached, so the next call for the same name or uuid looked it up again at once.
  Now a lookup that found no texture or threw is kept for 2 minutes from the moment it completed: calls in that
  time start no lookup and complete with a blank head, or exceptionally when the lookup threw an `Error`. A lookup
  the executor rejected is still not remembered.
- In `0.1` a resolved texture stayed for the life of the instance. Now it is looked up again once 60 minutes have
  passed since its lookup completed, and past 1000 entries the one whose lookup started longest ago is dropped.

**Migration:** a plugin that called `fromName` or `fromUuid` again right after a blank head to retry gets the same
blank head for 2 minutes. Show the blank head and ask again later, or use a new `SkullBuilder`, which starts with
an empty cache. [SkullBuilder](/docs/modules/platform#skullbuilder) has the full table.

### Scheduler.close completes unstarted dispatches

`Scheduler.close()` completes every future `Scheduler.dispatch` returned whose task has not started, as a refused
call does: with `RejectedExecutionException` for `ThreadTag.GLOBAL` and `ThreadTag.ASYNC`, and with
`EntityUnavailableException` for an entity tag, which covers `EntityThread.call` over a `Scheduler`. In `0.1` such
a future stayed incomplete for good when Paper accepted the task and dropped it as the plugin disabled, so a caller
waiting on it never returned. A task refused this way never runs, and a task that has started completes its future
with its own result. A dispatch Paper accepts as the plugin stops being enabled is refused the same way.

**Migration:** call `Scheduler.close()` in `onDisable`, handle the refusal where a dispatched future is awaited,
and drop an `orTimeout` that was there only for this case.
[Dispatcher, ThreadTag and EntityThread](/docs/modules/platform#dispatcher-threadtag-and-entitythread) describes
the refusals.

### Shutdown.closeQuietly logs the stack trace

`Shutdown.closeQuietly` logs a failed step with its stack trace. The warning reads
`Failed to <what> during shutdown` and carries the failure as the record's thrown. In `0.1` the failure's
`toString()` was appended to the message and no trace was logged.

**Migration:** a log filter or test that matched the failure text in the message matches
`Failed to <what> during shutdown` and reads the failure from `LogRecord.getThrown()`.
[Shutdown.closeQuietly](/docs/modules/platform#shutdownclosequietly) describes the step.

## 0.2.1

`0.2.1` needs no action from a plugin: change the version of the settings plugin and rebuild. Every signature of
`0.2.0` is still there and no call needs a change. What changes is what is sent and logged, listed below, and each
addition is unused until a plugin calls it.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.1"
}
```

The release changes what a plugin built with [taffy-metrics](/docs/modules/metrics) sends to FastStats and bStats,
so the plugin's error list and Taffy's usage graph read differently after the upgrade:

| Change | What is sent |
|---|---|
| [More of a message is hidden](/docs/modules/metrics#anonymizing) | The user name and password of a URI of any scheme, a UUID in upper case or without dashes, the quoted user and host of a MySQL or MariaDB account, the quoted name after `user` or `role` in a PostgreSQL message, the value of a key such as `password` or `token`, an absolute Unix path and a host name with a common ending are replaced by a placeholder. A jdbc URL with a user name before an `@` is redacted whole. |
| [The SQL rule needs the start of a statement](/docs/modules/metrics#anonymizing) | A message with the bare word `select`, `insert`, `update` or `delete`, such as `Failed to update balance for shop 12`, is sent as written, where it was cut to `Failed to [sql hidden]`. A statement of another shape, such as `SELECT 1`, is no longer hidden. |
| [Addresses and numbers no longer split a kind](/docs/modules/metrics#what-faststats-receives) | Reports whose messages differ only in an IPv4 address, an IPv6 address, a run of digits or a value the rules hide merge into one error with a count, sent with the message of the first report. Each took one of the 32 kinds of its source before. |
| [A task that throws under Scheduler is unhandled](/docs/modules/metrics#what-faststats-receives) | The error is sent with `handled` set to `false`, where it was sent as a handled error. It is sent once for its kind and source for the life of the handle, where a repeating task that threw on every run was one error with a count. |
| [One plugin per server reports the Taffy usage chart](/docs/modules/metrics#the-taffy-usage-chart) | On a server with several plugins built with Taffy `0.2.1` or newer, one of them starts the second FastStats context and the second bStats instance that report `taffy_version`. A plugin built with an older Taffy still starts its own. |

Two more changes are visible on the server and send nothing new:

- `Metrics.shutdown()` waits at most 5 seconds for the final FastStats send, which runs on a daemon thread named
  `taffy-metrics-final-send`. A chart supplier read during that send runs on that thread. A supplier already may
  run on any thread, as [the supplier contract](/docs/modules/metrics#the-supplier-contract) states.
- The first time a source of error reports holds 32 kinds, one warning that names the source is logged on the
  plugin's logger. Reports of a further kind were dropped with no log line.

Three additions are there for a plugin that wants them:

- `MetricsBuilder.usageChart(false)` leaves the Taffy usage chart off for that plugin alone, such as from a key of
  its own in the plugin's config. [Turning the chart off](/docs/modules/metrics#turning-the-chart-off) shows it.
- `ErrorReports.reportUnhandled` reports an error the plugin rethrows or lets escape, and FastStats receives it
  with `handled` set to `false`.
- `ErrorReports.install(handle, unhandled)` installs one handler for each of the two kinds of report. A plugin that
  installed a target of its own after `start()` with the one-handler `install` and passes every report to
  `Metrics.report` still receives each report, and a `Scheduler` failure it passes on is sent as a handled
  error, as in `0.2.0`. To send it as unhandled, install two handlers and pass the second one's reports to
  `Metrics.reportUnhandled`, as [The error sink has one target](/docs/modules/metrics#the-error-sink-has-one-target)
  shows.

## 0.2.2

`0.2.2` needs no action from a plugin: change the version of the settings plugin and rebuild. Every signature of
`0.2.1` is still there and no call needs a change. Every change is in [taffy-comficonf](/docs/modules/comficonf),
and each addition is unused until a plugin calls it.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.2.2"
}
```

A server owner who edits a plugin's settings through a `YamlFileProvider` sees one difference in the ComfiConf
editor:

| Change | What the owner sees |
|---|---|
| [Every waiting restart-only field is reported](/docs/modules/comficonf#restart-only-fields) | A save that changes only live fields is answered as saved with a restart required, with the paths that wait, for as long as a field declared `restartRequired()` differs from the value the file held when the provider was built. It was answered as applied, although a restart-only change of an earlier save, or of an edit of the file by hand, still waited. Once the file holds the startup values again, the answer is applied. A change of the save itself inside an object list is still reported as waiting even when its new value equals the startup value, as before. |

A plugin's own test that expects `applied` from a live-only apply after a restart-only change now receives
`savedRestartRequired` with the waiting paths.

Three more changes are visible on the server and none of them needs a change in the plugin:

- `ComfiConfRegistration.register` refuses a bridge whose `ComfiConfApi.apiVersion()` is lower than the
  `ComfiConfApi.API_VERSION` Taffy is compiled against. `ComfiConfConnection.connect` then gives `API_MISSING` and
  logs the one warning that asks the owner to update ComfiConf, with both versions in it. Such a bridge was noticed
  only when a call reached a class or method it lacks. [At enable](/docs/modules/comficonf#at-enable) lists the
  checks.
- `ComfiConfConnection.connect` reads the link's `resourceId()` once, and `ComfiConfConnection.resourceId()` returns
  that id. A `ComfiConfLink` of the plugin's own that throws from `resourceId()` is closed and gives `FAILED` with
  one warning and a report under `hook.comficonf`, where the error left `connect`. The link
  `ComfiConfRegistration.register` returns never throws there.
- `YamlFileProvider.read()`, the first read of `apply` and the read of `build` hold the lock
  `ComfiConfConnection.lockFor(file)` gives while a resource is registered, so none of them sees a file the plugin
  has written in part. A plugin that holds that lock around its own writes, as
  [Reloads and the plugin's own writes](/docs/modules/comficonf#reloads-and-the-plugins-own-writes) shows, changes
  nothing.

Two additions are there for a plugin that wants them:

- `YamlFileProvider.Builder.notLoadedMessage(String)` sets the message the editor shows when the file was saved and
  the plugin could not load it, so it can name the plugin's reload command.
  [The apply result](/docs/modules/comficonf#the-apply-result) shows it.
- `YamlFileProvider.Builder.backups(BackupPolicy)` sets the folder that receives the backups of the file and the
  number kept. Without it the 10 newest stay in the `backups` folder beside the file, as before. Each backup is a
  full copy of the file, secrets included, as [What the bridge calls](/docs/modules/comficonf#what-the-bridge-calls)
  states.

The docs of this release also describe a move that needs no new Taffy version and has no changelog entry: a
plugin that still reads `JavaPlugin.getConfig()` beside a `ConfigHolder` keeps old values after a reload and after
a save in the editor.
[Moving a plugin off getConfig()](/docs/modules/config#moving-a-plugin-off-getconfig) describes the move and what
the server owner sees after it.

| [PromptRequest has a fifth component](#promptrequest-has-a-fifth-component) | a plugin with a record pattern over `PromptRequest`; every `new PromptRequest(question, initial, origin, answer)` still compiles | add a fifth component to the pattern |
| [Menus read their text through a TextSource](#menus-read-their-text-through-a-textsource) | a plugin that calls `Menus.Parts.messages()` or `MenuText.messages()` | call `MenuText.source()`, or keep the plugin's own `Messages` |
| [Answer has a third result](#answer-has-a-third-result) | a plugin with a `switch` over `Answer` that has no `default` branch | add a `default` branch, or a case for `Answer.Later` |
| [EconomyProvider.vault takes a folia flag](#economyprovidervault-takes-a-folia-flag) | a plugin that calls `EconomyProvider.vault`; the old call still compiles, with a deprecation warning | pass `scheduler.mode() == Scheduler.Mode.FOLIA` |

### Menus refuse a material that is not an item

`Menus.register` and `Menus.reload` throw `IllegalArgumentException` for a material that is not an item a slot
can show, air included: the material of an `ItemLayout` (shown or not), the `filler` of a `MenuLayout`, the
`emptyMaterial` of a `PagerLayout`, and, in `register`, the `filler` and `loadingItem` of the `MenuSettings`. The
message names the menu and the item. In `0.2` such a layout registered and every open of the menu failed with a
stack trace.

**Migration:** give each of these an item material. A plugin that reads layouts or settings from a file catches
the `IllegalArgumentException` of `register` and `reload` and shows its message to the owner, as
[Reload](/docs/modules/gui#reload) shows; a refused `reload` leaves the layouts as they were.

```java title="0.2"
// MenuLayouts.shop() holds ItemLayout.of("buy", List.of(13), Material.WALL_TORCH).action("buy")
menus.register(new ShopMenu(menus));   // registers, and every open of the shop menu fails
```

```java title="0.3.0"
// MenuLayouts.shop() holds ItemLayout.of("buy", List.of(13), Material.TORCH).action("buy")
try {
    menus.register(new ShopMenu(menus));
} catch (IllegalArgumentException e) {
    // "item buy of the shop menu has the material WALL_TORCH, which is not an item" for the layout of 0.2
    getLogger().warning("The shop menu is not registered: " + e.getMessage());
}
```

### Menu settings, layouts and parts are built through factories

`MenuSettings`, `ItemLayout`, `MenuLayout`, `PagerLayout` and `Menus.Parts` are final classes with no public
constructor and are no longer records, so a value a later release adds to one breaks no plugin. Each is built
through a static factory that takes what has no default, and a method named after each other value gives a copy
with that value replaced. The methods that read a value keep their names, the layouts and `MenuSettings` still
compare by value, and every check a constructor made is made by the factory or the method that takes the value.
`Menus.Parts` compares by identity, and a record pattern over one of the five no longer compiles.

**Migration:** replace each `new` with the factory, and add a method call for each value that differs from the
default.

| `0.2` | `0.3.0` | Defaults left out |
|---|---|---|
| `new MenuSettings(28, filler, debounce, loading)` | `MenuSettings.DEFAULTS.pageSize(28).filler(filler).clickDebounce(debounce).loadingItem(loading)` | the values of `MenuSettings.DEFAULTS` |
| `new ItemLayout(id, slots, material, action, permission, enabled, name, lore)` | `ItemLayout.of(id, slots, material).action(action).permission(permission).enabled(enabled).name(name).lore(lore)` | no action, permission, name or lore, and shown |
| `new PagerLayout(slots, emptySlot, emptyMaterial)` | `PagerLayout.of(slots).emptySlot(emptySlot).emptyMaterial(emptyMaterial)` | no empty state |
| `new MenuLayout(menu, rows, filler, pager, items, title)` | `MenuLayout.of(menu, rows).filler(filler).pager(pager).items(items.values()).title(title)` | no filler, list, items or title |
| `new Menus.Parts(layouts, settings, messages, locales, server, preview, tasks, entity, sounds, home, logger, errors)` | `Menus.Parts.of(plugin, messages, tasks, entity, errors).layouts(layouts).settings(settings).locales(locales).sounds(sounds).home(home)` | no layouts, `MenuSettings.DEFAULTS`, `Player::locale`, no sounds, no home menu, and the plugin's own server, logger and `new NamespacedKey(plugin, "preview")` |

```java title="0.2"
MenuSettings settings = new MenuSettings(28, Material.GRAY_STAINED_GLASS_PANE, Duration.ofMillis(400),
    Material.CLOCK);
PagerLayout list = new PagerLayout(List.of(10, 11, 12, 13, 14, 15, 16), 13, Material.PAPER);
ItemLayout close = new ItemLayout("close", List.of(26), Material.BARRIER, MenuKind.CLOSE, null, true, null, null);
```

```java title="0.3.0"
MenuSettings settings = MenuSettings.DEFAULTS.pageSize(28).clickDebounce(Duration.ofMillis(400));
PagerLayout list = PagerLayout.of(List.of(10, 11, 12, 13, 14, 15, 16)).emptySlot(13).emptyMaterial(Material.PAPER);
ItemLayout close = ItemLayout.of("close", List.of(26), Material.BARRIER).action(MenuKind.CLOSE);
```

`ItemLayout.of(id, slots, material)` and the `ItemLayout` methods that replace a value are there in `0.2` too, so
an item built through them needs no change. [Building a layout in code](/docs/modules/gui#building-a-layout-in-code)
and [Enable and disable](/docs/modules/gui#enable-and-disable) show each type in a plugin.

### MenuLayout takes its items as a collection

`MenuLayout.items(Collection<ItemLayout>)` takes the items themselves, in the order `MenuLayout.items()` keeps,
and keys each by its own id. In `0.2` the constructor took a map and refused a key that differed from its item's
id. Two items with one id are refused with an `IllegalArgumentException` such as "item buy is in the shop menu
twice". `MenuLayout.item(ItemLayout)` adds one item, or replaces the item of the same id in its place.
`MenuLayout.items()` still returns the map.

**Migration:** pass `map.values()` where the plugin built a map, or build a list.

```java title="0.2"
Map<String, ItemLayout> items = new LinkedHashMap<>();
items.put("back", ItemLayout.of("back", List.of(45), Material.ARROW).action(MenuKind.BACK));
items.put("close", ItemLayout.of("close", List.of(53), Material.BARRIER).action(MenuKind.CLOSE));
MenuLayout layout = new MenuLayout("warps", 6, Material.BLACK_STAINED_GLASS_PANE, list, items, null);
```

```java title="0.3.0"
MenuLayout layout = MenuLayout.of("warps", 6)
    .filler(Material.BLACK_STAINED_GLASS_PANE)
    .pager(list)
    .items(List.of(
        ItemLayout.of("back", List.of(45), Material.ARROW).action(MenuKind.BACK),
        ItemLayout.of("close", List.of(53), Material.BARRIER).action(MenuKind.CLOSE)));
```

### Menus and Prompts register their own listeners

`Menus.Parts.of` takes the owning `Plugin` first. `new Menus(parts)` registers the menu listener with the plugin
manager of `Parts.server()` as a listener of that plugin, and `new Prompts(menus, ...)` registers the prompt
listener the same way before it links to the menus. In `0.2` the plugin registered `menus.listener()` and
`prompts.listener()` itself, and a plugin that forgot the call opened menus whose icons players could take.

The server, the logger and the preview key are no longer required: they default to `plugin.getServer()`,
`plugin.getLogger()` and `new NamespacedKey(plugin, "preview")`, and `Parts.server(Server)`,
`Parts.logger(Logger)` and `Parts.preview(NamespacedKey)` replace them. The server refuses a listener of a plugin
that is not enabled with an `IllegalPluginAccessException`, so the menus are built while the plugin is enabled,
such as in `onEnable`.

**Migration:** pass the plugin to `Menus.Parts.of`, add `.preview(key)` when the plugin's preview key is not
`new NamespacedKey(plugin, "preview")`, and delete both `registerEvents` calls.

```java title="0.2"
menus = new Menus(new Menus.Parts(layouts, MenuSettings.DEFAULTS, messages, Player::locale, getServer(),
    new NamespacedKey(this, "preview"), scheduler::entity, EntityThread.on(scheduler, getServer()),
    () -> sounds, null, getLogger(), errors));
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
getServer().getPluginManager().registerEvents(menus.listener(), this);
getServer().getPluginManager().registerEvents(prompts.listener(), this);
```

```java title="0.3.0"
menus = new Menus(Menus.Parts.of(this, messages, scheduler::entity, EntityThread.on(scheduler, getServer()), errors)
    .layouts(layouts)
    .sounds(() -> sounds));
Prompts prompts = new Prompts(menus, PromptMode.ANVIL, BedrockPlayers.NONE, scheduler::delayedAsync);
```

### Menus.listener() and Prompts.listener() register nothing

`Menus.listener()` and `Prompts.listener()` are deprecated and a later release removes them. Each returns a
listener with no event handler, so a `registerEvents` call left in a plugin registers nothing and cannot register
the menus or the prompts twice. In `0.2` each returned the listener that guards the menus or takes the prompt
answers, for the plugin to register.

**Migration:** delete the calls that pass them to `registerEvents`. `new Menus(parts)` and
`new Prompts(menus, ...)` have registered both listeners by then.

```java title="0.2"
Prompts prompts = new Prompts(menus, PromptMode.CHAT, BedrockPlayers.NONE, scheduler::delayedAsync);
getServer().getPluginManager().registerEvents(menus.listener(), this);
getServer().getPluginManager().registerEvents(prompts.listener(), this);
```

```java title="0.3.0"
Prompts prompts = new Prompts(menus, PromptMode.CHAT, BedrockPlayers.NONE, scheduler::delayedAsync);
```

### Menus and Prompts check the calling thread

`Menus.open`, `Menus.rerender`, `Menus.load` and `Prompts.ask` throw `IllegalStateException` on a thread that
does not own the viewer, before they change anything. The message names the method and what to call instead,
such as "Menus.open must run on the viewer's entity thread; use Menus.openLater". In `0.2` the call went on off
the viewer's thread, where it changed the session and the inventory unguarded on Paper and failed part way inside
the server on Folia. `rerender` still does nothing for a closed session, and `open` and `ask` still do nothing
once `Menus.shutdown` ran.

**Migration:** from a callback on another thread, such as `thenRun` of a storage future, call
`Menus.openLater`, `Menus.rerenderLater` or `Prompts.askLater`, which schedule the work on the viewer's entity
thread. Call `Menus.load` from `Menu.opened` or a click handler, or hop to the viewer's thread first through
`EntityThread.call`.

```java title="0.2"
storage.save(warp).thenRun(() -> menus.rerender(session));
storage.find(name).thenAccept(warp -> menus.open(player, new Route("warp", warp, null)));
storage.count(owner).thenRun(() -> prompts.ask(player, request));
```

```java title="0.3.0"
storage.save(warp).thenRun(() -> menus.rerenderLater(session));
storage.find(name).thenAccept(warp -> menus.openLater(player, new Route("warp", warp, null)));
storage.count(owner).thenRun(() -> prompts.askLater(player, request));
```

### A click just after a redraw is dropped

A click on a menu slot is dropped for the click debounce window (250 ms by default) after a redraw put another
button in that slot, as a click within that window of the menu opening already is. In `0.2` a click that arrived
just after `Menus.rerender` or a load redrew the menu ran the handler of whatever the slot showed by then, so a
viewer aiming at one listing bought the one that had moved into its slot. Another button is a list row with
another `Frame.Entry.key`, for a row with no key a row with another icon, a button of another layout item, or any
button in a slot that had none. A layout action that redraws with other text or another icon keeps taking clicks.

`Frame.Entry` has `key` as a fifth record component. `Entry.click`, `Entry.display` and the four-argument
constructor still compile and give a row with no key; a record pattern over `Frame.Entry` needs a fifth
component.

**Migration:** give each clickable row a key that stays the same while the row shows the same thing, as in
`Frame.Entry.click(icon, handler).key(listing.id().toString())`. A row with no key whose icon changes on every
redraw, such as an animated one, otherwise drops the clicks of the window after each redraw.
[Frame](/docs/modules/gui#frame) shows a keyed list.

```java title="0.2"
Frame.Entry row = Frame.Entry.click(icon(listing), click -> buy(click, listing));
if (row instanceof Frame.Entry(var icon, var handler, var clicks, var exclusive)) {
    // ...
}
```

```java title="0.3.0"
Frame.Entry row = Frame.Entry.click(icon(listing), click -> buy(click, listing)).key(listing.id().toString());
if (row instanceof Frame.Entry(var icon, var handler, var clicks, var exclusive, var key)) {
    // ...
}
```

### A load releases only its own hold

A load clears `MenuSession.busy()` only for the hold that belongs to it: the exclusive button whose handler
started the load, or a `busy(true)` taken in the same handler or `Menu.opened` as the `Menus.load` call. It
clears that hold when it applies, fails or is cancelled, also when a later load started meanwhile. In `0.2` the
end of the latest load of a session released every hold, so a refresh or a page turn that ended while a claim
held the session with `busy(true)` let the same claim run a second time. A handler that throws likewise clears
`busy()` only when the session was not busy before it ran. A handler that calls `busy(true)` and then
`Menus.load` needs no change.

**Migration:** a handler that takes `busy(true)` for work outside `Menus.load`, and relied on a later load or a
failing handler to release it, calls `session.busy(false)` on the viewer's entity thread when its work ends, on
success and on failure. [Exclusive buttons](/docs/modules/gui#exclusive-buttons) shows such a handler.

```java title="0.2"
frame.action("claim", Frame.Spec.click(click -> {
    session.busy(true);
    stash.claim(click.player(), card, () -> menus.load(session, stash.cards(owner), (s, cards) -> s.data(cards)));
}).exclusively());
```

```java title="0.3.0"
frame.action("claim", Frame.Spec.click(click -> {
    session.busy(true);
    stash.claim(click.player(), card, () -> {
        session.busy(false);
        menus.load(session, stash.cards(owner), (s, cards) -> s.data(cards));
    });
}).exclusively());
```

### PromptRequest has a fifth component

`PromptRequest` has `abandoned` as a fifth record component: a `Consumer<PromptEnd>` that runs once when an ask
ended and the prompts opened no menu for it, as
[When an ask opens no menu](/docs/modules/gui#when-an-ask-opens-no-menu) describes. Every
`new PromptRequest(question, initial, origin, answer)` compiles and behaves as in `0.2`, with a step that does
nothing, and `request.abandoned(step)` gives a copy with a step. `PromptEnd` and `PromptMode` may gain constants
in a later release.

**Migration:** a record pattern over `PromptRequest` takes a fifth component, as in
`PromptRequest(var question, var initial, var origin, var answer, var abandoned)`, and a `switch` over
`PromptMode` keeps a `default` branch. A menu that hands something to an ask, such as escrowed items, releases it
in the `abandoned` step.

```java title="0.2"
if (request instanceof PromptRequest(var question, var initial, var origin, var answer)) {
    // ...
}
```

```java title="0.3.0"
if (request instanceof PromptRequest(var question, var initial, var origin, var answer, var abandoned)) {
    // ...
}
```

### Menus read their text through a TextSource

The menus and prompts hold a [`TextSource`](/docs/modules/gui#text-source), a function from a locale, a lang key
and its placeholders to a `Component`, and no longer the `Messages`. `Menus.Parts.of` still takes the plugin's
`Messages` and reads them as before, so a plugin that passes them changes nothing there. `Menus.Parts.messages()`
and `MenuText.messages()` are gone; `Menus.Parts.text()` and `MenuText.source()` give the `TextSource`, whose
`render`, `has` and `lines` take the same arguments as those of `Messages`.

**Migration:** call `menus.text().source().render(locale, key)` where a menu called
`menus.text().messages().render(locale, key)`, and keep the plugin's own `Messages` field for anything else it
read from them.

```java title="0.2"
Component note = menus.text().messages().render(locale, "gui.shop.note");
```

```java title="0.3.0"
Component note = menus.text().source().render(locale, "gui.shop.note");
```

### Answer has a third result

`Answer.Later(CompletableFuture<Answer>)` is a third result of a `PromptRequest` answer function, as
[Text prompts](/docs/modules/gui#text-prompts) describes. `Answer` is sealed, so a `switch` over it that names
`Accept` and `Retry` and has no `default` branch no longer compiles, and one compiled against `0.2.2` throws a
`MatchException` when it is given a `Later`. An answer function that returns an `Accept` or a `Retry` needs no
change.

**Migration:** give the `switch` a `default` branch, which also covers a result a later release adds, or a case
for `Answer.Later`.

```java title="0.2"
String outcome = switch (answer) {
    case Answer.Accept accept -> "accepted";
    case Answer.Retry retry -> "refused";
};
```

```java title="0.3.0"
String outcome = switch (answer) {
    case Answer.Accept accept -> "accepted";
    case Answer.Retry retry -> "refused";
    default -> "pending";
};
```

### EconomyProvider.vault takes a folia flag

`EconomyProvider.vault(Plugin, ErrorReports, boolean switchedOn, boolean folia, Integer scale)` takes the server
kind as a flag, `true` on Folia, so a plugin with no Taffy `Scheduler` can look the economy up. The overload that
takes a `Scheduler.Mode` still works, gives the same result and is deprecated; a later release removes it.

**Migration:** pass `scheduler.mode() == Scheduler.Mode.FOLIA` in place of `scheduler.mode()`.

```java title="0.2"
Detected<EconomyProvider> economy = EconomyProvider.vault(this, errors, true, scheduler.mode(), null);
```

```java title="0.3.0"
Detected<EconomyProvider> economy =
    EconomyProvider.vault(this, errors, true, scheduler.mode() == Scheduler.Mode.FOLIA, null);
```

## 0.3.1

`0.3.1` needs no change to a call: change the version of the settings plugin and rebuild. Every signature of
`0.3.0` is still there. Every change but one is in
[taffy-hooks](/docs/modules/hooks), and each addition is unused until a plugin calls it. One case needs a look: a
plugin that waits for `CustomItems.ready()` on a server whose Nexo, Oraxen or HeadDatabase holds nothing, described
under the table.

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.3.1"
}
```

A plugin that uses `CustomItems`, `Detected` or `RegionProvider` reads four things differently after the upgrade:

| Change | What the plugin reads |
|---|---|
| [Nexo, Oraxen and HeadDatabase have a loading state](/docs/modules/hooks#per-plugin) | Each of the three is `LOADING` in `statuses()` and makes `ready()` `false` until it has loaded its items, where it read `ON` and `ready()` read `true` during the load. `create` returns `null` for their ids during the load, as before. `resolve` and `idOrNull` read Nexo and Oraxen ids during the load, as before. |
| [A reference whose hint names no plugin is offered to each plugin](/docs/modules/hooks#ids-and-references) | `create("gems:ruby")` builds the ItemsAdder item `gems:ruby`, where it returned `null` without asking any plugin. A reference that starts with a plugin's key or alias goes only to that plugin, as before. |
| [A replaced plugin instance has a reason](/docs/modules/hooks#detected) | The `NOT_ENABLED` status of an integration whose plugin was loaded again as a new instance carries a reason for the owner, where it had none. The state and the provider are unchanged. |
| [WorldGuard without WorldEdit is not visible](/docs/modules/hooks#regions) | `RegionProvider.worldGuard` gives `NOT_VISIBLE` with a reason that names the missing `WorldEdit` entry and reports nothing, where it gave `FAILED` with a report under `hook.worldguard`. The integration was off in both versions, and a plugin that lists `WorldEdit` beside `WorldGuard` under `dependencies.server` reads `ON`. |

The Nexo, Oraxen and HeadDatabase integrations each register a listener for the plugin, as the ItemsAdder one
already did, so `CustomItems.detect` still runs while the plugin is enabled, normally in `onEnable`.

A Nexo or Oraxen that loaded with no item at all, and a HeadDatabase whose database holds no head, give `detect`
nothing to tell a finished load from one still running. When `detect` runs after their load, and no earlier `detect`
of the plugin heard that load end in this server run, the integration reads `LOADING` and `ready()` reads `false`
until their next items-loaded event, where `0.3.0` read `ON` and `true`. A plugin that waits for `ready()` before it
builds bounds the wait, and builds what it can once the wait ends.
[Per plugin](/docs/modules/hooks#per-plugin) describes each of the three.

Three additions let a plugin deliver custom items it could only guess at before:

- **Wait for item plugins to load.** `ready()` is `true` only once ItemsAdder, Nexo, Oraxen and HeadDatabase have
  each loaded their items, so a plugin that builds its menus or rewards once `ready()` is `true` no longer builds
  them while one of the four knows no item. [Per plugin](/docs/modules/hooks#per-plugin) names the event that ends
  each load.
- **Read why an item did not build.** `CustomItems.build(String reference)` returns the item or a `Built.Reason`:
  `UNKNOWN_PLUGIN`, `PLUGIN_OFF`, `NOT_READY`, `UNKNOWN_ID` or `FAILED`. `create` still returns `null` for each of
  them. [Why no item was built](/docs/modules/hooks#why-no-item-was-built) lists the reasons.
- **Close `CustomItems` on reload.** `CustomItems.close()` unregisters every listener `detect` registered, so a
  reload command that detects again calls it first on the `CustomItems` it holds, as
  [Detecting again](/docs/modules/hooks#detecting-again) shows. A plugin that detects once needs no `close()`.

One addition is in [taffy-platform](/docs/modules/platform#itembuilder):
`ItemBuilder.deserializeOrThrow(String reference)` rebuilds the item of a `serialized:<base64>` reference or throws
`IllegalArgumentException` with the cause, so a plugin that stores items can log why a stored item is gone.
`ItemBuilder.deserialize` still returns `null` for every failure.

## 0.3.2

Change the version of the settings plugin:

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.3.2"
}
```

Every signature of `0.3.1` is still there, and a plugin that follows the two thread rules the Javadoc already
stated recompiles with no change. `0.3.2` enforces both rules, so a call that broke one ran before and throws now.
Every change is in [taffy-hooks](/docs/modules/hooks) and [taffy-storage](/docs/modules/storage).

| Change | Affects | Action |
|---|---|---|
| [An economy call off its thread throws](#an-economy-call-off-its-thread-throws) | a plugin that calls `balance`, `has`, `withdraw` or `deposit` of the Vault economy on a thread other than the one `thread(player)` names: an async thread on Paper, and under the default rule every region thread on Folia | run the call through `Scheduler.dispatch`, or look the economy up with the entity thread rule |
| [A LuckPerms write on a server thread throws](#a-luckperms-write-on-a-server-thread-throws) | a plugin that calls `addGroup`, `addTempGroup`, `removeGroup`, `setPermission` or `unsetPermission` on the main thread, a region thread or the global region thread, or in `onDisable`, directly or through `Scheduler.asyncOrRun` | run the write through `Scheduler.async`; a write made in `onDisable` moves to before the plugin disables |

[What a plugin can now do](#what-a-plugin-can-now-do) lists the additions and the calls that answer differently
with no change in the plugin.

### An economy call off its thread throws

`balance`, `has`, `withdraw` and `deposit` of the Vault economy throw `IllegalStateException` when the calling
thread is not the one `EconomyProvider.thread(player)` names. The message names `thread(player)` and
`Scheduler.dispatch`. The rule itself is not new: the `EconomyProvider` Javadoc states that every call runs on
that thread. Until `0.3.1` nothing enforced it, so a call from a Folia region thread or an async thread ran
unordered against the other callers of the economy. The check comes before anything in the economy is called, so
a refused call moves no money. [The thread rule](/docs/modules/hooks#the-thread-rule) names the server check
behind each tag.

A call made on the main thread of a Paper server, or through `Scheduler.dispatch` on the thread `thread(player)`
names, is unchanged. The mistake shows mostly on Folia, where a click handler or a command runs on a region
thread and `thread(player)` names the global region thread: the same code passes on Paper, where both are the
main thread.

**Migration:** run each call through `Scheduler.dispatch` on the thread `thread(player)` names, and hop back to
the player's thread for the result.

```java title="0.3.1"
EconomyResult result = money.withdraw(player.getUniqueId(), price);
```

```java title="0.3.2"
UUID id = player.getUniqueId();
scheduler.dispatch(money.thread(id), () -> money.withdraw(id, price))
    .whenComplete((result, failure) -> scheduler.entity(player, () -> deliver(player, result, failure)));
```

A plugin that must call the economy inline on the player's region thread, with an economy plugin that is safe
there, opts in to the entity thread rule at the lookup. `thread(player)` then names the player's own thread
while the player is online, and the inline call passes the check:

```java title="0.3.2"
Detected<EconomyProvider> economy = EconomyProvider.vault(
    VaultOptions.of(this, errors, scheduler.mode() == Scheduler.Mode.FOLIA)
        .threadRule(VaultOptions.ThreadRule.ENTITY));
```

### A LuckPerms write on a server thread throws

`addGroup`, `addTempGroup`, `removeGroup`, `setPermission` and `unsetPermission` of `PermissionProvider.luckPerms`
throw `IllegalStateException` when called on a server thread: the main thread on Paper, and every region thread
and the global region thread on Folia (a thread `Server.isPrimaryThread()` is `true` on). The rule itself is not
new: the `PermissionProvider` Javadoc states that writes run off the server thread, since a write loads the
player's data when it is not cached and blocks until the change is saved. Until `0.3.1` nothing enforced it. The
check comes before LuckPerms is asked, so a refused write changes nothing. `available`, `primaryGroup` and
`groups` are not checked.

A write made on an async thread is unchanged.

**Migration:** move each write to an async thread and take its result there, hopping back to the player's thread
for anything that touches the player.

A write made in `onDisable` runs on a server thread and throws too, where it blocked and saved until `0.3.1`.
`Scheduler.async` returns `false` once the plugin is disabling and never runs the task, and
`Scheduler.asyncOrRun` then runs it on the calling thread, where the write throws. Make the write before the
plugin disables, on an async thread, for example when the player quits or when the state it reflects changes.

```java title="0.3.1"
boolean added = permissions.addGroup(player.getUniqueId(), "vip");
```

```java title="0.3.2"
UUID id = player.getUniqueId();
boolean accepted = scheduler.async(() -> {
    boolean added = permissions.addGroup(id, "vip");
    scheduler.entity(player, () -> confirm(player, added));
});
if (!accepted) {
    getLogger().warning("The vip group was not added: the plugin is disabling");
}
```

### What a plugin can now do

Each addition is unused until a plugin calls it:

- **Ask whether the money moved.** `EconomyResult.moved()` is `true` for `OK` and `OVERDRAWN`. A plugin that
  refuses a purchase on `status() != Status.OK` keeps the money of an `OVERDRAWN` withdraw and delivers nothing, so
  branch on `moved()`, as [Charging a player](/docs/modules/hooks#charging-a-player-on-paper-and-folia) does.
- **Look the economy up with options.** `EconomyProvider.vault(VaultOptions options)` takes the owner, the error
  reports, the switch, the server kind and the scale as one object, with the two options below. The entry point of
  `0.3.0` is unchanged and gives the same result.
- **Call the economy inline on the player's thread.** `VaultOptions.ThreadRule.ENTITY` makes `thread(player)`
  name the player's own thread while the player is online, for an economy plugin that is safe on region threads.
  [The thread rule](/docs/modules/hooks#the-thread-rule) states what is no longer ordered under it.
- **Let the economy decide an overdraft or a loan.** `VaultOptions.FundsCheck.NATIVE` answers `has` through Vault's
  `Economy.has` and lets `withdrawPlayer` decide a withdraw. A withdraw the economy refuses then gives `FAILED`,
  for a short balance too, and never `INSUFFICIENT` or `OVERDRAWN`, as
  [The funds check](/docs/modules/hooks#the-funds-check) describes.
- **Store a balance above the money ceiling.** `Params.decimal(BigDecimal)` and `Row.decimal(String)` bind and
  read a decimal number of any magnitude, for a balance that passes `MoneyColumn.MAX` (about 9.22e14).
  [Amounts above the money ceiling](/docs/modules/storage#amounts-above-the-money-ceiling) gives the column of each
  dialect and the limits on SQLite.
- **Refuse a signed amount that is out of range.** `Params.signedMoney(BigDecimal)` binds like `moneyOrNull` and
  throws `MoneyOutOfRangeException` above `MoneyColumn.MAX` in magnitude, where `moneyOrNull` stores `NULL`.
  `moneyOrNull` is unchanged.

Six calls answer differently after the upgrade and need no change in the plugin. A plugin that worked around one of
them can drop the workaround:

- **Revoke a temporary rank.** `PermissionProvider.removeGroup` removes a membership `addTempGroup` added, and one
  held in a context, and returns `true`, where it left the membership and returned `false`.
- **Flip a permission.** `PermissionProvider.setPermission` replaces a node the player already holds without
  context, so a granted node becomes denied and a denied one granted, where it returned `false` and saved nothing.
- **Reach the other servers of a network.** A saved LuckPerms write is pushed through LuckPerms' messaging service
  when one is set up, so the plugin needs no push of its own.
- **Charge a balance kept as a `double`.** A balance read from Vault is rounded to 8 decimal places before it is
  compared, and one within 16 units in the last place of the `double` of an amount at `scale()` reads as that
  amount, so a stored `0.09999999999999998` covers `0.10` and a stored `1000000428.0799999` covers
  `1000000428.08`, where `has` answered `false` and `withdraw` gave `INSUFFICIENT`. From about 1e13 at 2 decimal
  places, and about 1e11 at 4, a `double` no longer holds the amount and a comparison can be off by one unit of
  `scale()`.
- **Read a confirmed withdraw as `OK`.** A withdraw the economy confirmed returns `OK` when the balance read that
  follows it throws, where the throwable left `withdraw` and the outcome read as unknown.
- **Read a disabled economy plugin as `FAILED`.** `withdraw` and `deposit` return `FAILED` with the message
  `the economy plugin <name> is disabled` while the plugin that registered the economy is disabled, where the call
  reached that plugin. No money moves.

[Economy](/docs/modules/hooks#economy) and [Permissions](/docs/modules/hooks#permissions) describe each of them.

### Storage settings are built through factories

`StorageSettings`, `StorageSettings.Server` and `StorageSettings.Pool` are final classes with no public constructor
and are no longer records, so a value a later release adds to one breaks no plugin. Each is built through a static
factory that takes what has no default, and a method named after each other value gives a copy with that value
replaced. The methods that read a value keep their names, the three still compare by value, `Server.toString()`
still hides the password, and every check a constructor made is made by the factory or the method that takes the
value. A record pattern over one of the three no longer compiles, `sqliteFile()` is empty for a server, and
`StorageSettings.server(Dialect.SQLITE, server)` throws `IllegalArgumentException`.

**Migration:** replace each `new` with the factory, and add a method call for each value that differs from the
default.

| `0.3` | `0.4.0` | Defaults left out |
|---|---|---|
| `new StorageSettings(Dialect.SQLITE, file, null, pool, threads, keep)` | `StorageSettings.sqlite(file).pool(pool).asyncThreads(threads).backupKeep(keep)` | `Pool.of(4)`, 2 threads, 5 backups |
| `new StorageSettings(dialect, file, server, pool, threads, keep)` | `StorageSettings.server(dialect, server).pool(pool).asyncThreads(threads)` | `Pool.of(4)`, 2 threads |
| `new StorageSettings.Server(host, port, database, user, password, sslMode, prefix)` | `StorageSettings.Server.of(host, port, database, user, password, sslMode).tablePrefix(prefix)` | no table prefix |
| `new StorageSettings.Pool(maxSize, minIdle, timeout)` | `StorageSettings.Pool.of(maxSize).minIdle(minIdle).connectionTimeout(timeout)` | 1 idle connection, 10 seconds |

```java title="0.3"
StorageSettings.Server server = new StorageSettings.Server("db.example.net", 3306, "minecraft", "plugin", "secret",
    StorageSettings.SslMode.VERIFY_FULL, "myplugin_");
StorageSettings settings = new StorageSettings(Dialect.MARIADB, "data.db", server,
    new StorageSettings.Pool(8, 2, Duration.ofSeconds(10)), 4, 0);
```

```java title="0.4.0"
StorageSettings.Server server = StorageSettings.Server
    .of("db.example.net", 3306, "minecraft", "plugin", "secret", StorageSettings.SslMode.VERIFY_FULL)
    .tablePrefix("myplugin_");
StorageSettings settings = StorageSettings.server(Dialect.MARIADB, server)
    .pool(StorageSettings.Pool.of(8).minIdle(2))
    .asyncThreads(4);
```

[Settings](/docs/modules/storage#settings) lists every value with its default and its rule.

### SslMode has a fourth constant

`StorageSettings.SslMode.PREFER` stands between `DISABLE` and `TRUST`. It encrypts the connection when the server
offers TLS and connects without encryption when it does not, which is what the MySQL and PostgreSQL drivers do for
a JDBC URL that names no mode; on MariaDB it is `DISABLE`. A `switch` expression over the three earlier constants no
longer compiles, a `switch` statement runs no branch for `PREFER`, and the ordinals of `TRUST` and `VERIFY_FULL`
are one higher. `SslMode` may gain a constant in a later release.

**Migration:** add a `default` branch to each `switch` over `SslMode`, and store a mode by its name, not its
ordinal. A plugin that reads the mode from its config with `SslMode.valueOf` needs no change.

```java title="0.3"
String label = switch (server.sslMode()) {
    case DISABLE -> "not encrypted";
    case TRUST -> "encrypted";
    case VERIFY_FULL -> "encrypted and verified";
};
```

```java title="0.4.0"
String label = switch (server.sslMode()) {
    case DISABLE -> "not encrypted";
    case TRUST -> "encrypted";
    case VERIFY_FULL -> "encrypted and verified";
    default -> "encrypted where the server offers it";
};
```

A plugin that built its JDBC URL itself, with no SSL setting, moves its owners to `PREFER` and they keep the
encryption they have. `StorageSettings.Server` also takes a socket timeout and driver properties from `0.4.0`:
[SSL modes](/docs/modules/storage#ssl-modes), [The socket timeout](/docs/modules/storage#the-socket-timeout) and
[Driver properties](/docs/modules/storage#driver-properties) describe them.

### The version table is named after the plugin

On MySQL, MariaDB and PostgreSQL, storage records the applied migrations in `<prefix><plugin>_schema_version`,
where `<plugin>` is the plugin's name in lowercase with every character other than a lowercase letter, a digit or
an underscore replaced by an underscore. In `0.3` the table was `<prefix>schema_version` for every plugin, so two
plugins that shared a database and a table prefix shared one history and one migration lock, and the second to
start stopped with `set up by a newer version of the plugin` or `changed after it ran on this database`. SQLite
keeps `schema_version`.

The first start under `0.4.0` finds the plugin's earlier table by its content: a `<prefix>schema_version` in
storage's layout that records at least one migration with the checksum of one of this plugin's scripts. It copies
the rows into the new table and logs one line that names both. The earlier table stays as it was and is not read
again, so a server that still runs a build on `0.3` against the same database keeps starting.

A `<prefix>schema_version` that records this plugin's migrations by version and name, but none under the checksum
of the current script, is taken as the plugin's earlier table whose scripts changed: the start stops before
anything is copied or run, as `changed after it ran on this database` stopped it in `0.3`. The message starts with
`the table <prefix>schema_version records migration <id> with another checksum` and names both checksums. Another
plugin under the same prefix whose migrations carry the same versions and names gives the same rows, so the message
names that case as well: that plugin starts once the plugin that owns the table has started on `0.4.0` and copied
it. A `<prefix>schema_version` whose rows match neither by checksum nor by version and name belongs to another
plugin and is left alone, and the start logs one warning that names it.

**Migration:** a plugin that only starts storage changes nothing. Four things need a look:

- A plugin, a test or an owner's query that reads `<prefix>schema_version` reads the new name. A plugin that must
  keep the earlier name sets it.
- A migration applied under `0.4.0` is recorded only in the new table. A build on `0.3` that holds the same
  migration and starts afterwards runs it again, so update every server that shares the database before the plugin
  ships its next migration.
- The name must not change after the first start on a database, and neither must the plugin name the default is
  built from: under another name storage finds no history and runs every migration again. Decide before the first
  `0.4.0` release whether to keep the earlier name. A plugin that ships one release on the default name and pins
  the earlier name afterwards is stopped at start with `the table <table> continues the migrations
  <prefix>schema_version records and holds newer ones`, since the earlier table no longer holds the whole history.
- Two plugin names that differ only in characters the default replaces, such as `My-Plugin` and `My_Plugin`, or
  only after the cut at 54 characters, give the same default name. One of the two plugins sets a name.

```java title="0.3"
// records migrations in myplugin_schema_version, the table of every plugin under the prefix myplugin_
StorageSettings settings = new StorageSettings(Dialect.MYSQL, "data.db", server, pool, 2, 0);
```

```java title="0.4.0"
// records migrations in myplugin_my_plugin_schema_version for the plugin My-Plugin
StorageSettings settings = StorageSettings.server(Dialect.MYSQL, server).pool(pool);

// keeps the table of 0.3
StorageSettings pinned = settings.versionTable(settings.tablePrefix() + "schema_version");
```

`StorageSettings.versionTable(String)` also gives a plugin whose tables have fixed names a version table beside
them, as [The version table](/docs/modules/storage#the-version-table) describes.

### More database threads than connections stop the start

`Storage.start` throws `IllegalArgumentException` when `asyncThreads` is above `Pool.maxSize`. Each database
thread uses one connection at a time, so in `0.3` the threads beyond the pool's size waited for a connection
another thread held and failed with a connection timeout under load.

**Migration:** set `maxSize` to `asyncThreads` or more. A plugin that reads both from its config catches the
exception, or checks the two, and shows the owner the message.

```java title="0.3"
// starts, and under load a third and fourth thread wait 10 seconds for a connection and fail
StorageSettings settings = new StorageSettings(Dialect.SQLITE, "data.db", null,
    new StorageSettings.Pool(2, 1, Duration.ofSeconds(10)), 4, 5);
```

```java title="0.4.0"
// "asyncThreads is 4, above the pool's maxSize of 2; ..." from Storage.start for Pool.of(2)
StorageSettings settings = StorageSettings.sqlite("data.db").pool(StorageSettings.Pool.of(4)).asyncThreads(4);
```

### A script the splitter cannot read stops the start

A migration script that is still to run stops the start, before the SQLite backup and before any migration, when
it holds what the [script rules](/docs/modules/storage#script-rules) cannot read: a single-quoted string that does
not end on the line it starts, a block comment that never closes or holds another block comment, `$$` outside a
quoted string and outside a block comment, or, on MySQL and MariaDB, a quote directly after a backslash. The
`StorageException` names the file and the line. In `0.3` such a script was split at the wrong place, or ran only
because the construct held no semicolon. A block comment that closes is kept and sent with its statement, and a
quote after a backslash ends the string on SQLite and PostgreSQL, as both did in `0.3`. A script that already ran
on a database is only compared by its checksum, so it never stops a start for this.

**Migration:** in a script that has not shipped yet, close each block comment, keep each quoted string on one line,
write a quote inside a string as two quotes, and create a function or trigger outside the migration scripts. Do not
edit a script that already ran on any database: its checksum would no longer match there, and that database would
stop with `changed after it ran on this database`. Put the corrected statement into a new migration instead.

```sql title="0.3: a MySQL or MariaDB script that has not shipped yet"
CREATE TABLE ${prefix}accounts (
    player BINARY(16) NOT NULL PRIMARY KEY,
    note VARCHAR(64) NOT NULL DEFAULT 'the owner\'s account'
) ENGINE = InnoDB;
```

```sql title="0.4.0"
CREATE TABLE ${prefix}accounts (
    player BINARY(16) NOT NULL PRIMARY KEY,
    note VARCHAR(64) NOT NULL DEFAULT 'the owner''s account'
) ENGINE = InnoDB;
```

### A commit the database rolled back is retried

A commit the database refuses because it rolled the transaction back, an `SQLTransactionRollbackException` or an
`SQLException` whose SQLState (or that of a cause) starts with `40`, completes the future of `async` and `read`
with that exception, and `asyncRetrying` and `readRetrying` run the work again. Nothing was written by such a
commit. In `0.3` it completed the future with a `CommitUnknownException`, which is never retried, so PostgreSQL
`SERIALIZABLE` work, which learns of a serialization failure (`40001`) at its commit, could not use `asyncRetrying`.
Any other failed commit is a `CommitUnknownException` as before, and so is one with SQLState `40003` (statement
completion unknown), which does not say whether the commit was written.

**Migration:** code that caught `CommitUnknownException` to retry a serialization failure itself calls
`asyncRetrying` and drops that branch. Code that treats every `CommitUnknownException` as unknown needs no change.

```java title="0.3"
storage.async(work).exceptionallyCompose(failure -> {
    Throwable cause = failure instanceof CompletionException ? failure.getCause() : failure;
    if (cause instanceof CommitUnknownException unknown && "40001".equals(unknown.getSQLState())) {
        return storage.async(work);   // the plugin's own retry
    }
    return CompletableFuture.failedFuture(cause);
});
```

```java title="0.4.0"
storage.asyncRetrying(work);
```

### A SQLite write takes the write lock when it begins

On SQLite storage from `Storage.start`, a write transaction (`async`, `asyncRetrying`) begins with
`BEGIN IMMEDIATE`: the writer connection is opened with `transaction_mode=IMMEDIATE`. While another process holds
the file's write lock, the work waits for it up to the busy timeout of 5 seconds and then reads what that process
wrote. In `0.3` the transaction began deferred, and work that read and then wrote failed at once with
`SQLITE_BUSY`.

**Migration:** work passed to `async` holds the write lock for as long as it runs, so work that only reads goes to
`read`. A test that opens `Storage.over` on SQLite and should behave as `start` adds the property.

```java title="0.3"
storage.async(tx -> tx.queryOne("SELECT balance FROM accounts WHERE player = ?",
    params -> params.uuid(player), row -> row.money("balance")));
```

```java title="0.4.0"
storage.read(tx -> tx.queryOne("SELECT balance FROM accounts WHERE player = ?",
    params -> params.uuid(player), row -> row.money("balance")));
```

### A SQLite backup is named with safe characters only

The file name of a SQLite backup holds the plugin version with every character other than an ASCII letter, a
digit, a dot, an underscore or a hyphen written as an underscore, so a version with a path separator cannot leave
the `backups` folder. Backups an earlier release wrote are still counted and pruned.

**Migration:** a tool that looks a backup up by the version replaces those characters the same way.

```text title="0.3"
backups/data-1.4.0+build.7-20261102-101530.db
```

```text title="0.4.0"
backups/data-1.4.0_build.7-20261102-101530.db
```

### The checksum ignores line endings and a byte order mark

The checksum storage records for a migration script is the SHA-256 of its text without a leading byte order mark
and with every line ending as a line feed. In `0.3` it was the SHA-256 of the script's exact bytes, and a script
that differed from the one that ran even in its line endings stopped the start. A row `0.1.0` to `0.3.2` wrote is
accepted when the script has the same text, with LF or CRLF endings and with or without a mark, so no row is
rewritten. [Checksums](/docs/modules/storage#checksums) states the rule.

**Migration:** a test that compares the stored checksum with the SHA-256 of the script's bytes compares it with the
SHA-256 of the normalized text. A row written under `0.4.0` for a script with CRLF endings or a mark is not the
SHA-256 of its bytes, so a build on `0.3` that reads the same version table stops with `changed after it ran on
this database`: update every server that shares the database before a migration is applied.

```java title="0.3"
String expected = sha256(Files.readString(script));
assertThat(storedChecksum).isEqualTo(expected);
```

```java title="0.4.0"
String text = Files.readString(script);
String normalized = (text.startsWith("\uFEFF") ? text.substring(1) : text).replace("\r\n", "\n").replace('\r', '\n');
assertThat(storedChecksum).isEqualTo(sha256(normalized));
```

### A SQLite migration ignores rows that already broke a foreign key

On SQLite, `PRAGMA foreign_key_check` runs before a migration and again before it commits, and the migration is
rolled back only for a row the second check finds and the first did not. One warning per start names the tables of
the rows that were already broken. In `0.3` every row the check found after the migration rolled it back and
stopped the start, so one orphaned row from an earlier bug blocked every later migration. The rows of a
`WITHOUT ROWID` table have no row id in that check, so they are counted per table, parent and foreign key.

**Migration:** a plugin that relied on the start stopping for such rows runs the check itself after the start.

```java title="0.3"
// a row of child that refers to a missing parent stops the start at the next migration with a StorageException
Storage.start(this, errors, settings, MIGRATIONS, Clock.systemUTC());
```

```java title="0.4.0"
// the start succeeds with one warning that names child
Storage.start(this, errors, settings, MIGRATIONS, Clock.systemUTC())
    .thenCompose(storage -> storage.read(tx -> tx.query("PRAGMA foreign_key_check", Tx.Binder.NONE,
        row -> row.text("table"))))
    .thenAccept(tables -> {
        if (!tables.isEmpty()) {
            getLogger().severe("Rows with a broken foreign key in " + tables);
        }
    });
```

### A PostgreSQL start waits at most a day for the migration lock

On PostgreSQL a start waits at most a day for the migration lock and then fails with a `StorageException`, as on
MySQL and MariaDB. In `0.3` it waited with no limit for a holder that stayed connected.

**Migration:** a plugin that holds the lock longer than a day on purpose, or a test that expects the start to wait
without limit, handles the exception and starts again.

```java title="0.3"
// completes only once the other start has released the lock, however long that takes
Storage.start(this, errors, settings, MIGRATIONS, Clock.systemUTC());
```

```java title="0.4.0"
// "another start has held the migration lock of <version table> in database <schema> for a day; restart once
// the other server has started"
Storage.start(this, errors, settings, MIGRATIONS, Clock.systemUTC()).exceptionally(failure -> {
    Throwable cause = failure instanceof CompletionException ? failure.getCause() : failure;
    if (cause instanceof StorageException held) {
        getLogger().severe("Cannot start the database: " + held.getMessage());
    }
    return null;
});
```

### A shipped config.yml needs a config-version

`ConfigLoader.load()` throws `ConfigLoadException` with the message `the config.yml inside the plugin jar has no
whole number of 1 or more under config-version` when the shipped file has no `config-version`, or has one that is
quoted, a decimal, text, below 1 or above 2147483647. It throws on every load, the first start included, and writes
nothing. In `0.3` such a shipped file counted as version 0: no owner's file was ever older, so new shipped keys were
never added, and nothing was logged.

**Migration:** write `config-version: 1`, without quotes, into the shipped `config.yml`. A plugin whose released
versions shipped the file without the key also sets the baseline, so the files its owners have, which lack the key
too, are left as they are and not rewritten on the first start.

```yaml title="0.3: config.yml (shipped)"
# loads, and no owner's file is ever upgraded
prefix: "<gray>[Shop]"
```

```yaml title="0.4.0: config.yml (shipped)"
config-version: 1
prefix: "<gray>[Shop]"
```

```java title="0.3"
ConfigLoader files = new ConfigLoader(getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger());
```

```java title="0.4.0"
// an owner's file without config-version reads as version 1, the layout the earlier releases wrote
ConfigLoader files = new ConfigLoader(getDataPath(), () -> getResource(ConfigLoader.FILE_NAME), getLogger())
    .baselineVersion(1);
```

A plugin whose shipped file always carried a whole-number `config-version` changes nothing.
[A file without a version](/docs/modules/config#a-file-without-a-version) describes the baseline.

### The message for a file that is not UTF-8 names the line

`StrictYaml.read` names the line of the first byte that is not UTF-8, counted from 1, in the message of its
`ConfigLoadException`. The same message is the error line of a `YamlFolder` for such a file and the message of
`ConfigLoader.load()` for such a `config.yml`. An owner who saved one line with an umlaut in a legacy code page
now learns which line. `YamlFileProvider` keeps the message without the line for a file an editor read or save
refuses.

**Migration:** code or a test that compares the whole message compares its start.

```java title="0.3"
// "config.yml is not saved as UTF-8"
boolean encoding = failure.getMessage().equals("config.yml is not saved as UTF-8");
```

```java title="0.4.0"
// "config.yml is not saved as UTF-8: the first byte that is not UTF-8 is on line 12"
boolean encoding = failure.getMessage().startsWith("config.yml is not saved as UTF-8");
```

A plugin that would rather load such a file, as Bukkit's `YamlConfiguration.loadConfiguration` does, reads it with
`StrictYaml.readLenient`, `YamlFolder.lenient` or `Messages.loadLenient`, which are new in `0.4.0`:
[StrictYaml](/docs/modules/config#strictyaml),
[Files saved in a legacy code page](/docs/modules/config#files-saved-in-a-legacy-code-page) and
[Messages](/docs/modules/platform#messages) describe them. `Messages` also names the line in the warning for a
language file it skips.

### Read and write failures name the file, not its path

The messages of `taffy-config` for a file or folder that cannot be read or written hold the name the plugin gave
and no longer the absolute path on the server, which a plugin often shows to a player or a web editor. In `0.3` the
path was in the message twice, once from Taffy and once from the message of the I/O failure. The I/O failure is
still the cause, so a logged stack trace holds the path.

| Method | `0.3` | `0.4.0` |
|---|---|---|
| `StrictYaml.read` | `cannot read <path>: <exception class> <message>` | `cannot read <source>: <exception class>`, then a space and the reason when the failure states one |
| `ConfigLoader.load` | `cannot write <path>: <exception class> <message>` | `cannot write config.yml: <exception class>`, then the reason |
| `YamlFolder.load` | `cannot read the folder <path>: <exception class> <message>` | `cannot read the folder <folder name>: <exception class>`, then the reason |

**Migration:** code that read the path out of the message takes it from the `Path` it passed, or from the cause.

```java title="0.3"
// "cannot read /srv/mc/plugins/Shop/menus.yml: NoSuchFileException /srv/mc/plugins/Shop/menus.yml"
String path = failure.getMessage().substring("cannot read ".length(), failure.getMessage().indexOf(": "));
```

```java title="0.4.0"
// "cannot read menus.yml: NoSuchFileException"
```

### YamlFolder skips dot files and reports .yaml files

`YamlFolder` skips every file whose name starts with a dot, without an error line, and `loadOne` returns `null`
for an id that starts with a dot. In `0.3` a `.hidden.yml` was an entry with the id `.hidden`, and the
`._<name>.yml` files macOS writes beside a file on a foreign file system were reported as files that are not UTF-8.
`YamlFolder.load` also adds an error line for a regular file whose name ends in `.yaml`, which `0.3` skipped
without a word while its owner wondered why the entry was missing.

**Migration:** give an entry file a name that does not start with a dot. An owner renames a `.yaml` file to
`.yml`; a plugin that keeps other `.yaml` files in the folder on purpose drops the line.

```text title="0.3"
kits/.vip.yml      loaded as the entry ".vip"
kits/._bank.yml    "._bank.yml is not saved as UTF-8"
kits/bank.yaml     skipped, no line
```

```text title="0.4.0"
kits/.vip.yml      skipped, no line
kits/._bank.yml    skipped, no line
kits/bank.yaml     "bank.yaml: rename it to bank.yml to have it read"
```

```java title="0.4.0"
List<String> errors = loaded.errors().stream()
    .filter(line -> !line.endsWith(" to have it read"))
    .toList();
```

### Owner-keyed sections are checked

`new ConfigLoader(Path, Supplier, Logger, Map)` throws `IllegalArgumentException` when a listed owner-keyed path
is blank or when one listed section lies inside another. The Javadoc of `0.3` ruled the second out without a check,
and which of the two sections applied to a key beneath both was not defined.

**Migration:** list each owner-keyed section once and none inside another.

```java title="0.3"
// accepted; kits.special.gold was handled by either section
Map<String, Set<String>> ownerKeyed = Map.of("kits", Set.of("default"), "kits.special", Set.of());
```

```java title="0.4.0"
// "the owner-keyed section kits.special lies inside the owner-keyed section kits" for the map above
Map<String, Set<String>> ownerKeyed = Map.of("kits", Set.of("default"));
```

### ConfigReader.parsed treats a DateTimeException as a rejection

`ConfigReader.parsed` treats a `DateTimeException` its parser throws as a rejection of the value, as it treats an
`IllegalArgumentException`: the owner gets the warning and the fallback is used. In `0.3` the
`DateTimeParseException` of `LocalTime::parse` or the `ZoneRulesException` of `ZoneId::of` left `parsed` and failed
the load. Any other exception of the parser is still thrown on.

**Migration:** a plugin that caught the exception around its load to report the value drops that branch. A parser
that must stop the load throws another exception type, such as `IllegalStateException`.

```java title="0.3"
LocalTime resetAt;
try {
    resetAt = reader.parsed("reset-at", LocalTime.NOON, "a time such as 18:30", LocalTime::parse);
} catch (DateTimeParseException invalid) {
    getLogger().warning("reset-at is not a time such as 18:30, so 12:00 is used.");
    resetAt = LocalTime.NOON;
}
```

```java title="0.4.0"
// "25:99" gives the fallback and the reader's own warning
LocalTime resetAt = reader.parsed("reset-at", LocalTime.NOON, "a time such as 18:30", LocalTime::parse);
```

### CustomItemPlugin may gain a constant

The Javadoc of `CustomItemPlugin` states that constants may be added in any release. `0.4.0` adds none, and the four
constants keep their order. In the release that adds one, a `switch` expression over the four constants with no
`default` branch no longer compiles, a `switch` statement runs no branch for the new constant, and a plugin that
passes `EnumSet.allOf(CustomItemPlugin.class)` to `CustomItems.detect` detects the added plugin too.

**Migration:** add a `default` branch to each `switch` over `CustomItemPlugin`.

```java title="0.3"
String label = switch (plugin) {
    case ITEMSADDER -> "ItemsAdder item";
    case NEXO -> "Nexo item";
    case ORAXEN -> "Oraxen item";
    case HEADDATABASE -> "head";
};
```

```java title="0.4.0"
String label = switch (plugin) {
    case ITEMSADDER -> "ItemsAdder item";
    case NEXO -> "Nexo item";
    case ORAXEN -> "Oraxen item";
    case HEADDATABASE -> "head";
    default -> plugin.plugin() + " item";
};
```

### The first start on 0.4.0

A server owner updates the plugin and starts the server. Three things differ from a start on `0.3`, and none of
them needs an action from the owner.

| What | Who sees it | What the owner sees |
|---|---|---|
| The version table name | a server on MySQL, MariaDB or PostgreSQL | One console line, once, and a new table `<prefix><plugin>_schema_version` beside the earlier `<prefix>schema_version`, which stays. Where the earlier table belongs to another plugin under the same prefix, one warning that names it instead. |
| The checksum rule | a server whose plugin build holds scripts with other line endings than the build that set the database up | The start succeeds, where it stopped with `changed after it ran on this database`. Nothing is logged and no row is rewritten. |
| The config upgrade | a server whose plugin gave its shipped `config.yml` a `config-version` for `0.4.0` without setting a baseline | One console line, a `config.yml` written anew with `config-version` in it, and the previous file as `config.yml.v0.bak`. |

**The version table name.** The start copies the plugin's history into the table named after the plugin and logs,
for the plugin `My-Plugin` under the prefix `myplugin_`:

```text title="Console"
[My-Plugin] Copied the migrations myplugin_schema_version records into myplugin_my_plugin_schema_version, which records them from now on. myplugin_schema_version stays as it was and is no longer read.
```

Later starts log nothing, because the new table exists. A server on SQLite keeps `schema_version` and sees no line.
A plugin that set `StorageSettings.versionTable` to the earlier name keeps that table, and no line is logged.
[The version table](/docs/modules/storage#the-version-table) describes the copy.

Where `<prefix>schema_version` holds only rows of another plugin, nothing is copied and the start logs once, for
the same plugin and prefix:

```text title="Console"
[My-Plugin] The table myplugin_schema_version records migrations, but none under the checksum of one of this plugin's scripts, so it is read as another plugin's version table and this plugin starts a new history in myplugin_my_plugin_schema_version, which runs every migration. If myplugin_schema_version is this plugin's table, a script changed after it ran: stop the server, restore the script, and restore a backup of the database if a migration ran twice.
```

**The checksum rule.** The rows of the version table keep the checksums `0.1.0` to `0.3.2` wrote, and a script that
still has the bytes it ran with is accepted as before. A build whose scripts differ from those bytes only in their
line endings (LF or CRLF) or a leading byte order mark now starts as well, in either direction: a database a CRLF
build recorded starts on an LF build too. One limit remains: a row recorded from a script with lone carriage returns
or mixed line endings is accepted only while the script still has those exact bytes. A script whose text changed
still stops the start with `changed after it ran on this database`. That holds on the first start under `0.4.0`
too, while the rows are still in `<prefix>schema_version`: the start stops before anything is copied or run.
[Checksums](/docs/modules/storage#checksums) states the rule, and
[The checksum ignores line endings and a byte order mark](#the-checksum-ignores-line-endings-and-a-byte-order-mark)
what it changes for a plugin.

**The config upgrade.** What happens to an owner's `config.yml` depends on what the plugin did about
[the shipped config-version](#a-shipped-configyml-needs-a-config-version):

| The plugin | The owner's `config.yml` at the first start |
|---|---|
| Its shipped file always carried a whole-number `config-version` | Read as before. It is rewritten only when the plugin's release ships a higher version, as in `0.3`. |
| Wrote `config-version: 1` into the shipped file and set `baselineVersion(1)` | Read as it is. Nothing is written and no copy is made. |
| Wrote `config-version: 1` into the shipped file and set no baseline | Counted as version 0 and upgraded to 1: the shipped keys it lacks and `config-version: 1` are added, the file is written anew and the previous file is kept as `config.yml.v0.bak`. |
| Left the shipped file without a `config-version` | Not read: `load()` throws `the config.yml inside the plugin jar has no whole number of 1 or more under config-version`, and the file is not changed. |

An upgrade logs one line that names the versions and the copy, and the shipped keys it added when there are any:

```text title="Console"
[My-Plugin] Upgraded config.yml from version 0 to 1; the previous file is kept as config.yml.v0.bak.
```

Every value of the owner's file is kept, and the way it is written can change: quotes, the form of a number, the
place of an added key and comments inside a list, as
[What an upgrade rewrites](/docs/modules/config#what-an-upgrade-rewrites) lists. From `0.4.0` a text longer than 80
columns stays on one line in the saved file, through an upgrade and through a save from the ComfiConf editor.

Every signature of `0.4.10` is still there, and a plugin changes nothing to move to `0.4.11`.

`0.4.11` adds, in [`taffy-hooks`](/docs/modules/hooks): `HologramProvider.displays`, which gives a

## 0.4.12

Change the version of the settings plugin:

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.4.12"
}
```

Every signature of `0.4.11` is still there. `0.4.12` adds `CustomItemPlugin.CRAFTENGINE` and
`CustomItemPlugin.MMOITEMS`, which a plugin that uses [`CustomItems`](/docs/modules/hooks#custom-items) meets in
three places.

### craftengine: and mmoitems: name a plugin

From `0.4.12`, a reference that starts with `craftengine:` or `mmoitems:` goes only to that plugin, whatever set
`CustomItems.detect` was given, and `CustomItemRef.hasKnownProvider()` is `true` for it. Before `0.4.12` neither
key names a plugin and the whole reference is offered to each plugin, so `mmoitems:ruby` builds an ItemsAdder
item of the namespace `mmoitems`. From `0.4.12` `create` returns `null` for it and `build` gives `PLUGIN_OFF`
while MMOItems has no integration on, where `0.4.11` builds the other plugin's item or gives `UNKNOWN_PLUGIN`.

**Migration:** write an id of another plugin that itself starts with `craftengine:` or `mmoitems:` with that
plugin's key, as in `itemsadder:mmoitems:ruby` or `ia:mmoitems:ruby`. No other reference changes.

### statuses() holds six entries

From `0.4.12`, `CustomItems.statuses()` holds six entries where it held four and the detection log line names six
plugins, for every plugin: CraftEngine and MMOItems come after HeadDatabase and are `SWITCHED_OFF` unless the set
given to `CustomItems.detect` holds them.

**Migration:** find a status by `HookStatus.plugin()`, not by its position from the end. `statuses().getLast()`
gives MMOItems' status, and HeadDatabase's is at index 3.

### EnumSet.allOf detects both

A plugin that passes `EnumSet.allOf(CustomItemPlugin.class)` to `CustomItems.detect` detects CraftEngine and
MMOItems from `0.4.12`. An installed one that the plugin's `paper-plugin.yml` does not list is `NOT_VISIBLE` and
warned about.

**Migration:** list both under `dependencies.server`, or pass the set of plugins the plugin supports.

```yaml title="src/main/resources/paper-plugin.yml"
dependencies:
  server:
    CraftEngine:
      load: BEFORE
      required: false
    MMOItems:
      load: BEFORE
      required: false
```

### Additions that change nothing

`0.4.12` also adds, in [`taffy-hooks`](/docs/modules/hooks): `RegionProvider.canBuild`, a default method that
answers `true` and that the WorldGuard provider answers from the `build` flag, and `NpcProvider` with `NpcPlugin`,
which give the location of an NPC and its clicks for Citizens, FancyNpcs and ZNPCsPlus. A plugin that calls
neither behaves as on `0.4.11`. A server owner changes nothing for `0.4.12`.

Change the version of the settings plugin:


Every signature of `0.4.12` is still there, and a plugin changes nothing to move to `0.4.13`, with one exception

`0.4.13` adds, in [`taffy-hooks`](/docs/modules/hooks#setting-a-balance-currency-names-and-receipts), seven default
methods on `EconomyProvider`: `setBalance`, `currencyNameSingular`, `currencyNamePlural`, `currencySymbol`, `format`,
`withdrawReceipt` and `depositReceipt`, with the record `EconomyReceipt`. A plugin's or a test's own
`EconomyProvider` compiles unchanged and answers `UNSUPPORTED`, `null` and a receipt with no transaction id. A
plugin that calls none of them behaves as on `0.4.12`. A server owner changes nothing for `0.4.13`.

The exception: an `EconomyProvider` implementation that already declares `setBalance(UUID, BigDecimal)`,
`currencyNameSingular()`, `currencyNamePlural()`, `currencySymbol()`, `format(BigDecimal)`,
`withdrawReceipt(UUID, BigDecimal, BooleanSupplier)` or `depositReceipt(UUID, BigDecimal)` with another return type
than the new method has, such as `void setBalance(UUID, BigDecimal)`, no longer compiles against `0.4.13`. Rename
that method or give it the new return type: `EconomyResult` for `setBalance`, `String` for the names, the symbol and
`format`, and `EconomyReceipt` for the two receipts. A method with the same return type overrides the default and
needs no change, and a plugin jar built against `0.4.12` keeps running on `0.4.13`.

The names, the symbol and `format` return the economy's own text, unchanged. It can hold legacy colour codes or the
economy plugin's own tags, which are not MiniMessage, so show it with `Component.text`.

## 0.4.14

Change the version of the settings plugin:

```kotlin title="settings.gradle.kts"
plugins {
    id("so.alaz.taffy.settings") version "0.4.14"
}
```

Every signature of `0.4.13` is still there, and a plugin changes nothing to move to `0.4.14`.

`0.4.14` adds, in [`taffy-config`](/docs/modules/config#items), `ConfigReader.item(String)` and
`item(String, ItemKeys)`, which read an item definition out of a group of keys into the class `ItemSpec` without a
running server, and `ItemSpec.overMaterial` and `overStack`, which give an `ItemBuilder` with the spec applied.
`ItemKeys` names the keys to read, so a plugin that adopts the reader passes the key names its files already have
and no owner file changes. A plugin that does not call `item` reads its files as on `0.4.13`.

`0.4.14` adds, in [`taffy-hooks`](/docs/modules/hooks#conditions), `ConditionRegistry`, which builds the conditions
an owner lists in a config file (a `type`, the keys of that type and an optional `deny` text for each entry) into
one `Condition` and tests them for a player in file order, stopping at the first denial. It holds the types
`permission`, `world`, `papi` and `region`, and a plugin registers its own, an economy type included. A mistake in
the list is an error with its path, passed to the `ConditionProblems` the plugin gives, and never an exception. The
keys are read only through `ConditionRegistry.build`, so a plugin that does not call it reads its files as on
`0.4.13`.

`0.4.14` lets a lang entry name where `Messages.send` shows it, in
[`taffy-platform`](/docs/modules/platform#delivery-in-the-lang-file): a message written as a section named
`delivery` under its key, with any of `chat`, `actionbar`, `title`, `subtitle`, `times` and `sound`, is shown to a
player as those entries say, and a sender that is not a player gets one chat message. The call is the `send` a
plugin already makes, so an owner moves a message to the action bar in the lang file alone. A message written as a
value is sent as chat as on `0.4.13`, and `render`, `lines`, `has`, `template`, `sendActionBar` and `showTitle`
read every file as on `0.4.13`. A `delivery` section with any other entry, such as a menu item named `delivery`
with a `name`, stays a plain section, as does a key named `delivery` at the top of a file. The load and `reload()`
log nothing new: a warning about a bad `times`, a bad `sound` or a section with another entry is logged by the
first `send` that reads the section. The warning about the keys a file lacks and `addMissingKeys` treat each entry
of a bundled delivery section as the key it is, as on `0.4.13`, so a section a file has in part is listed and
completed key by key. They leave out two shapes: the entries of a bundled delivery section whose message the file
has as a value, and a message the bundled file has as a value and the file has as a delivery section. On `0.4.13`
a file of either shape got the warning at each load and made `addMissingKeys` change nothing.

## 0.4.15

`0.4.15` adds, in [`taffy-storage`](/docs/modules/storage#generated-keys), `Tx.insert(String sql, String keyColumn,
Tx.Binder binder)`, which runs an `INSERT` of one row and returns the key the database generated for it as a
`long`. The key column is named in the call, so PostgreSQL returns that column and not the first one of the table;
MySQL and MariaDB return the `AUTO_INCREMENT` value and SQLite the rowid. A statement that is not an `INSERT`, that
counts another number of rows than 1 or that generated no key throws `SQLException`. `update` and `batch` run as
on `0.4.14`, so a plugin that does not call `insert` changes nothing.

`0.4.15` adds, in [`taffy-platform`](/docs/modules/platform#importers), the shape of an import from another
plugin: the interface `Importer` with `id()`, `displayName()`, `present()` and `run(boolean dryRun)`, which
returns a `CompletableFuture<ImportReport>`; the class `ImportReport`, built with `ImportReport.builder()`, which
holds the count of entries read, the counts and lines of the imported and the skipped entries and the warnings;
and the registry `Importers`, whose `byId` finds an importer without regard to case and whose `presentIds()` and
`allIds()` give the ids a command suggests. The reading of the source, the writing of the result and the backup
before a real run stay in the plugin, so a plugin with an import of its own keeps it until it moves to these types,
and a plugin without one changes nothing.

`0.4.15` adds, in [`taffy-gui`](/docs/modules/gui#animating-a-menu), `Menus.animate(MenuSession<S> session,
Duration period, Predicate<MenuSession<S>> step)`, which runs `step` and redraws an open menu every `period`
(whole ticks, at least one) until `step` returns `false`, the session closes, `Menus.shutdown` runs or `animate` is
called again for the session. It is called on the viewer's entity thread like `rerender` and counts its ticks through
the `tasks` the menus already have, so `Menus.Parts` is built as on `0.4.14`. `rerender`, `rerenderLater` and the
click rules run as on `0.4.14`, so a plugin that does not call `animate` changes nothing, and one that chains
`rerenderLater` by hand keeps working.
