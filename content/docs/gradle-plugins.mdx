---
title: Gradle plugins
description: The seven Taffy Gradle plugins, what each applies and configures, and the alaz version catalog they expose.
---

Taffy ships Gradle plugins, published together as `so.alaz.taffy:taffy-gradle`, and a version catalog, published as `so.alaz.taffy:taffy-catalog`. Together they give a plugin build the repositories it resolves from, the Java 25 toolchain, test defaults that catch locale and time zone bugs, a coverage gate on `check`, one relocated shadow jar for the server, and the `RuntimeLibraries` class a `PluginLoader` reads its downloads from.

| Plugin id | Applied in | Applies | Adds |
|---|---|---|---|
| `so.alaz.taffy.settings` | `settings.gradle.kts` | `so.alaz.taffy.repositories` | The `alaz` version catalog, at the plugin's own version |
| `so.alaz.taffy.repositories` | `settings.gradle.kts` | the foojay toolchain resolver | Maven Central, Paper, repo.alaz.so and the integration repositories |
| `so.alaz.taffy.java` | any Java module | `java-library` | Java 25 toolchain, compiler and javadoc flags, JUnit Platform, test defaults, `LICENSE` in `META-INF` |
| `so.alaz.taffy.coverage` | any Java module | `so.alaz.taffy.java`, `jacoco` | The `coverage` extension and an instruction coverage gate on `check` |
| `so.alaz.taffy.paper-plugin` | the plugin module | `so.alaz.taffy.coverage`, `com.gradleup.shadow` | The `paperPlugin` extension, the relocated shadow jar, `${version}` expansion in `paper-plugin.yml` |
| `so.alaz.taffy.paper-api` | a published API module | `so.alaz.taffy.java`, `maven-publish` | Sources and javadoc jars, the `library` publication and the `alazso` repository |
| `so.alaz.taffy.library` | a published, tested library module | `so.alaz.taffy.paper-api`, `so.alaz.taffy.coverage` | A per-class coverage floor of 0.50 |

A Paper plugin usually needs only two of them: `so.alaz.taffy.settings` in `settings.gradle.kts` and `so.alaz.taffy.paper-plugin` in `build.gradle.kts`. A plugin can also keep its own Gradle build and declare the modules by their coordinates, without any of these plugins, as [Without the Gradle plugins](/docs/consuming-by-coordinates) describes.

## Applying the plugins

The settings plugin is the one applied with a version. It puts every Taffy plugin on the build's classpath, so project build scripts apply the others by id alone. `exclusiveContent` makes Gradle ask `repo.alaz.so` for the `so.alaz.taffy` group and its subgroups only, which hold the Taffy plugins, and ask the Gradle Plugin Portal for every group but those.

```kotlin title="settings.gradle.kts"
pluginManagement {
    repositories {
        exclusiveContent {
            forRepositories(maven("https://repo.alaz.so/releases"))
            filter { includeGroupAndSubgroups("so.alaz.taffy") }
        }
        gradlePluginPortal()
    }
}

plugins {
    id("so.alaz.taffy.settings") version "0.4.11"
}

rootProject.name = "myplugin"
```

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.platform)
    testImplementation(alaz.junit.jupiter)
    testRuntimeOnly(alaz.junit.platform.launcher)
}
```

```properties title="gradle.properties"
group=com.example.myplugin
version=1.0.0
```

The plugins are Java 25 class files loaded into Gradle's own JVM, so Gradle itself runs on Java 25. A file `gradle/gradle-daemon-jvm.properties` holding `toolchainVersion=25` makes Gradle pick a Java 25 JVM whatever `JAVA_HOME` points to.

The plugins need Gradle 9.2.0 or newer. Gradle 9.1.0 is the first release that runs on Java 25, and on 9.1.0 the Shadow plugin that `so.alaz.taffy.paper-plugin` applies fails with a `NoSuchMethodError` for `AdhocComponentWithVariants.addVariantsFromConfiguration`. Taffy's own build and the examples use 9.9.1, and Taffy's tests build a plugin on 9.2.0. From `0.4.1`, `so.alaz.taffy.settings` stops a build on an older Gradle before it applies anything:

```text
so.alaz.taffy.settings needs Gradle 9.2.0 or newer, and this build runs on Gradle 9.1.0. Set a newer version in distributionUrl in gradle/wrapper/gradle-wrapper.properties.
```

Before `0.4.1`, a build on Gradle 9.1.0 failed with that `NoSuchMethodError` when it applied `so.alaz.taffy.paper-plugin`, and ran when it applied only the other plugins. The wrapper's own `wrapper` task cannot raise the version here, since it loads the settings plugin first: edit `distributionUrl`, and `distributionSha256Sum` when the file has one.

Every push to Taffy's `main` branch publishes the next version as a `-SNAPSHOT` to `https://repo.alaz.so/snapshots`; a build that uses a snapshot adds `maven("https://repo.alaz.so/snapshots")` to `forRepositories(...)` in `pluginManagement.repositories`, as [Building against a snapshot](/docs/versioning#building-against-a-snapshot) shows. [Getting started](/docs/getting-started) covers building against a local publish.

## so.alaz.taffy.settings

Applies `so.alaz.taffy.repositories` and creates the version catalog `alaz` from `so.alaz.taffy:taffy-catalog` at the same version as the plugin. Applying `so.alaz.taffy.settings` version `0.4.11` gives catalog `0.4.11`, which in turn pins every Taffy module to `0.4.11`. The plugins, the catalog and the runtime modules share one version, as [Versioning](/docs/versioning) describes. The catalog's aliases are listed at the end of this page.

From `0.4.1`, it first checks the Gradle version and fails on a Gradle older than 9.2.0 with the message shown under [Applying the plugins](#applying-the-plugins). A release candidate or milestone of 9.2.0 passes.

## so.alaz.taffy.repositories

Applies `org.gradle.toolchains.foojay-resolver-convention`, so Gradle downloads a Java 25 toolchain when the machine has none, and declares these repositories in `dependencyResolutionManagement`, in this order:

| Name | URL | Content |
|---|---|---|
| `MavenRepo` | Maven Central | releases of every group except `so.alaz` and its subgroups |
| `papermc` | `https://repo.papermc.io/repository/maven-public/` | `io.papermc` and its subgroups, `com.mojang`, `net.md-5` |
| `alazso` | `https://repo.alaz.so/releases` | releases of the `so.alaz` group and its subgroups |
| `alazsoSnapshots` | `https://repo.alaz.so/snapshots` | snapshots of the `so.alaz` group and its subgroups |
| `placeholderapi` | `https://repo.extendedclip.com/releases/` | `me.clip` |
| `faststats` | `https://repo.faststats.dev/releases` | `dev.faststats.metrics` |
| `vaultunlocked` | `https://repo.codemc.io/repository/creatorfromhell/` | `net.milkbowl.vault` |
| `playerpoints` | `https://repo.rosewooddev.io/repository/public/` | `org.black_ixx` |
| `oraxen` | `https://repo.oraxen.com/releases` | `io.th0rgal`, `md.thomas.hopper` |
| `nexo` | `https://repo.nexomc.com/releases` | `com.nexomc`, `com.tcoded`, `me.gabytm.util`, `team.unnamed` |
| `enginehub` | `https://maven.enginehub.org/repo/` | `com.sk89q`, `org.enginehub` and their subgroups |
| `fancyinnovations` | `https://maven.fancyspaces.net/fancyinnovations/releases` | `de.oliver` |
| `thenextlvl` | `https://repo.thenextlvl.net/releases` | `net.thenextlvl` |
| `packetevents` | `https://repo.codemc.io/repository/maven-releases/` | `com.github.retrooper` |
| `jitpack` | `https://jitpack.io` | `com.github.MilkBowl`, `com.github.Arcaniax-Development`, `com.github.decentsoftware-eu`, `com.github.HologramLib`, `com.github.maximjsx.EntityLib` |

Gradle asks a repository only for the groups in its Content column. A row that names subgroups covers every group below the ones it names, and every other group is matched exactly. The groups are the ones the `alaz` catalog's entries and their dependencies come from. The hologram rows, `fancyinnovations`, `thenextlvl` and `packetevents`, are available from `0.1.2`. The limit of `MavenRepo` to releases is Gradle's own and holds on Gradle 9.5.1 and newer: on Gradle 9.4.1 and older, Maven Central is also asked for a snapshot version of the groups it serves.

From `0.2.0`, every repository except Maven Central has a content filter and `jitpack` is last. Before `0.2.0`, only `alazso`, `alazsoSnapshots` and the three hologram rows had one, `jitpack` stood between `faststats` and `vaultunlocked`, and the other repositories were asked for any module an earlier repository lacked. A build that took a module of another group from one of these repositories now fails with `Could not find` for that module, and declares the repository itself, as shown below.

From `0.2.0`, `alazso` and `alazsoSnapshots` are declared through Gradle's `exclusiveContent`, so the `so.alaz` group and its subgroups resolve from those two repositories and from no other, Maven Central and a repository the build adds included. A `mavenLocal()` in `dependencyResolutionManagement.repositories` is therefore not asked for a locally published Taffy. [Build against a snapshot or a local publish](/docs/getting-started#build-against-a-snapshot-or-a-local-publish) shows how to point `alazsoSnapshots` at the local Maven repository.

The plugin sets `RepositoriesMode.PREFER_SETTINGS`: Gradle ignores a repository declared in a project build script. A build that needs another repository declares it in `settings.gradle.kts`:

```kotlin title="settings.gradle.kts"
dependencyResolutionManagement {
    repositories {
        maven("https://repo.example.org/releases") { name = "example" }
    }
}
```

`so.alaz.taffy.repositories` creates no version catalog. A build that wants the repositories without the `alaz` catalog applies it instead of `so.alaz.taffy.settings`.

## so.alaz.taffy.java

Applies `java-library` and sets the conventions every Taffy module and plugin build compiles and tests under.

| Area | Setting |
|---|---|
| Toolchain | `java.toolchain.languageVersion` 25 |
| `JavaCompile` | `options.encoding = "UTF-8"`, compiler argument `-Xlint:all,-processing,-serial` (warnings, the build does not fail on them) |
| `Javadoc` | `-Xdoclint:all,-missing`, `-quiet`, `--no-fonts`, UTF-8 encoding |
| `Test` | `useJUnitPlatform()`, logs `passed`, `skipped` and `failed` events, Mockito agent, test locale and time zone |
| `Jar` | The root project's `LICENSE` file in `META-INF` |

### Javadoc

Doclint runs with every group except `missing`. A public member without a comment passes, and a broken comment fails the `javadoc` task, for example an `@param` that names no parameter of the method. `--no-fonts` keeps the web fonts out of the generated javadoc.

### Test locale and time zone

Every `Test` task runs with these system properties:

| Property | Value |
|---|---|
| `user.language` | `tr` |
| `user.country` | `TR` |
| `user.timezone` | `Pacific/Auckland` |

Under the Turkish locale, `"TITLE".toLowerCase()` gives a dotless `ı`, so code that reads the default locale instead of passing `Locale.ROOT` fails in a test instead of on a server. Auckland is ahead of UTC, so code that reads an instant late in the UTC day in the default zone gets the next day. A test task replaces a default with `systemProperty`:

```kotlin title="build.gradle.kts"
tasks.test {
    systemProperty("user.language", "en")
}
```

### Mockito agent

Each test task passes every `mockito-core-*.jar` on its own classpath to the test JVM as `-javaagent`, so Mockito's inline mock maker is loaded at JVM start and does not attach itself to the running JVM. The classpath is read when the task runs, so a test task or source set the build adds later gets the agent from its own classpath. A test task without Mockito on its classpath gets no agent argument. The agent sits beside the JaCoCo agent that `so.alaz.taffy.coverage` adds. `taffy-test` declares `mockito-core` as an `implementation` dependency, so it is on the test runtime classpath of a plugin that declares `testImplementation(alaz.taffy.test)`, and that test task gets the agent. Test code that calls Mockito itself declares `testImplementation(alaz.mockito.core)`, because a runtime dependency of `taffy-test` is not on the test compile classpath.

### LICENSE

Every `Jar` task (the plain jar, the sources and javadoc jars, and the shadow jar) copies the file `LICENSE` from the root project directory into `META-INF`. When the root project has no `LICENSE`, the jars build without one.

From `0.4.1`, the shadow jar of `so.alaz.taffy.paper-plugin` keeps that copy when the plugin shades a Taffy module or any other jar that carries a license. `META-INF/LICENSE` in the plugin jar is the root project's own file, and the jar has no `META-INF/LICENSE` when the root project has none. The license files of each shaded jar, which are the files directly in `META-INF` whose name starts with `LICENSE` in any case, ship under `META-INF/licenses/<jar file name without .jar>/`:

```text
META-INF/LICENSE
META-INF/licenses/taffy-platform-0.4.11/LICENSE
META-INF/licenses/taffy-config-0.4.11/LICENSE
```

Two shaded jars with one file name, compared without case, get `META-INF/licenses/<name>/` and `META-INF/licenses/<name>-2/`, in runtime classpath order, and a third gets `-3`. A second license file of one jar whose name differs only in case, such as `license` beside `LICENSE`, gets the same suffix. A `META-INF/LICENSE*` file the build adds to `shadowJar` by hand, such as `from("LICENSE.md") { into("META-INF") }`, still ships: only the copies from the shaded jars move.

The task `collectDependencyLicenses` gathers those files into `build/generated/resources/dependencyLicenses`, and `shadowJar` depends on it. A `META-INF/LICENSE` in the plugin's own main resources also ships as the plugin's own file, and comes before the root project's. Only the shadow jar changes: the plain, sources and javadoc jars that `so.alaz.taffy.java` builds are as before.

Before `0.4.1`, the copy did not survive. Shadow copies the plugin's own classes and resources first, then the dependency jars, then files added on the `shadowJar` task itself, and `DuplicatesStrategy.EXCLUDE` keeps the first copy of each path. Every Taffy module carries Taffy's MIT `LICENSE` in `META-INF`, so the shadow jar shipped that license and dropped the root project's, and shipped it even when the root project had no license. A plugin on an older version ships its own license by copying it into its main resources, which come first:

```kotlin title="build.gradle.kts"
tasks.processResources {
    from(rootProject.file("LICENSE")) {
        into("META-INF")
    }
}
```

That block is not needed from `0.4.1` and does no harm there. `unzip -p build/libs/myplugin-1.0.0.jar META-INF/LICENSE` prints the license the jar ships. The plain `jar` task, which would hold both copies of the file, is disabled under `so.alaz.taffy.paper-plugin`.

## so.alaz.taffy.coverage

Applies `so.alaz.taffy.java` and `jacoco`, and adds the `coverage` extension (`so.alaz.taffy.gradle.CoverageExtension`).

| Property | Type | Default | Meaning |
|---|---|---|---|
| `minimum` | `Property<BigDecimal>` | `0.80` | Instruction coverage the whole module must reach |
| `classMinimum` | `Property<BigDecimal>` | `0`, and `0.50` under `so.alaz.taffy.library` | Instruction coverage each class must reach. `0` turns the per-class rule off |
| `exclusions` | `ListProperty<String>` | empty | Ant patterns of class files left out of the gate, relative to the classes directory |
| `conventionExclusions` | `ListProperty<String>` | empty, `**/RuntimeLibraries.class` under `so.alaz.taffy.paper-plugin`, from `0.4.5` also `**/RuntimeLibrariesLoader.class` while `paperPlugin.generateLoader` is on | Patterns other conventions add, applied in addition to `exclusions` |

```kotlin title="build.gradle.kts"
coverage {
    minimum.set("0.70".toBigDecimal())
    classMinimum.set("0.40".toBigDecimal())
    exclusions.addAll("**/command/**", "**/hook/**", "com/example/myplugin/MyPluginLoader.class")
}
```

What the plugin wires:

- Every `Test` task is finalized by `jacocoTestReport`, which writes XML and HTML reports.
- `jacocoTestCoverageVerification` depends on `test` and checks the module's main classes, minus both exclusion lists, against a `BUNDLE` rule (`INSTRUCTION`, `COVEREDRATIO`, `minimum`) and, when `classMinimum` is above zero, a `CLASS` rule with `classMinimum`.
- `verifyCoverageData` depends on `test` and fails when the module has classes under the gate, at least one of `minimum` and `classMinimum` is above zero, and no coverage data exists (`build/jacoco/test.exec`), which is the case when no test ran.
- `check`, and so `build`, depends on `jacocoTestCoverageVerification` and `verifyCoverageData`.

The gate covers the module's own compiled classes only. Libraries that a shadow jar carries are not part of it.

A module with classes and no tests fails `check` in `verifyCoverageData` with the message `No coverage data for <project path>: it has classes under the coverage gate but no test ran. Add tests, exclude the classes with coverage.exclusions, or set coverage.minimum and coverage.classMinimum to 0.` The project path of a root project is `:`. A module without tests passes `check` once its classes are all excluded, or once both `minimum` and `classMinimum` are `0`.

<Callout type="warn" title="Set the minimums in the build script">
`minimum` and `classMinimum` become JaCoCo rule limits in an `afterEvaluate` block, so the value a build script sets while it is evaluated is the one used. A value set in a later `afterEvaluate` or in a task action does not reach the rules. `exclusions` and `conventionExclusions` are read lazily, so a value set in a later `afterEvaluate` still applies.
</Callout>

An exclusion pattern matches class file names. A nested or anonymous class compiles to its own file such as `Menu$Page.class` or `Menu$1.class`, which the pattern `**/Menu.class` does not match; `**/Menu*.class` matches all three, and also any other class whose name starts with `Menu`.

## so.alaz.taffy.paper-plugin

Applies `so.alaz.taffy.coverage` and Shadow (`com.gradleup.shadow`), and builds the one jar a server owner installs. It adds no dependency on Paper: the plugin declares `compileOnly(alaz.paper.api)` itself, and anything on `compileOnly` stays out of the shadow jar.

### The shadow jar

| Task | Setting |
|---|---|
| `shadowJar` | `archiveClassifier` is empty, `duplicatesStrategy = DuplicatesStrategy.EXCLUDE`, `mergeServiceFiles()`, the license handling under [LICENSE](#license), relocations below |
| `jar` | disabled |
| `assemble` | depends on `shadowJar` |

`./gradlew build` therefore leaves one file, `build/libs/<project name>-<version>.jar`, with no classifier. With `DuplicatesStrategy.EXCLUDE`, the first copy of a path wins, which keeps one `META-INF/faststats.properties` when several dependencies carry it.

From `0.4.1`, the files under `META-INF/services` are the exception: the build calls Shadow's `mergeServiceFiles()` and sets `DuplicatesStrategy.INCLUDE` on `META-INF/services/**`, so the jar holds one file per service with the provider lines of the plugin and of every shaded jar, each relocated like its class. A plugin that shades two JDBC drivers keeps both in `META-INF/services/java.sql.Driver`. One file is left out: `META-INF/services/org.codehaus.groovy.runtime.ExtensionModule`, which Shadow's service merge does not take, keeps its first copy like any other path. Before `0.4.1`, the first file of a name won and the providers of the other jars were lost to `ServiceLoader`.

Three packages are relocated under `<group>.libs`, where `<group>` is the project group:

| Package | Relocated to |
|---|---|
| `org.bstats` | `<group>.libs.bstats` |
| `dev.faststats` | `<group>.libs.faststats` |
| `so.alaz.taffy` | `<group>.libs.taffy` |

From `0.4.1`, each relocation carries an include pattern (`org.bstats.**`, `dev.faststats.**`, `so.alaz.taffy.**`), so it covers the package and its subpackages and nothing else. Before `0.4.1`, Shadow matched the raw path prefix: a package such as `so.alaz.taffyshop`, `org.bstatsx` or `dev.faststatsx` was relocated as well, and a plugin whose group was `so.alaz.taffyshop` shipped a main class Paper could not find under the name in `paper-plugin.yml`.

From `0.4.1`, `shadowJar` and `generateRuntimeLibraries` fail when the project group is blank or has an empty segment, such as `com..myplugin`:

```text
so.alaz.taffy.paper-plugin relocates Taffy under <group>.libs, and the project group "" is blank or has an empty segment. Set group in gradle.properties, for example group=com.example.myplugin.
```

Before `0.4.1`, a project without a group built a jar whose Taffy classes sat under `/libs/taffy/`, which no server loads. The group is read when one of the two tasks is configured or run, so a `group = "..."` line in `build.gradle.kts` after the `plugins` block counts. A group that is not a Java package name, such as `com.example.my-plugin`, builds as long as the plugin lists no [runtime library](#runtime-libraries).

From `0.4.2`, `shadowJar` also fails when the project group is `so.alaz.taffy` or a package inside it, such as `so.alaz.taffy.shop`:

```text
so.alaz.taffy.paper-plugin relocates Taffy under <group>.libs, and the project group "so.alaz.taffy.shop" is so.alaz.taffy or inside it, so the relocated copy would still be inside so.alaz.taffy and Taffy refuses it when the plugin enables. Set group in gradle.properties to a package outside so.alaz.taffy, for example group=com.example.myplugin.
```

Before `0.4.2`, such a project built a jar with Taffy under `so/alaz/taffy/shop/libs/taffy/`. [`Relocation.check()`](/docs/consuming-by-coordinates#relocation) counts a copy inside `so.alaz.taffy` as not relocated, so the plugin threw `IllegalStateException` when it enabled. A group that only starts with the name, such as `so.alaz.taffyshop`, builds. `generateRuntimeLibraries` does not make this check.

With `group=com.example.myplugin`, Taffy's `so.alaz.taffy.platform.Scheduler` ships as `com.example.myplugin.libs.taffy.platform.Scheduler`. Each plugin carries its own copy of Taffy, so plugins built on different Taffy versions share no Taffy classes on one server. bStats refuses to start from classes that were not relocated, so a build that shades `taffy-metrics` without this plugin relocates the same three packages itself and keeps `META-INF/faststats.properties` in its shadow jar ([metrics](/docs/modules/metrics) has the details, and [Without the Gradle plugins](/docs/consuming-by-coordinates#the-shadow-jar) the whole shadow jar setup).

From `0.4.1`, Taffy refuses to run unrelocated inside a plugin: a jar built another way that leaves Taffy in `so.alaz.taffy` fails on the server with an `IllegalStateException` that names the plugin and the missing `relocate("so.alaz.taffy", ...)` line. A jar this plugin builds passes the check. [Relocation](/docs/consuming-by-coordinates#relocation) has the message and the rule.

`com.comficonf` is never relocated: the ComfiConf API comes from the installed bridge, and a plugin declares it `compileOnly(alaz.comficonf.api)` ([ComfiConf](/docs/modules/comficonf)). Any other library a plugin adds with `implementation` is shaded unrelocated unless the build adds its own `relocate` call:

```kotlin title="build.gradle.kts"
tasks.shadowJar {
    relocate("com.example.lib", "com.example.myplugin.libs.lib")
}
```

### paper-plugin.yml

`processResources` expands `${version}` in `src/main/resources/paper-plugin.yml` to the project version, and declares the version as a task input. No other descriptor key is written: `name`, `main`, `api-version`, `loader`, `folia-supported` and the dependencies come from the plugin's own file.

```yaml title="src/main/resources/paper-plugin.yml"
name: MyPlugin
version: "${version}"
main: com.example.myplugin.MyPlugin
```

The file goes through Gradle's `expand`, and `version` is the only property defined. Another `${...}` expression in it fails `processResources`, and `\$` gives a literal dollar sign.

From `0.4.1`, every backslash in the file stays as it is: `description: "First\nSecond"` and `Reads C:\data\shop` reach the jar unchanged. Before `0.4.1`, `expand` read `\n`, `\t`, `\\` and the other backslash sequences as the characters they name, so the first description came out with a line break in the middle of the YAML string and the second lost its backslashes, while the build passed.

### Compiler flag

The plugin adds `-Xlint:-classfile` to every `JavaCompile` task. Some integration APIs are Kotlin-compiled and declared without their transitive dependencies, so the `kotlin.*` annotation types their class files name are absent; the flag keeps javac from warning about each of them.

### Compiling against the oldest supported Paper

From `0.2.0`, the plugin registers `compileAgainstPaperFloor`, a `JavaCompile` task that compiles the `main` Java sources against `paper-api` `26.2.build.135-stable`, the build of the oldest Paper server Taffy supports ([Servers](/docs/versioning#servers)). `alaz.paper.api` is a newer build, so `compileJava` accepts a call that Paper 26.2 does not have. This task fails on it:

```text
> Task :compileAgainstPaperFloor FAILED
Stored.java:8: error: cannot find symbol
        return data.getPrimitiveStorageType(key) != null;
                   ^
  symbol:   method getPrimitiveStorageType(Key)
```

No task depends on it. Run it by name, in CI for one, or make it part of `check`:

```kotlin title="build.gradle.kts"
tasks.check {
    dependsOn("compileAgainstPaperFloor")
}
```

- Its classpath is the `paperFloorCompileClasspath` configuration: what `compileOnly` and `implementation` declare, with every request for `io.papermc.paper:paper-api` answered by the floor build. Every other dependency, Taffy included, resolves as it does for `compileJava`.
- It compiles with the compiler of the project's Java toolchain, as `compileJava` does.
- It writes its class files to `build/classes/java/paperFloor`. They go into no jar.
- It compiles Java sources only, and it only compiles: a method that exists on Paper 26.2 and behaves differently there is found by running the plugin on that server.
- It checks the plugin's own calls. Taffy's calls are checked by Taffy's own build, which compiles every module against the same `paper-api` build.

[Without the Gradle plugins](/docs/consuming-by-coordinates#compiling-against-the-oldest-supported-paper) has the same task for a build that does not apply this plugin.

### Runtime libraries

The `paperPlugin` extension (`so.alaz.taffy.gradle.PaperPluginExtension`) lists the Maven coordinates Paper downloads before the plugin loads, in resolution order. `taffy-storage` needs it: it ships neither HikariCP nor any JDBC driver ([storage](/docs/modules/storage)).

| Member | Type | Meaning |
|---|---|---|
| `runtimeLibraries` | `ListProperty<String>` | Coordinates as `group:name:version` |
| `runtimeLibrary(library)` | takes `Provider<MinimalExternalModuleDependency>` | Adds a version catalog entry as `group:name:version`, with the version the catalog requires |
| `generateLoader` | `Property<Boolean>`, `false` unless set | From `0.4.5`. Also generates the `PluginLoader` that reads the coordinates: see [Generated loader](#generated-loader) |

```kotlin title="build.gradle.kts"
dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.storage)
    testImplementation(alaz.junit.jupiter)
    testRuntimeOnly(alaz.junit.platform.launcher)
    testRuntimeOnly(alaz.hikari)
    testRuntimeOnly(alaz.sqlite.jdbc)
}

paperPlugin {
    runtimeLibrary(alaz.hikari)
    runtimeLibrary(alaz.sqlite.jdbc)
    runtimeLibrary(alaz.mysql.connector)
    runtimeLibraries.add("org.example:extra:1.2.3")
}
```

The runtime libraries are not on any Gradle classpath. Tests that start storage declare HikariCP and each driver they use on `testRuntimeOnly`, as above.

When the list is not empty, the `generateRuntimeLibraries` task writes `RuntimeLibraries.java` to `build/generated/sources/runtimeLibraries/java/main`, a source directory of the `main` source set, in the package named by the project group. With `group=com.example.myplugin` and the block above it generates:

```java title="build/generated/sources/runtimeLibraries/java/main/com/example/myplugin/RuntimeLibraries.java"
package com.example.myplugin;

import java.util.List;

/** Generated from the version catalog at build time. Do not edit. */
final class RuntimeLibraries {

    /** Maven coordinates of the libraries Paper downloads before the plugin loads. */
    static final List<String> COORDINATES = List.of(
        "com.zaxxer:HikariCP:7.1.0",
        "org.xerial:sqlite-jdbc:3.54.1.0",
        "com.mysql:mysql-connector-j:26.10.0",
        "org.example:extra:1.2.3");

    private RuntimeLibraries() {
    }
}
```

The class and its field are package-private, so the code that reads them lives in that same package. The project group becomes the `package` declaration as it is, so it must be a valid Java package name. With an empty list, no class is generated. `**/RuntimeLibraries.class` is in `coverage.conventionExclusions`, outside the gate.

From `0.4.1`, `generateRuntimeLibraries` checks what it writes and fails, writing nothing, in two cases. A group that is not a Java package name fails before javac reads the generated file:

```text
paperPlugin.runtimeLibraries generates RuntimeLibraries in the package named by the project group, and "com.example.my-plugin" is not a Java package name. Set group in gradle.properties to one, for example group=com.example.myplugin.
```

An entry that is not `group:name:version` fails with the entry named. Each segment holds at least one character and no whitespace, quote or backslash:

```text
The paperPlugin.runtimeLibraries entry "org.junit.platform:junit-platform-launcher:" is not group:name:version, with an extension or an extension and a classifier allowed before the version, in segments that are not blank and hold no whitespace, quote or backslash. A version catalog entry passed to runtimeLibrary needs a version.
```

`runtimeLibrary` takes the version a catalog entry requires, so an entry the catalog gives no version, such as `alaz.junit.platform.launcher`, has none to write. Before `0.4.1`, that entry generated a coordinate ending in a colon and the build passed; the loader below then threw `Bad artifact coordinates` at server start.

The Aether forms with an extension or a classifier, `group:name:extension:version` and `group:name:extension:classifier:version`, pass the check and are written as they are.

The build does not register a loader. The plugin writes a Paper `PluginLoader` in the group package that hands the coordinates to Paper's `MavenLibraryResolver`, or from `0.4.5` has the build [generate it](#generated-loader):

```java title="src/main/java/com/example/myplugin/MyPluginLoader.java"
package com.example.myplugin;

import io.papermc.paper.plugin.loader.PluginClasspathBuilder;
import io.papermc.paper.plugin.loader.PluginLoader;
import io.papermc.paper.plugin.loader.library.impl.MavenLibraryResolver;
import org.eclipse.aether.artifact.DefaultArtifact;
import org.eclipse.aether.graph.Dependency;
import org.eclipse.aether.repository.RemoteRepository;

public final class MyPluginLoader implements PluginLoader {

    @Override
    public void classloader(PluginClasspathBuilder classpathBuilder) {
        MavenLibraryResolver resolver = new MavenLibraryResolver();
        resolver.addRepository(new RemoteRepository.Builder(
                "central", "default", MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR).build());
        for (String coordinates : RuntimeLibraries.COORDINATES) {
            resolver.addDependency(new Dependency(new DefaultArtifact(coordinates), null));
        }
        classpathBuilder.addLibrary(resolver);
    }
}
```

```yaml title="src/main/resources/paper-plugin.yml"
loader: com.example.myplugin.MyPluginLoader
```

From `0.4.1`, the build fails when a runtime library is listed and that key is missing. The task `verifyPluginLoader`, which `processResources` depends on, reads the `paper-plugin.yml` at the root of each main resources directory, one that a task generates included, and looks for a `loader` key at the first column of a line. A byte order mark before the first line is skipped. A top-level mapping that is indented as a whole, or written in flow style such as `{name: MyPlugin, loader: a.B}`, is not recognised and fails the same way. From `0.4.3`, a `loader` key with no value fails the same way too: `loader:` followed by nothing, by spaces or by a comment only. A value counts on the same line, or indented on the next line that is neither blank nor a comment. The values `""`, `''`, `~`, `null`, `Null` and `NULL` are no value, and neither is `|` or `>` with no indented line below it. Before `0.4.3`, such a key passed the check, and the plugin failed at its first use of a library. With the four libraries listed above it fails with:

```text
paperPlugin.runtimeLibraries lists 4 libraries and src/main/resources/paper-plugin.yml has no top-level loader key, so Paper downloads none and the plugin fails at its first use of one. Add loader: with the name of the PluginLoader class that reads RuntimeLibraries.COORDINATES: https://alaz.so/taffy/docs/gradle-plugins#runtime-libraries
```

Before `0.4.1`, such a build passed, with tests green on the `testRuntimeOnly` copies of the libraries, and the plugin failed on the server with a `NoClassDefFoundError` such as `com/zaxxer/hikari/HikariConfig`. The check reads only the key: it does not look at the class the key names. It does nothing while the list is empty, and nothing when the main resources hold no `paper-plugin.yml`.

HikariCP and the drivers in the catalog are published on Maven Central, and `MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR` is the Maven Central address Paper's API provides for a loader. The loader class is plugin code under the coverage gate like any other class; the `coverage` example above excludes it. Paper's documentation on [plugin loaders](https://docs.papermc.io/paper/dev/getting-started/paper-plugins/) covers the loader itself.

### Generated loader

From `0.4.5`, the build can write the loader class. `generateLoader` is off unless the build sets it:

```kotlin title="build.gradle.kts"
paperPlugin {
    runtimeLibrary(alaz.hikari)
    runtimeLibrary(alaz.sqlite.jdbc)
    generateLoader.set(true)
}
```

With runtime libraries listed, `generateRuntimeLibraries` then writes a second file beside `RuntimeLibraries.java`, in the same package. With `group=com.example.myplugin` it generates:

```java title="build/generated/sources/runtimeLibraries/java/main/com/example/myplugin/RuntimeLibrariesLoader.java"
package com.example.myplugin;

import io.papermc.paper.plugin.loader.PluginClasspathBuilder;
import io.papermc.paper.plugin.loader.PluginLoader;
import io.papermc.paper.plugin.loader.library.impl.MavenLibraryResolver;
import org.eclipse.aether.artifact.DefaultArtifact;
import org.eclipse.aether.graph.Dependency;
import org.eclipse.aether.repository.RemoteRepository;

/** Generated at build time. Do not edit. */
final class RuntimeLibrariesLoader implements PluginLoader {

    /** Has Paper download {@link RuntimeLibraries#COORDINATES} from its Maven Central mirror. */
    @Override
    public void classloader(PluginClasspathBuilder classpathBuilder) {
        MavenLibraryResolver resolver = new MavenLibraryResolver();
        resolver.addRepository(new RemoteRepository.Builder(
            "central", "default", MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR).build());
        for (String coordinates : RuntimeLibraries.COORDINATES) {
            resolver.addDependency(new Dependency(new DefaultArtifact(coordinates), null));
        }
        classpathBuilder.addLibrary(resolver);
    }
}
```

The plugin deletes its own loader class and names the generated one. The build still writes no descriptor key:

```yaml title="src/main/resources/paper-plugin.yml"
loader: com.example.myplugin.RuntimeLibrariesLoader
```

What the setting changes, and what it leaves alone:

- **The class is always `<group>.RuntimeLibrariesLoader`.** It is package-private, like `RuntimeLibraries`: Paper makes the constructor of the class under `loader` accessible before it calls it. Its name and package cannot be set.
- **One repository.** The loader gives the resolver Paper's Maven Central mirror and nothing else. A library published elsewhere needs a loader the plugin writes in the group package, which can call `new RuntimeLibrariesLoader().classloader(classpathBuilder)` and then add a resolver of its own.
- **paper-api on the compile classpath.** The class compiles with the plugin's other sources, so the build needs `compileOnly(alaz.paper.api)`. `compileAgainstPaperFloor` compiles it too: `MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR` is in the oldest supported paper-api.
- **Outside the coverage gate.** While the setting is on, `**/RuntimeLibrariesLoader.class` is in `coverage.conventionExclusions`.
- **The `loader` key is still checked, and only the key.** With the key missing, `verifyPluginLoader` fails with the line to add: `Add loader: com.example.myplugin.RuntimeLibrariesLoader, the PluginLoader class paperPlugin.generateLoader generates`. A key that names another class passes, and Paper then runs that class, not the generated one.
- **No libraries, no loader.** With an empty `runtimeLibraries`, neither class is generated. A `loader` key that still names `<group>.RuntimeLibrariesLoader` then fails `verifyPluginLoader`, with a message that says to remove the key or list a library, so the build does not produce a jar Paper cannot load. The check reads a plain or quoted value on the line of the key or on the line after it.

A build that leaves `generateLoader` off generates the same source and builds the same jar as on `0.4.4`.

<Callout type="error" title="Never list the metrics SDKs">
bStats and FastStats come as runtime dependencies of `taffy-metrics` and are shaded and relocated. Listing `alaz.bstats.bukkit` or `alaz.faststats.bukkit` as a runtime library makes Paper load an unrelocated copy.
</Callout>

### Kotlin plugins

From `0.4.8`, a plugin written in Kotlin is a supported build: Taffy's own tests build one with `org.jetbrains.kotlin.jvm` `2.4.21` applied beside `so.alaz.taffy.paper-plugin`, on Gradle 9.9.1. The Kotlin Gradle plugin comes from the Gradle Plugin Portal, which the `pluginManagement` block under [Applying the plugins](#applying-the-plugins) already names, and its version is the build's own choice: the `alaz` catalog has no Kotlin entry.

```kotlin title="build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-plugin")
    id("org.jetbrains.kotlin.jvm") version "2.4.21"
}

dependencies {
    compileOnly(alaz.paper.api)
    implementation(alaz.taffy.platform)
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.11.0")
    testImplementation(alaz.junit.jupiter)
    testRuntimeOnly(alaz.junit.platform.launcher)
}

tasks.shadowJar {
    relocate("kotlin", "com.example.myplugin.libs.kotlin") {
        include("kotlin.**")
    }
    relocate("kotlinx", "com.example.myplugin.libs.kotlinx") {
        include("kotlinx.**")
    }
}
```

What the conventions do for Kotlin sources, and what stays with the build:

- **Java 25 class files.** The Kotlin plugin takes its JVM target from the Java toolchain that `so.alaz.taffy.java` sets, so `src/main/kotlin` compiles to Java 25 class files with no `kotlin` block. A build adds one for its own compiler options, such as `-Xjsr305=strict`.
- **The standard library is shaded.** The Kotlin plugin adds `kotlin-stdlib` to `implementation`, so the shadow jar carries it. Taffy relocates only its own three packages: the two `relocate` calls above move `kotlin` and `kotlinx` under the plugin's group, each with an include pattern so that `kotlin` does not also match `kotlinx`. Taffy's tests build no plugin that uses `kotlin-reflect`. What the two libraries bring outside those packages stays at the root of the jar under its own name: the `org.jetbrains.annotations` and `org.intellij.lang.annotations` classes of the `org.jetbrains:annotations` dependency of `kotlin-stdlib`, and from `kotlinx-coroutines-core` the `_COROUTINE` classes and `DebugProbesKt.bin` of its debugger, `META-INF/kotlinx_coroutines_core.version` and its ProGuard rule files under `META-INF`. The `_COROUTINE` package is a fixed name the coroutine debugger looks up and is not relocated.
- **Taffy is relocated in Kotlin classes too.** A Kotlin class that names `so.alaz.taffy.gui.Answer` ships naming `<group>.libs.taffy.gui.Answer`, in its bytecode and in its Kotlin metadata.
- **Module files are kept.** Shadow writes the `META-INF/*.kotlin_module` file of each Kotlin module it relocates as `META-INF/<module>.shadow.kotlin_module`, one per module, the plugin's own included. No two share a name, so `DuplicatesStrategy.EXCLUDE` drops none. Shadow still prints a warning for each module file on every `shadowJar` run, because the convention sets that strategy: `'META-INF/kotlin-stdlib.kotlin_module' is matched by ... KotlinModuleMetadataTransformer ... but its DuplicatesStrategy is EXCLUDE`, with the advice to set `INCLUDE` or `WARN`. The warning is harmless here and the jar is complete.
- **Tests and coverage.** Kotlin tests under `src/test/kotlin` run on the JUnit Platform with the [test locale and time zone](#test-locale-and-time-zone). The coverage gate measures the Kotlin class files, where a top-level function of `Shop.kt` is in `ShopKt.class`, and JaCoCo counts the instructions the compiler generates for coroutines and inline functions. A build sets `coverage.minimum` from what it measures.
- **`RuntimeLibraries` is Java.** The generated class compiles beside the Kotlin sources, and Kotlin code in the group package reads `RuntimeLibraries.COORDINATES` directly.
- **Java-only settings.** The javac and javadoc flags apply to Java sources only, and `compileAgainstPaperFloor` compiles the Java sources only, so it does not check a Kotlin call against the oldest supported Paper. Its classpath holds no Kotlin output, so in a plugin whose Java sources name a Kotlin class of the same project the task fails with `cannot find symbol`, and such a plugin cannot run it. A plugin written in Kotlin only, and one whose Java sources name no Kotlin class, run it as before.

Taffy's sealed types and enums are exhaustive in a `when`. Over `Answer`, `Icon` and `EconomyResult.Status`, a `when` used as an expression compiles with no `else` branch:

```kotlin
fun label(answer: Answer): String = when (answer) {
    is Answer.Accept -> "accept"
    is Answer.Retry -> "retry"
    is Answer.Later -> "later"
}
```

A later release may add a result to `Answer`, and such a `when` then stops compiling on the upgrade until it names the new one. An `else` branch keeps it compiling.

Taffy has no Kotlin in a runtime module and no `kotlinx` type in a public signature, so a coroutine dispatcher over [`Scheduler`](/docs/modules/platform#scheduler) is the plugin's own class. One for the global region thread:

```kotlin title="src/main/kotlin/com/example/myplugin/GlobalDispatcher.kt"
package com.example.myplugin

import kotlin.coroutines.CoroutineContext
import kotlinx.coroutines.CoroutineDispatcher
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.cancel
import so.alaz.taffy.platform.Scheduler

class GlobalDispatcher(private val scheduler: Scheduler) : CoroutineDispatcher() {
    override fun dispatch(context: CoroutineContext, block: Runnable) {
        if (!scheduler.global(block)) {
            context.cancel()
            Dispatchers.IO.dispatch(context, block)
        }
    }
}
```

`Scheduler.global` returns `false` when the plugin is not enabled, and a dispatcher may not drop a block: the coroutine is cancelled and its block runs on `Dispatchers.IO`, where it meets the cancellation. `scheduler.asyncExecutor().asCoroutineDispatcher()` gives a dispatcher for async work, and a `CompletableFuture` that Taffy returns is awaited with `kotlinx.coroutines.future.await`.

## so.alaz.taffy.paper-api

Applies `so.alaz.taffy.java` and `maven-publish`, for a module other plugins compile against, such as a plugin's public API.

```kotlin title="myplugin-api/build.gradle.kts"
plugins {
    id("so.alaz.taffy.paper-api")
}

description = "MyPlugin public API"
```

It adds no Paper dependency and no coverage gate. It configures:

- `java.withSourcesJar()` and `java.withJavadocJar()`.
- A `MavenPublication` named `library` from the `java` component, published as `<group>:<project name>:<version>`. The POM `name` is the project name, the POM `description` is the project `description`, and the license is the MIT License.
- The POM `url` from the Gradle property `alaz.repositoryUrl`, or `https://github.com/alazso/<root project name>` when the property is unset.
- A Maven repository named `alazso`: `https://repo.alaz.so/snapshots` when the version ends with `-SNAPSHOT`, `https://repo.alaz.so/releases` otherwise.

```properties title="gradle.properties"
alaz.repositoryUrl=https://github.com/example/myplugin
```

The `alazso` repository takes its credentials from the environment variables `ALAZSO_REPO_USER` and `ALAZSO_REPO_TOKEN`. They are read with `System.getenv`, not as Gradle properties, so a `-P` flag or an entry in `gradle.properties` does not set them.

```bash
export ALAZSO_REPO_USER=...
export ALAZSO_REPO_TOKEN=...
./gradlew publishLibraryPublicationToAlazsoRepository
```

A build that publishes elsewhere adds its own repository next to `alazso`; Gradle then creates one publish task per repository, such as `publishLibraryPublicationToExampleRepository`:

```kotlin title="myplugin-api/build.gradle.kts"
publishing {
    repositories {
        maven("https://repo.example.org/releases") { name = "example" }
    }
}
```

`publishToMavenLocal` publishes the `library` publication to the local Maven repository with no credentials.

## so.alaz.taffy.library

Applies `so.alaz.taffy.paper-api` and `so.alaz.taffy.coverage`, and sets the convention of `coverage.classMinimum` to `0.50`. It is the plugin for a published library module with tests: every class under the gate holds at least half its instructions covered, and the module as a whole holds `coverage.minimum` (default `0.80`). Every Taffy runtime module is built with it.

A class below the floor fails `jacocoTestCoverageVerification` with a message of the form `Rule violated for class com.example.Demo: instructions covered ratio is 0.00, but expected minimum is 0.50`. `coverage.classMinimum.set("0".toBigDecimal())` turns the per-class rule off.
